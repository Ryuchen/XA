# 签到、积分抽奖、权益与其他功能

本页补充与三端订单、资金和运营相关的非主流程功能。每项都归属本店，配置统一进入[系统字典与门店初始化](12-系统字典与门店初始化.md)；“当前”表示已查阅源码，不等于真实环境已启用或本轮完成验收。

## 1. 签到、补签与全勤

| 环节 | 老板端 | 后台及系统 |

| 签到奖励 | 查看真实签到记录和实际到账的本店店币。 | 签到记录与钱包奖励在同一业务结果中对应，同一天不能重复领取；签到奖励不是积分。 |

| 后续退款 | 已领取的签到奖励和补签卡保留，不因之后订单退款而追回。 | 用户已确认该规则；退款前是否达到门槛和实际领取事实分别记录，未来新的资格判断仍使用最新净消费。 |

## 2. 积分商品兑换与权益交付

1. 老板或陪玩按本店商品的适用身份、积分价格、库存和有效状态兑换；积分不足、商品下架、库存不足或条款变更时返回可执行提示。支付积分、库存变化和权益记录必须对应同一笔请求，不能重复扣分或超卖。
2. 用户已确认停止**积分商城直接兑换钱包余额**；其他原有积分商品兑换保留。历史直接兑余额记录和已产生的钱包余额保留。
   门店停用积分发放、积分抵扣、积分商城或积分抽奖中的任一项时，所有积分使用暂时暂停，已取得积分和中奖权益仍保留；当被停用项重新启用且其余三项均启用后，积分使用自动恢复。例如仅停用抽奖但积分发放仍开启时，符合条件的消费继续获得积分，只是暂时不能使用积分。VIP 停用导致不发消费积分属于另一个独立条件；不能只看积分发放开关。既有退款应返积分、已发积分冲回与业务查询须可继续正确处理，不能因暂停使用丢账。
3. 权益可以是实物、游戏内物品、服务、冠名或 TAG 等；用户提交收件、游戏或其他必要资料，只允许本人及获授权本店工作人员访问。不要把资料提交或进入队列显示为已经完成实际交付。
4. 当前交付记录包含待处理、交付中、已完成和已取消；后台可按权限核对资料、要求补充、更新状态和填写原因。普通积分商品兑换取消时按现有规则退回原积分并恢复对应库存；抽奖奖励不能简单当作普通兑换直接取消，退款引起的 VIP／赠礼权益变动按对应专项处理。
5. TAG 等内容需要核对及审核；有效期从实际完成交付的时间及该权益规则确定。权益条款变化、用户补充资料和客服并发操作必须核对当前版本，不能覆盖对方刚提交的内容。
6. 赠礼退款导致不再达到门槛时，已经发放的赠礼相关权益和标签保留，待交付权益继续按原事实处理；礼物已带来的陪玩冠名有效期也不因退款缩短。订单、退款、权益与实际交付关联保留，不因此重复发放。

当前实现和状态见 [`engagement/models.py`](../../services/backend/engagement/models.py)、[`engagement/services.py`](../../services/backend/engagement/services.py) 及 [`engagement/console.py`](../../services/backend/engagement/console.py)。

## 3. 积分抽奖

1. **保留积分抽奖，也可保留余额类中奖奖品**；只有真实中奖后才按奖品规则增加本店钱包余额。余额中奖与被禁止的积分商城直接兑余额是不同业务，必须分别保留抽奖批次、中奖记录、积分扣减和钱包流水，不能通过伪造来源绕过商城限制。
2. 同一家门店允许多个积分抽奖同时开放，老板自行选择活动并查看各自奖池、消耗积分、可参加次数、概率说明及中奖／交付状态；可按当前系统支持的单抽或十连操作。草稿和未来活动不能遮挡已开放活动；奖池、库存、计数和保底按活动区分。动画可跳过或减少，但不能由页面动画决定中奖或重复发奖。
3. 后台按权限配置奖品、概率、库存、适用人群、活动时间及启停；奖池和规则变更要有版本。当前配置要求奖项概率合计为 100%，已产生中奖记录的奖项不能简单删除以破坏历史。
4. 当前代码支持十连至少一个非积分奖；特定“68 体验单”奖项存在 240 次保底计数。它是当前实现的具体规则，不应把该奖品或 240 次写成所有门店都已配置的事实。保底及次数在本店字典中维护；**门店修改保底次数后，已有未中奖计数重新从零开始**。例如由 240 次改为 100 次、某老板原累计 200 次，调整生效后按新规则从零计数；旧抽奖、积分和中奖记录保留。仅更换保底目标奖品、保底次数不变时，原计数保留并继续累计；不能把两种配置变更混为一谈。
5. 同一次抽奖须核验用户积分、每日次数、奖池版本、库存及本店范围；抽奖请求重试应恢复同一批次结果，不能重新抽取。中奖权益与实际交付分别记录；余额类中奖产生的赠送店币消费不产生消费积分。

## 4. 成就、标签与排行榜

### 4.1 成就与会员标签

- 用户已确认：成就页面与会员标签统一按**本店已确认实销的非礼物订单**计算；订单数和累计净消费分别按配置指标统计，退款后有效实销及进度按实际退款冲减。老板已解锁的消费成就，退款导致有效实销低于门槛时仍保持解锁，会员成就标签与成就页一致；未解锁成就以有效实销判断门槛，实际解锁还须符合该成就功能的授权规则。
- 老板看到成就名称、目标、已完成进度、解锁状态和可展示标签；不能仅在成就页显示已解锁，但在会员标签处因为不同口径而无法使用。门店可在字典中维护成就名称、指标、目标、排序和启停。
- 现有 [`CustomerAchievementView`](../../services/backend/users/views.py) 统计已完成订单，未与会员标签统一排除礼物及等待实销确认；[`engagement/views.py`](../../services/backend/engagement/views.py) 的可用标签则使用当前业务周期已确认的非礼物订单。需要统一计算来源并核对历史行为；不能仅改前端文案。
- VIP 标签、自定义 TAG 和成就标签有不同来源和审核方式；到期、停用等按各自实际来源处理，已解锁消费成就不因退款撤销。公开展示不应泄露用户生日、收件或聊天私有信息。

- 用户已确认：双陪或转单中，每位实际参与履约的陪玩各计 1 单，同一人同单不重复；即使老板后来全额退款，确实参与履约的陪玩仍计入。不能只统计主陪玩或把整笔金额分别当成每人的收益；仅接单但未实际履约者不因分配而自动计单。
- 用户已确认：排行榜的日／周／月按每位陪玩本人的履约结束或转出时间归属；即使订单整单未正常完成、后续取消或全额退款，也应保留可核对的真实履约事实和统计时间。同一人同单多次转出又转回时只计一次，按该人**最后一次**履约结束或转出时间归属；跨周期变化时须重算受影响周期并保留追踪记录。具体履约证明应与现有入队、结单、报单和转单记录对应。
- 用户 2026-11-12 确认：双陪本人首次通过订单履约入口提交结单截图即视为本次履约结束；后续更换截图不改变本人结束时间，无须等待另一人提交。
- 用户已确认：老板消费榜**包含礼物订单**，金额与对外下单额统一按优惠前原价统计。部分退款冲减退回店币及退回积分的原单等值，全额退款补齐冲销剩余原价；榜单数字不是实际支付或现金实收。成就统一排除礼物，按已确认服务实付净额计算，独立于 VIP 成长开关。
- 当前 [`orders/views.py`](../../services/backend/orders/views.py) 的榜单按旧用户 ID 及主陪玩聚合，默认展示前 5 名；可能遗漏仅有新业务账号的用户、双陪及转单人员，须按本店账户和真实履约份额核对。展示人数、称号门槛及展示状态应纳入本店字典，历史默认不等于各店实际配置。
- 当前 [`OrderProvider`](../../services/backend/orders/models.py) 主要保存人员份额与当前 `released_at`，同一订单／人员存在唯一约束，转回时可能复用该记录；不能仅凭此字段声称完整记录了每轮履约。新榜单需要可审计的个人履约／转单事件及时间，历史缺少可靠证明时标记待核对，不凭现有主陪玩字段猜测。
- 后台陪玩经营看板的接单指标、资金快照与老板端公开榜单用途不同，应标出筛选日期、统计时间与口径。当前 [`PlayerDashboardView`](../../services/backend/console/views.py) 的 `settled_salary` 实际累加已审核提现申请金额，并非职能人员工资；新两级流程中应分别展示实际打款的提现金额、手续费及职能薪资，不能把初审通过称为已结工资。

## 5. 收藏、内容与客服入口

- 老板收藏本人可见服务，查看或取消收藏；服务下架、资格失效或删除时显示不可用，仍可移除，不能把占位价格当成实际可购买报价。当前收藏范围和具体对象以 [`orders/views.py`](../../services/backend/orders/views.py) 为准，不擅自宣称已有跨店收藏。
- 游戏、玩法、服务、公告、轮播、活动内容及客服名片由本店按权限维护；启停、排序和可见时间生效后，各端读取同一店真实数据。不可用、未配置和加载失败分别提示。
- 老板与陪玩从业务页联系本店客服时，按[咨询消息规则](15-咨询消息与通知.md)领取和接待；关联订单卡片、通知和私有附件均重新校验身份及权限。

## 6. KOOK 绑定与积分

- 老板和陪玩可在本店启用 KOOK 积分功能时申请绑定；绑定码有期限，必须由该用户在真实渠道完成验证，不能把填写昵称或前端点击当作绑定成功。一个本店 KOOK 身份和业务账号的绑定冲突须提示。
- 当前 [`kook_points.py`](../../services/backend/engagement/kook_points.py) 记录真实语音在线与签到事件，历史实现为累计在线 2 小时 1 积分、指定频道每日签到 5 积分；监听断连期间不凭空累计。频道、开关、倍率／门槛及接入凭据在本店配置与验收，未启用时不得显示真实获分成功。
- KOOK 签到产生积分，与本系统“当日消费门槛签到发店币”是不同功能；积分流水、事件去重、账号和门店分别核对。外部消息、在线状态和实际积分到账不能彼此冒充。

## 7. 老板退店与业务周期

用户已确认保留老板退店清空本店业务权益，但必须具有**独立于普通资料编辑的退店权限**，操作前明确显示清空范围、积分余额及后果并确认，完整留存操作人、原因、前后快照和时间。

现有 [`engagement/retirement.py`](../../services/backend/engagement/retirement.py) 要求先处理进行中的订单、有效预约、开放售后、待结算订单及钱包可用／冻结余额；随后清空本店积分、会员等级、未用券和未交付权益，进入新的业务周期，历史订单和资金流水保留。用户已进一步确认：负积分也允许清零，但确认页必须明确展示负数并留痕。

退店时本月尚未使用的补签卡一并清空，并在确认内容和退店审计中列明数量；历史签到记录保留。重新入店后，当日消费门槛按新业务周期的实际支付计算，原周期消费不能再次用于获取新周期补签卡。

该操作不能在另一家店执行或清空另一店权益；普通 `user:edit` 不自动获得独立的 `user:retire` 权限。已清空的退店请求不得因页面重试而重复执行。首次部署按空库初始化，不增加旧线上账号及数据迁移要求；新系统产生的业务周期和历史记录需要完整保留。退店、签到及重新入店的并发和门店隔离仍需在最终联调验证。

成就页与会员成就标签使用同一套本店确认实销口径：排除礼物和其他业务周期，未确认的服务不计入；已确认服务按实付店币减实际退回店币计算，协商终止后保留的实销计入。已确认的加购按实付净额并入金额成就，订单数量按主单去重。VIP 关闭或 License 不允许发放 VIP 权益，不影响已确认服务的成就统计；VIP 成长与权益仍按各自授权规则处理。若主单全退但仍有已确认且未全退的加购，按一笔服务订单及加购净额统计。
