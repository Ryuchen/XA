# 门店初始化与系统字典：字段、依赖和源码对照

状态：**产品设计与静态源码复核，尚未实现或执行验收**。本页细化[系统字典与门店初始化](12-系统字典与门店初始化.md)；业务决定以总纲、专项 PRD 和用户最新确认优先。本页的建议字段编码、交互、状态和启用校验是可供评审的设计，不表示数据库字段或 API 已存在，也不表示所有门店已经采用某个历史默认值。

## 1. 使用边界、单位和权限

- **配置和业务事实分开**：统一目录管理游戏、等级、规则、选项、比例、金额、时间和开关；订单、余额、流水、人员、券和报单是独立业务对象，不作为可任意改写的字典项。复杂规则可以由专用编辑器持有，但统一入口必须能发现其负责人、校验、版本、状态和使用处，避免维护两份相互冲突的权威值。
- **范围**：平台目录管理门店注册、库、域名及独立平台授权；门店业务配置归该店独立业务库。平台财务和超级管理员负责授权范围内的薪资配置；普通门店管理员、运营只能按本店细分权限配置，不能借字典权限读取其他店或获得平台权限。
- **单位**：用户重新确认 1 元人民币＝10 本店店币；现有内部钱包账务 `100` 单位＝1 元人民币等值＝10 店币，`10` 内部单位＝1 店币。积分余额 `100` 内部单位＝1 积分。薪资、真实收付款与成本按人民币，积分、店币、人民币和内部整数不得直接相加。配置页明确输入／展示单位，API 使用约定单位，变更币名不能改写金额。
- **状态符号**：`开店`＝开放下单或资金业务前必须有明确值及校验结果；`启用时`＝该功能选择启用时必填；`后补`＝明确停用后可开店、开启前必须补齐；`固化`＝用户已确认的业务约束或系统状态，不提供任意编辑。这里的细项分组是对用户“下单和资金核心项必须完成、其他可停用后补录”的落地建议，遇到具体业务是否可关闭的分歧仍需确认。
- **来源符号**：`现有`指静态源码字段或默认值，不推断已生产生效；`模板`指历史海报、参考表或系统预填，须由授权人员逐店确认；`新增`指目标仍需开发。配置缺失、明确的零、停用和验证失败均为不同状态；不能把 `0`、样例或代码 fallback 自动冒充门店已确认配置。
- **字段编码**：下文 `S01`、`F01` 等是追踪编号而不是已存在的字段或数据库表名；每一项需记录类型、单位、是否适用、来源、操作人、版本、生效时点和关联消费者。引用对象必须与当前店及其启用状态一致。

## 3. 创建与启用流程

| 阶段 | 平台及门店操作者 | 进入下一步应检查的结果 |
| --- | --- | --- |
| 1. 门店草稿 | 平台超级管理员录入基本身份、业务入口、目标数据库服务及首位门店管理员。 | 标识、域名、简称、数据库标识和账号均合法且唯一；来源明确。尚未开通时不暴露成已营业。 |
| 2. 库创建和结构迁移 | 在受控环境为新店创建独立数据库，执行版本化迁移并登记结果。 | 验证数据库服务、库名、归属、连接和迁移版本；非空或归属不明的现有库不能仅因“数据库已存在”自动接管。失败不清库、不复制其他店客户和资金。 |
| 3. 首位管理员与权限 | 建立本店可登录管理员，绑定所需的手机号／验证因素；平台授权单独维护。 | 实际身份可验证；店内管理员不自动取得平台权限。首位管理员、口令和短信状态不输出明文。 |
| 4. 复制配置模板或逐项录入 | 仅复制允许复用的配置模板及其版本，逐组填写下文 `开店` 项；其他能力可明确停用。 | 不复制客户、陪玩、员工、订单、资金、积分、消息和文件；模板值经本店确认，关联其他店对象不得通过。 |
| 5. 依赖与试算 | 按服务、价格、抽成、钱包、VIP／积分、押金／提现及已启用功能进行校验，检查权限及可达服务。 | 缺项列明影响的功能和修复入口；仅计算预览，不产生真实充值、订单、提现、佣金或发券。 |
| 6. 汇总并启用 | 平台超级管理员确认缺项、停用项、外部接入状态及负责人员。 | 核心通过后才切为营业；缺项、建库失败、凭据失效或验证无法完成时不冒充成功。 |
| 7. 后续维护 | 获授权人员从本店「快捷配置」进入对应业务页面、配置窗口或分类列表。 | 保存前展示影响、来源和生效方式；冲突重读；历史订单、流水及已使用权益按原事实保留。 |

**源码差异**：现有 `create_database` 使用预设 alias；MySQL 执行 `CREATE DATABASE IF NOT EXISTS`。现有函数本身没有证明已存在库为空且仅属于新店。新设计需在创建前和恢复时核对库归属、迁移状态与首位管理员状态，不把错误重试当成可重复创建；不能根据本 PRD 声称已经安全支持任意在线建库。

**状态建议**：门店级区分“草稿／建库中／待配置／待校验／营业中／停用／初始化失败”；每组配置区分“未填写／草稿／待确认／校验中／已确认／明确停用／校验失败”。这两组是产品状态建议，不直接等同当前 `Store.Status` 的三个枚举。网络超时应能按门店与初始化任务重查结果；重试复用已完成的受控步骤，不重复创建账号、改写业务库或将未知视为成功。

## 4. 字段级配置目录

权限栏使用现有权限名作为**源码定位**，不自动构成最终授权方案。下列范围中标记“当前”的值是代码约束；其他说明是目标规则或需要在实现时确定的输入约束，不把历史限制硬编码成用户新需求。`快照`意味着需有可追溯的适用值及版本，具体存储结构由实现设计决定。

### 4.1 门店、身份、域名及库

| 编号／字段 | 类型、范围、单位及初始化状态 | 权限、依赖、生效、现状 |
| --- | --- | --- |
| S01 中文名 `name` | 字符串；当前最长 80；`开店`。 | 平台门店授权；与展示、消息、审计关联，名称变更不改历史交易。见 [`Store`](../../services/backend/stores/models.py)。 |
| S02 内部标识 `slug` | 小写字母开头，含小写字母、数字或短横线，当前最长 48、唯一；`开店`。 | 平台分配；影响域名、令牌和任务；创建后当前不可由普通更新修改。声浪 `shenglang`，兴安 `xinan`，兴安原独立库不迁移。 |
| S03 陪玩展示简称 | 店级大写英文简称；已确认声浪 `SL`、兴安 `XA`；`开店`。 | 影响老板端 `SL-昵称` 等展示；实现时评估是否复用业务编号 `entity_prefix`，须保护既有编号及确认后的展示值，不能默认采用 slug 前两位。 |
| S04 业务编号前缀 `entity_prefix` | 当前 2–4 位大写字母或数字、唯一；`开店`前明确。 | 现有用于业务编号，不应因修改展示简称悄然重编历史 ID；不填时当前由 slug 推导。 |
| S05 店币名称 `currency_name` | 字符串，当前最长 16；`开店`。 | 声浪浪花、兴安星辉；服务端、页面、消息均读所属店。当前模型默认浪花，新店不得把默认值当作已确认币名。 |
| S06 Logo `logo_url` | 受控上传的图片地址；`后补`。 | 现有校验仅接受本服务媒体地址；展示素材不进入资金运算。 |
| S07 老板／陪玩域名及入口 | 两个 URL，同店域名分别 `/boss`、`/player`；`开店`。 | 域名服务端绑定门店；跨店 token 不可使用，未知主机不回退默认店；业务端无切店。后台为统一 `admin.esports.club`。 |
| S08 业务库登记及归属 | 库服务、受控数据库名／alias、归属与迁移版本；`开店`。 | 仅平台受权管理；凭据安全保存；当前 alias 须预注册且不被门店目录占用，已分配库不能更名接管。 |
| S09 首位管理员 | 身份、登录凭据、昵称和可验证手机号；`开店`。 | 本店权限与平台授权分离；当前提交管理员信息要求四项一起提供，手机号验证不能伪造。 |
| S10 门店生命周期 | 草稿、初始化、营业、停用等服务状态；`固化`由流程驱动。 | 不能在通用字典中随意修改订单或资金状态；启用须通过本店依赖验证。 |
| S11 三端身份认证 | 三端均可账号密码登录；未绑定 OTP 用短信，已绑定默认手机验证器动态口令并可切短信；已绑定微信可扫码或快捷登录；`固化`。 | 老板可自行填写手机号并短信验证；未绑定微信可以先登录，陪玩正式接单前另须绑定微信。平台共享微信／短信接入，不合并门店账号与令牌。 |

### 4.2 游戏、服务、资格与报价

| 编号／字段 | 类型、范围、单位及初始化状态 | 权限、依赖、生效、现状 |
| --- | --- | --- |
| C01 游戏类目 | 唯一名称、图标、排序、启停；`开店`时对已销售服务必填。 | `service:edit` 所涉授权；[`GameCategory`](../../services/backend/orders/models.py)；停用后新单不可引用，历史保留。 |
| C02 服务分类 | 名称、方向、礼物标识、排序、状态；`开店`时已销售服务必填。 | 礼物标识影响看板和订单逻辑，不得随意把历史服务改成礼物。 |
| C03 玩法 | 稳定编码、名称、封面、说明、排序、归档／启停；`开店`时适用服务必填。 | [`Gameplay`](../../services/backend/orders/models.py)；已有单按快照，展示配置不能替代真实玩法和资格。 |
| C04 套餐价格、单位 | 服务项目标价为 10 店币的整数倍，单位如份／小时、购买数量；`开店`。 | 记录门店币和内部单位，价格由服务端报价；`ServiceItem.price` 及 `price_unit` 为现有字段。按预约时长计算或单一比例折扣后有小数店币时分别按已确认规则向上取整；历史金额不得静默改写。 |
| C05 人数与计费人数 | 分开配置服务实际履约人数与按人／整单计价方式；当前 `billing_provider_count` 为 1–2；`开店`。 | 区分双陪报价已含两人还是每人计价，不能将整单价再次乘二。现有创建逻辑将履约人数赋为计费倍率，整单价双陪可能被误作单陪；报价、选人、报名、派单及历史快照均须贯通。 |
| C06 服务性质与限购 | 普通／体验／活动限定／附加费、适用时间、购买资格与数量；`启用时`。 | 体验套餐不适用普通活动及积分抵扣；特殊玩法加购须关联本店正在履约且符合该玩法条件的主单，老板从主单直接购买，不能当独立普通服务；不使用折扣、券或积分。预约转服务订单时选普通券，按一般规则校验。 |
| C07 资格维度 | 游戏、方向、端游／手游、难度、档位及技能；`开店`。 | 资格与价格、接单、后台派单和查询共用；[`qualifications.py`](../../services/backend/users/qualifications.py) 部分选项与费率目前写死，逐店配置是新增目标。 |
| C08 陪玩档位与晋级关系 | 档位编码、显示名、顺序、启停及适用资格组合；`开店`。 | 同一范围内明确上下级及引用服务；不得因为全局新排序自动改已支付订单资格。 |
| C09 订单等待时长 | 分钟整数，当前 1–1440，历史默认 30；`开店`。 | `order:timeout`；[`OrderTimeoutConfig`](../../services/backend/orders/models.py) 和历史记录；新单记录当时规则，不把 30 当作各店已确认值。 |
| C10 高峰、低谷和配额 | 开关、小时起止、每账号／分钟与全店每分钟／秒配额，分别配置下单、抢单、刷新、报价；`启用时`。 | 当前 [`traffic_views.py`](../../services/backend/orders/traffic_views.py) 校验峰谷不重叠、三时段四动作完整，`order:traffic` 修改；关闭和被全局运行开关禁用需分别提示。 |
| C11 老板游戏资料字段 | 各店按游戏或服务设置哪些资料必填、其余选填；字段标识、展示名称、启停、归属范围与校验；`开店`前配置适用服务。 | 服务级规则优先，未设置时继承游戏级；老板下单、预约和后台代单共同校验，缺少必填项提示补齐；历史订单资料不抹除，不能据一店要求影响另一店。 |
| C12 预约时间范围 | 每店预约起止时间粒度、单次最短／最长时长、最远提前期；`启用时`。 | 小时服务按老板下单时选择的预约时长报价，出现小数店币向上取整至整数店币；不在平台计时或核算实际陪玩时长。服务项目标价须为 10 店币的整数倍。当前代码固定 15 分钟粒度、30 分钟至 12 小时、最多提前 30 天，仅作历史参考。 |
| C13 预约确认时限 | 每店待确认预约的有效时长；`启用时`。 | 已提交预约按提交时的时限快照执行，修改只影响新预约；距开始不足确认时限不得提交新预约，双陪补位可在不足时限时继续邀请且最晚开始前确认。仅本人可确认或拒绝。 |
| C14 预约付款截止 | 每店已确认预约的付款有效时长；`启用时`。 | 从所有陪玩确认后开始计算，以门店时限届满或预约开始中较早者为截止；已进入待付款的预约保留当时的时限快照，新预约用新时限。未付款到期取消释放，付款与到期并发只能有一个结果。 |
| C15 双陪预约换人截止 | 当一名陪玩拒绝或超时后的替换处理；`固化`。 | 保留已确认者及其档期供老板重选；即使剩余时间不足常规确认时限仍可邀请替代者，最晚须在预约开始前确认。到开始仍未完成则取消并释放档期。 |
| C16 抢单自动分发 | 门店配置秒级抢单收集窗口，与 C09 的订单总等待时限分别保存；按提交时通行证等级→近 30 天接单额→好评率依次比较；`开店`前若开放未指定陪玩或客服安排的新单则必填。 | 新单进池即开始首轮计时，各人可见时间按入池时本人通行证及门店延迟配置确定；首轮长于总等待时至少延长至首轮结束。双陪可提前邀请但队友须到本人可见时间后确认。接单额本人开始履约后计入，按各次接入时间与份额归属。双陪各取本人提交时等级并逐项取最高，同分按提交完成时间；连时间也相同则即使总等待已到也延长并重开完整窗口，所有当前合资格者同时可见并重新抢。首名失去资格时，未到期则重开、已到期则退款，两种原因不可混淆。有效提交后通行证到期不使该次候选失效，其他资格仍须复核；首轮无人抢且仍未到期时，已到可见时间的首个合资格单陪或完整双陪队伍直接获得。 |
| C17 玩法房间及结单确认 | 通用房间启停与所属玩法关联、老板待确认时限、规则版本及适用角色；`启用时`。 | 本期建设通用房间，旧九种具体玩法另行接入。时限从进入待确认时开始并保存当时配置；老板提出异议时暂停并通知客服，处理后原条件仍满足则继续剩余时长；纠正后不满足、重新履约达标则按再次待确认时配置开启完整新时限。无异议超时自动确认；不推定缺失值。 |
| C18 已确认的加购初始化参考价 | 银行手游绝密加仓 1080 店币；环太平洋／盲盒预言家端游绝密 680、机密 480 店币；跑刀百万房卡 40 店币；`启用时`按适用门店确认。 | 两店对前两组均可参考并独立修改；跑刀百万房卡为用户核对原价后确认的新价，各店按实际适用范围确认。配置价格不代表对应玩法已上架；记录端、难度、规则来源、版本及修改人，不回写历史订单。 |
| C19 瓦罗兰特加收单位 | 按适用附加项目配置可选小时／局、该单位单价、购买数量范围及精度；`启用时`。 | 老板自主选择加购小时数或局数并由服务端核价，不按主单总数或实际在线时长自动加收。1 陪 2／1 陪 4 是一名陪玩服务两位／四位同队老板，仅一位订单老板下单付款，其他队友无需注册；不能误当两名／四名陪玩。 |

## 5. 配置依赖、版本和失败处理

### 5.1 最小依赖链

1. **门店身份 → 业务库 → 本店管理员 → 配置归属**：库和域名验证未完成不能进入营业。平台超级管理员与平台财务不应被建成某店临时员工来借用权限。
2. **游戏／服务 → 资料必填项、资格与价格 → 分成 → 下单**：目标店启用一个服务时，检查其对应分类、计价人数、价格、资格、抽成路径均能得到明确结果；本店按游戏或服务配置游戏资料必填项，其余选填；老板预览、陪玩接单和后台派单读同一套生效配置。
3. **钱包 → 预存／积分 → 支付 → 退款**：本期由客服核验线下充值、老板用钱包支付；先确定本金与赠送规则，积分功能启用时先确认普通／VIP 发分倍率、抵扣汇率及低于 100% 的上限。代单可按老板明确告知代填积分／赠送／赔付并保留确认。报价须保留所选资金来源和版本，退款以原记录及用户确认的退回次序执行。
4. **押金／结算 → 提现规则 → 平台财务授权**：店内客服初审与平台财务终审／打款分离；申请时保存费率和金额；申请、冻结、拒绝和付款有各自状态。
5. **岗位字典 → 薪资方案 → 真实员工安排 → 月度核算**：平台公共人员使用独立平台归属；跨月退款对工资的影响在退款月扣减，不静默改写原月已确认工资。投流和工资缺失不能显示成零成本。尚未开启薪资的店可以明确标为未配置，不冒充已核算。
6. **功能开关 → 关联对象 → 外部接入**：VIP、优惠券、抽奖、KOOK 等选择启用时，关联服务、库存、权限、时间和渠道必须符合各自规则；尚未启用的能力不可出现在业务操作入口并伪装成成功。

### 5.2 生效和追溯

- 每组配置至少记录当前值、草稿、版本、修改人、批准／确认人（如适用）、变更原因、保存与生效时间、依赖对象及权限；预览列出受影响的新报价、人员、活动和已有权益。需要 OA 的充值赠送例外必须关联独立审批记录，不能将字典保存当作审批。
- 配置保存须服务器端校验；两名管理员同时编辑时按版本检测并提示重新读取；不能把失败写入展示为已生效。停用被引用配置须展示影响，保留历史引用与旧版本，不直接物理删除已发生业务依赖。
- 多数价格、抽成、支付、提现和工资变更作用于新业务或相应未来周期；已支付订单、已提交提现及已确认工资按对应快照核对。VIP 券须区分仍在使用等级修改条款、取消等级、退款降级、月中升级、VIP 停用和全退返券等各自已确认规则；月券数量变动从下次发券生效，不能把所有事件简化成同一条更新规则。
- 可退回店币的部分退款先按原店币／积分比例计算，再按本金、赠送、赔付依序退回；与发放或冲回消费积分、已发推荐佣金不追回分别记账。配置回滚不得自动撤销真实支付、退款、发券、记账或外部打款。
- 店 A 配置改变后只影响店 A；跨店报表按店明确显示适用版本、币名与不可用状态；不能将店 B 未完成的配置或查询失败折算成零或借用店 A 的配置。

### 5.3 变更和数据来源核对

| 情况 | 产品要求 |
| --- | --- |
| 模板导入 | 记录模板名、来源、版本和人工确认值；仅导入选项和规则，不导入任何人员、资金或业务数据。 |
| 历史代码默认 | 明确展示“历史默认／未确认”，不把 30 分钟、2% 或某店海报直接视为每个新店已确认。 |
| 存量店补配置 | 先核对当前真实值和引用，不因补录重建库、清零钱包或追溯重算旧订单。 |
| 数据源不一致 | 标明各入口读取的权威配置、旧字段和默认回落；对会改变资金或权限的冲突阻止启用并列出处理方式。 |
| 外部接入不可用 | 区分未配置、已保存、验证失败、验证中与真实可用；不发送真实客户消息或触发生产付款进行初始化试验。 |

## 6. 需要进一步确认的规则和实现边界

1. **业务编号前缀与陪玩展示简称**：现有 `entity_prefix` 是业务编号前缀；用户要求的是展示 `SL-`／`XA-`。实现设计须评估是否共用字段，确保简称展示正确，且以后简称变化不擅自重编历史编号，不能由“同为英文”直接假定已有能力。
2. **提现余额门槛边界**：已确认按店分别设置最低单笔和可用余额门槛、申请时同时满足；可用余额须严格大于门槛，等于不通过。当前特定规则开关会令单笔最低额返回零，需调整。
3. **外部身份与渠道作用范围**：已确认各店共享平台微信／短信接入；仍须保留并校验门店身份和回调，不能借环境默认把一个店的 KOOK／企微接收对象用于另一店。
4. **售后和冻结两段时间**：用户已确认普通订单售后等待从整单完成开始，协商终止的售后等待从相关方确认终止时开始；收益冻结从本人最后一次有效报单提交开始，两段重叠计时。即使双陪中一人先协商终止、两段均已到期且审核通过，该人收益仍须等整单完成并满足其他条件后才释放；整单完成不重置已启动的协商等待。当前收益释放、售后窗口和实销确认代码有不同时间点，实施时须按新规则逐路径对齐，不能声称已经实现。
5. **VIP 降级与升级后的权益**：退款降级时已发未用月券、升级券、安全箱券和未交付权益全部保留；月中升级不补发月券，原券条款不变，下月按新等级发券。客服不得临时改单笔抽成、保底次数修改后重新计数、老板消费榜包含礼物均已确认。
6. 参考金额、日期及初始化权限颗粒度须在实际开店时按门店和人员授权核对；数据库服务是否允许网页创建新库、现有库可否接管以及故障恢复能力均需隔离环境实测，当前仅有静态代码证据。
