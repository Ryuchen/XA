# 老板端原型、源码与跨端链路复核

日期：2026-11-06。本页是在既有[老板端 PRD](02-老板端.md)、[订单及资金](05-跨端订单资金售后.md)和[门店配置](12-系统字典与门店初始化.md)基础上，对现有原型和当前产品代码做的静态复核；目标行为、代码现状及待确认事项分别标记。这里不是完整联调或真实资金验收报告。

## 1. 原型的适用范围与优先级

- `../../design-demos/shenglang-web-prototype/README.md` 说明当前 React 原型为视觉与流程示意，操作使用本地演示数据，不能证明真实认证、消息、资金和数据库功能已完成。原型中的示例价格、人员、账户和成功状态不能写成门店默认配置或真实业务事实。
- 原型的 [`direction-approved.md`](../history/design-directions-20261117/shenglang-web-prototype-direction-approved.md) 记录沿用已确认的“澄海：任务优先”；它引用的旧 `design-demos/huashu-20261101/direction-approved.md` 在当前工作区未找到，不能将缺失文件的内容当作已重新核验。
- 原型 `../../design-demos/shenglang-web-prototype/app/STORE-DESIGN.md` 中查询参数切店、三端共享切换器、独立店内后台入口、示例门店及平台不看各店明细等，是较早概念演示，均以当前用户确认的固定门店子域名、统一后台、独立平台授权和平台聚合规则为准。老板与陪玩端不提供切店 UI；不要把旧门店名、旧币名或原型示例数据库当作现网配置。
- 老板端正式源码从 [`App.tsx`](../../fronted/boss/src/App.tsx) 的路由及实际 import 判断；同文件中的兼容跳转和原型里独立的内容页不能只按页面数比较。原型的活动／权益／积分规则及其详情，在当前源码中由 [`content.tsx`](../../fronted/boss/src/business/content.tsx) 的 `/club-content` 按 `kind` 和 `id` 表达；不能仅因路由名称不同认定能力缺失，也不能仅因能打开内容页认定活动报名或交付功能已存在。
- 为避免把原型里的全局切换当成当前设计要求，后续复核仅使用其服务信息、角色动作、交互状态及页面之间关系；老板、陪玩两端继续适配手机和桌面，后台适配约 1366×1024 及以上，当前阶段不做视觉重设计。

## 3. 各条独立支付入口的共同要求

本期采用客服核实线下充值、老板钱包支付。网页微信直付是后续能力，不能因已有相关源码或历史原型而当作本期可用渠道；历史真实交易仍按实际渠道和状态展示。

| 场景 | 当前实际链路与已有代码证据 | 本轮需求及验收 |
| --- | --- | --- |
| 普通服务下单 | 前端 [`checkout.tsx`](../../fronted/boss/src/business/checkout.tsx) 报价、确认后进入 [`CreateOrderView`](../../services/backend/orders/views.py)；现有实现验证并直接减少 `Wallet.balance`。 | 所有比例折扣互斥，每单最多一张券；金额券可叠加会员或门店活动折扣，合资格服务再按本店规则选择积分，默认推荐合法组合中最终实付最低者。赠送及赔付默认 0 并分别可填，其余从本金支付；体验套餐不使用积分，保存支付构成及适用快照。 |
| 预约确认后转服务订单 | 前端 [`reservations.tsx`](../../fronted/boss/src/business/reservations.tsx) 调用 `GET /api/orders/reservations/{id}/quote/`，提交 `POST /api/orders/reservations/{id}/convert/`；[`ReservationQuoteView`／`ReservationConvertView`](../../services/backend/orders/reservation_views.py) 分别报价和成单，[`convert_reservation_to_order`](../../services/backend/orders/reservation_services.py) 锁预约和钱包后从总余额扣款、创建并指派订单。 | 允许选普通优惠券，适用资格、比例折扣互斥及金额券的可叠加范围与普通服务一致；仅合资格服务单支持积分，老板可分别填写赠送／赔付。报价与提交核对券、来源构成及积分规则，资格、余额或金额变化须重算，重复请求只形成一次扣款及订单。 |
| 直接赠礼／服务后赠礼 | 前端 [`gifts.tsx`](../../fronted/boss/src/business/gifts.tsx) 调用 `/api/orders/gifts/send/` 或 `/api/orders/orders/{id}/tip/`；[`TipOrderView`](../../services/backend/orders/views.py) 与 [`send_basket`](../../services/backend/orders/gift_basket.py) 按当前总余额扣款，多款分成多个礼物订单。 | 两种入口只能使用本金，不能使用赠送、赔付和积分抵扣；服务端也拒绝伪造参数。本金不足时即使赠送／赔付余额充足也不能支付。每款独立记录本金支付和退款，原有本金消费赠分按付款时 VIP／普通会员倍率核对；礼物收益与服务收益分开，礼物不计推荐佣金。 |
| 客服代老板下服务单 | 后台 [`OrderDispatch.tsx`](../../fronted/admin/src/pages/OrderDispatch.tsx) 试算并由 [`quick_dispatch`](../../services/backend/console/views.py) 按目标老板钱包余额扣款；现状不能等同于已支持本轮积分和钱包分类。 | 客服按老板明确告知代填所选积分、赠送及赔付数量，保留老板确认事实、内容和操作记录。试算、券资格、积分比例、资金选择和支付记录与老板自主下单遵循相同业务边界；不得擅自代老板选择。 |

各条链路的店币分类要由服务端校验，不能只改页面。每笔应记录订单、老板、门店、本金／赠送／赔付、积分抵扣、配置及请求快照。取消或售后退款时，先按已确认规则计算应退店币和积分，再将店币依次退回本单本金、赠送、赔付；已发消费积分按实际退回本金冲回。礼物只用本金，退款退回本单本金，仍需追溯每张礼物单的真实支付和消费赠分。

## 4. 本轮发现、待确认及应验证的情形

1. **多款礼物支付及退款**：用户已确认礼物只能用本金，因此每款礼物订单支付及退款均记录本金，不再存在赠送／赔付在多张礼物单之间分配的问题。现有 [`gift_basket.py`](../../services/backend/orders/gift_basket.py) 把一个请求拆为多张可分别退款的礼物订单；服务端必须从本金余额检查整篮可用金额，避免总余额足够而本金不足时错误成功。**现有代码每款独立调用礼物订单逻辑，人民币 20 元抽成门槛按各款订单金额判断，不按一次购物篮合计判断。**
2. **服务所需游戏资料**：目前 [`checkout.tsx`](../../fronted/boss/src/business/checkout.tsx) 对所有服务都要求填写游戏大区和昵称，而 [`CreateOrderSerializer`](../../services/backend/orders/serializers.py) 的对应字段允许为空。用户已确认由每个门店按游戏或服务配置各资料字段是否必填，其他字段选填；普通下单、预约创建和预约转单均须读取对应配置并在服务端校验，订单保留下单时的资料规则和实际资料。配置继承、优先级及变更生效方式仍需与完整系统字典设计一致，不能仅改前端提示。
3. **身份与安全页**：按统一规则保留老板密码登录，贯通 OTP 绑定、默认验证及短信切换，并允许本人填写手机号后验证短信；`audience=boss` 接口、安全页、微信扫码和旧账号关联必须端到端核对。普通浏览器微信扫码当前 UI 标为待开发，不能把 `verify_phone=1` 旧页面视作真实扫码授权已完成。
4. **收款与优惠入口的并发**：同一老板先在普通下单页选择部分赠送，再在预约／礼物页消费或进行退款时，各入口应按最新可用余额校验；礼物另须检查本金是否足额。余额变更、店币分类变化、券失效、积分汇率变更或 VIP 等级变化须重新确认，不能按旧页面超额扣款。
5. **礼物结果和售后**：一批次礼物可以按商品生成多张订单；每单只记录本金额，确保单张退款不会退回其他子订单资金；一笔请求超时须用原请求查结果，不能再次发出另一批礼物。现有 `tests/test_gift_basket.py` 和 `tests/test_gift_basket_refund_journey.py` 是历史测试源码线索，不代表本轮新增规则已测试通过。
6. **原型覆盖审计**：分别从原型的服务详情、结算、订单详情、预约详情、礼物、会员、权益与客服入口，沿生产路由核对状态和返回路径。原型存在的场景和演示文案不自动构成已上线能力，尤其不能把历史查询参数切店、旧登录或原型静态支付当作验收。
7. **订单客服、咨询领取人和薪资归属不能混同**：老板确认单可选“订单客服”，[`CreateOrderSerializer`](../../services/backend/orders/serializers.py) 将 `support_contact_id` 解析为启用的 [`SupportContactCard`](../../services/backend/support/models.py)，该名片模型当前没有关联后台员工账号。用户已确认名片须绑定本店员工，并作为订单负责人；咨询仍由本店共享会话池的领取人接待，**订单负责人不因此取得聊天正文权限**；业绩按实际工作记录核算，不能直接把名片 ID 当成员工 ID、领取人或提成归属。
8. **预约转单与优惠券**：[`reservation_order_pricing`](../../services/backend/orders/reservation_services.py) 当前以预约资料构造普通订单校验，但没有传入老板选定的 `user_coupon_id`；预约转单页面也没有普通券选择入口。用户已确认转单时可选普通券，资格和优惠互斥同普通下单；体验套餐中的资格券另按其资格规则处理。新增选券时，报价、选券、资格变化、成单、过期及退款须同步核对，不能只在页面展示可选券。
9. **客服代单确认与真实操作人**：当前后台快捷派单可代老板扣钱包；用户已确认客服可按老板明确告知代填积分、赠送和赔付，并须留存老板确认。具体记录应能关联老板、订单、选择数额、确认事实及客服操作，不把客服本人当作付款老板，不绕过本店配置、优惠互斥与资金校验。

建议在隔离真实业务数据库中，针对普通下单和预约转单覆盖比例折扣互斥、金额券合法叠加、默认推荐最低实付、默认不使用赠送／赔付及分别选择；针对客服代单核对老板明示内容、确认记录与真实操作人；针对直接礼物和订单后礼物覆盖只能使用本金、赠送／赔付充足但本金不足、伪造积分及资金来源参数；各入口均覆盖并发、重复请求、订单详情与退款结果。再在可安全使用的外部测试环境单独核对微信授权。以上均为**待执行**验证。
