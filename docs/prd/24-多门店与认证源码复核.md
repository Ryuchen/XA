## 1. 入口、数据和角色边界

| 对象 | 目标规则 | 当前源码证据及差距 |
| --- | --- | --- |

两家门店的同数字 ID 是不同业务对象；平台汇总和待办定位须以“门店＋对象 ID”区分。同一人可以在各店有各自的业务身份，但微信服务共享并不合并账户、钱包或历史记录。

## 2. 三端登录目标与当前实现差异

用户已确认：

1. 老板、陪玩、后台三端均支持账号密码登录。账号尚未绑定手机验证器时使用短信验证；已绑定时默认使用手机验证器动态口令，并可切换到短信验证。老板可自行填写手机号并通过短信验证；手机号归属及接入状态须真实核验。
2. 微信已绑定时，可以扫码或快捷登录；微信授权确认后直接进入对应账号，不额外要求密码或动态口令。具体可用授权渠道必须满足微信真实接入能力，不能以演示二维码冒充成功。
3. 后台未绑定微信也可先登录，不强制在首次密码登录时绑定；需要使用微信快捷登录前再完成绑定。陪玩可先登录，但正式接单前必须完成微信绑定和其他规定资格校验。
4. 各方式均须定位到正确角色、账号及其所属门店，并检查账号、门店、权限和微信绑定状态；验证结果不能借助 URL 或请求头切换到其他身份。手机验证器与微信绑定的状态须按所属账号管理。

老板端 [`login.tsx`](../../fronted/boss/src/business/login.tsx) 和陪玩端 [`Login.tsx`](../../fronted/provider/src/pages/Login.tsx) 当前均调用 [`PasswordLoginView`](../../services/backend/users/password_login.py) 的账号密码＋短信流程；后台挂载 [`fronted/admin/src/App.tsx`](../../fronted/admin/src/App.tsx) 中的 [`DualLogin.tsx`](../../fronted/admin/src/pages/DualLogin.tsx)，实际也是账号密码＋短信，但要求首次微信绑定。三个页面尚未体现“已绑验证器默认动态口令且可切短信”的完整选择；后台强制首次绑微信也与新目标不符。

后台 [`console/auth.py`](../../services/backend/console/auth.py) 的登录入口委托 [`ConsolePasswordLoginView`](../../services/backend/console/dual_auth.py)。代码保留了 [`otp.py`](../../services/backend/club_accounts/otp.py) 的验证器 TOTP、首次绑定及恢复码机制，也保留旧的后台 [`Login.tsx`](../../fronted/admin/src/pages/Login.tsx) OTP 交互，但不能据此认定当前三端页面、接口和令牌已实现用户确认的切换流程。原 [`tests_admin_entry.py`](../../services/backend/stores/tests_admin_entry.py) 对相同入口仍有 `requiresOTP` 断言，其适用性须随改造重新核实；本轮未执行测试。

当前 [`DualLogin.tsx`](../../fronted/admin/src/pages/DualLogin.tsx) 在微信内提供 H5 授权入口，而普通浏览器的微信扫码按钮标为待开发。另有微信桥接接口及 [`users/h5_login.py`](../../services/backend/users/h5_login.py) 逻辑，但接口存在不等于当前桌面浏览器扫码可用。上线前须核实平台账号资质、授权域名、回调、微信身份关联及实际运行环境，不模拟授权成功；前端应清楚区分不可用和已开通方式。

同一微信若对应多个门店后台账号，当前 H5 回调会提示身份不唯一并要求使用 `门店标识/账号` 密码登录，不默认选择。密码路径恢复后应继续保持这一安全行为；如果未来希望扫码后列出多个身份，须另做已验证身份的明确选择和授权设计，不能以未经验证的请求参数选店。

## 3. 平台人员跨库写入的特别核验

平台查看和处理不同门店数据时，操作人身份与目标店本地账户不能仅凭数字 ID 关联。当前 [`StoreSwitchView`](../../services/backend/stores/views.py) 发出的目标店平台令牌由 [`account_for_claims`](../../services/backend/club_accounts/tokens.py) 找回默认库的平台账号；而现有提现领取使用 `request.account` 写入目标店 `WithdrawRequest.claimed_by_account`，见 [`console/views.py`](../../services/backend/console/views.py) 和 [`wallet/models.py`](../../services/backend/wallet/models.py)。该字段是目标业务库内 `ClubAccount` 的外键。若不同库恰有相同数字 ID，或目标库没有对应 ID，必须分别验证领取、审核、流水及操作日志如何行为；不能假定目标店本地同 ID 账户就是平台人员，也不能把本段静态风险当作已验证的线上事故。

目标实现需要稳定的**平台操作人身份**、所属平台授权、目标门店、操作时间和原始业务记录关联。必要时设计明确的平台主体引用／审计快照或其他有验证依据的方案；不要为绕过跨库外键而复制客户、钱包或伪造门店员工。平台财务终审、打款登记、工资确认、跨店配置、后台审计和通知都要覆盖同一身份规则，资金写入仍只落目标店。

## 4. Web 建店、域名与初始化的真实边界

1. 现有 [`StoreManageView.post`](../../services/backend/stores/views.py) 在收到完整首位管理员信息时可调用建库与初始化；[`StoreCreateSerializer`](../../services/backend/stores/serializers.py) 只接受部署配置中已存在且未分配的数据库 alias。网页可以触发这个受控流程，但当前不是网页任意录入一组新数据库服务凭据后即可完成注册。
2. [`create_database`](../../services/backend/stores/provisioning.py) 对 MySQL 使用 `CREATE DATABASE IF NOT EXISTS`，不能单凭执行成功证明已有库为空、由新店独占或适合迁移。创建前及失败重试须核对归属与迁移进度；不能清库、接管已有业务库或重复创建首位管理员。当前迁移及管理员检查结束后即将门店标为 `ACTIVE`，不等于核心业务字典已填完、入口已验证或达到开业条件。
3. [`STORE_HOST_BINDINGS`](../../services/backend/config/settings.py) 现写明声浪和兴安两个域名，[本地 Nginx 域名配置](../../deploy/esports-local/nginx/conf.d/domains.conf)也只转发这两个店及统一后台。新增门店的 URL 字段保存成功不等于正式主机已绑定。初始化须将受控域名注册、路由和允许主机、DNS／证书、外部授权及回调逐项核验纳入状态；缺项时保留真实待完成状态。具体部署能力和是否需要运维介入须实际验证。
4. 目录记录中的业务编号前缀用于实体编号，用户可见的陪玩名称前缀须明确满足 `SL-`、`XA-` 等展示规则。新店默认前缀可能由 slug 前两位推导，不得用它代替对展示简称的显式校验；已有业务编号和历史票据不得因展示改名被擅自重写。
5. 微信与短信由平台统一共享接入，按门店保留回调和业务身份上下文；每家店的客服消息目标等须独立。现有 [`stores/conf.py`](../../services/backend/stores/conf.py) 仍允许门店级覆盖 `WECHAT_` 和 `SMS_`，因此统一接入是目标规则，不能仅凭当前回退机制宣称已经实施。无真实凭证时 [`settings.py`](../../services/backend/config/settings.py) 存在可配置的模拟登录默认路径；验收真实授权前应核对实际环境，模拟结果不能作为真实微信登录成功凭据。

## 5. 缓存、文件、实时消息和异步任务

[`StoreRouter`](../../services/backend/stores/router.py) 将平台门店目录与业务对象分流，并对部分跨库模型关系进行检查；[`stores/cache.py`](../../services/backend/stores/cache.py) 为缓存键加入门店；[`stores/media.py`](../../services/backend/stores/media.py) 区分非默认店的文件目录；[`stores/channels.py`](../../services/backend/stores/channels.py) 按门店隔离实时群组，[`channels_middleware.py`](../../services/backend/club_accounts/channels_middleware.py) 校验域名与令牌门店。这些实现是隔离基础，仍需逐类验证权限、下载链接、令牌、不同门店同 ID 和异步上下文，不能仅凭文件路径断言完整安全。

[`stores/tasks.py`](../../services/backend/stores/tasks.py) 为已列举周期扫描按门店派生任务，为上下文内提交的任务携带店标识；对无店标识的非周期任务及部分直接执行仍保留回落 `shenglang` 的兼容逻辑。新产生的业务任务应明确来源门店并在执行前核验，不能因为上下文缺失而意外把其他店任务落到默认店；历史无标识任务如何识别和安全处理需有迁移方案。一个门店不可用时，其他门店的周期任务结果、失败重试和账务必须仍能各自追踪，不以一个店成功代替所有店成功。

## 6. 门店统一配置陪玩并发上限

用户已确认每家门店设置统一上限，对该店所有陪玩一致；不是按陪玩单独设置。当前 [`Order.MAX_CONCURRENT_ORDERS`](../../services/backend/orders/models.py) 固定为 3；[`orders/applications.py`](../../services/backend/orders/applications.py)、[`orders/views.py`](../../services/backend/orders/views.py)、[`orders/serializers.py`](../../services/backend/orders/serializers.py) 和 [`users/views.py`](../../services/backend/users/views.py) 均有相关判断或展示。改造必须让陪玩列表状态、报名／接单、指定陪玩下单、后台派单和陪玩工作台显示使用同一门店规则，并对并发提交作服务器端校验；仅改字典页面或提示文案不足以实现规则。

配置项需要记录值、有效状态、修改人和生效时刻，并校验为合理的正整数。下调时已有履约如何处理、以及历史默认值的迁移方式须在实施前明确；不能在没有业务依据时直接中断订单。其他门店的配置不得受到影响。

## 7. 专项验收场景

以下为待实施的目标验收，不代表本轮已执行：

1. 在两套独立测试库建立相同数字 ID 的不同账号、订单及钱包；分别通过声浪／兴安四个入口执行查询、下单、回执与刷新，验证跨店令牌、错误域名和伪造路由提示均不能越界或回退默认店。
2. 三端分别验证未绑验证器时账号密码＋短信、已绑时默认手机验证器且可切换短信；后台先登录不强绑微信，陪玩未绑微信不能正式接单，绑定后微信授权确认直接登录；解绑、账号停用、授权失效、验证码重放与账号多店重名均正确反馈，不凭请求参数决定身份。真实微信渠道未开通时明确标示，不能以模拟数据冒充通过。
3. 平台超管默认看到授权范围内的聚合和可溯源的分店明细；普通店员无法读取他店。平台财务只具备授权的财务与薪资权限，不获得平台建店、人员管理等超管职责。
4. 平台人员在目标店处理提现／工资时，分别构造“目标库同 ID 为另一个人”和“目标库不存在同 ID”的情况，核对领取、审核、操作人、日志、通知及资金账务：不得误认成本店员工、丢失操作人或落入错误业务库。
5. 新店选择独立库、迁移、配置、域名及外部接入验证、启用，逐步展示真实状态；模拟库已存在、归属不明、迁移中断、网络超时和管理员创建失败后安全恢复，不覆盖其他店。只有核心业务配置及必要验证完成后允许营业。
6. 测试缓存键、公开／私有文件、WebSocket、下载票据、消息队列和周期任务：两店同 ID 相互隔离；伪造店标识被拒；店 B 失败不改写店 A；无上下文的新业务任务不得悄悄归入声浪。
7. 两店分别设不同并发上限，在所有接单与派单入口验证容量、页面一致性和同时提交；已有订单及配置变更边界按最终确认规则处理。

陪玩并发上限已确定每店统一配置；下调时保留已接订单，达到新上限后不能再接新单。实际微信授权与域名证书能力属于接入及部署验证，不应由 PRD 假定已经具备。
