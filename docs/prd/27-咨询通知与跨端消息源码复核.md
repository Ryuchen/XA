# 咨询、通知与跨端消息源码复核

状态：根据用户已确认规则，对现有页面、接口和主要消息模型做静态分析。本文中的现状、目标和待验收分别标明；没有执行三端联调，也没有发送真实消息。与[咨询与通知需求](15-咨询消息与通知.md)、[页面接口追踪](08-页面接口追踪.md)和[差距与验收](07-差距待决与验收.md)配合使用。

## 1. 四种信息与三端职责

| 类型 | 老板／陪玩 | 后台 | 当前实现与目标 |
| --- | --- | --- | --- |
| 本店在线咨询 | 向本店客服发送文字、图片，可带订单上下文；查看客服回复。 | 客服查看本店会话列表，领取后接待；授权主管可看正文、重分配。 | [`ChatSession`](../../services/backend/chat/models.py) 当前为每个业务账号／旧用户的共享会话，尚无领取人、接待状态或转交记录；已确认规则需要新增完整归属链。 |
| 站内业务通知 | 查看与自己相关的订单、售后、钱包、活动等通知，阅读后跳转业务详情。 | 有权人员可向本店目标用户发送；系统按业务事件创建。 | [`site_messages/models.py`](../../services/backend/site_messages/models.py) 与聊天是两类独立记录，`is_read`、未读数、跳转和接收人分别管理。 |
| 客服名片与外部入口 | 老板可看公开客服、订单对应客服名片或外部联系方式。 | 维护名片、启用与排序；订单名片对应本店员工及订单负责人。 | [`support/views.py`](../../services/backend/support/views.py) 已提供公开联系方式和按老板订单查询名片；[`SupportContactCard`](../../services/backend/support/models.py) 当前没有后台员工关联。订单负责人不自动成为咨询领取人。 |
| 公告、俱乐部动态与外部消息 | 阅读本店公开内容或按已有入口联系外部客服。 | 运营维护发布；KOOK／企微等单独配置和发送。 | 公告与站内通知、在线聊天的权限和已读不能混同；外部渠道接入、接收人及送达事实需另行核验。 |

同一业务账号的现有聊天会话可承载多个问题；一个人的老板和陪玩身份、不同门店中的同数字账号均不得自动合并。新规则不把老板下单所选名片、会话实际接待人、派单人和业绩归属人视为同一事实。

## 2. 老板、陪玩和后台如何串联

### 2.1 老板从订单联系本店客服

1. 已有老板订单详情从 [`orders.tsx`](../../fronted/boss/src/business/orders.tsx) 进入 `/support?order_id=...`；[`SupportPage`](../../fronted/boss/src/business/content.tsx) 请求本店 `/support/contact-card/`。现有服务端按 `customer_account` 验证订单归属，名片停用时回退到本店当前启用名片；未登录仅可读取允许公开的联系方式。
2. 老板可进入同一页面提供的在线咨询。当前 [`content.tsx`](../../fronted/boss/src/business/content.tsx) 读取订单详情、把“订单号 …”拼入聊天文字；消息保存模型没有订单外键或正式关联。即使页面显示“已关联订单”，现状也只说明已读取该订单和带入上下文，并非已建立服务端聊天关联。
3. **目标**：发送订单卡片前在服务端校验老板、门店和订单；消息保存对应正式订单关联及必要展示快照。客户打开卡片看到自己可访问的最新订单／售后状态。即使名片负责人发生变化，也不能由名片直接改变在线咨询领取人。

### 2.2 陪玩从订单联系本店客服

1. 现有 [`provider/Orders.tsx`](../../fronted/provider/src/pages/Orders.tsx) 将订单号放入 `/support-chat?order_no=...`；[`providerChatScope`](../../fronted/shared/src/business.ts) 验证编号文本格式，[`Messaging.tsx`](../../fronted/provider/src/pages/Messaging.tsx) 发送时把它拼入文字。这个上下文目前不是与订单对象建立的关系，也不能证明提交内容中的订单一定归本人。
2. **目标**：以服务端订单及实际参与者关系验证本店陪玩是否可关联；双陪、转入／转出和历史履约需按已有订单查看权限判断。关联失败要保留草稿、明确说明，不允许仅凭看起来合法的订单号建立关系。
3. 订单信息变更、退款或售后处理后，卡片中的动态状态从最新授权数据读取；已有消息所需的名称、编号等快照不能被误写为新状态。

### 2.3 后台接待和流转

[`ChatSessionViewSet`](../../services/backend/console/views.py) 目前按 `chat:view` 列出和读取共享会话，按 `chat:reply` 回复、查询本人消息发送状态和标记已读；[`AdminChatSessionSerializer`](../../services/backend/console/serializers.py) 返回 `last_message`，前端 [`Support.tsx`](../../fronted/admin/src/pages/Support.tsx)直接展示正文预览并按订单号文本匹配跳转。模型无客服领取人，因此不是本轮目标中的领取制。

| 阶段 | 目标状态与动作 | 须保留的事实 |
| --- | --- | --- |
| 待领取 | 本店客服只看会话列表、身份信息及接待状态，不看正文、图片或含正文的预览；可领取。 | 原客户及历史消息不因领取而重建；同一会话只能有一个有效领取人。 |
| 已领取 | 领取人查看内容并回复；授权主管可查看或不领取直接回复；其他普通客服仍只看列表和状态。 | 主管直接回复不改变原领取人；消息记录真实回复人及顺序，领取动作和责任人可追踪。 |
| 交还／转交 | 当前领取人可交还共享池或转交给具备接待权限的同店客服。 | 会话、历史消息、订单关联和处理记录保留；成功后及时更新两人的权限和待办。 |
| 主管重分配 | 授权主管可指定另一位有资格的本店客服。 | 记录操作者、原／新责任人、时间和原因；失权者不可继续获取正文或发送回复。 |

客服离线、下班或无活动时不自动回收；权限失效或离职时及时停止其读取和回复，主管人工处理会话。用户确认有相应权限的主管可不领取直接回复已由其他客服领取的会话，原领取人不变；主管查看、回复、订单查看和售后查看分别授权。

当前后端支持一次带图片和文字的消息，但后台回复的 [`AdminChatReplySerializer`](../../services/backend/console/serializers.py) 只声明通用 `ImageField`，没有看到与用户端相同的 5 MB 和 JPEG／PNG／WebP 专门校验；用户端 [`ChatSendView`](../../services/backend/chat/views.py) 则显式执行这些校验。若三端统一使用现有用户端约束，后台服务端、页面及失败提示都须补齐；不能将用户端的校验描述为后台已实现。

## 3. 权限、隐私与实时推送需要一起改变

| 接触点 | 当前代码行为 | 目标验收 |
| --- | --- | --- |
| 列表及详情 | [`AdminChatSessionSerializer`](../../services/backend/console/serializers.py) 包含 `last_message`；详情接口按后台权限读取消息。 | 非领取的普通客服从 API、页面、筛选、缓存及分页结果均不得读到正文或正文预览；领取人／授权主管可读。 |
| 正文与已读 | [`ChatSessionViewSet.messages/read/reply`](../../services/backend/console/views.py) 目前没有领取人校验。 | 在服务端按本店、账号状态、当前领取人／主管及动作权限分别验证；转交或撤权即时生效。 |
| 私有图片 | [`private_media.py`](../../services/backend/common/private_media.py) 用短期签名链接，读取与续签时重查账号、资源与当前权限；聊天图片目前以 `chat:view` 判断后台权限。 | 同一检查须增加当前会话归属；撤权或转交后旧链接和续签不能继续读取，且不能跨店访问。公开 `/media/` 不得绕过私有图片授权。 |
| WebSocket | [`chat/notifier.py`](../../services/backend/chat/notifier.py) 广播含消息数据的事件给本店 `operators`；[`orders/consumers.py`](../../services/backend/orders/consumers.py) 每次投递重新读取账号、会话和 `chat:view` 权限。 | 正文只投递领取人／授权主管及会话本人；其他普通客服收到独立、不含正文和图片的状态刷新即可。不能只在页面隐藏正文。 |
| 工作台提醒 | [`Notifications.tsx`](../../fronted/admin/src/components/Notifications.tsx) 目前依赖 `chat_message` 提醒、去重及控制咨询提示音。 | 将待领取／新消息的非正文提醒与有权读正文事件分开设计；隔离正文时保持共享池、接待人和主管所需的未读状态与声音可用。 |
| 存量页面 | [`Support.tsx`](../../fronted/admin/src/pages/Support.tsx) 当前页面已有消息和草稿状态，靠实时事件重新加载。 | 会话被转走或员工撤权时，长连接后续推送须重验权限，页面清除不再有权展示的旧正文与图片并提示状态变化；不能靠隐藏发送按钮代替权限校验。 |

现有消息涉及门店上下文隔离，所列权限仍须落到对应门店；不同门店的会话／消息数字 ID 可重复，不能仅凭 ID 找另一家店的会话。平台人员是否可查看聊天正文取决于明确的数据权限，不因可以看平台总账而默认可见。

## 4. 消息发送、失败恢复与已读范围

1. **已实现的基础**：[`ChatMessage`](../../services/backend/chat/models.py) 保存发送方账号、消息内容、可选 `client_message_id` 及指纹，并对同会话、发送账号和客户端编号设唯一约束；用户与后台发送代码在会话行加锁，相同编号、相同内容可回读，内容变化会冲突。老板、陪玩和后台页面均有发送结果待核对路径，前端使用原编号调用状态接口，避免误把超时当未发送。
2. **范围限制**：客户端编号在当前接口中是可选项，不能推断所有历史客户端都具备幂等；图片文件在页面重载后未必还能恢复。新客户端应保证编号、会话、发送人、订单关联和内容一起校验；重试要复用同一请求事实，重新选择或修改图片时必须有明确反馈。
3. **通知失败不等于消息未保存**：[`ChatSendView`](../../services/backend/chat/views.py) 和后台回复在数据库事务后调用实时广播；若广播或网络发生错误，需要按消息编号查持久结果，不能简单再次创建一条消息。实时推送是提醒和刷新，不是持久消息或送达的唯一依据。
4. **已读当前缺口**：[`mark_read_through`](../../services/backend/chat/read_state.py) 在未传 `through_id` 时选取全部未读；[`ChatReadSerializer`](../../services/backend/chat/serializers.py) 和后台同类序列化器允许不传范围，后台回复也允许省略 `read_through_id`。新版页面通常传具体 ID 或范围，但直接 API 或旧客户端的空范围可能把并发到达的新消息一起标已读。目标需在服务端约束实际已看范围，并核对兼容与并发行为。
5. 当前 `unread_support` 和消息的 `is_read` 是会话共享状态，不是客服个人已读。新增领取／转交时，要区分“消息是否已读”和“是否仍有待接待任务”；前任已读并不证明新领取人完成接待。转交成功应让新领取人看到实际接待状态和必要提醒，不伪造用户已收到回复。
6. 查看历史消息、页面在后台、会话正在滚动和实时新消息同时出现时，保持历史位置，只标记实际阅读的消息；刷新、切换账号或门店后不得把上一身份的草稿和待核对编号错误带入。当前共享 [`business.ts`](../../fronted/shared/src/business.ts) 的草稿与发送编号 key 已纳入门店和账号，仍需在目标领取制及重新登录场景核验。

## 5. 站内通知、广播和业务事实

- 老板 [`content.tsx`](../../fronted/boss/src/business/content.tsx) 与陪玩 [`Messaging.tsx`](../../fronted/provider/src/pages/Messaging.tsx) 分别调用 [`site_messages/views.py`](../../services/backend/site_messages/views.py) 的列表、详情及全部已读接口。详情 GET 标记该条已读；全部已读只处理当前接收业务账号；聊天未读是另一项统计。打开通知或链接不重复执行订单、付款、售后等业务。
- [`site_messages/utils.py`](../../services/backend/site_messages/utils.py) 的 `create_message` 在创建失败时捕获异常并返回空值，成功后通过 [`site_messages/notifier.py`](../../services/backend/site_messages/notifier.py) 在事务提交后发送账户级实时刷新；实时广播失败会记录警告。需要区分“业务已成功”“站内记录是否创建”“是否发出实时刷新”和“外部渠道是否实际送达”，不能互相代替。关键通知缺失时应可按业务事实核对和补发，并避免重试重复；不能依赖让资金操作回滚来证明消息已送达。
- 后台 [`MessageViewSet.push`](../../services/backend/console/views.py) 指定业务账号时可处理没有旧用户映射的账号；全员／角色路径当前从旧 `User` 表枚举，可能遗漏仅有新业务账号的目标。现有 [`test_message_account_only_live.py`](../../services/backend/console/test_message_account_only_live.py) 主要覆盖指定新账号，不能据此证明全员／角色广播完整。目标按当前本店业务账号和目标范围去重统计，并核对失败与重复提交，不跨店发送。
- 前端的通知跳转只表示导航意图；订单、售后、钱包和私有图片目标仍在读取时重新检查所属店与账号权限。历史通知中的旧路径、已失效订单或已撤销权限应给出可理解的状态，而非伪造目标已可访问。

## 6. 待执行验收清单

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| N01 | 两名客服同时领取同一条待领取会话。 | 最多一人成功；另一人读到最新接待状态，不能读取正文或回复。 |
| N02 | 客服甲领取、查看、回复；客服乙和主管同时查看。 | 甲与获授权主管可读；乙仅看列表和状态；乙的列表、接口和推送都无正文或图片。 |
| N03 | 甲转交乙，或主管重分配；甲的页面、WebSocket 和图片链接仍打开。 | 乙获得接待权限及提醒；甲的后续读取、续签和回复被拒，前端同步更新；历史和订单关系保留。 |
| N04 | 甲离线、下班、失权或离职。 | 离线不自动回收；撤权不保留内容权限；主管可人工重新分配，过程可追溯。 |
| N05 | 老板从自己订单发起；陪玩从本人双陪／转单订单发起，另尝试同店其他人及跨店订单。 | 合法订单形成正式关联与卡片，未授权关联被拒并保留草稿；订单和售后详情分别校验权限。 |
| N06 | 同一会话先后咨询多笔订单，之后订单退款／售后状态变化。 | 各卡片不串单，展示正确订单快照及最新授权状态；原有纯文字历史不被自动猜测重绑。 |
| N07 | 两店存在相同会话／消息数字 ID；以错店令牌、图片票据及 WebSocket 请求另一店。 | 一律不能读取、回复或误投；系统不回落到默认门店。 |
| N08 | 用户、后台分别上传正常图片、超限图片、伪装格式和不支持的图片。 | 所有端及服务端执行一致的允许格式与大小规则，错误提示清楚，失败不留假消息。 |
| N09 | 发送已入库后连接中断、重试或推送失败；同编号内容改变。 | 原消息可核对且只存在一条；变更内容被拒，图片文件不可恢复时提示重新核对。 |
| N10 | 在历史消息加载、回复及标记已读期间又收到新消息；空请求、旧客户端和并发请求同时操作。 | 已读只覆盖实际指定且获授权的范围，后到消息不被误清，未读数和会话状态与真实数据一致。 |
| N11 | 全员／按角色通知含仅有业务账号和有旧映射的用户；模拟发送中断与重试。 | 目标用户按本店和角色去重，准确记录成功／失败；消息不因重试重复，不把实时刷新当成送达。 |
| N12 | 双端查看站内通知、聊天消息及公开客服；订单完成、撤权或消息链接过期后跳转。 | 分类与未读各自正确，跳转重校验权限，业务状态以实际结果为准；提示音可控且不泄露正文。 |
| N13 | 客服甲已领取咨询，授权主管不领取直接回复；普通客服乙尝试同样操作。 | 主管回复成功且消息显示真实主管，领取人仍为甲；乙无法读取正文或回复；接待记录与消息顺序可追溯。 |

主管可不领取直接回复已由其他客服领取的会话，原领取人不变。真实微信、企微、短信或 KOOK 的开通、消息投递与附件可用性属于外部链路验证，不得以页面存在或模拟结果冒充通过。
