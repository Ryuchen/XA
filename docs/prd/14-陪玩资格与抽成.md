# 陪玩资格、订单抽成与分账

用户已确认：各门店可分别配置陪玩资格及抽成，已成交订单保留原抽成快照。**按陪玩档位区分的抽成仅适用于三角洲；瓦罗兰特和英雄联盟的普通服务抽成只分“陪玩”和“代肝”两类。**本文说明老板下单、陪玩接单和后台设置／派单怎样使用同一规则；具体字段由[系统字典](12-系统字典与门店初始化.md)统一维护。

> 用户确认：陪玩服务收益继续按优惠后、积分抵扣前成交额分成；对外接单额等指标及自动分发排序则采用优惠前原价，本人份额扣实际分摊退款。按订单计提的岗位提成、绩效及适用福利按实付，固定底薪按薪资方案；续单 188 元门槛仍按抵扣前成交额。

## 1. 资格与门店规则

| 信息 | 老板端 | 陪玩端 | 本店后台 |
| --- | --- | --- | --- |
| 游戏、方向、端游／手游、难度、档位 | 在套餐及选择陪玩时看到服务要求和合格人员。 | 查看本人经过配置和审核的资格、已授权服务及可接订单。 | 维护本店游戏、服务、资格与抽成；资格变化仅影响允许的新操作。 |
| 入驻与身份 | 服务人员显示 `SL-` 或 `XA-` 和本人头像。 | 正式接单前须绑定微信；新入驻者首次接单前须真实取得微信头像，取得后可更换。已绑定的存量陪玩可保留历史头像。 | 检查认证、绑定、新入驻者首次微信头像获取、押金、可见、封禁、档期和接单资格；存量来源不明不伪造成微信头像。 |
| 时间与容量 | 看到可选择的人员和实际派单结果。 | 查看接单状态、档期、容量及通行证带来的公开池可见延迟。 | 指派或转单时重新核对本人资格、时间、容量及订单当前状态。 |

现有 [`users/qualifications.py`](../../services/backend/users/qualifications.py) 将资格限定在游戏类目、服务方向、端手游、难度和档位的组合内：较高档可承接同范围内较低档服务，但不能用另一个游戏、平台、难度或服务方向的资格拼凑通过。服务技能匹配还依赖本人已配置服务或同一已配置玩法／套餐家族；业务入口需与查询筛选使用一致规则。

**接单资格、抽成档位和通行证等级是不同概念。**瓦罗兰特、英雄联盟不按陪玩档位区分抽成，不等于删除这些游戏现有的服务技能、可见名称或资格审核；抢单排序仍按已确认的通行证等级规则，与三角洲抽成档位无关。

## 2. 店内抽成配置

| 游戏范围 | 门店配置及适用边界 |
| --- | --- |
| 三角洲行动 | 按订单对应游戏、玩法、方向、端和难度，分别使用每位陪玩本人的适用资格档位匹配本店抽成；双陪可使用不同档位与比例。覆盖此前按所购服务档位取抽成的口径；其他服务方向是否使用档位仍以其明确配置为准，不应臆造比例。 |
| 瓦罗兰特（现有目录的游戏类目名为“无畏契约”） | 按本店的该游戏分别配置“陪玩”“代肝”两类普通服务抽成；**上分按代肝抽成**。同一类抽成不因陪玩档位不同而改变。已有服务名称或等级可以用于展示、定价和资格，不能自动变成档位抽成。 |
| 英雄联盟 | 按本店的该游戏分别配置“陪玩”“代肝”两类普通服务抽成；**上分按代肝抽成**。同一类抽成不因陪玩档位不同而改变，与瓦罗兰特和其他门店各自独立。 |
| 其他游戏 | 不因这次决定自动套用三角洲档位表或为其指定抽成分类；按门店该游戏经确认的适用规则配置。 |

1. 初始化门店及后续维护时，管理员按授权为本店启用的游戏和服务填写其适用抽成；瓦罗兰特和英雄联盟的两类分别配置，不预填未经确认的实际比例。尚未确定映射的其他服务方向不能悄然套用其中一类。
2. 配置项展示服务范围、币种单位、抽成方式、数值、适用时间、来源、适用条件和启用状态。服务端应校验比例及范围、拦截冲突；只对适用三角洲服务显示或允许填写档位抽成，不能给另外两个游戏保存并使用按档位区分的普通服务抽成。礼物、体验套餐等已确认的特殊规则仍按各自范围处理。
3. 涉及下单和资金的核心抽成配置是开店校验的一部分。实际要开放的服务缺少明确有效的本店抽成规则时，不允许把缺失项当零、套用其他游戏或其他门店的比例，也不能将其当成已具备营业条件。
4. 订单报价、人员选择、抢单／客服代单、报单、结算、退款和报表按同一门店、游戏、服务类别及当时生效规则核对；已成交份额保留配置来源、版本、适用范围、比例及参与份额快照。**所有订单后续转入陪玩时，按本人接入时本店生效配置新建该次份额快照**；不得回写之前已成交的其他人或其他次履约快照。客服不得临时覆盖单笔抽成。
5. 当前一些资格与抽成在代码中写死，须改为读取本店配置；不能只在后台增加可编辑字段，却让抢单、派单或结算继续读取旧常量。

**现状差距**：[`users/qualifications.py`](../../services/backend/users/qualifications.py) 的 `grade_options` 和 `commission_for` 只根据方向、端、难度和档位分支，没有用游戏限定档位抽成；[`orders/commission.py`](../../services/backend/orders/commission.py) 的 `automatic` 会优先调用这一规则。因此目前不能证明不同游戏已按新决定隔离抽成，尤其不能让三角洲护航档位表按同名字段泄漏到其他游戏。现有目录中瓦罗兰特服务的 `game` 名称为“无畏契约”，应按稳定的游戏关联识别，而不是单靠展示文字猜测或重写历史游戏名称。

## 3. 一笔订单如何计算

1. 老板先按服务人数、数量及原优惠规则得到成交金额，再按已确认规则决定是否使用积分。**陪玩收益基数为积分抵扣前成交金额**；有多个陪玩时先按适用的参与份额分配，再分别按各人的订单规则计算，不能每人都拿整单。
2. 百分比模式按本人结算基数与该单适用比例计算抽成；固定额模式按**整单固定额**核算，再按既有分配与尾差规则分到参与者，不能双陪每人再扣一次整单固定额。金额均采用系统最小单位与可追溯的整数规则。
3. 例如双陪服务积分抵扣前成交 1000 店币，A、B 各分 500 店币基数，A 抽成 20%、B 抽成 30%，各自应得 400、350 店币；原门店抽成合计 250 店币。若老板再用积分抵扣 200 店币，实际支付 800 店币，A、B 服务收益仍为 400、350 店币，积分抵扣由门店承担。推荐佣金及其他成本另按规则计算。
4. 有邀请人时，主服务订单按积分抵扣后的实付店币乘本单推荐佣金比例；加购不计推荐佣金。陪玩收益及需要的门店补资分别核算；具体示例见[订单与资金](05-跨端订单资金售后.md#21-积分抵扣示例)。
5. 分成、押金单抵、收益冻结、可提现余额和站内消息分别记录；报单审核通过、订单完成或预计收益不能直接当成已经到账和可提现。

## 4. 活动、特殊服务与手工派单

- 当前 [`orders/commission.py`](../../services/backend/orders/commission.py) 同时处理手工百分比／整单固定额、特定活动、服务自定义、特殊服务、资格档位和全店默认等分支；[`orders/pricing.py`](../../services/backend/orders/pricing.py) 中部分资格、陪玩等级及活动又有各自条件。**不能把它们简化成任何情况下统一“活动 > 等级 > 门店”**。新配置须在规则冲突时给出实际命中项，按服务类型分别验收。
- 体验套餐有其专价、资格及特殊抽成，不参与积分抵扣；礼物以单笔礼物订单总额及对应礼物规则处理，不套用普通服务报单与抽成。VIP 免费安全箱报酬有独立补贴来源，不使用积分将一般订单变成零实付。
- 当前客服代派单代码允许填写人员比例或整单固定额，而相应操作使用 `order:dispatch`；用户已确认**不允许对单笔订单临时修改抽成，统一执行本店配置**。前端不得提供绕过入口，报价、代单、派单及服务端直接请求均不得接受单笔覆盖；正常活动、服务和资格配置仍按所属店规则生效，已成交订单保留快照。
- 促销更改或规则更新不能回写已成交订单；未付款报价变化需重新确认。老板选择、客服指派和陪玩报名应使用相同资格、抽成来源及订单人数快照，不能同一单在三端显示不同的预计收益。

## 5. 转单、退款与来源追踪

1. 转单保留转出、转入人员的实际服务份额、金额和结算／退款状态；不能把整笔原分成再次分给新陪玩。双陪中不受转单影响者的份额保留。
   转出陪玩可以再次转回同一订单，各次履约与份额分别记录；**新规则下旧份额须等整单完成后才开始售后等待，整单完成前不能结算**。历史已形成的已结算份额仍按用户此前确认的转回及兼容规则保留，不回写或重复支付。接单数量榜按本人同单一次、最后一次履约结束或转出时间归属；抢单排序金额按各次接入时间和原价份额分别归属。
   所有订单从 A 转给 B 时，B 以**接入订单时**本店生效配置形成本人份额抽成快照；A 之后再转回时也对新接入份额保存当时快照，之前份额与本人历史不重算。特殊玩法的房间和已记录进度同时保留，之后实际由 B 负责的加购沿用 B 的主单快照；不能将 B 接入时的新比例回写到 A。
   固定抽成转单按成交份额占整单成交额的比例计算。双方规则相同，原陪玩向下取到 0.1 店币、原席位固定扣额的其余部分分给接替陪玩；双陪另一席位扣额不变。接替人固定扣额不得超过其成交基数，不足由门店承担。规则不同，原陪玩按旧规则向下取整，接替陪玩按新规则对应本人份额向上取整。详见 [D176–D180](20-产品决策逐项复核.md) 和 [T224–T228](07-差距待决与验收.md)。
2. 退款按实际已结算或未结算份额、原支付和原分账记录处理，关联陪玩钱包、店币／积分、补贴、押金及对应冲正。老板或陪玩推荐人已经获得的推荐佣金不因退款追回，由门店承担；若同一陪玩同时取得服务收益和推荐佣金，两类流水分别处理，服务收益不因此自动免于适用的退款冲正。不能用当前新配置重新计算历史订单或对未入账收益虚构追偿。
3. 一笔合格续单的 5 元奖励是独立钱包奖励，不是将抽成比例改成 5 元；续单若发生转单，或发奖前发生退款，不发本次续单奖励。奖励发放后的退款按已确认规则不追回。
4. 老板、陪玩和后台各展示其获准查看的信息；后台可核对计算来源、配置版本、金额、操作人和历史流水。个人钱包和完整客户资料不得因店内查看订单而无条件公开。

## 6. 差距与验收

现有 `qualification` 组合和若干费率在代码中固定；`OrderProvider` 与现有结算还假定分账基数和 `order.amount` 之间的关系。新增按店可配、积分抵扣及推荐佣金新口径时，必须同时修改后台配置读取、报价、接单、分账、退款和报表，验证资金来源与守恒；这些是待开发，不能仅修改展示。
