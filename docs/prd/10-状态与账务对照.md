# 三方状态、关键数据与账务对照

2026-11-11 前端统一展示增量：下单来源与分配路径分开，订单、支付、售后及结算分别展示；具体标签、来源字段和待对接接口见[模块与三端闭环](34-SaaS产品模块与三端前端闭环.md)。资金规则和下列专项时序保持有效。

本页将已核对的现有代码与用户确认的目标分开。字段名仅用于研发追踪，不代表新增需求已经有对应字段或接口；本页不替代真实交易和数据库验收。

## 1. 一笔服务涉及的独立状态

| 对象 | 当前代码状态或事实 | 老板、陪玩、后台如何理解 | 新需求影响 |
| --- | --- | --- | --- |
| 门店 `Store` | `PROVISIONING`、`ACTIVE`、`DISABLED`，另有数据库别名、初始化时间和店币名称。 | 老板／陪玩只进入所属域名；后台按有效身份访问。 | 网页建库需要能区分初始化进行中、失败和检查结果；失败不能冒称营业。 |
| 订单 `Order.status` | `PENDING` 待接单、`GRABBED` 已接单、`IN_SERVICE` 服务中、`COMPLETED` 已完成、`CANCELLED` 已取消。 | 三端按同一订单查看不同权限的动作与进度。 | 试音报名不应成为已接单；低星、退款、积分和提现不能用订单状态代替。 |
| 订单 `payment_status` | `UNPAID`、`PAID`、`REFUNDED`、`PARTIALLY_REFUNDED`，与订单状态分开。 | 老板看到实际付款／退款；后台核对资金；陪玩按本人可见规则查看。 | 积分抵扣需分开记录积分、实际店币、门店承担额及退款构成。 |
| 报名 `OrderApplication` | `PENDING`、`SELECTED`、`NOT_SELECTED`、`WITHDRAWN`；双陪有 `partner_confirmed`。 | 现有陪玩报名和确认，老板选人，后台按权限看安排。 | 试音每名成员须有本人本次录音及可用状态；录音不是现有报名字段。普通新单和客服安排新单还须新增自动分发候选、窗口、提交等级快照及系统分配记录，不能把候选视为老板选人或已接单。 |
| 预约 `Reservation` | `PENDING`、`CONFIRMED`、`REJECTED`、`CANCELLED`、`CONVERTED`、`EXPIRED`。 | 老板发起、陪玩确认／拒绝、后台查看；只有成单才发生订单扣款。 | 成单时若使用积分，要按届时报价与该店规则确认，不把预约快照当成付款。 |
| 履约份额 `OrderProvider` | 有 `settlement_base`、抽成方式／费率／固定额、`provider_income`、`settled_at`、`released_at`。 | 每位陪玩只操作本人份额；后台查看分账与转单。 | 积分抵扣由店承担，分成基数与实际支付可能不同；必须设计补贴和退款对应，不能靠前端改显示。 |
| 报单 `ProviderReport` | `DRAFT`、`PENDING`、`APPROVED`、`REJECTED`，关联陪玩、订单、入队／结单图、战绩图及审核。 | 陪玩提交和补充，后台审核，老板查看授权状态。 | 报单通过不等于可提现；新积分结算基数必须兼容 `amount`／`payout_amount` 约束。 |
| 售后 `AfterSale` | `OPEN`、`RESOLVED`、`REFUNDED`、`PARTIALLY_REFUNDED`，同一订单有唯一工单约束及历史。 | 老板申请／看进度；售后处理；陪玩看本人允许信息。 | 低星触发及双陪按人暂缓仍是目标；不能假定现有整单阻断已满足。 |
| 提现 `WithdrawRequest` | 当前 `PENDING`、`APPROVED`、`REJECTED`；申请冻结，当前审核通过与付款登记耦合。 | 当前仅能解释原单级流程，不能代表新客服初审＋平台财务终审。 | 必须独立表达初审、待平台处理、付款事实、驳回及待核对；历史单保留真实原结果。 |
| 通行证 `ProviderPassPurchase` | 保存购买价格、实际支付、开始／结束时间和支出流水；当前陪玩档案另保存档位及到期时间。 | 陪玩查看每笔购买及当前权益；后台按店核对购买和收入。 | 新购支付成功即生效 24 小时，期间禁止再买任何等级；历史已购未生效可自动全退、原构成返店币及积分、冲回收入并调整后续历史时段。须保留原计划和调整历史，不能只缩短档案到期时间。 |
| 钱包流水 `Transaction` | `PENDING`、`SUCCESS`、`FAILED`；类型包含充值、消费、收益、提现、押金、退款、奖励、补贴及冻结释放。 | 申请成功、待处理和实际成功支出必须区分。 | 提现冻结不是成功出账；支付成功登记只产生一次终态及对应余额变化。 |
| 收益冻结 `IncomeHold` | 保存收益到期释放时间及实际释放时间，与账户余额和订单份额相关。 | 陪玩看到已冻结和可用收益；后台可追溯。 | 低星未结算暂缓不应伪造为已经入账的钱包冻结。 |
| 积分 `MemberProfile`／`PointLedger` | 积分以百分之一积分保存，流水记录来源、变动、余额及事件标识。 | 老板和陪玩只使用本人本店积分。 | 新增门店汇率、单笔上限、抵扣及退款快照；不能与钱包店币共用余额字段。 |
| 工资方案／月结 | `SalaryPlan`、`SalaryAssignment`、`SalaryActivity`、`PayrollRun` 分别保存方案、人员、来源和月度快照。 | 平台财务和超管按店核算；店员角色不自动获得工资权限。 | 平台公共财务工资需要独立平台归属，不在各店重复建立同一成本。 |

现有工资安排和业绩的 `created_by`、月结的 `confirmed_by` 均引用本库的 `ClubAccount`；平台身份跨库办理时必须另行准确记录真实平台操作人、门店和授权，兼容既有员工关联与历史记录，不能凭相同数字 ID 冒用店内账号。见[差距 G21](07-差距待决与验收.md)。

## 2. 金额组成与一致性

对一笔**使用积分抵扣**的订单，产品必须能分别核对：

| 项目 | 意义 | 不能误认成 |
| --- | --- | --- |
| 服务原价 | 套餐价格及数量计算的原始金额。 | 最终应付或现金收入。 |
| 价格优惠 | 会员、活动和折扣券等比例优惠选其一；每单最多一券，金额券可与会员或门店活动折扣叠加。 | 积分消耗或现金退款。 |
| 积分抵扣前成交额 | 原有优惠后的金额，也是本次已确认的陪玩分成和续单 188 元门槛判断基数。 | 老板实际支付店币或现金实收。 |
| 积分抵扣 | 本人积分按本店汇率折算的店币金额，受低于 100% 的单笔上限约束。 | 跨店可流通的店币、充值本金或第二次现金支出。 |
| 实际支付店币 | 抵扣前成交额减去本次积分抵扣后，老板实际从本店钱包支付的部分。 | 真实现金实收：钱包原余额可能包括赠送余额。 |
| 门店承担额 | 本次积分抵扣对应的店币等值及其实际资金来源。 | 可以无来源凭空发给陪玩的余额；不能在经营利润中重复扣减。 |
| 陪玩／店铺／推荐人分配 | 按抵扣前成交额、订单规则、实际份额及其他真实成本核算。 | 每位陪玩各拿整笔订单金额。 |
| 退款 | 实际支付店币及使用积分按原构成计算；店币依次退本金、赠送、赔付，消费获赠积分按已退本金冲回。已发推荐佣金不追回，由门店承担。 | 按当前新汇率重算历史交易、重复退还，或把推荐佣金和陪玩服务收入当作同一份收益。 |

客服派单提成、客服绩效和店长绩效使用积分抵扣后的实际支付额，并按既有规则处理退款。例如抵扣前成交 200 元、积分抵扣 30 元、实付 170 元时，这三项业绩按 170 元核算；陪玩分成与续单金额门槛按抵扣前 200 元核算。

同一例中，老板本次新增消费积分只按实际支付 170 元等值中属于本金的部分，结合付款时老板 VIP 等级对应的门店倍率及生日规则计算，未达 VIP 则取本店普通会员基础倍率；赠送和赔付店币消费不产生积分。会员等级累计消费按实际支付的 170 元等值并经既有实销确认；退款要分别回冲。用于抵扣的积分、因此订单新获得的消费积分是两条独立账务。

例如成交 1,000 店币、积分抵 200 店币、实际支付 800 店币；单陪按 20% 抽成时，作为对照的陪玩服务分成基数为 1,000 店币、服务收益为 800 店币，积分抵扣由本店承担。实际订单若包含固定抽成、邀请人、礼物、押金、历史模式或其他优惠，应按对应已确认规则单独计算，不能照搬此例。

**实现约束差异**：当前 [`OrderProvider`](../../services/backend/orders/models.py) 的代码说明将各陪玩 `settlement_base` 总和与 `order.amount` 对应；`ProviderReport` 也对报单金额和实得有数据库约束。新增积分抵扣后，如果沿用 `order.amount` 表示实际店币支付，按抵扣前金额分成就不能只改页面或无条件修改现有守恒关系。应设计明确的门店承担来源及金额快照，并对普通／双陪／转单／退款／历史订单逐项验证；是否复用现有补贴模型由研发在不改变业务结果的前提下评估。

## 3. 支付、退款和提现的状态边界

- **订单付款**：创建或确认业务交易时，钱包支付成功和积分扣减必须与订单及快照一致；失败不留下部分成功，响应丢失先恢复原请求结果。
- **订单退款**：多次部分退款按原支付构成计算；退老板店币向下取整至整数店币，积分以积分最小单位向下取整，最后一次全额退款补齐。退款不改变原始报价和原流水，使用关联记录或冲正描述新的事实。
- **提现申请**：可用余额减少、申请金额转为冻结，提现流水保持待处理；仅门店客服初审不能变成已打款。
- **平台付款成功**：平台财务完成实际线下付款并记录凭证；本店账务消耗该冻结并将对应提现记录记成功。失败、付款不确定或写入结果不明时不能重复打款或擅自解冻。
- **工资与续单奖**：工资确认是经营成本快照；续单奖是符合条件后进入陪玩钱包的业务奖励。二者必须区分，不能把工资确认当成钱包付款，也不能重复计入经营成本。

## 4. 需与三端一起核对的兼容边界

首版不接管旧订单、旧接口或旧业务数据；以下历史兼容事项仅供追溯，不能作为本期迁移要求。

1. 兴安内部标识以当前代码的 `xinan` 为准，简称 `XA`、店币星辉；开发配置保留原独立业务库别名 `store_b`。历史 `south` 引用需核对兼容，但不迁回旧标识，不能更改历史数据库或账务归属。
2. 现金押金已缴额与单抵进度均按实际流水记录；接单资格使用本店配置的现金或单抵目标，已接订单继续履约。
3. 已存在的提现单及已打款凭证按原流程事实保存；不能把旧 `APPROVED` 猜测为已经经过新的客服初审和平台终审。
4. 积分不得再直接兑换钱包余额；其他原有商品兑换和积分抽奖保留。已有余额兑换记录和已产生的钱包余额不得删除或改值。
5. 新低星规则、订单试音、续单奖励、平台财务与积分抵扣分别需要明确上线边界，避免将历史订单批量改成新规则处理。
