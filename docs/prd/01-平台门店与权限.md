# 平台、门店与权限

状态：已确认目标与现有代码静态核对；新能力未声称已实现。本文按老板、陪玩和后台对同一门店订单及资金的使用范围定义权限。

## 1. 门店是业务边界

| 对象 | 目标规则 |
| --- | --- |
| 数据库 | 一家门店一个独立业务数据库；门店目录和平台身份可以使用独立的逻辑控制域，不要求复制业务数据。 |
| 老板和陪玩入口 | 声浪分别使用 `sl.esports.club/boss`、`sl.esports.club/player`；兴安分别使用 `xa.esports.club/boss`、`xa.esports.club/player`。老板端和陪玩端没有切换门店入口。 |
| 后台入口 | 所有后台人员使用 `admin.esports.club`；未登录时不预选门店。账号密码登录时，未绑定 OTP 使用短信验证码，已绑定 OTP 默认验证手机验证器动态口令且可切换短信；未绑定微信的员工也可先登录。已绑定微信可扫码或快捷登录，授权确认后直接进入。所有路径都须核验真实身份、门店和授权。 |
| 门店身份 | `shenglang`／`SL`／浪花；`xinan`／`XA`／星辉。用户已确认兴安内部标识采用当前代码的 `xinan`，继续使用原独立业务库，不迁回 `south`；对外英文名、域名、简称不能破坏现有账户和票据。 |
| 数据范围 | 客户、陪玩、服务、价格、订单、履约、售后、钱包、押金、积分、营销、店员、成本及工资业务归属各自门店。 |
| 名称和头像 | 老板端展示陪玩 `SL-昵称` 或 `XA-昵称`，前缀使用可读的艺术字样式；保存业务昵称时不把前缀反复写入，避免改名或重复前缀污染历史。头像按[陪玩端规则](03-陪玩端.md)执行。 |
| 用户跨店 | 同一个人可以在不同门店具有分别建立的业务身份，账户、余额、积分和订单不能默认互通或自动合并。 |

域名、令牌、接口、WebSocket、缓存、任务、文件和下载票据须校验一致的门店上下文。未知域名、停用门店、伪造 `query/header` 或其他门店令牌不能退回默认门店。后台同名同密码造成多个有效店内身份时必须明确消歧，不能默认进入某一家；更换店内身份须重新登录。

## 2. 角色和权限矩阵

| 身份 | 数据范围 | 主要动作 | 边界 |
| --- | --- | --- | --- |
| 平台超级管理员 | 获授权的全部门店及平台公共数据 | 默认聚合、按店查看、建店建库、平台和门店账号管理、薪资与经营管理 | 独立平台授权；门店内的管理员角色不自动拥有平台权限。 |
| 平台财务 | 各门店的提现、薪资和履行职责所需数据；平台公共薪资成本 | 接收客服初审通过的提现、终审、线下打款和登记，配置及核算各店薪资 | 不因提现授权自动拥有门店管理或全部订单、客户、钱包调账权限；按具体动作授权。 |
| 门店管理员／店长 | 本店及授权的平台可见内容 | 本店人员、服务、积分兑换比例、配置、经营管理 | 店内角色不能自行授予平台权限；其薪资岗位与后台权限角色分别管理。 |
| 客服 | 本店 | 客户咨询、获授权订单与派单、提现初审、已授权的老板充值及相关业务核对 | 充值赠送修改须门店管理员 OA 同意；陪玩无充值，仅按授权调账。不能登记平台财务打款，不能访问其他门店提现。 |
| 售后 | 本店 | 查看和处理获授权的售后、转单及退款业务 | 实际退款与资金动作遵守细分权限和现有规则，不因创建售后自动退款。 |
| 运营 | 本店 | 获授权商品、活动、积分、内容和接单资格运营 | 不自动取得提现、薪资、资金调整或跨店权限。 |
| 老板 | 本人、当前店 | 授权登录、选服务、下单、报名选人、评价、售后、积分抵扣和查看本人钱包 | 不能读取他人或他店账户与订单。 |
| 陪玩 | 本人、当前店及获准公开订单 | 入驻、绑定、接单、履约、报单、积分抵扣和提现 | 不能操作他人订单、工资、私有材料或其他门店资产。 |

门店不再设置财务岗位。既有财务账号、权限及历史数据不能在 PRD 编写时删除或修改；实际实施须盘点和迁移授权，保留历史审计。平台财务的权限边界、岗位薪资与平台超级管理员权限不得混同。

## 3. 平台超级管理员工作台

1. 登录后默认展示有权访问的全部门店聚合，支持按门店与时间筛选并进入单店详情。订单、提现和员工明细须保留门店标识；不同数据库可能存在相同的数字 ID，身份以“门店＋业务 ID”唯一定位。
2. 汇总人民币指标时显示日期、口径、是否完整及分店明细；浪花和星辉分别列示，不能把不同店币当成同一种余额。统计率使用对应汇总分子与分母计算，不能直接累加各店比例。
3. 门店库不可用、数据延迟或口径不一致时，标记缺失店与数据时间，不能以零补齐或冒称完整。允许重试；不以汇总页可见推导到具体记录的写权限。
4. 跨店薪资和提现只执行用户已授权的动作。任何针对单店订单、提现或配置的写操作都必须明确目标门店、操作者和对象，服务端重新校验，不使用用户可伪造的门店参数提升权限。

## 4. 新建门店与数据库

**目标**：平台超级管理员在网页登记门店名称、英文名称、唯一简称、店币名称及老板／陪玩入口，并在服务端已配置、已授权的数据库服务上创建和初始化该门店的独立业务库。

1. 创建前检查门店标识、简称、入口、数据库名称的唯一性和允许范围；不接受网页任意指定数据库主机、管理员凭据或任意 SQL。
2. 依次执行登记、建库、结构迁移、必要基础配置、账号及连接检查；显示待初始化、初始化中、失败、可使用等真实状态及错误。缺少域名、证书或外部授权时标出未完成项，不能声称入口已可用。
3. 新店可建立必要的初始规则模板，但不能复制其他门店的客户、陪玩、员工、订单、账户余额、流水、收款凭证和真实消息收件人。微信和短信接入由平台统一共享；其他支付和群消息按实际授权及门店归属配置，不得串用其他店的接收对象。
4. 初始化失败后允许核对和安全重试；不得删除、清空或接管已存在的数据库。停用门店不删除历史账目，重新启用须核验所需依赖。
5. 升级、备份和恢复应覆盖门店目录、每店业务库与各自媒体；先在隔离环境验证，记录失败门店，不把部分迁移当作全部成功。

创建门店后须进入[系统字典与初始化](12-系统字典与门店初始化.md)：由平台超级管理员完成门店管理员、预存、VIP、抽成及其他配置；下单和资金核心配置完成并核验后才可启用，其他能力可暂不启用并在开店后补充。

**现状证据**：[`stores/models.py`](../../services/backend/stores/models.py) 中门店目录已有名称、币名、数据库别名、业务编号前缀和状态；[`stores/views.py`](../../services/backend/stores/views.py) 的门店创建请求在提交首位管理员时已调用建库和初始化，但仅可使用部署预配置且未占用的数据库别名。[`stores/provisioning.py`](../../services/backend/stores/provisioning.py) 迁移及管理员校验后即标记营业，尚未包含本轮要求的完整系统字典和开业校验；平台身份、跨库汇总及目标财务流程须另行核实。网页路径存在不等于真实环境建库或整套开店流程已经验收。

## 5. 安全、审计与迁移

- 平台与门店授权分离；状态、权限和令牌变化须影响 API、实时订阅与私有文件，不以隐藏菜单代替后端校验。
- 记录谁在何时、对哪个门店和对象进行了什么操作、结果及必要的前后版本；账号密码、验证码和数据库凭据不写入业务日志。
- 平台人员对门店薪资、提现等发起操作时，保留真实平台操作者身份、目标门店、业务对象和授权依据；店内员工身份仍由所属店数据库管理。不能将其他库中碰巧相同的账号 ID 当成本店员工，也不能冒用店员记录代替平台操作人。现有外键及历史记录须有兼容迁移和可核对的审计关联。
- 新发起的门店业务异步任务必须携带且核对所属门店；缺失、无效或冲突时停止并记录，不能默默写入默认店。历史无门店标识的任务须依据可验证来源制定受控迁移方案，不把所有缺标识消息一概推断为声浪任务。周期任务按有效门店分别执行，失败范围逐店可见。
- 门店简称用于展示，与数据库别名、历史订单编号、账号唯一键分开；昵称和历史业务内容不批量改写。
- 兴安原独立业务库、声浪默认库、已登录会话、订单及资金历史须有兼容和回退方案；开发配置中兴安库别名为 `store_b`，不能未经实际核对假定其他环境相同。清点可能保留的历史 `south` 引用，不迁回旧标识，不得复制客户和资金来构造第二家店。
- 聚合不要求跨数据库事务。每笔资金写入只落入其所属店的业务库，并提供平台侧可追踪的执行记录；外部打款和记账之间的失败恢复见[资金流程](05-跨端订单资金售后.md)。
