## 2. 老板订单的金额和分账关系

以下记号均应换算为同一账务最小单位，仅为产品口径，不指定最终数据表：

- `A`：按最新比例折扣互斥及单券规则计算后的成交额；不扣本次积分。
- `D`：本次消费积分抵扣的店币等值。`C = A - D` 是本次实际从钱包支付的店币。
- `P`：陪玩按 `A`、各自份额及已成交抽成快照计算的应得；`I = C × 推荐比例` 是主服务订单的推荐佣金，按系统最小单位和已确认规则取整。加购和礼物不计推荐佣金；未发佣金按退款后的主单实付净额计算，已发佣金不追回。
- `G = C - P - I` 是排除其他成本的门店订单贡献，可以为负；它不是另一个可以自动支付的真实钱包余额。老板实际支付也不等于现金实收，因为钱包可包含赠送、赔付及推荐收益。

例：成交 200 元等值、积分抵扣 30、钱包实付 170，陪玩应得 160，推荐比例 10%，推荐基数为实付 170、佣金为 17，未计其他成本前门店贡献为 -7。若实付全部来自本金、不考虑其他资金来源，门店需补足 7 元等值；实付中的赠送或赔付由门店另行承担。另一笔成交 100、抵扣 40、实付 60、陪玩应得 80 且无推荐佣金时，门店贡献为负 20，不能因此减少陪玩应得；但还必须有可核实的资金来源来支付收益。**用户确认门店资金不足时仍可下单，陪玩收益保持待结算，门店补足资金后再结算。**不能凭空入账，也不能把待结算显示成已到账。

**代码差距**：[`orders/models.py`](../../services/backend/orders/models.py) 的 `Order.amount`、`provider_income`、`inviter_commission`、`shop_income` 是非负金额；`OrderProvider.settlement_base` 的源码约束假设各人结算基数之和对应 `order.amount`。[`orders/settlement.py`](../../services/backend/orders/settlement.py) 的 `aggregate_order_split` 和 `assert_order_conserved` 以订单金额为界限，不能直接表达“实付 60、陪玩应得 80”的资金来源。[`OrderPlatformSubsidy`](../../services/backend/orders/models.py) 服务于现有 VIP 免费安全箱；能否复用应评估真实资金来源、退款和成本，不能把新增积分补贴直接当成已有能力。

落地时需清楚区分：①老板本次钱包实际支付；②积分抵扣等值；③每位陪玩的应得与实际入账；④推荐佣金；⑤门店为优惠承担的来源；⑥已结算、待支付、冻结或退款结果。同一笔优惠若已体现在实际支付减少，经营报表不能再把它无凭证重复扣一次；但也不能忽略真实需要补足的门店支出。

## 3. 退款、积分与权益

### 3.1 普通退款与本金优先

用户已确认：有积分抵扣的订单，退款先按原支付构成计算应退店币与应退积分；部分退款店币向下取整到整数店币，积分按自身最小单位向下取整，最后一次全额退款补齐余数。再将应退店币依次退回**该单实际支付的本金、赠送和赔付**，每类累计不得超过原支付。已发的消费积分按实际退回的本金及该单原倍率冲回；抵扣积分的返还与消费积分冲回是两条不同流水。

例如原单实际店币支付中本金 50、赠送 30、赔付 20，第一次应退店币 70，则退本金 50 和赠送 20；第二次应退店币 30，退剩余赠送 10 和赔付 20。若原本金消费 50 产生了 50 积分，第一次退完本金时即按该 50 本金冲回对应已发积分；不能只按整单退款 70% 或 50% 一概计算。礼物均为本金付款，退款只退回该礼物单已支付本金。

**现有实现**：[`orders/services.py`](../../services/backend/orders/services.py) 的 `refund_to_customer` 锁单、创建 `OrderRefund`、退回钱包并调用积分回滚；普通部分退款限定为已完成且已结算订单。 [`engagement/services.py`](../../services/backend/engagement/services.py) 的 `release_order_allocations` 目前按原资金批次比例恢复，`reverse_order_points` 按整单累计退款比例回冲，均不等于新确认的本金优先和按退回本金冲回。 [`orders/refunds.py`](../../services/backend/orders/refunds.py) 的 `proportional_targets` 是现有内部整数分摊方法，也不能不经验证直接等同用户已确认的“每次分别向下取整、最终补齐”。

原订单、退款记录、三类支付构成、店币退款、积分返还、消费积分冲回、优惠券、陪玩收益和门店承担额须互相指向同一门店和订单；请求重试、补退、抵扣汇率变化、退后积分不足时都要可追踪。已发积分不足时现有账本支持负积分，不能通过把返还的抵扣积分和冲回赠分合并一条记录掩盖真实过程。

### 3.2 协商终止的保留消费

[`orders/negotiated_refunds.py`](../../services/backend/orders/negotiated_refunds.py) 允许部分结算转单进入协商退款，退款后将部分保留金额分别结给履约陪玩、推荐人和门店，再将订单置为 `CANCELLED`。 [`engagement/confirmation.py`](../../services/backend/engagement/confirmation.py) 的会员实销处理要求订单状态为 `COMPLETED`；[现有测试源码](../../services/backend/orders/tests/test_negotiated_three_role_realtime.py) `test_team_negotiation_preserves_coupon_points_and_vip` 明确检查协商终止后的订单没有消费积分流水，也没有 `ConsumptionConfirmation`。上述测试只是现状证据，不是本次执行通过结果。

此前 [`users/views.py`](../../services/backend/users/views.py) 的 `_daily_paid_amount` 按订单创建日统计；现已按用户最新决定改为实际付款日，计入服务、礼物和加购的店币实付净额，相关代码待最终联调。不要求订单状态为完成，因此部分退款但有净额的协商终止单仍可能计入签到门槛。用户已确认：**实付 200 元、原陪玩收益 160 元、协商退款 100 元由陪玩承担时，老板保留消费 100 元，陪玩保留收益 60 元。保留消费 100 元计入会员实销，按其中保留的本金发放消费积分，并计入非礼物订单成就；协商处理和退款完成，且满足适用报单审核及等待条件后确认。**不能因订单 `CANCELLED` 就将实际保留消费全部清零，也不能将退回的本金算作保留消费。

### 3.3 已发推荐佣金与服务收益要拆开

用户已确认，无论推荐人是老板还是陪玩，订单退款后**已经发出的推荐佣金不追回，由门店承担**。若同一人既是服务陪玩又是邀请人，不能以钱包归属一刀切处理：推荐佣金与实际服务收益必须有可区分的原始流水；服务收益继续按照已确认的售后／退款规则处理。

当前 [`orders/refunds.py`](../../services/backend/orders/refunds.py) 的退款试算按原成功入账与钱包余额计算可追回额； [`negotiated_refunds.py`](../../services/backend/orders/negotiated_refunds.py) 还将 `INVITER` 列为协商承担方。新目标必须覆盖退款预览、普通／部分／协商退款执行、余额不足处理、消息和审计；不能只在前端隐藏推荐人一行，而后台仍继续扣回。已发佣金不应因退款人余额不足阻止本不需追回的佣金处理，其他必须核对的服务收益或资金条件仍独立执行。

## 4. 结算时间、押金和可提现余额

当前 [`engagement/confirmation.py`](../../services/backend/engagement/confirmation.py) 的服务收益结算要求订单完成后的 72 小时售后窗口结束，并满足各陪玩报单审核和无开放售后；会员实销确认还另等最后有效报单提交后的 72 小时。 [`wallet/income.py`](../../services/backend/wallet/income.py) 在收益入账后，再按照 `hold_hours` 将可冻结部分冻结；[`wallet/club_rules.py`](../../services/backend/wallet/club_rules.py) 的现有开关在启用时返回 72 小时。

**售后截止的新目标及现状差距**：用户确认售后等待和收益冻结默认各 72 小时，门店可分别配置；普通服务超过适用售后期后，老板和后台均不得新建售后或新发起退款，期限内已建立的售后继续处理。当前 [`can_request_aftersale`](../../services/backend/orders/refunds.py) 对已经结算的订单直接放行，而同文件 `apply_admin_refund` 的已结算退款入口未看到按上述售后截止阻止新退款，现状因此可能出现售后期后才申请并追回已结算收益。这是需要改造的旧行为，不应当作新目标正常流程；已建立的售后和历史订单仍须保留真实处理记录。

**礼物收益的单独起点**：[`orders/views.py`](../../services/backend/orders/views.py) 当前支付礼物时将订单标记完成并直接增加陪玩可用钱包，未经过普通服务收益冻结；新目标改为礼物支付后，售后和收益冻结都从付款成功时重叠起算，双时限到期且无未结售后等阻断后才释放，不引入礼物报单。老板礼物消费在支付成功时立即计 VIP 成长，不能因为收益尚未释放而延迟成长。

因此，若订单完成后立即报单、审核通过，并且没有其他阻断，在现有开关适用且后台任务按时运行的情况下，陪玩收益可能是完成约 72 小时后结算，再冻结约 72 小时后可用，合计约 144 小时；迟交报单、售后或任务延迟可更久。这是当前实现分析，不是新目标或运行时效承诺。用户确认的新规则为：**普通订单的售后等待从整单完成时开始计时，收益冻结从本人最后一次有效报单提交时开始计时，两段计时重叠；驳回重提重算。**双陪中 A 协商终止而 B 继续履约，即使 A 两段已到期且本人审核通过，也须等整单完成才可结算；整单完成不重置 A 从协商确认起开始的售后等待。整单完成后双陪分别检查本人条件，不必因另一人冻结未到期而一律延后。服务中协商终止时，客服完成退款及其他适用条件后才能确认保留的实销；不能伪造普通完成时间。其他已确认的售后和资金条件仍需满足，会员实销与收益释放分别记录，不能凭一个状态推断全部完成。

现金押金新目标 400 元，单抵目标 800 元，用户确认存量也适用；旧押金流水不能改写。代码 [`wallet/income.py`](../../services/backend/wallet/income.py) 的 `hold_provider_income` 在冻结时长小于等于零时先返回，单抵押金分配在返回之后。若未来把冻结时长与单抵比例分别配置为 0 小时、非零单抵比例，直接复用当前逻辑会跳过单抵扣款。冻结时长、单抵比例和押金目标必须分别验证。用户确认**单抵比例按付款时快照**；当前代码在结算时读取当时配置，须调整并验收付款后修改比例但旧订单仍用原快照。

现金押金不足时，用户确认统一线下补款，客服核验后直接登记增加已缴押金并记录调账原因，不经过陪玩可用余额，也不得称为陪玩普通充值。 [`console/provider_registration.py`](../../services/backend/console/provider_registration.py) 当前现金押金审核建立 `TOPUP`／`DEPOSIT` 配对流水并增加 `total_recharge`，它是历史内部过账，不应因禁止陪玩充值而删除真实押金凭证；新的线下补差要确保押金与线下实收各自只记一次，并与历史过账正确区分。

## 5. 经营成本和跨月退款

[`orders/refunds.py`](../../services/backend/orders/refunds.py) 的 `PAID_STATES` 只有 `PAID` 和 `PARTIALLY_REFUNDED`。当前 [`payroll_calculation.py`](../../services/backend/console/payroll_calculation.py) 的经营 ROI 订单 cohort 从这一集合构建，并依据成功流水核对部分退款的推荐成本、陪玩收入及平台补贴。按用户新规则，订单全额退款后如果先前已发推荐佣金或续单奖励不追回，订单状态变成 `REFUNDED`，但真实支出依然存在；仅沿用该订单 cohort 会漏掉这类成本。全退订单净消费可为零，留存佣金、奖励及经确认应承担的其他支出仍须以真实事实计入所属店，并在平台汇总中只算一次。

用户确认经营净消费包括老板实际使用的赠送与赔付，但计算经营利润时须**扣除实际消费的赠送及赔付成本**。例如老板实付 100 元等值，其中赠送 20、陪玩应得 80，不考虑其他成本时经营利润为 `100 - 80 - 20 = 0`；不能把店币消费当现金实收，也不能在充值发放和实际消费时对同一赠送重复扣成本。积分抵扣若已通过实际支付额减少体现，也要避免再次重复扣减相同金额；退款后相应冲回和经营时间归属需按真实支付及退款事实核对。

现有薪资和 ROI 分别按订单创建日或完成／结算日归属订单，并读取截至查询时的累计退款；已确认薪资则直接返回历史月结快照。用户确认：跨月退款不追扣原月绩效，退款计入发生月绩效；应扣提成进入退款月工资，若该月工资已确认则提成和绩效影响均在下一期调整。经营报表原消费按付款月归属、退款按发生月冲减：11 月付款 200 元、12 月完成并退款 50 元，分别在 11 月记 200 元、12 月冲减 50 元。真实付款时间须核对成功支付流水，不能用创建或完成时间替代；相关成本和退款事实均须关联原单并避免重复计算。

| 普通服务、预约转单、后台代单分别发起消费 | 分别核对老板可见报价、可用来源、授权选择、本店订单、钱包流水与陪玩结果；不能仅因为共用服务就假设调用相同 API。预约转单可按普通订单规则使用普通券；客服代单须留老板对积分／赠送／赔付的明确确认。 |
| 礼物购物篮包含多款；本金不足但赠送／赔付充足 | 全部礼物只扣本金；本金不足则不能靠其他余额完成支付。逐款订单、单独退款、送出数量、赠分和真实收礼人对得上；请求结果未知不重复发礼。 |
| 成交 100、积分抵 40、实际支付 60、陪玩应得 80 | 订单、积分、付款、陪玩应得和门店资金来源一致；门店资金不足仍允许下单，陪玩待结算，补足后再结算，不能削减应得或凭空入账。 |
| 老板部分退款、本金先退完，且曾消耗消费积分 | 原抵扣积分返还、赠分冲回、余额分类及负积分各自可追溯；零头在最终全退时补足，不重复超退。 |
| 老板／陪玩推荐人已得佣金，订单先部分退再全退 | 原推荐佣金不追回；零净消费订单的保留佣金成本仍进入门店经营账；同一人是陪玩时服务收入按各自规则单独处理。 |
| 用户领取续单奖励后发生全退 | 奖励保留，订单全退后真实支出仍计入门店成本，不能漏算或重复计入员工工资。 |
| 协商终止订单实付 200、陪玩原收益 160、退款 100 由陪玩承担 | 老板保留消费 100、陪玩保留收益 60；保留消费计入会员实销及非礼物订单成就，消费积分只按其中保留的本金和原倍率计算。后台分配、原订单、积分及三端结果一致。 |
| 订单完成、报单及后台任务分别延后；设置冻结 0／正数 | 售后等待从订单完成计时，收益冻结从报单提交计时，两段重叠、均到期且审核通过后释放；单抵比例不因冻结设置为 0 被静默跳过，付款后改单抵比例不改原快照。 |
| 11 月订单消费 200，12 月退款 50，原月工资已确认 | 经营报表 11 月记录 200、12 月冲减 50；11 月已确认工资保留快照，12 月退款触发的工资调整在 12 月扣减，所有调整须可追溯原单和来源。 |
| 两店相同数值 ID、交易和汇率 | 订单、积分、账户、资金、佣金、钱包及任务严格归属本店；任一店暂不可用时不得写入另一店或把缺失数据展示为零。 |
