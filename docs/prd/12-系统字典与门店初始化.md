# 系统字典、门店配置与初始化

状态：用户已确认各门店独立配置预存、VIP、陪玩抽成及其他可配置业务规则，并在新建门店时统一填写；本文是产品目标，当前代码尚未实现完整初始化向导。功能使用、订单与资金逻辑仍以各专项 PRD 为准。

当前后端提供平台超级管理员只读接口 `GET /api/admin/platform/store-management/{id}/setup/readiness`，按指定门店核对有效授权、可登录的店内超级管理员、门店身份与域名、部分已确认核心配置、等待时限、可售服务和游戏抽成。该接口只返回阶段性证据，`can_open` 和 `opening_implemented` 均为 `false`：完整检查、并发保护和正式启用事务仍未实现。游戏抽成只有在运行环境明确启用 `GAME_COMMISSION_PAYMENT_ENABLED` 后才用于普通服务付款；保存草稿不代表已启用。待配置门店的首位管理员可按现有权限配置游戏、服务、玩法和订单等待时间，订单及钱包操作仍不可用。

## 1. 目标与范围

1. 平台超级管理员从统一后台创建门店，并进入“门店初始化”流程：建立独立业务库、填写该门店所需的系统字典和规则、核验并启用。已营业门店也能在授权范围内维护本店配置。
2. 系统字典是**统一的配置目录、维护入口和规则清单**：既包含名称、分类等选项，也包含金额阶梯、百分比、规则开关、关联对象及生效时间等有类型的业务规则。它们必须能被实际报价、校验、账务和报表读取，不是只保存供展示的备注。
3. 涉及下单和资金的核心配置必须完成并通过校验，门店才能启用；其他配置允许显式选择暂不启用，开店后再补充。未启用能力不能展示成可用或静默继承另一家店的规则。各项核心／非核心的具体判定须随功能、外部依赖和开店能力一同维护，不能用空值冒充已确认的零。
4. 每店独立维护自己的配置及变更历史；允许参考已确认的规则模板，但创建或初始化不得复制其他门店的客户、陪玩、员工、订单、钱包、积分、资金流水或私有文件。模板的来源、版本和最终确认值要清楚可查。
5. 金额、比例、数量、时间、状态开关和对象引用应有明确单位、合法范围与生效条件；已支付订单、提现、预存、报单与工资保留其适用配置快照，不因后续配置修改而悄然重算。

### 1.1 门店后台的快捷配置

店内入口为「系统管理 → 门店设置 → 快捷配置」，原「统一字典」名称可在功能搜索中找到。进入首页先选择要做的事，再进入该设置的业务页面、配置窗口或分类列表。首页只负责导航。保存、校验、核对与生效沿用对应业务流程。

| 本店任务 | 入口及落点 |
| --- | --- |
| 商品与下单 | 游戏类目和服务分类打开服务商品内各自的维护窗口。下单游戏资料打开按游戏或服务维护必填项的窗口。 |
| 派单与接单 | 接单名额、抢单窗口、待接单时限和峰谷限流直接打开各自的配置窗口。通行证和 KOOK 群派单进入各自的业务页面。 |
| 会员与陪玩 | 老板分级、陪玩等级、会员与积分设置进入各自页面。仅有字典权限的人员仍可通过「积分规则」查看获授权的抵扣及使用设置。 |
| 资金与结算 | 押金与结款、支付费率进入对应规则页。提现规则、订单默认抽成及游戏抽成草稿打开对应配置窗口。 |
| 薪资与经营 | 薪资岗位、投流渠道、运营成本类别分别进入指定类型的维护列表，保留原有的编码、启停、删除引用校验和结果核对。 |

首页按本店筹备状态、目录可见范围及具体操作权限展示入口。筹备门店的「开店设置清单」和营业门店的「核心配置核对」单独呈现服务端证据。访问入口不计作保存、确认或开店。目录读取失败时可重试，已知本店有权访问的独立入口仍可使用。

预约确认和付款时限、房间确认时限目前可读取核对记录，清单标明「编辑入口待对接」。后续接入专用编辑器时应复用原规则的权限与校验。

### 2.1 统一目录中的配置项如何表达

系统字典是一个统一的产品入口和配置目录，不要求把有复杂校验的套餐、活动、等级等业务对象压成无类型的键值字符串。每类配置均应有唯一且稳定的配置编码、归属门店、名称／说明、数据类型、单位、可选值或允许范围、状态、当前生效值、来源模板及版本、修改人和生效时间；金额、比例、时间和对象引用由服务端按对应业务校验。每项还应显示被哪些三端页面、报价／发放／核算流程使用，以及缺失或停用后的影响。

| --- | --- | --- |
| `store.identity` 门店 | 店名、英文标识、简称、币名、入口域名、业务库和启停状态；标识及域名需唯一，入口域名须属于正确门店。 | 老板和陪玩按域名进入；后台授权识别店；业务库连接信息属于受控设置，不能在普通配置列表明文泄露。 |

| `engagement.rewards` 运营权益 | 商品、积分价格、库存、兑换资格；抽奖消耗、奖池、概率、库存、保底；签到、补签、成就、排行榜及播报参数。 | 同店允许多项抽奖同时开放；积分商品不得直接兑换钱包余额，但真实抽奖可以发放余额奖。保底次数变更清零原计数，仅改目标奖品则保留原计数。 |
| `provider.deposit` 陪玩押金 | 现金押金目标、单抵押金目标、收益抵扣比例、收益冻结及释放规则；核对门店适用值及人民币／店币单位。 | 当前已确认现金 400 元、单抵目标 800 元；单抵比例按付款时订单快照。线下补差由客服核验后直接登记增加已缴押金并记原因，不经过陪玩可用余额。旧缴纳和历史流水保留。 |
| `provider.withdrawal` 提现 | 单笔最低申请金额、申请前钱包可用余额门槛、扣除比例、资格及配置版本；两项门槛分别配置，申请金额至少达到最低额且可用余额严格大于门槛。 | 先冻结，本店客服初审、平台财务终审和线下付款，按申请快照结算并可核对；不借用固定默认值覆盖门店配置。 |
| `provider.dispatch` 接单与通行证 | 每店统一并发上限、公开订单总等待时限、秒级抢单收集窗口、通行证档位／价格／权益及可见延迟、预约确认和付款时限、时长范围和峰谷限制。 | 老板未指定及客服安排的新单自动收集、排序并分配；可见时间按订单入池时本人通行证及门店配置确定，排序等级按本人提交时通行证快照；双陪可先邀请但队友须到本人可见时间后确认。接单额本人开始履约后按各次接入时间与份额归属。首轮入池即计时，之后新增合资格者可在剩余时间参与但不延长。新购通行证即生效 24 小时，期间不得购买任何等级；历史已购未生效者仍可按确认规则全退并调整后续历史时段。陪玩本人确认／拒绝预约，时间不足确认时限不能提交；转单后继续防重叠。 |
| `staff.payroll` 薪资与经营 | 岗位、薪资底薪与绩效、日夜班时段、派单及预存提成、考官、投流渠道、其他成本类别。 | 使用人民币，薪资岗位与权限角色分离；平台财务工资只计平台公共成本一次。 |
| `support.content` 客服与内容 | 咨询参与权限、客服名片及其对应本店员工、公告、轮播、推送和声音偏好；已确定的领取／隐私规则不能被开关绕过。 | 老板下单所选名片绑定的员工为订单负责人；聊天仍仅领取人与获授权主管可看正文，薪资按实际工作归属。 |
| `integration.channels` 外部渠道 | 平台统一微信与短信连接状态，本店 KOOK、企微或支付等连接状态及受控凭据。 | 所有门店共享平台微信及短信接入，但门店业务身份与数据独立。单陪及双陪按本店设置群发原价和订单要求，混合群须等所有等级达到本单可见时间；订单先结束则不发送待抢消息。凭据不得以明文混入普通字典，真实授权和发信或支付结果分别校验。 |

以上编码是 PRD 的配置分组示意，不要求开发沿用同名数据表或 API。每组新增、停用、恢复或调整时须有业务权限、有效性校验、影响预览和操作记录；配置值与订单、资金、券和资格的历史快照各自保存。配置删除不能物理抹去已经被历史订单、券或账务引用的事实。

### 2.2 开店时的完成状态

- **必须明确并验证**：门店身份和入口、独立业务库、门店管理员、当前要开放的服务报价与抽成、老板钱包记账、资金与权限、陪玩接单资格、押金／提现等资金链的必要规则。无法算出价格、扣款、分成或正确归属时，不允许把门店标成可营业。
- **按功能开关校验**：积分抵扣启用时必须填写汇率和低于 100% 的上限；积分赠分启用时须填写普通会员及已启用 VIP 的倍率；预存、VIP、活动、优惠券、通行证或外部通知等能力启用时，须填写该能力实际必需的档位、范围或接入并通过校验。未启用的非核心能力应明确显示为未启用，后续配置完成后才能开放。
- **不能混淆零和未配置**：允许为零的业务数值需由授权人员明确保存；缺项、验证失败、凭据失效、停用和合法的零分别显示。预览使用测试计算，不直接创建订单、钱包流水或发放权益。
- 初始化完成后仍可修改有权限的配置；页面提示变更影响、立即生效或下一次发放的规则，并保留旧交易和历史凭据。已有店可以分组补齐，不得为了填字典重建数据库、覆盖客户资料或清空资产。

## 3. 新建门店流程

| 步骤 | 操作者与系统行为 | 结果与异常 |
| --- | --- | --- |
| 1. 创建草稿 | 平台超级管理员填写门店名称、英文标识、简称、币名与入口。 | 检查名称、标识、简称、域名及受控库名的唯一性与合法性；未登录店员不能指定或切换目标店。 |
| 2. 建库初始化 | 在预先授权的数据库服务中创建该店独立业务库，执行必要结构迁移及初始化。 | 过程、状态和失败原因可见；失败支持安全核对和重试，不能清空或接管已有库。 |
| 3. 配置门店管理员 | 为新店设置实际业务管理身份与权限，确认与平台授权分离。 | 店内管理员不自动成为平台超级管理员或平台财务；真实账号与凭据按安全流程设置。 |
| 4. 填写系统字典 | 按配置清单逐组填写；可按已确认模板带入、预览并修改，或选择暂不启用非核心能力。 | 每组显示必填项、单位、冲突、版本和缺项；规则不完整时不得冒充已生效。 |
| 5. 分项验证 | 对商品价格、预存、VIP、抽成、积分、押金、提现及已启用能力进行一致性检查；核对域名、登录和必须的外部接入。 | 可给出计算预览但不能创建真实订单或记账；失败项可返回修改，凭据和联通性不能以模拟结果充当真实结果。 |
| 6. 确认并启用 | 汇总门店、业务库、核心配置、暂未启用功能及其负责人；超级管理员核对后启用。 | 核心配置缺失或建库失败时不可营业；门店初始化、失败、待配置、待验证及营业状态须可区分。 |
| 7. 开店后维护 | 本店获授权人员修改本店配置；平台角色按各自授权管理。 | 记录操作人、门店、前后值和生效时间；冲突须重读，已发生业务的历史快照不变。 |

## 4. 预存档位组合与记账

### 4.1 用户已确认的组合规则

1. 每家门店分别配置若干老板预存档位：每档包含**人民币金额、赠送金额及启停状态**。本次预存按单笔实收人民币从高到低依次匹配，同一档可重复使用；剩余不足最低档的金额不获得档位赠送。
2. 例如配置“充 3000 元赠 100 元等值店币、充 6000 元赠 250 元等值店币”：充值 7000 元匹配一次 6000 元档，余 1000 元不赠送；充值 9000 元匹配一次 6000 元档和一次 3000 元档，合计赠送 350 元等值店币；充值 12000 元匹配两次 6000 元档，合计赠送 500 元等值店币。
3. 老板实收本金分别为 7000、9000、12000 元，均全额换算为本店店币并合入一个本金余额；每笔充值组合及优惠作为历史记录保留，但**不将本金拆成供消费选择的批次**。不同笔充值不合并凑档，已发生充值的组合快照不因后续配置修改而改变。
4. 老板的钱包需区分汇总本金、赠送、赔付。服务订单支付时，赠送和赔付默认都不使用；老板可选择是否使用并分别输入本次使用数量，其余应付由本金支付。礼物订单只能使用本金，不使用赠送、赔付及积分抵扣。余额、金额和本店单位由服务端校验，不能多扣、透支或越店支付。支付记录须保留本次各类资金构成。
5. **只有本金被消费才产生消费积分**，赠送、赔付及积分抵扣部分不产生消费积分。倍率取付款时老板所属 VIP 等级对应的本店配置并保存快照；尚未达到任何 VIP 等级时，使用本店配置的普通会员基础倍率。另按既有适用的生日等规则计算，后续升级和配置修改不重算本单。原来按预存档位分别决定消费倍率的方案被此新决定替代；预存本身不等同会员有效消费。
6. 系统计算标准赠送后，客服如需修改，必须发起 OA 审批并由本店门店管理员同意才可按修改额生效。确认收款后本金先到账，审批期间赠送尚未到账；通过后发放审批金额，驳回则按系统原赠送额发放。老板和客服能区分本金已到账、赠送待审批、审批通过或驳回以及赠送实际到账，审批和入账均留痕且防重复。
7. 只有老板存在充值及预存福利；陪玩没有充值业务，只有按授权执行、记录原因和流水的钱包调账。旧陪玩充值事实及原流水保留，不能将调账伪装成实收充值或重新计算预存赠送。
8. 积分抵扣订单退款先按原支付构成计算应退店币和应退积分；应退店币在不超过本单对应来源尚未退回金额的前提下，依次退回**本金、赠送、赔付**。部分退款店币的比例零头向下取整到整数店币，积分按自身最小单位向下取整，最后一次全额退款补齐剩余；同一来源不重复或超额返还。已发的消费积分按本次实际退回本金对应的原规则冲回，不能简单按整单退款比例冲回。
9. 老板获得的推荐佣金归入本金余额，与充值本金合并；后续实际消费时同样按付款时 VIP／普通会员倍率计算积分。积分抽奖的店币奖品和客服赠送的店币均归入赠送余额，消费不产生积分。佣金、实收充值、中奖及客服赠送仍按真实来源记录，不能因为合并展示就将推荐佣金记成现金充值或将赠送记成订单收入。

### 4.1.1 充值赠送修改与 OA 流转

| 阶段 | 客服及本店管理员操作 | 老板钱包和后台事实 |
| --- | --- | --- |
| 系统试算 | 客服选择本店老板、录入实际收款及凭证；系统按当前档位组合展示本金和标准赠送。 | 本金、标准赠送、匹配档位及配置版本分别可核对；未确认收款不产生实际到账。 |
| 按标准办理 | 客服认可系统标准赠送并按权限确认收款。 | 按充值结果分别登记本金和标准赠送；无需为未修改的金额虚构一次赠送变更审批。 |
| 申请修改赠送 | 客服提出修改后金额并发起 OA；系统记录标准值、申请值、充值单、门店、申请人和时间。 | 核实收款后本金先到账一次；赠送处于待审批，不能提前显示为可用余额或声称已到账。 |
| 本店管理员通过 | 本店具有相应权限的门店管理员核对充值及赠送变更并同意。 | 按批准金额登记一次赠送到账，保留申请、审批和账务关联；老板与客服能看到真实结果。 |
| 本店管理员驳回 | 本店管理员驳回，记录审批结果。 | 发放该充值当时系统计算并保存的标准赠送，而不是用之后的新档位重算；标明审批驳回及标准赠送实际到账状态。 |
| 结果待核对 | 遇到并发审批、网络超时、赠送入账失败或结果未知时，按原充值和原审批核查并安全恢复。 | 不重复收本金或赠送，不把审批通过当成赠送已经记账；审批结果与入账状态分开显示。 |

例如充值 7000 元，系统匹配标准赠送 250 元等值店币，客服申请调整为 300 元等值：本金先入账；同意后发放 300，驳回后发放 250。赠送金额及店币换算以当时记录为准；示例不是所有门店的默认档位。

### 4.2 当前实现与新增差距

- [`engagement/catalog.py`](../../services/backend/engagement/catalog.py) 有历史海报转录的预存及 VIP 模板，不代表两店数据库当前已经配置这些数值。
- [`console/views.py`](../../services/backend/console/views.py) 的充值接口当前接受老板或陪玩、人工填写 `gift_amount`；[`engagement/services.py`](../../services/backend/engagement/services.py) 的 `record_recharge` 按单笔实充匹配一个最高档取得积分倍率，本金与赠送记录在同一资金批次。新目标的组合赠送、VIP 消费倍率、钱包分类和赠送 OA 流程不能仅靠这些现有字段实现。
- [`wallet/models.py`](../../services/backend/wallet/models.py) 的钱包账本目前只有一个 `balance`；[`engagement/services.py`](../../services/backend/engagement/services.py) 的 `wallet_funding_parts` 已按资金批次推算本金、赠送、赔付，[`account.tsx`](../../fronted/boss/src/business/account.tsx) 已显示这三项，但当前支付仍按 FIFO 消费批次，而不是由老板分别指定。历史混合充值批次按先实充后赠送的规则推算，未覆盖余额按预存展示，不能把计算结果直接当成对所有历史资金的充分证明。
- 迁移先依据真实流水核算可辨认的余额，**无法准确归类的部分全部按本金处理**，记录依据和这一归类事实；不能更改迁移前后总余额或改写原历史流水，历史已发积分不因分类自动追溯重算。核对冻结、冲正和其他特殊余额时须避免重复计算。
- 必须在服务端限制仅老板充值，新增可审计的充值异常赠送审批和状态，校验归属及门店管理员权限；不要只隐藏陪玩充值按钮或在客户端判断审批结果。当前针对常见“OA 审批／充值审批”名称的源码检索未发现可直接确认的通用流程，实施时继续核对并决定复用还是新增。

## 5. 现状及验收边界

[`console/dictionaries.py`](../../services/backend/console/dictionaries.py) 当前提供统一目录，实际可直接维护的通用字典类型主要为薪资岗位、投流渠道、成本类别；游戏、等级与各类规则仍分别指向原有业务编辑器。[`stores/views.py`](../../services/backend/stores/views.py) 在创建请求包含首位管理员时已调用建库和初始化，但数据库别名必须预先配置且尚未分配；[`stores/provisioning.py`](../../services/backend/stores/provisioning.py) 迁移及管理员校验后即标记 `ACTIVE`，尚无本轮完整配置向导和核心开店校验。门店 `entity_prefix` 当前用于业务编号，空值可能从 slug 推导为与 `SL`／`XA` 不同的值；展示简称需明确配置，不能假设编号前缀即已满足展示。新系统字典须在保留专业规则校验、资金权限和历史关联的前提下，形成统一配置体验与明确的权威数据来源。

验收至少覆盖：创建两店并输入不同档位、核心缺项阻止营业、非核心停用后补录、7000／9000／12000 元组合、本人分别选择赠送和赔付、VIP 积分倍率、OA 通过及驳回、禁止陪玩充值、重复收款凭证、历史配置变更、退款、跨店权限和初始化失败安全恢复。以上均是**待执行**场景。
