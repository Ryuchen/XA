# 押金、提现与平台财务：源码和跨端复核

本文补充[陪玩端](03-陪玩端.md)、[后台职能](04-后台职能与操作.md)、[跨端资金](05-跨端订单资金售后.md)与[差距清单](07-差距待决与验收.md)。**现状**依据当前静态代码；**目标**依据用户已确认要求；示例仅为说明账务。本文未执行真实转账、外部收款或端到端测试。

首版以全新部署为准，现金与单抵押金目标均由门店配置；本文关于旧流水、旧订单及迁移的内容仅供追溯，不构成首版兼容或迁移要求。退押金等待期以已确认的七天规则为准。

## 1. 涉及人员与资金

| 参与者 | 用户动作及看到的事实 | 权限与责任 |
| --- | --- | --- |
| 陪玩 | 提交所属店入驻和押金材料；查看押金目标、已缴和欠额；查看订单收益及冻结；自行核对收款账户和提现试算，提交后追踪审核和付款。 | 只操作本人本店账户。微信绑定是新接单资格，不应剥夺本人已合法取得资金的查看与提现能力。 |
| 门店客服 | 现金押金线下收款或补差后核验，登记本人、本店、原因、金额及有效凭证；初审本店提现，查询后续状态。 | 按授权处理本店事项；初审通过并非付款；不能越过平台财务直接登记提现打款。 |
| 平台财务 | 对已通过本店初审的提现终审；核对目标店、原申请、收款快照及金额，实际线下打款后登记凭证；对异常结果查证。 | 只能访问被授权范围，记录真实平台身份和目标门店；其提现权限不自动包含其他资金或用户管理权限。 |
| 老板 | 正常查看自身订单履约、售后及钱包，不参与陪玩押金或提现审核。 | 订单完成、报单审核和售后影响相关陪玩收益，但不暴露陪玩收款账户。 |

一店一业务库；账户数字 ID、提现单号、订单号或同一手机号在不同门店即使相同，也不能用于跨店认领、记账或合并钱包。平台汇总必须标明各店查询状态，不可将不可用库当作零。

## 2. 押金事实与配置

### 2.1 现金模式

1. 现金押金目标由各门店配置，已缴金额以本店真实资料与流水为准；规则变更不自动制造收款。例如本店设置 400 元且已缴 200 元时，待补差为 200 元，该数值仅作示例。
2. 现金不足时，陪玩**线下补款**，客服核验后直接登记押金补差、真实收款与原因；不先通过陪玩可用钱包余额，也不称为陪玩普通充值。应可关联收款人、时间和可核验的凭证，避免同一事实重复登记。
3. 已缴押金低于本店适用目标的现金模式陪玩原则上不能取得新正式订单；仅退款造成的押金缺口可按用户确认的“每次放行一单并用收益补齐”例外处理，其他接单资格仍须满足。老板选人、试音报名、队友确认、抢单、后台指派及转单均在写入时复核，现有订单按既有事实继续履约。
4. 当前[入驻审核](../../services/backend/console/provider_registration.py)核对线下现金已到账，录入金额不得低于当时应缴；同事务建立陪玩侧 `TOPUP/+金额`、`DEPOSIT/-金额` 配对流水，平台侧 `DEPOSIT_INCOME/+金额`，并增加钱包 `total_recharge`。这是一条真实现金押金的历史内部过账，不代表开放陪玩普通充值；旧凭证、流水、余额和押金池不能为消除“充值”文案而删除。旧入驻代码允许核实额大于当时目标，历史超额应按真实已缴保留，不能随新目标静默截断。
5. 现有陪玩端[客服页](../../fronted/provider/src/pages/Messaging.tsx)仍引导线下交钱后由客服给陪玩“充值”，[资料页](../../fronted/provider/src/pages/Account.tsx)及 [`DepositView.post`](../../services/backend/wallet/views.py)仍支持从陪玩钱包缴纳现金押金；这些入口需要按已确认的现金线下直接登记流程调整。禁止普通充值与保留押金专用资金闭环须同时落实服务端、页面、通知和统计。

### 2.2 单抵模式

1. 单抵押金目标由各门店配置。单抵陪玩按适用条件接单，随后将订单净收益按付款时保存的单抵比例逐步抵扣，直至本店目标；剩余收益按该单适用的收益释放条件进入可用余额。
2. 每笔抵扣不能超过当时剩余应缴押金；已经缴足后新收益不再继续扣押金。新目标适用存量陪玩，但不重写原来已缴金额、历史订单、原配置或历史流水。
3. [当前收益代码](../../services/backend/wallet/income.py)先读结算时当前单抵比例，计算 `min(本次收入 × 比例, 剩余应缴)`，记陪玩 `DEPOSIT` 和平台 `DEPOSIT_INCOME`；收益余额另建冻结。用户已确认改为**订单付款时比例快照**，不能用后续更改的比例覆盖已付订单。
   同一笔可释放收益同时需要补退款产生的押金缺口及普通单抵时，先补退款缺口，再对剩余收益按本单付款时比例抵扣，且不超过剩余目标。例如收益 100 店币、退款缺口 20、比例 60%，普通目标仍足够大：先补 20，再从剩余 80 抵 48，共抵 68，余 32 正常结算。
4. 当前 `hold_provider_income()` 在 `hold_hours <= 0` 时先返回，导致后续单抵逻辑也未执行；旧[专项测试](../../services/backend/wallet/test_deposit_rules.py)甚至把这一现状作为断言。目标下冻结时长为零也不能跳过本应发生的单抵，须更新实现和预期，而非据历史测试断言认定目标已满足。
5. 普通订单售后等待从**整单完成时**开始，服务中协商终止从老板与受影响陪玩确认终止时开始；收益冻结从该陪玩**最后一次有效报单提交时**开始，驳回后重新提交则重新计时。两段时间重叠；双陪中 A 协商终止但 B 尚未完成整单时，A 即使本人两段到期且审核通过也不能结算。整单完成后不重置 A 的等待，A 满足其他条件可释放，不必等 B 的本人冻结到期。

### 2.3 同一有效目标与退押金

- [规则代码](../../services/backend/wallet/club_rules.py)的历史开关目前使用现金 200 元、单抵 400 元；[接单资格](../../services/backend/users/models.py)及列表等位置还存在不同的判断路径和现金 200 元硬编码。须核对注册、详情、老板列表、报名／选人、抢单、客服派单及最终写入均使用同店生效目标。
- [陪玩押金概览](../../services/backend/wallet/views.py)使用 `effective_deposit_required`，而[退押金结果](../../services/backend/console/deposit_refund.py)的 `_overview()` 使用档案原始 `deposit_required`。两者可能在规则覆盖时不一致，不能只修改一个目标值或一个列表。
- 现有[退押金实现](../../services/backend/console/deposit_refund.py)允许有权限的后台人员按不超过已缴押金的金额部分或全部退回**本店陪玩钱包**，需填写原因；受平台钱包余额及押金池余额约束，四项变动在同一事务：陪玩可用余额增加、已缴押金减少、陪玩侧正向 `DEPOSIT`、平台侧负向 `DEPOSIT_INCOME`。
- 用户最新确认：陪玩存在**进行中订单、未结束售后或尚未结清的订单收益**任一情况时，暂不允许部分或全部退还押金；即使收益已入钱包但仍冻结，也须等该笔冻结释放。系统应明确显示阻断类型和可核查的相关业务，核对时区分每位陪玩本人实际参与的双陪或转单份额，并在提交时重新校验。现有[历史交付说明](../history/product/DP1-ORD12-delivery-2026-08-07.md)及实现仅对进行中订单软提示，已被此新决定覆盖，须修改服务端及页面。退还后现金模式接单资格仍按最新已缴与应缴核验；不能把提现两级审核擅自套用到退押金。
- 退款中陪玩承担分摊额依次由本人本单待结算收益、本人可用钱包、本人已缴押金承担；合计不足时暂停退款，待补足后重核，不能部分扣款并显示退款成功。退款实际扣减押金形成待补缺口；已有订单正常履约，且仅就该原因在其他资格合格并有本店普通并发名额时额外放行一张新服务单，已满上限须等有名额。本人已有或新单中最先满足结算条件的收益优先补缺口，礼物收益到期释放时也优先补且不占服务名额。额外放行的单未结算、缺口仍在时不能再放行下一张；该单结算后仍不足才放行下一张。全部补齐后恢复常规资格，剩余收益正常结算，押金扣减与补回须分别有原订单、退款和资金流水。
- 账务核对使用同店真实成功流水及历史迁移依据：传统配对口径下，`陪玩押金 DEPOSIT 净额 = -平台押金 DEPOSIT_INCOME 净额 = -当前已缴押金`。历史缺失、人工调整或新补差记账方案须有能解释差异的凭据；不能强行改旧流水凑平，也不能把普通经营留存当押金池。

## 3. 提现：目标流程与三方状态

### 3.1 提现条件和申请快照

1. 本店分别配置**单笔最低提现额**与**可用余额门槛**；申请额须达到最低额，申请前可用余额必须**严格大于**余额门槛，且不超过本店本人的可用余额。例如门槛为 50 元，余额恰为 50 元时不能申请；余额超过 50 元仍须另满足单笔最低额。
2. 服务端试算应展示申请店币、所属店币名称、适用扣除比例、扣除店币、实际人民币和收款账户；**计算后实际人民币打款为 0 时不允许申请**。确认时校验本店最新规则及收款账户版本并保存原申请快照。微信、支付宝、银行卡每种可保存一个账户，申请后改绑或解绑不改原申请快照。
3. 已有 [提现模型](../../services/backend/wallet/models.py)记录金额、费率、扣额、应付、账户和时间。历史字段名称 `tax_rate`、`tax_amount` 不能单凭名称推断为法定税款；其现有计算按内部最小单位十进制四舍五入。店币、人民币及积分的换算单位不能混用。
4. 每笔申请先将**全额申请额**从可用转入该申请专属冻结，生成待处理流水，但不记作成功提现支出。金额受冻结，不可同时用于其他提现或钱包消费。每家门店须独立运行自己的实际配置，不借用另一门店规则。

### 3.2 审核、打款与恢复

| 阶段 | 陪玩端 | 本店客服 | 平台财务及资金 |
| --- | --- | --- | --- |
| 待本店初审 | 显示申请额、预估实付、申请时间及冻结中。 | 按本店权限查看并核对，记录本人、时间、意见；可通过或驳回。 | 未初审通过不能当作可付款任务；审核前无成功提现支出。 |
| 待平台处理 | 显示初审已完成、等待平台处理。 | 查看本店处理进度，不代财务打款。 | 独立授权的财务查看目标店和原始账户快照，核对后终审，冻结持续。 |
| 明确未付款、驳回 | 显示驳回阶段与原因、退回可用余额。 | 本店初审驳回，或查看平台终审结果。 | 财务终审驳回前应明确尚未付款；解除**本申请**冻结并退回可用，不产生成功提现支出。 |
| 线下付款已核实并登记成功 | 显示真实已登记打款、实际金额及关联成功提现流水。 | 本店按权限查看结果。 | 必须保留实际付款时间、登记时间、渠道明细及凭证、真实平台操作者；成功记账时消耗原冻结，不能再重复扣可用余额。 |
| 付款或记账结果不明 | 显示处理中／待核对，不宣称已到账或已退回。 | 可查询本店状态，不重新创建打款结果。 | 先核对付款渠道和原申请；已付款只补记原申请，未付款且已核实后才可走允许的驳回或恢复；不得重复支付或盲目解冻。 |

实际线下付款不在本店数据库事务中。产品需要保留足够的处理中及人工核对记录，让另一位获授权人员在接手时能识别“付款结果不明”；用户端、客服端和平台端均以实际记录回读，不能把一条失败通知或超时响应冒充资金事实。客服初审前陪玩可本人取消；初审后由工作人员确认尚未付款后才能取消，付款结果不明时先核对。

### 3.3 金额守恒示例

以本店现行 1 元＝10 店币、店铺配置扣除比例 2% 为说明，陪玩原有可用 200 元等值、申请 100 元等值：

| 时点 | 可用金额 | 本申请冻结 | 结果及可核对事实 |
| --- | ---: | ---: | --- |
| 申请前 | 200 元等值 | 0 | 尚无申请及提现支出。 |
| 提交后／初审通过 | 100 元等值 | 100 元等值 | 全额冻结；扣除额 2 元等值、预估人民币实付 98 元；未记成功。 |
| 未付款时驳回 | 200 元等值 | 0 | 全额 100 解冻；无成功提现及扣除收入。 |
| 已线下付款并成功记账 | 100 元等值 | 0 | 仅一次提现支出 100 元等值；实际外部打款 98 元人民币、业务扣除 2 元等值，三者合计守恒。 |

以上是固定示例：`申请额 = 业务扣除 + 实际支付等值`，并以申请时适用费率、精度和收款账户快照为准；不能因为申请时已经把可用余额转到冻结，就在成功时再从可用余额扣一次。实际线下转账结果需独立证据，不能仅凭系统账面守恒宣称到账。

| WE06 | 当前通过需非空凭证号，随后清除钱包冻结、将提现流水设成功、将业务扣额入平台钱包、状态设 `APPROVED`。打款是人工线下行为，接口本身不调用渠道打款。 | 初审通过不能触发这些终态；真实付款核实并登记后才消耗本申请冻结，且保留真实外部付款证据，不以按钮或系统状态替代银行结果。 |

## 6. 继续确认和实施前核对

1. **提现取消**：已确认初审前本人可取消，初审后工作人员确认未打款才可取消；任何结果不明的真实付款不得盲目解冻。现有系统无本人撤销入口，须补齐并发、权限及申请级解冻。
2. **凭证与历史**：两店历史押金余额、收款证据、未完成提现及旧审核记录须按真实数据盘点；是否已有足够的付款时点及银行凭证不能从模型推断。旧 `APPROVED` 不能仅因状态名推定新的两级审核全过程已发生。
3. **未完事项的准确识别**：退押金阻断条件已确认；须核对进行中订单、未结束售后和未结清收益在单陪、双陪、转单及历史记录中的真实关联，不能漏拦或误将他人的未完事项计入本人。与退押金并发的新服务、售后、结算操作须保证最终满足同一套条件。

微信／支付宝／银行卡的真实线下转账、短信及对外通知仅可在安全测试环境验证；本次静态复核未触发任何外部付款、生产资金或真实消息。
