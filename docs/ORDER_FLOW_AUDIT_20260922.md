# 老板端、陪玩端与管理端订单流程验收

日期：2026-09-22。范围：微信原生老板端、陪玩端、管理后台、Django 订单/钱包/报单及消息模块。以下描述对应本地工作区代码，未发布到生产，也未向真实 KOOK 频道或企微联系人发送消息。

## 各环节的职责与状态

| 环节 | 入口与规则 | 状态 / 资金结果 |
| --- | --- | --- |
| 下单 | 老板选玩法、内部价格档位及数量，后端计算会员、活动和优惠券价格；确认价变化时重新确认；请求标识避免重复扣款 | 钱包扣款一次，记录冻结价格与分账；进入已支付待接单 |
| 指定陪玩 / 派单 | 老板指定、后台指派、后台代下单；资格、档期、档位、押金、可接状态及剩余名额均需通过 | 指派成功进入已接单；代下单无法接单时在扣款前拒绝 |
| 抢单 | 按通行证可见延迟、服务档位和名额筛选；只接已支付、未过期、无人接手的普通单陪订单 | 行锁仲裁，只有一人能拿到同一订单；各派单入口共享陪玩名额锁 |
| 拒单 | 单陪已接单、未开工时可拒单；双陪需客服处理 | 释放旧份额及名额，回到待接单并重设超时；新陪玩接手后只结算有效份额 |
| 打单 / 开工 | 主陪玩提交有效入队截图；客服可按权限手动推进已支付且已指派订单，凭证必须在报单前补齐 | 进入服务中；不向陪玩发放收入 |
| 结单 | 陪玩端提交有效结单截图；客服确认履约后可手动推进，新单仍须报单补齐凭证 | 完成履约并形成报单草稿，保留参与人与转单份额；不立即到账 |
| 报单 | 每名有结算份额的参与者补齐入队、结单、战绩凭证后提交；驳回可修改后再提交 | 本人凭证由本人维护；取消、退款、零份额退出后停止编辑和提交 |
| 审核结算 | 所有应报单人员均审核通过才结算；双陪及中途转单保留各自份额 | 陪玩、推荐人、平台按冻结金额入账；重复审核不重复付款 |
| 取消 / 退款 | 老板只取消待接单；客服按权限处理退款；完成但未审核结算的新订单仍可售后退款 | 返还钱包、恢复可退优惠券；已结算收入不允许再直接全额退款 |
| 消息 | 老板、参与陪玩和具备订单权限的后台人员接收更新；KOOK/企微群负责待接单通知 | 公共陪玩广播仅包含订单 ID、状态，详情重新通过权限接口获取 |

“完成履约”和“结算到账”是两个节点。新订单采用 `REPORT_APPROVAL`；历史 `COMPLETION` 订单按其保存的结算模式处理。充值仍采用客服收款凭证审核入账，当前没有接入微信支付自动收款。

忙碌状态的陪玩在名额未满时可以主动抢单；老板指定和客服指派保留“可接单 / AVAILABLE”要求。押金应缴为零时不要求额外付款。价格继续采用 **1 元 = 10 兴安币**，数据库账务整数由统一金额模块转换。

## 本轮修复

1. 统一认证、停用、押金、档期、档位准入，覆盖老板指定、抢单、后台指派、快捷派单和转单；修复忙碌但有名额时抢单按钮与后端不一致。
2. 修复拒单后旧陪玩分账明细继续占用的问题；再次接手时保留冻结价格、重建有效份额，并兼容旧版本待接单残留明细，防止错付、重复分账或报单被旧参与人卡住。
3. 旧派单、退款、订单查询及实时广播接口补齐后台权限；已超时但任务尚未执行的订单也无法被指派；礼物和双陪不进入普通抢单池。
4. 报单上传、删除及提交统一先锁订单再锁报单，与退款和审核使用相同顺序；服务端返回 `can_edit` / `can_submit` / 阻止原因，陪玩端按真实状态展示操作。
5. 快捷派单携带确认价，价格变化时阻断扣款、刷新报价，由客服再次确认；陪玩列表忽略旧筛选请求的迟到响应并阻止连续点击执行操作。
6. 实时通道异常只记录通知失败，避免已提交订单被前端误认为扣款失败；公共广播不再包含老板手机号等完整订单信息。
7. 开工、结单、取消、拒单、退款日志补齐业务操作账户；发单消息数量使用实际购买单位，不再一律显示“局”。

## 验证方式

- Django 全量 SQLite 回归：检查所有应用的业务逻辑；不具备行锁的测试在 MySQL 单独覆盖。
- 独立本地 MySQL 8 测试库：执行真实迁移与全量业务回归，包括六种派单名额竞争、重复消息投递、微信绑定并发，以及新增重复审核/审核与退款竞争。仅限 SQLite 的本地价目导入测试在 SQLite 执行，未放开其远程数据库保护。
- 原生页面控制器通过真实 Django HTTP 执行登录、报价、下单、取消退款、再下单、抢单、开工、结单、上传战绩、提交报单、审核入账及评价。
- 原生前端逻辑与资金请求测试；微信 WXML/WXSS 编译器；管理端和陪玩端 TypeScript 检查与生产构建。

具体通过数量及日志见本文件末尾验收记录。消息 API 在测试中使用模拟响应；真实 KOOK 投递和微信真机客服唤起需配置正式平台账号后验收。H5 构建保留依赖包体积提醒，当前没有做额外拆包优化。

## KOOK 与企业微信配置

完整表单字段、环境变量、运行依赖和获取位置见 [上线对接凭证清单](INTEGRATION_CREDENTIALS.md)。正式环境模板见 [release.env.example](../deploy/release.env.example)。

KOOK 必填：`KOOK_ENABLED=true`、`KOOK_BOT_TOKEN`、`KOOK_DISPATCH_CHANNEL_ID`。自动新单与拒单回池由两个 `KOOK_DISPATCH_*_ORDERS` 开关控制；角色提醒、后台链接和请求超时可选。Web 与 Worker 配置须一致，Redis/Worker/Beat 须正常。机器人须加入服务器并能访问和发消息到目标文字频道。[KOOK 官方鉴权](https://developer.kookapp.cn/doc/reference)、[频道消息接口](https://developer.kookapp.cn/doc/http/message)。

当前 KOOK 集成是发送待接单通知；陪玩在陪玩端接单。KOOK 内点击抢单、指令回调和身份绑定没有实现，不需要为当前单向通知配置 OAuth 或事件回调密钥。

微信客服必填：管理后台“客服名片”的企业 ID `wecom_corp_id`、官方客服链接 `wecom_service_url`，并启用名片。微信/企微平台需建立客服账号、配置接待人员和小程序绑定。二维码、微信号、头像和提示语可作备用。小程序调用 `wx.openCustomerServiceChat` 打开企业微信侧接待；当前模式无需在 XA 保存客服 Secret、回调 Token 或 EncodingAESKey。

若要让 XA 后台直接收发企微客服消息，还需开发回调验签解密、消息同步、坐席与身份关联。这不是填写名片配置即可实现的功能。企微群机器人派单是另一项独立能力，其 Webhook 不得与客服链接混用。
