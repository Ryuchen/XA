**交付类型**：界面与体验定义（Design Specification）  
**适用对象**：老板端、陪玩工作台、管理后台（后台管理端）三端  
**事实来源**：`fronted/{boss,provider,admin,shared}`、`services/backend/*`，以及 `fronted/PRODUCT.md`、`DESIGN.md`、`VISUAL-UPDATE.md`、`ACCEPTANCE.md`、`AUTHENTICATION.md`、`verification-matrix.md`、各端 `MIGRATION.md` / `VISUAL-MAPPING.md` / `PROTOTYPE-TODO.md` / `REALTIME.md`。

## 0. 文档定位与边界

### 0.1 这份方案回答什么

在**不改动任何业务功能、页面结构、接口能力与权限规则**的前提下，把现有三端界面统一到一套可交付的现代苹果风视觉与体验定义：全局视觉规范、三端页面设计、状态与反馈、现有业务映射。

### 0.2 这份方案不回答什么

- 不提供实现教程、实施步骤、代码组织方式或代码片段。
- 不引入项目现有约定之外的技术栈、组件库或设计工具（沿用现有 React + Tailwind CSS 4 + shadcn 生成的组件体系、MiSans 自托管字体、Lucide 图标）。
- 主体四部分以现有代码为准：不新增业务能力、页面、接口、字段或状态。所有界面对象、动作、金额口径、状态取值与可见性，均以服务端返回与现有前端实现为准。
- **例外（由用户后续指令驱动）**：本次交付过程中追加了「后台 SaaS 化」「License 三档授权与功能拦截」「高斯液态玻璃」三条产品／视觉指令，「目标简单、设计简单、少标语提示与次要标签、看不懂就改布局、兼顾 UX 与 DX、不破坏业务串联」的后台组织约束（1.11、2.6），以及「管理后台的陪玩／老板重点 profile 画像 + 系统内自主统计汇总」（2.8、4.13；画像明确归属后台，不进入老板端／陪玩端）。液态玻璃（1.10）、简洁性约束（1.11、2.6）与后台画像／统计（2.8）是纯视觉、体验与信息组织定义，不新增页面、接口或业务能力；画像与统计明确只在后台现有路由内重排字段层级，自定义报表、导出、跨店聚合等标为「平台能力待定义」。后台 SaaS 化（2.4）与 License（2.5）属于**产品级设计增补**——现有代码没有 License、订阅、配额、计费模型或端点，方案中明确标注为「需服务端新增的判定结果」与「平台能力待定义」，只定义界面与体验，不宣称已具备、不摆放可点击的假功能。这两节突破了前述边界，其范围、红线与待确认项见 2.4 / 2.5 / 4.11。

- **交付形态增补**：用户最新要求「以指导开发为根本目的」，故新增**第五部分 · 开发交付规格**（5.0–5.10），把前四部分的定义转成设计令牌契约、组件规格、后台画像页逐区块规格、状态与错误契约、性能预算、反模式清单与可勾选 QA 断言；并结合用户指定的四个技能，按 5.0 的适用边界吸收反通用、可读性、性能与诚实内容规则，不引入新字体、组件库、动画库或方向重选。第五部分是规格与验收清单，**不含实现教程、步骤或代码片段**。
- 不把原型示例账号、示例余额、示例订单、示例头像、演示用场景切换器当作真实业务；不把「待开放」控件表述为已具备能力；不把页面可读、构建通过或静态状态映射表述为业务链路验收通过。

### 0.3 一致性基线（不可被视觉方案覆盖）

| 基线 | 内容 |
|---|---|
| 门店即租户边界 | 三端入口按门店隔离；域名决定门店，不可由查询参数或请求头覆盖；未知／停用／待初始化门店不得回落默认门店；切店整页重载并清理会话、草稿、未确认请求与实时订阅 |
| 角色与权限 | 老板、陪玩、后台 STAFF 各有独立身份；后台按权限点（模块:动作）授权；店内超级管理员不自动获得平台门店管理授权；界面动作以服务端 `allowed_actions` 与权限点为准 |
| 数据与金额 | 门店币（浪花／星辉）用整数账务单位换算展示；薪资、投流、经营成本、支付费率、人民币打款单独显示人民币；实销与充值本金、暂估与已确认、审核通过与实际到账不可互相替代 |
| 资金与幂等 | 稳定请求编号、`expected_version` / `expected_details` / `expected_status` 等版本校验、结果未知后的核对恢复、重复请求不重复扣款或建单 |
| 状态来源 | 所有状态、计数、资格、报价、允许动作、分页游标来自真实接口；实时事件只触发局部重读，不直接作为账务结果 |
| 简洁性与串联 | 布局、分组、默认值承担解释职责；遮罩测试不通过就改布局而非补文案；任何调整不改变路由、参数语义、字段、动作、权限、状态回读与跨页返回位置（1.11、2.6.5） |

# 第一部分 · 全局视觉规范

## 1.1 设计基线与苹果风转译原则

### 1.1.1 必须继承的现有基线

| 维度 | 现有基线 |
|---|---|
| 品牌色 | Blue Planet 六色：`#020617`、`#0F172A`、`#1E3A8A`、`#2563EB`、`#38BDF8`、`#7DD3FC`；奶白中性背景；状态色仅表达业务含义 |
| 主题令牌 | `shared/src/theme.css` 为唯一颜色与字体来源，OKLCH 语义令牌定义浅色与 `.dark` 两套；深浅色偏好持久化 |
| 字体 | 自托管 MiSans 400/500/600/700，按 Unicode 分片按需加载，回退 `-apple-system`、`PingFang SC`；不依赖外部字体服务 |
| 组件 | 三端由 shadcn 组件体系生成，20 类基础 UI 组件共用同一套语义；`Dialog` / `AlertDialog` 统一「标题与关闭区 — 可滚动正文 — 固定底部操作区」 |
| 节奏 | 4pt 整数倍间距；按钮／输入／筛选／下拉 6–8px、标签 4px、内容卡 8–12px；选中态不放大圆角；避免胶囊与大圆角 |
| 框架 | 老板端、陪玩端：64px 顶栏、1120px 内容框架（桌面内宽 1072px，左右 24px）、768px 起五项主导航、手机五项悬浮 Dock；后台：1366×1024 最小视口、72px 收缩／232px 展开左栏（设计基线；见 1.8 现状差异裁决）、64px 顶栏 |
| 密度 | 后台表格与筛选密集区以 40px 控件为基准、表头 44px（组件源码口径，见 1.8）、单元格 12px 内边距、卡片 14/20 正文；三端按区块与主次选尺寸，已取消全局 medium 强制覆盖 |

### 1.1.2 苹果风三原则在本系统的转译

| HIG 原则 | 本系统的落地定义 | 明确不做 |
|---|---|---|
| **清晰 Clarity** | 内容优先：页面标题说明当前任务；金额、状态、下一步操作靠近相关对象；次要规则收进可点击／可聚焦的说明；正文 14/1.65、辅助 12/1.5，字重区分信息层级；数字等宽对齐 | 不用装饰性渐变、说明性长文案、重复标题挤占业务信息 |
| **顺从 Deference** | 界面退到内容之后：中性奶白／深墨占绝大多数面积；海洋蓝只用于可操作、选中、深色摘要与重点表面；状态色只在有业务含义时出现 | 不把品牌蓝铺满页面、不用彩色卡片区分普通分区、不用颜色表达「好看」 |
| **深度 Depth** | 用层级而非线条表达结构：L0 页面底 → L1 内容卡 → L2 卡内分组信息区 → L3 浮层；顶栏与手机 Dock 用低不透明度背景加模糊形成轻量玻璃层；弹层用阴影与背景层次而非重边框 | 不引入拟物质感、不做多层重叠阴影、不把玻璃效果用于普通内容卡 |

### 1.1.3 一致性承诺

- 同一业务字段在三端同名、同口径、同状态文案；桌面与手机只改变布局密度与导航形态，不改变字段集合与动作语义。
- 视觉升级不重排既有信息架构、不合并或拆分页面、不改变按钮的主次用途。
- 深浅色切换后，所有文字、状态、金额、图表、私有媒体占位与焦点环保持同一可读性标准。

## 1.2 色彩系统

### 1.2.1 中性层（面积主体）

| 语义令牌 | 浅色角色 | 深色角色 | 用途 |
|---|---|---|---|
| `background` / `foreground` | 纯白／近黑 | 深墨／近白 | 页面底与一级文字 |
| `card` / `card-foreground` | 纯白 | 略高于背景的深灰 | 内容卡、表格、弹层容器 |
| `muted` / `muted-foreground` | 浅灰／中灰 | 深灰／浅灰 | 次级文字、分组底、筛选底、占位 |
| `border` / `input` | 极浅灰 | 白色低透明度 | 1px 分隔线、控件描边 |
| `ring` | 中灰 | 中灰 | 焦点环（2px，offset 2–3px） |
| `popover` | 纯白 | 深灰 | 下拉、气泡、Tooltip |

**规则**：内容卡的边框只用 1px 语义描边；阴影按现有源码的显式矩阵使用，不统一给所有卡片加阴影。深色模式下不硬编码灰度，一律走语义令牌；`.text-primary` 在深色弹层／下拉内改用提亮的侧栏主色，保证蓝字可读。

### 1.2.2 品牌层（克制使用）

| 用途 | 允许范围 |
|---|---|
| 深色摘要表面 | 订单状态 Hero、钱包余额卡、陪玩钱包深海军蓝卡、后台登录品牌区、会员／积分英雄卡、内容预览深色标题区 |
| 主操作与选中 | 单一 ``default`` 主按钮、选中态页签／筛选项、当前导航项（浅底 10% 主色）、进度条、图表主序列 |
| 重点渐变 | 首页 Hero 圈线、登录品牌区径向渐变、极少数活动主卡；渐变不得铺满内容区，不得作为普通卡片背景 |
| 图表 | `chart-1` 至 `chart-5` 蓝色序列，仅用于真实数据图表 |

**规则**：一屏之内主操作尽量唯一；次级动作用 `outline` / `secondary` / `ghost`；风险最终确认才用 `destructive`；不得把支付行为一律标红。

### 1.2.3 语义状态色

| 语义 | 业务含义 | 呈现 |
|---|---|---|
| `success` | 已通过、已完成、已入账、资格已满足、仅可约／成功 | 状态标签、进度完成节点、结算完成提示 |
| `warning` | 待核对、结果未知、暂估、缺成本、即将到期 | 警示条与状态标签，必须同时给出可执行的下一步 |
| `destructive` | 已驳回、已取消、已过期、冲突、不可逆操作的最终确认 | 状态标签＋`destructive` 确认按钮；错误文案靠近相关操作 |
| `info`／中性 | 处理中、待审核、待确认、只读、待开放 | 中性或低饱和蓝，避免与警示混淆 |

**关键约束**：状态色只服务业务含义；不用红绿表达资金增减方向（涨跌色属证券语境，本系统是资金流水）。流水的收入／支出用**方向图标 + 正负号 + 等宽金额 + 文案**表达，颜色只用于标注「已入账／冻结中／已冲正／已退回」等账务状态。

### 1.2.4 派单状态色板（易读性核心）

同一状态在三端使用同一文案与同一视觉强度；视觉强度分三级：**强**（深色摘要／大号状态）、**中**（彩色状态标签）、**弱**（中性标签或纯文字）。

| 业务对象 | 状态取值 | 界面文案 | 建议强度 |
|---|---|---|---|
| 订单 `Order.Status` | `PENDING` / `GRABBED` / `IN_SERVICE` / `COMPLETED` / `CANCELLED` | 待接单／已接单／服务中／已完成／已取消 | 订单详情用强；列表与卡片用中；已取消用弱中性 |
| 支付 `PaymentStatus` | `UNPAID` / `PAID` / `REFUNDED` / `PARTIALLY_REFUNDED` | 未支付／已支付／已退款／部分退款 | 付款未知／待确认用警示强；已退款用中性 |
| 派单路径 `DispatchRoute` | `PUBLIC` / `STAFF` | 公开接单／客服派单 | 弱，作为订单元信息 |
| 报单 `ProviderReport.Status` | `DRAFT` / `PENDING` / `APPROVED` / `REJECTED` | 待提交／待审核／已通过／已驳回 | 陪玩报单页用中；「已通过」不得等同「已结算」 |
| 预约 `Reservation.Status` | `PENDING` / `CONFIRMED` / `REJECTED` / `CANCELLED` / `CONVERTED` / `EXPIRED` | 待确认／已确认／已拒绝／已取消／已转订单／已过期 | 详情用强；列表用中；终态用弱 |
| 预约席位 `ReservationSeat.Status` | `VACANT` / `PENDING` / `CONFIRMED` | 待选人／待确认／已确认 | 弱，作为选人进度 |
| 提现 `WithdrawRequest.Status` | `PENDING` / `STORE_APPROVED` / `PLATFORM_APPROVED` / `PAYMENT_UNKNOWN` / `PAID` / `APPROVED` / `REJECTED` / `CANCELLED` | 待审核／门店初审通过／平台终审通过待打款／打款结果待核实／已打款／已通过／已驳回／已取消 | 资金相关一律中以上，未知态用警示 |
| 权益交付 `RewardClaim.Status` | `PENDING` / `FULFILLING` / `COMPLETED` / `CANCELLED` | 待处理／交付中／已完成／已取消 | 中；完成后资料只读 |
| 陪玩接单 `EscortProfile.Status` | `AVAILABLE` / `BUSY` / `OFFLINE` | 可接单／忙碌／休息 | 工作台开关用中；忙碌不得显示为关闭，也不自动写为休息 |
| 门店 `Store.Status` | `PROVISIONING` / `CONFIGURING` / `ACTIVE` / `DISABLED` | 待初始化／待配置／营业中／已停用 | 非营业中一律警示或中性禁用，不得呈现为可营业 |
| 试音／注册审核 | `PENDING` / `APPROVED` / `REJECTED` | 待审核／已通过／需补充资料 | 中；「需补充资料」须给重新提交入口 |
| KOOK 派单记录 | `PENDING` / `SENDING` / `SENT` / `FAILED` / `UNKNOWN` / `SKIPPED` | 待发送／发送中／已发送／发送失败／结果待核对／已跳过 | 弱，仅后台记录表；`UNKNOWN` 用警示 |

**状态不得以颜色单独承载**：每个状态标签必须同时具备文字；时间线节点必须同时具备时间戳；进度必须同时具备阶段名。深浅色下状态标签的文字与底色对比度均满足 4.5:1，大号状态文字满足 3:1。

### 1.2.5 深浅色适配

- 所有表面、文字、描边、状态、图表、阴影、玻璃层走语义令牌；不写死浅色或深色专用值。
- 深色模式下：主色提亮用于文字与图标；深色摘要表面保持足够对比，避免白字压在浅色渐变上；私有图片加载失败占位保持可见。
- 主题偏好持久化，并尊重系统偏好；切换时不做整页闪烁，只替换语义层。
- 玻璃层：顶栏为 90% 背景 + 20px 模糊；手机 Dock 为 75% 背景 + 模糊 + 1px 描边 + 轻阴影；深浅色各自重算透明度。
- 图表在深色下使用同一 `chart-*` 序列，但需保证数据标签与网格线对比度。

## 1.3 排版层级

### 1.3.1 字体

MiSans 自托管四字重为主字体，回退链含 `-apple-system` / `PingFang SC`；禁用合成字重；数字统一 `tabular-nums`；正文全局 16px / 1.65，业务组件内明确使用 14px 与 12px 的辅助文字。

### 1.3.2 层级表

| 层级 | 字号 / 行高 / 字重 / 字距 | 用途 |
|---|---|---|
| 页面大标题 | 26px / 1.3 / 600 / -0.03em | 三端页头标题（现有原型上限语义） |
| 登录品牌标题 | 42px / 1.2 / 600 / -0.04em | 仅后台登录品牌区 |
| 区块标题 | 18px / 1.4 / 600 | 卡片分组、预约详情标题、弹窗标题（Alert 18/500，Dialog 16/500 按现有约定） |
| 卡片／条目标题 | 16px / 1.5 / 600 | 订单服务名、陪玩昵称 24px 例外、通知标题 14px |
| 正文 | 14px / 1.65 / 400（页面底 16px / 1.65） | 说明、表格、消息正文、表单值 |
| 辅助 | 12px / 1.5 / 400 | 时间、编号、次要说明、状态标签、时间线 |
| 金额 · 一级 | 34–36px / 600 | 订单详情金额、钱包余额 |
| 金额 · 二级 | 32px / 600 | 赠礼回执、积分英雄数值 |
| 金额 · 三级 | 24px / 600 | 结算摘要、下单确认金额、报价合计 |
| 金额 · 列表 | 16–18px / 600 | 钱包流水变动额、订单卡片实付 |
| 单位 | 12px / 400，与金额共基线 | 浪花／星辉／元／单／% |

### 1.3.3 对齐与字重语义

- **字重**：400 正文与表单值；500 按钮、选中项、导航当前项；600 标题与金额；700 仅极少量强调，不用于金额。
- **对齐**：身份、状态、标题默认左对齐；金额、数量、费率、变动后余额右对齐；订单／预约／流水编号用等宽风格并保留完整 `title`，不裁切；状态标签内部居中。
- **例外**：身份中心卡、优惠数值、签到日历、空态、礼物回执、转盘结果保留居中；钱包余额 Hero、订单状态 Hero、手机底部金额条保留左锚点。
- **长文本**：公告／规范／通知正文完整换行，长标题不裁切；表格日期与订单编号不按金额规则右对齐。
- **金额不折行**：单位小一号共基线；正负号与方向图标紧邻；缺失真实金额显示占位，不用 0 或示例值冒充。

## 1.5 圆角、卡片与材质

### 1.5.1 圆角矩阵

| 对象 | 圆角 |
|---|---|
| 按钮、输入框、Select、Tab、下拉项 | 6–8px（Tab trigger 6px） |
| 状态标签 Badge | 4px |
| 内容卡、分组卡、Dock | 8–12px |
| Dialog / AlertDialog / Sheet / Popover | 12px |
| 头像、状态点、开关、原型圈线 | 圆形（语义保留） |

项目已明确「避免胶囊和大圆角」，因此本方案在苹果风方向上**不放大圆角**，改以留白、分组、排版与材质表达现代感；选中态保持小圆角，不通过放大圆角表示选中。

### 1.5.2 卡片层级

| 层 | 表现 | 使用 |
|---|---|---|
| L0 页面底 | 无边框无阴影 | 页面背景 |
| L1 内容卡 | 8–12px、1px 语义描边、按源码决定的 `shadow-sm` | 订单卡、工作台概况、报单卡、后台表头与表格面板 |
| L2 卡内信息区 | 8px、浅底或分隔线，卡内 8px 信息格 | DetailGrid、凭证状态格、FAQ 答案、回复灰块 |
| L3 浮层 | 12px、`shadow-lg`、玻璃或实底、固定底部操作区 | Dialog / AlertDialog / Sheet / Popover / 手机 Dock |

**阴影矩阵（沿用源码，不统一化）**：工作台概况／订单卡／近期预约／预约列表／钱包余额卡／后台页头与表格面板使用 `shadow-sm`；订单卡 hover 使用 `shadow-md`；个人中心、资料、技能、评价、消息、FAQ、会话、预约详情保持无阴影。

### 1.5.3 分组卡片（苹果风主要表达）

- 设置类、明细类、表单类内容采用「分组卡 + 卡内分隔行」：组内行高 44–56px、行内左右 12–16px、分隔线 1px 且内缩对齐文字起点；组与组之间 24px。
- 分组标题用 12px 辅助色置于组上方 8px；必要说明收进可点击／可聚焦的说明组件，不常驻重复文案。
- 卡片高度随内容自适应，金额、状态、错误文案一律不裁切；表格只在表格容器内横滚并可由键盘聚焦。

## 1.6 细腻动效

| 场景 | 时长 / 曲线 | 定义 |
|---|---|---|
| 悬停、按下、聚焦、选中 | 160ms ease-out | 背景、描边、轻阴影变化；整行 Ghost 入口保留 hover / active / focus-visible 三种反馈 |
| 状态切换、内容更新 | 200–300ms ease-out | 局部替换，不整页重绘；已有快照刷新只显示「正在更新」条 |
| 弹层出现／关闭 | 300ms ease-out | 背景淡入 + 轻微位移；不遮挡固定底部操作区 |
| 骨架 | 仅首载；低频微光 | 按页面真实几何分支，不用通用三块代替 |
| 实时合并 | 350ms 事件合并 | 只重读相关区域；读取期间最多保留一次后续核对 |
| 转盘与揭晓 | 由真实抽奖结果驱动 | 可跳过、可「减少动态」；不因动画重复发起写请求 |

**原则**：动效只表达层级与反馈，不改变数据、不预判结果。结果未知不播放成功动效；`prefers-reduced-motion` 或系统减少动态时直接呈现结果；页面隐藏时结束展示。刷新与自动更新不清空整页、不丢失筛选、滚动、输入焦点、草稿与已打开表单。

**声音反馈**：接单、后台派单、消息提示音各自可开关并试听一次；正常通知保持静音、去重与门店会话隔离；应用内主音量默认 100%，不控制系统扬声器音量；提示音不重复打扰。

## 1.7 图标、触控与无障碍

- **图标**：沿用现有 Lucide 图标体系，按语义使用 16 / 18 / 20 / 24 / 28 / 36px；方向、状态、金额图标与文案成对出现。
- **触控**：源明确的 44px 主操作、48px 搜索壳、44px 页头主操作与认证区域保留；手机通用按钮不低于 40px；固定分类 Tab 均分单行；后台保留平板触控空间。
- **键盘**：`:focus-visible` 2px 焦点环 + 2–3px 偏移；跳转链接 `skip-link`；弹层焦点循环、Esc 关闭并返回触发控件；抽屉／侧栏关闭后焦点归位。
- **读屏**：短标签提供完整 `aria-label`；加载区 `aria-busy`；选中项 `aria-pressed`；状态轮询 `role="status"`；空图、无头像、加载失败的图片均有可访问占位与名称。
- **对比度**：普通文字 4.5:1、大号文字与图形 3:1（WCAG AA）；深色模式下蓝色文字、警告文字、状态标签单独校验。
- **不依赖悬停**：所有 Tooltip 有可聚焦或可点击替代；不可逆后果与失败处理步骤不得藏进悬停提示；文本放大 200% 不裁切金额与状态。

## 1.8 与既有设计方向的关系

项目已确认的视觉方向是「澄海：任务优先」（Operate 模式：优先角色任务、金额、状态与可执行的下一步），且历史协作约定「沿用现有界面、优先打通功能，不开展视觉重设计」。本方案由本次明确要求「现代苹果风 UI 前端设计方案」驱动，定位为**该方向内的视觉语言细化与体验统一定义**：

- 不重新选型、不重做品牌、不改变 Blue Planet 六色与奶白中性、不改变信息架构与页面结构。
- 苹果风表达从现有已具备的资产中提炼并统一：玻璃顶栏、手机浮岛 Dock、Blue Planet 深色渐变摘要卡、8px 小圆角体系、MiSans 排版层级、克制的中性面积与 4pt 留白。
- 本文件是界面与体验定义，不宣称已在生产代码落地，也不等同于批准直接改造生产界面；任何视觉落地仍须遵循项目关于「功能优先、逐项验收」的阶段约定。

三端现有实现存在少量口径分叉。下表给出本方案采用的**唯一设计基线**；这些是界面定义，不构成对现有生产代码的改动要求。

| 差异项 | 现状 | 统一设计基线 |

| 根圆角 | 共享主题 14px，陪玩端与后台 8px | 根 8px；控件 6–8px、Badge 4px、卡片 8–12px、Dialog 12px；**手机浮岛 Dock 16px 为唯一较大圆角例外**（容器而非胶囊控件） |
| 手机浮岛 Dock | 三端均有玻璃模糊，但实现路径与数值不同：老板端 CSS 20px → 32px + `saturate(150%)` + 半透明白边/内高光 + 渐变蓝选中图标与弹性动效、16px 圆角；陪玩端由 JSX 的 `backdrop-blur-xl`（约 24px）+ 12px 圆角实现，无饱和与内高光 | 统一为玻璃浮岛：16px 圆角、背景模糊与饱和增强、1px 半透明描边、内高光、选中图标渐变与轻微弹性反馈；五项均分、底部安全区、隐藏滚动条但保留滚动 |

| 表头高度 | 文档 48px，组件源码 44px | 设计基线 44px；单元格 12px 内边距，表格区域内横滚且可聚焦 |

## 1.10 高斯液态玻璃材质系统

> 本节由用户新增指令驱动：**模糊效果参考苹果的高斯液态玻璃，卡片与背景也用这种方式做渐变**。属于纯视觉定义，不引入新的技术栈、组件库或动画运行时；沿用现有 CSS 语义令牌与 Blue Planet 色系。

### 1.10.1 材质三要素

| 要素 | 定义 |
|---|---|
| 高斯模糊与折射 | 背景内容经高斯模糊后作为玻璃下层，透过玻璃可见模糊的环境色与形体；边缘 1px 半透明描边 + `inset` 内高光形成「厚度」，底部外阴影形成悬浮深度 |
| 环境色渗透 | 玻璃层不是纯灰，而是从下层的低饱和 Blue Planet 渐变中取色，配 `saturate(150–180%)` 轻微增强；深浅色各取对应语义色，不硬编码 |
| 层级与动态 | 越靠近用户操作层，模糊越强、透明度越低、高光越明显；动效只表达出现／消失与按压弹性，玻璃本身不持续流动、不随滚动实时重绘 |

### 1.10.2 分层定义（覆盖 1.5.3 与 1.9 的玻璃行）

| 层 | 应用对象 | 模糊 | 承载面透明度 | 描边 / 高光 / 阴影 | 动态 |
|---|---|---|---|---|---|
| **L0 背景液态渐变** | 页面底、登录品牌区、首页 Hero、深色摘要底 | 极缓或静态（不做实时模糊） | 低饱和 Blue Planet 多色径向渐变，大面积柔化 | 无描边、无阴影 | 极缓位移或完全静止；减少动态时静止 |
| **L1 卡片玻璃** | 内容卡、分组卡、表格面板、金额与状态摘要卡 | 20–24px | 背景色 70–88% | 1px 半透明描边 + 顶部内高光 + `shadow-sm` | 静态 |
| **L2 浮层 / 导航玻璃** | 顶栏、手机浮岛 Dock、Dialog / Sheet / Popover / 下拉 | 28–32px + `saturate(150–180%)` | 60–80% | 1px 半透明白边 + 内高光 + 底部外阴影 | 出现／消失 300ms，按压轻微弹性反馈 |
| **L3 重点深色表面** | 订单状态 Hero、钱包余额卡、积分英雄卡、内容预览深色标题区 | 可选内层柔化 | 深蓝渐变 + 低饱和光晕 | 细边高光，不用强模糊 | 静态 |

### 1.10.3 渐变规则

- 渐变只使用 Blue Planet 六色的**低饱和派生**，多色径向叠加，形成「液体」般的柔和过渡；不使用高饱和彩虹、不使用霓虹、不铺满内容区。
- 渐变用于**背景与重点表面**，不作为普通文字、表格数据、状态标签的底。
- 卡片玻璃的渐变是**透过下层的环境色**，不是给每张卡单独刷一层彩色；同屏玻璃层颜色应收敛，避免视觉噪声。
- 深色模式下渐变亮度降低、面积收敛，白色内高光改为低透明度白边，避免发灰发白。

### 1.10.4 可读性护栏（优先级高于材质效果）

1. **文字、金额、状态、错误、表格数据永不直接放在强模糊或强渐变层上**：其下必须有实色或高不透明度承载面（内容卡内的 8px 信息区），对比度仍按 4.5:1 / 3:1 校验。
2. 玻璃层不承载长正文、富文本、明细表格；长内容区一律用实色卡片。
3. 状态色仍只表业务含义，不因玻璃效果改变色相；不用颜色单独承载状态。
4. 文字放大 200%、高对比模式、减少动态偏好下，玻璃退化为实色 + 1px 描边；不得为保留效果牺牲可读性。
5. 焦点环、选中态、错误提示在玻璃层上仍需清晰可辨；`focus-visible` 不被内高光吞没。

### 1.10.5 性能与降级

- 高斯模糊是昂贵效果：同屏限制玻璃层数，滚动长列表、宽表、虚拟列表使用实色；顶栏与 Dock 可常驻，其余按需。
- 不做随滚动实时变化的模糊采样，不做持续流动的动画背景；低性能设备、省电模式、高对比模式、`prefers-reduced-motion` 与 `prefers-reduced-transparency` 统一降级为实色 + 描边（`prefers-reduced-transparency` 浏览器支持不一，须实测并保证无模糊时对比度仍达标）。
- Web 端高斯液态玻璃是 `backdrop-filter` 近似实现，**不是 Apple 官方 Liquid Glass**；设计交付与交付物须标注为近似，不声称使用官方材质或官方 Web 包。
- 深浅色切换只替换语义令牌与渐变参数，不重建模糊层；切换时无闪烁。
- 手机端保留触控反馈与滚动流畅性优先于材质层数。

### 1.10.6 与既有约定的取舍

- 仍**不放大圆角为胶囊**（手机浮岛 Dock 16px 为唯一容器例外）、**不统一给所有卡片加阴影**、**不铺满渐变**。
- 仍以「澄海：任务优先」为方向：液态玻璃服务于层级、深度与可读性，不喧宾夺主；老板端与陪玩端的核心任务（下单、接单、报单、金额）始终是最清晰的一层。
- 这是视觉定义，不宣称已在生产代码落地；现有三端的 `blur(20px)` / `backdrop-blur-xl` / `blur(32px) saturate(150%)` 是可用起点，差异见 1.9。

## 1.11 简洁性作为全局裁决原则

> 由用户后续指令驱动，适用三端，**以管理后台为首要对象**；完整落地见 2.6。

| 原则 | 定义 | 冲突时的裁决 |
|---|---|---|
| **目标简单** | 每个页面只解决一个任务；页头标题即任务名，不写宣传语 | 一屏出现两个主任务 → 拆页或分区，不加说明文字 |
| **设计简单** | 布局、分组、默认值、列顺序、状态标签承担解释职责 | 需要靠标语、提示文字或次要标签才看得懂 → **改布局**，不补文案 |
| **文案预算** | 标语 0；区块说明 ≤1 条且可收起；次要标签只用于状态、单位、数量 | 超出预算即重排；错误、不可逆后果、资金口径是例外，必须直接可见 |
| **双重收益** | 每个决定同时提升 UX（更快看懂、更少误操作）与 DX（更少特例、更可复用） | 只美化、不改善易用性或复用性 → 不做 |
| **串联优先** | 任何调整不改变路由、字段、动作、权限点、状态回读与返回位置 | 视觉与业务串联冲突时，以业务串联为准 |

这条原则优先于装饰性视觉：液态玻璃（1.10）只服务层级、深度与可读性，不得成为新增说明文字的理由；减少文案不能以删掉必要金额、状态、错误与后果标记为代价。

## 2.0 三端共性

### 2.0.1 导航层级模型

```
门店层（顶栏唯一切店入口）
  └─ 一级导航（顶部五项 / 手机 Dock / 后台业务域）
       └─ 二级导航（后台业务域下的功能组与页面；老板与陪玩为页内分区与 Tab）
            └─ 页面内容（页头 → 摘要 → 主内容 → 侧栏 → 固定操作区）
                 └─ 浮层（Dialog / AlertDialog / Sheet / Popover / 说明）
```

- **门店由访问域名／入口绑定，老板端与陪玩端不提供界面切换门店**：顶栏只静态展示当前门店真实名称与币名；`StoreGate` 在挂载业务页前确认门店营业状态，未知／停用／待初始化门店不读取默认门店数据。代码中虽有 `BossStoreSwitcher` / `ProviderStoreSwitcher` 组件，但未挂载进业务框架，本方案不把它们纳入可用导航。
- **后台的门店上下文切换有且仅有两条路径**（仅对具备独立平台门店管理授权者可见）：在 `admin.esports.club` 中性入口，通过 `POST /api/stores/switch/`（权限 `IsPlatformStoreManager`）校验目标门店为 `ACTIVE` 且已初始化后**换发目标门店的 platform 会话**，前端持久化新令牌并进入该店工作台，无需重新登录；在门店绑定域名入口，改用整页 URL 导航至目标店登录页，不携带原店令牌、路由、草稿或实时订阅。两条路径互斥，切换后均须重建业务上下文（见 2.4.3、2.4.5、4.9）。只读公开目录 `GET /api/stores/available/` 对非平台管理员仅返回当前门店。
- 顶栏统一承载：品牌与门店信息、主导航（桌面）、搜索（后台含 Ctrl+K 功能搜索）、主题切换、通知／声音、账号菜单。老板端与陪玩端顶栏不放置个人头像（陪玩端按最新批注移除）；账号信息在「我的」页内。
- 后台账号菜单显示真实身份、权限说明与退出确认；功能搜索只显示当前权限允许的功能。

### 2.0.2 角色可见性的五种表达

| 表达 | 触发 | 界面定义 |
|---|---|---|
| 可见可操作 | 服务端 `allowed_actions` 与权限点均允许 | 正常主／次按钮，状态可提交 |
| 只读 | 有查看权限、无写权限 | 字段与按钮锁定，显示只读说明；不发写请求，不发已读等隐式写 |
| 禁用 | 条件不满足（余额不足、资格不符、人数不齐、报价中、并发上限） | 控件可见但禁用，紧邻显示原因与可执行的下一步 |
| 隐藏 | 无对应权限或该对象不属于本人 | 菜单项、按钮、关联链接不渲染；不生成无效 ID 或猜测跳转 |
| 无权限页 | 直接深链到未授权路由 | 后台 `/403` 居中无权限空态 + 返回首个有权功能；不渲染旧身份或旧店数据 |

### 2.0.3 桌面与移动一致性

同一路由、同一字段集合、同一动作语义、同一状态文案；差异仅在于：主导航形态（顶部 / Dock）、分栏折叠为单列、侧栏内容下移、固定操作条位置、表格转为可横滚区域。不得在手机端隐藏关键金额、状态、错误与不可逆后果说明。

**② 预约链路**：创建（未来时间、15 分钟档、数量校验、提交中、结果未知核对）→ 待陪玩确认（不显示可成单）→ 实时报价中／报价已更新／服务信息已变化 → 余额不足（成单禁用）→ 成单结果待核对（原凭证，禁止重复成单）→ 已转订单／已取消／已拒绝／已过期（关联订单或重新预约）。

**③ 订单详情链路**：待接单与报名 → 已接单 → 服务中 → 完成待评价 → 售后处理中 → 取消与退款；每一步由 `status` / `payment_status` / `allowed_actions` / `refund_summary` / `aftersale_status` 决定可用动作与信息可见性，分人评价、逐人履约、赠礼记录、退款口径与 72 小时售后时钟保持真实。

**④ 钱包与权益链路**：余额／冻结／流水分类与分页 → 联系客服充值（线下企微收款，后台按 1:10 兑换人工入账；界面只提供咨询编号、复制与到账核对，**不发起在线支付、无收银台与支付结果页**）→ 积分兑换（积分不足／已兑完／待核对／冲突草稿）→ 权益交付（实物／虚拟／TAG／冠名、版本冲突、完成只读）→ 转盘（真实结果驱动揭晓、可跳过、日限额、凭证核对）。

**⑤ 客服会话链路**：普通咨询／关联订单咨询 → 文本与私有图片 → 已读边界 → 发送结果待核对（原消息核对／重试／放弃后果确认）→ 历史加载失败保留已加载内容与游标 → 草稿按订单隔离。

### 2.2.2 核心流程对应的界面状态

**① 抢单与履约**：接单开关真实三态（可接单／忙碌／休息，忙碌显示为未选中但可明确打开，渲染不自动写为休息）→ 抢单池与五种状态筛选 → 并发上限与资格限制提示 → 报名／队友确认／等待老板 → 已接单（开始服务）→ 服务中（完成）→ 已完成（报单入口）→ 取消原因。所有动作由 `providerOrderActions` 与服务端 `allowed_actions` 决定；未获授权的游戏账号不展示；报单进度、组队提交进度、退款与分佣追回、本单剩余冻结保留。

**② 报单与审核**：草稿（黄）→ 待审核（蓝）→ 已通过（绿）→ 已驳回（红）；三类凭证准备状态与缺失提示、最多 9 张战绩图逐图结果、上传失败或部分成功／响应未知保留原恢复说明；售后冻结、审核意见、结算通知与「APPROVED 不等于 SETTLED」的文案必须保留。

**③ 提现与资金**：提现试算中／试算失败（可重试）→ 有效报价才展示金额／税率／税额／预计人民币打款 → 规则更新、账户变化、结果未知均有核对路径 → 审核中／通过／驳回／退回余额／打款凭证由真实状态呈现；重复原请求不重复扣款。

**④ 预约确认**：待确认／已确认／已拒绝／已取消／已过期／已转订单；原因必填、已转订单展示真实链接、结果未确认提示刷新核对。

**⑤ 资料与技能**：首载骨架、读取失败重试、部分失败逐条提示；空字段照实显示可填写表单；空档期为未选择矩阵而非「无资料」；技能资格不满足可移除不可新增；未保存草稿与清空／放弃确认；自由服务日、常用位置、声音标签、服务等级、公开招募等按待开放状态呈现，不发写请求。

## 2.4 后台 SaaS 化：平台层 / 门店层双工作台

> 本节与 2.5 由用户后续指令驱动（「引入租户概念，把后台构建成 SaaS 化产品」「用 license 控制授权」）。它们**突破**了 0.2 的「不新增业务能力」边界，属于产品级设计增补：现有代码具备多租户底座，但**没有** License、订阅、配额、计费模型或端点。本节只定义界面与体验，并把需要服务端新增的判定结果以字段清单列出；不宣称这些能力已存在，不提供实现教程。

### 2.4.1 定位与边界

现有系统已是多租户架构：`Store`（slug / 名称 / 币名 / 四态生命周期 / 三端入口 / 独立业务库）、每店独立业务数据库、平台门店管理独立授权、中性后台入口与门店绑定域名、会话换发与整页导航两条切店路径。SaaS 化是把这套底座**在信息架构上表达为两个工作区**，而不是新增计费或自助开通能力。

| 层 | 谁可见 | 承载内容 | 数据范围 |
|---|---|---|---|
| **平台工作区** | 仅具备独立平台门店管理授权者 | 租户目录与生命周期、平台成员与授权、License 与订阅（2.5）、平台级只读视图、进入门店 | 只读取门店公开元数据与授权信息，**不读取任一门店的余额、订单、客户、资金** |
| **门店工作区** | 该店 STAFF 角色，及换发会话后进入的平台管理员 | 现有 10 个业务域与全部页面（2.3，结构不变） | 严格限定本店，权限由该店角色决定 |

**老板端与陪玩端保持单租户**：按域名绑定，不提供界面切换门店，不承担平台层界面（见 2.0.1 与 `AGENTS.md`）。

### 2.4.2 双层信息架构

```
平台工作区（Platform Console）
├─ 租户总览       目录 / 四态生命周期 / 三端入口 / 币名 / 初始化与配置状态
├─ 授权与订阅     License 档位、配额、有效期、功能范围（2.5）
├─ 平台成员与授权 平台账号、独立平台授权、角色与审计（现有 /admins /roles /audit-logs 的平台层视图）
└─ 进入门店       ← 唯一受控通道
        ↓ 中性入口：POST /api/stores/switch/ 换发 platform 会话
        ↓ 门店绑定域名入口：整页导航至目标店登录页
门店工作区（Store Workspace）
└─ 现有 10 业务域 / 45+ 业务入口 / 13 运营 Tab（结构、路由、权限不变）
```

平台层不复制、不合并、不聚合各店业务数据；跨店汇总报表、租户自助注册与开通、在线订阅支付、用量计量、白标主题、多层级组织等**当前代码不存在**，列为「平台能力待定义」，不进入导航、不设计成可用界面。

### 2.4.3 租户上下文作为一等界面对象

- **顶栏常驻租户标识**：门店名 + 币名 + 状态点 + 「本店数据」范围标签；平台工作区显示「平台 · 未选择门店」，不预选门店。
- **切换器 5 态**（沿用现有 `AdminStoreSwitcher` 的真实交互）：目录（真实公开目录、当前项勾选）→ 二次确认 → 切换中（禁用）→ 成功 → 失败（toast + 保留当前上下文）。确认文案须说明「不会携带当前门店的草稿或未确认请求，平台授权会在服务端再次核验」。
- **成功态有两条互斥分支**：在 `admin.esports.club` 中性入口，换发目标店会话后**留在当前 SPA**，替换会话并导航至工作台；在门店绑定域名入口，用整页 URL 导航至目标店登录页，**销毁当前页面上下文**。两条分支都须关闭旧实时订阅、离开订单详情、清理筛选／滚动／草稿／未确认请求，并重新读取新店权限与菜单；不可把「留在 SPA」误做成整页刷新，也不可把整页分支误做成携带旧令牌的无缝切换。
- **非平台管理员降级为只读标识**，不显示切换器；普通门店角色不得看到其他门店条目。
- **同名同密码账号消歧**：登录时明确列出可归属门店供选择，不默认选店；更换店内身份须重新登录。
- **跨店 ID 重叠**：列表与详情保留「本店」范围标签与真实业务 `account_id`，不猜测 legacy ID。

### 2.4.4 租户生命周期状态界面

| 状态 | 界面表达 | 允许动作 |
|---|---|---|
| `PROVISIONING` 待初始化 | 警示状态 + 「需完成独立业务库初始化、配置与首位管理员」说明；不可呈现为可营业 | 查看、复制登记信息；不可进入、不可启用 |
| `CONFIGURING` 待配置 | 中性状态 + 待办清单 | 配置；不可进入、不可启用 |
| `ACTIVE` 营业中 | 成功状态；可显示三端入口与币名 | 进入、改名与入口、停用（默认店不可停用） |
| `DISABLED` 已停用 | 中性禁用；入口不可复制 | 查看、重新启用；不可进入、不回落默认门店 |

新店登记后一律不展示为可营业；不能把尚未初始化的门店放入可切换目录。

### 2.4.5 隔离的可见化与切换后果

- 切换成功后重建业务上下文：关闭旧实时订阅、离开订单详情、清理筛选／滚动／表单草稿／未确认请求，重新读取新店权限与菜单。
- 令牌、私有媒体、WebSocket、异步任务、缓存、审计日志、通知均带门店上下文；跨店令牌或错店图片请求给出明确拒绝反馈。
- 平台层任何视图不得出现他店余额、订单或客户；只读目录只返回已初始化且启用的公开元数据。

### 2.4.6 SaaS 化的视觉表达（克制、苹果风）

- **不新造品牌色**：平台层用更深的中性表面与更疏留白（24–32px 区块间距），门店层沿用 Blue Planet 与现有紧凑密度（16–24px）。
- 租户标识是「状态点 + 文字 + 范围标签」，不是彩色横幅；档位与许可状态用中性／`warning` 强度，不用 `destructive`。
- 平台层页面以液态玻璃 L1 卡片与 L0 低饱和渐变承载（1.10），但表格与金额仍用实色承载面。
- 不在普通门店角色的侧栏塞入「租户列表 / 订阅 / 计费」等无权菜单；平台层入口只在授权后出现并返回门店工作区。
- 深浅色、触控、键盘焦点与减少动态规则与全局一致。

### 2.5.4 被拦截功能的界面表达

| 拦截等级 | 界面定义 |
|---|---|
| 可见但锁定（推荐） | 菜单项与页面入口**保留**，加锁形标记与「当前档位不可用」；点击展示档位对比、当前档位与升级收益，不静默失败、不跳空白页 |
| 只读 | 已有数据可查看、筛选与导出受控，写按钮隐藏或禁用并说明原因；不发写请求 |
| 配额上限 | 老板／陪玩**新增账号**被阻止，但**已有账号继续使用核心功能不受影响**；显示已用／上限与释放方式（停用、清理） |
| 完全不渲染 | 仅用于当前代码不存在的平台级能力，避免把「待定义」做成可点击占位 |

**配额与许可状态反馈**：

- 配额将满（80% / 95%）显示轻量预警条，可收起；已达上限显示明确的阻止原因与下一步（升级 / 停用不活跃账号），不使用 `destructive` 红。
- 许可状态：有效 / 将到期（临近续费）/ 宽限期 / 已过期 / 未授权，顶栏轻量标识 + 平台层详情页展示到期时间（北京时间）、档位、已用配额与功能范围。
- **过期处理建议**：不立即锁死核心交易。给只读宽限期，保留履约、报单、退款、提现的对账与收尾能力，避免资金与履约中断；只阻止新增账号与增值功能。到期信息常驻但可收起，不重复打扰。
- **服务端为准**：前端拦截只是表达，真正的拦截、配额计数与许可校验必须由服务端判定；界面需处理「未授权 / 配额已满 / 许可过期」三类原因码并给出可执行下一步。

**界面依赖（需服务端新增的判定结果，当前代码不存在）**：当前档位、许可状态、老板／陪玩配额上限与已用、功能开关集合、到期时间、升级目标档与价格、拦截原因码。另需产品确认：配额计数口径（活跃 / 累计、封禁是否计入、按店还是按平台）、续费／降级／过期后的数据处置、是否提供试用期。

## 2.6 管理后台 SaaS 化：功能组织、页面布局、内容安排与串联

> 本节对象为**管理后台（后台管理端）**，是 2.4 / 2.5 的落地细化，也是 1.11 简洁性原则的主战场。约束：只改变**入口的呈现顺序与分组、页面内部结构、文案密度**，不改变任何路由、页面组件、接口字段、动作、权限点或业务串联。

### 2.6.1 简洁性的可执行裁决

| 裁决规则 | 判定方式 |
|---|---|
| **遮罩测试** | 把页面上所有标语、提示文字、次要标签遮住后，仍能看出「这是做什么的、现在该点哪里」→ 通过；否则改布局（列名、分组、默认值、位置、空态、状态标签），不补说明 |
| **一屏一任务** | 页头只有任务名 + 唯一主操作 + 本页真实指标；出现第二个主任务即拆分区或拆页 |
| **说明不代替结构** | 「请先选择筛选条件」「这里可以查看…」「操作不可逆请谨慎」这类句子一律删除；改为默认筛选范围、表格列名、就近的一次性最终确认 |
| **文案预算** | 标语 0；页面级说明 ≤1（可收起）；字段级说明按需可点击；次要标签 ≤3 类（状态 / 单位 / 数量）；错误与资金后果直接可见，不受预算限制 |
| **双重收益** | 每个改动须同时说明 UX 收益与 DX 收益；只影响观感的改动不做 |

### 2.6.2 功能组织：从「数据表菜单」到「角色任务流」

**保留**现有 10 个业务域、45+ 路由与 13 个运营 Tab 的路径与组件；**重排**它们在导航中的呈现顺序、分组与默认落点：

| 动线 | 顺序 | 说明 |
|---|---|---|
| **每日经营动线**（默认展开） | 工作台待办 → 订单与派单 → 报单审核 → 提现 / 钱包 → 结算与对账 | 按客服／财务每天的真实操作顺序，而不是按数据表字母顺序 |
| **配置动线** | 商品与营销 → 陪玩与客户 → 会员与运营 → 系统管理 | 低频配置集中，默认折叠，不挤占每日动线 |
| **平台动线**（仅平台授权可见） | 租户目录 → 授权与订阅 → 平台成员与授权 → 进入门店 | 2.4 的平台工作区，与业务数据完全分离 |

- 每个域的二级导航按「**先看队列 → 再查列表 → 最后配置**」排序；默认落点取该角色最常用且有权限的页面，不落到说明页。
- **工作台只放「今天要做什么」**：三列角色待办、本页真实指标、状态分布、最近订单；不出现欢迎语、运营口号、帮助卡、「快速上手」或功能介绍。
- **13 个运营入口收敛为 3 组呈现**（其中 5 个走通用资源配置页、8 个为独立业务组件；`?tab=` key 与权限过滤不变）：
  - 会员与权益：`tiers` / `rewards` / `claims` / `external` / `kook`
  - 活动与内容：`lotteries` / `packages` / `giftBenefits` / `content` / `rules` / `feed` / `namings`
  - 运营设置：`settings`
- 平台层不出现任何门店余额、订单、客户或资金；门店层不出现订阅、租户目录等无权菜单（2.4.1）。

### 2.6.3 页面布局：一套后台模板

```
顶栏 64px   租户上下文(门店名·币名·状态·本店数据) │ 面包屑(平台/门店 › 域 › 页) │ 功能搜索 │ 通知·声音 │ 账号
左栏 232px  业务域 rail(72px 可收缩) → 域内页面二级面板
内容区      max 1600px · p24 · min-w-0
  ① 页头   任务标题(26px) + 唯一主操作 + 本页真实指标(≤4)
  ② 筛选   单行；只渲染服务端支持的筛选；不支持的不显示为占位
  ③ 主内容 宽表(区域内横滚) / 分组卡 / 分区表单，三选一
  ④ 页脚   分页 / 固定操作条，随内容滚动，不遮挡标题
  ⑤ 浮层   详情抽屉或 1120px 弹窗，保留列表返回位置
```

| 每屏上限 | 数值 |
|---|---|
| 主任务 / 主操作 | 各 1 |
| 指标卡 | ≤4，且只汇总本页或取接口 `total` |
| 筛选行 | 1 行；更多条件收进「高级筛选」，默认折叠 |
| 欢迎横幅、说明卡、小贴士、营销标语 | **0** |
| 次要标签 | ≤3 类，仅状态 / 单位 / 数量 |
| 常驻 Toast / 提醒条 | ≤1，可收起，不重复打扰 |

- 表格列顺序固定为「身份 / 对象 → 状态 → 时间 → 金额 → 动作」；金额与数量右对齐等宽，身份与状态靠左，动作靠右。
- 宽表只在表格容器内横滚且可键盘聚焦，不产生整页横向溢出；1366×1024 与 1920 使用同一模板。
- 深色／浅色、液态玻璃按 1.10：平台层更深中性表面 + 24–32px 疏朗留白，门店层保持 16–24px；表格与金额一律实色承载面。
- 详情／编辑用右侧抽屉或弹窗，不用整页跳转；关闭后回到原列表的筛选、滚动、分页位置。

### 2.6.4 内容安排：用结构替代文字

| 原本靠文字 | 改为结构 |
|---|---|
| 「这里可以查看所有订单」 | 页头任务名 = 订单与派单 + 表格列名 |
| 「请先选择筛选条件」 | 默认即常用队列；筛选控件成行 |
| 「操作不可逆，请谨慎」 | 最终确认弹窗内一次，用「对象 / 金额 / 后果」三行信息格 |
| 区块说明、规则长文 | 分组标题 + 字段名 + 可点击说明（可聚焦，不常驻） |
| 状态旁的解释句 | 1.2.4 状态色板文案 + 真实时间戳 |
| 堆叠的次要标签与徽标 | 只留状态 / 单位 / 数量；其余移入详情 |
| 空态的大段引导 | 一句「暂无 X」+ 一个下一步动作 |
| 「待开放」整页横幅 | 控件就地禁用 + 可聚焦说明，不占版面 |
| 常驻的许可 / 配额提示 | 顶栏轻量标识（可收起）+ 平台层详情页；不打断主流程（3.1.2） |

**不删减的例外**：金额、状态、错误、不可逆后果、资金口径、72 小时售后时钟、结果待核对的恢复说明、隔离验收 / 模拟数据 / 未启用能力标识。压缩文案不能以隐藏这些信息为代价。

### 2.6.5 串联不变量（不可被布局重排破坏）

1. **路由与组件不变**：45+ 业务路由、13 个 `?tab=`、以及 `?detail=` / `?dispatch=quick` / `?id=` / `?status=` 等既有参数语义全部保留；导航重排只改呈现顺序与分组。
2. **核心闭环不断**：下单 → 派单 → 履约 → 报单 → 审核 → 结算 → 退款／提现，每一步的对象 ID、门店上下文、状态与 `allowed_actions` 由服务端返回；页面只重排信息，不推断动作。
3. **跨页上下文**：详情关闭返回原列表位置与筛选；深链与刷新后仍能读取同一对象；不以内存态作为唯一真相。
4. **状态回读**：写操作后回读最新状态；`APPROVED` 不等于已结算，`COMPLETED` 不等于实销；前后台、老板端、陪玩端读取同一状态。
5. **实时与门控**：WebSocket 事件按当前业务区触发局部重读（350ms 合并），不因布局调整扩大订阅范围；刷新不清空筛选、滚动、草稿与已开表单。
6. **资金与幂等**：稳定请求编号、`expected_version` / `expected_details` / `plan_token`、待核对与原请求恢复、私有媒体续签、统一错误解包全部沿用（3.4.1 / 3.5 / 4.3）。
7. **权限单一来源**：登录响应 `permissions[]` + `is_superuser` + 服务端权限点；菜单重排不产生新的前端权限判断，无权页面仍走 `/403`。
8. **平台⇄门店切换**：2.4.3 的 5 态与两条成功分支不变；切换后重建上下文、关闭旧订阅、清理草稿与未确认请求。

### 2.6.6 每个决定的 UX / DX 双重收益

| 决定 | UX 收益 | DX 收益 |
|---|---|---|
| 一套页面模板 | 任意页面定位路径一致 | 一套页头 / 骨架 / 状态契约，减少逐页特例 |
| 单一主操作 | 减少误点与犹豫 | 一个动作契约，权限与幂等判定集中 |
| 文案预算 | 更少阅读、更快完成任务 | 更少文案分支与国际化特例 |

| 详情保留返回位置 | 不丢失上下文 | 统一的列表—详情状态契约 |
| 筛选只渲染已支持项 | 无无效操作与假结果 | 不为「待开放」写伪过滤逻辑 |
| 统一错误解包 | 一致且可执行的反馈 | 一张按形状分派的映射，页面只绑业务端点 |
| 玻璃分层护栏 | 金额与状态始终清晰 | 一套语义令牌，深浅色无需逐页覆写 |

### 2.6.7 简洁性 QA 与串联回归

- **遮罩测试**：遮住全部标语／提示／次要标签后，页面仍能看懂并完成主任务。
- **预算检查**：标语 0、说明 ≤1、主操作 1、指标 ≤4、筛选 1 行、次要标签 ≤3 类。
- **布局检查**：1366×1024 与 1920 无整页横向溢出；浅深色、200% 文字缩放、键盘焦点、WCAG AA 一致。
- **串联回归**：核心闭环在三档 License 下逐档可完成；深链、刷新、返回、切店、断线重连后状态与草稿不丢；原请求不重复扣款。
- **权限回归**：普通门店角色看不到平台层；无权菜单不渲染；动态撤权后旧请求与订阅失效。

## 2.8 管理后台的角色重点画像与自助统计汇总

> 由用户后续指令驱动，并已按最新澄清定位：**画像属于管理后台系统**，不是老板端／陪玩端的功能。本方案覆盖后台的**陪玩重点画像**、**老板重点画像**与**自助统计汇总**；老板端与陪玩端只保留完成自身任务所需的公开／本人字段，不承载画像。遵守 1.11 / 2.6 的简洁性与串联约束，逐区块开发规格见第五部分 5.4。

### 2.8.1 定位与三条硬约束

| 约束 | 定义 |
|---|---|
| **归属后台，不新增页面** | 画像是**管理后台现有详情／看板页面内的信息组织方式**：主落点为 `/escorts` 陪玩档案详情、`/users` 老板资料详情、`/player-dashboard` 陪玩业绩、`/dashboard` 运营工作台；自助统计落在这些页与 `/operating-roi` 的现有筛选、周期、日期区间与指标中。不新增「画像中心」「报表中心」「用户 360」页面，也不把画像搬进老板端／陪玩端 |
| **「重点」= 分层，不是堆字段** | 按「决策字段 → 依据字段 → 明细与历史」三层组织；首屏只放决策字段，其余进分区或下钻，不以更多标签和说明弥补层级 |
| **「自主」= 服务端已支持范围内自由组合** | 在现有周期、日期区间、状态、关键词、排序、分页与指标口径内自助组合；不做本地演算、不伪全局汇总、不生成服务端未返回的指标 |

### 2.8.2 陪玩重点画像（后台主视角）

**管理后台 `/escorts` 详情**是画像的唯一主载体，在 `AdminEscortSerializer` 已有字段上按五区组织：

| 分区 | 真实字段 | 界面职责 |
|---|---|---|
| 身份与状态 | `display_name` / 头像、`entity_no`、`status` / `status_display`、`gender_display`、`is_verified`、认证状态、`active_pass_tier` / `pass_tier_display` | 一眼确认「是谁、当前能否接单」 |
| 资格与技能 | `qualifications`、`game_categories` / `game_category_names`、`service_items` / `service_item_names`、`rank_tier`、`win_rate`、`level` / `level_name` | 判断能接什么服务、什么档位 |
| 商业与抽成 | `price_per_hour`、`city` / `service_area`、`recommendation_slot`、抽成率与来源标签 | 定价与推荐位依据 |
| 资金与风险 | 押金应缴／已缴、奖惩记录、钱包余额与冻结、封禁状态 | 风险与账务核对 |
| 履约与材料 | 完成数、评分与评价数、报单与结算记录、私有材料（头像／视频／查外挂依据图）签名加载 | 下钻核对，不占首屏 |

**老板端 `/companion-detail` 与 `/companions` 不是画像**，只是完成选人所需的公开字段（昵称与头像、可约状态与不可约原因、参考时价、擅长游戏、评分／完成数、权益标签、语音卡、段位、城市、资格），沿用现有布局与唯一主操作「选择 TA / 预约」；不得把后台五区字段搬到老板端，也不得在老板端出现「画像」字样。

**陪玩端 `/orders` 概况与 `/mine` 也不是画像**，只是本人接单统计与资料自维护视图；陪玩无权查看后台档案字段。

**待开放字段**（不得伪造，见 4.6）：擅长位置、声音标签、本人服务等级只读展示、结构化位置／声音标签；现有 `display_tags` 是审核通过的权益 TAG，`rank` 是游戏段位，`qualifications` 是接单资格，三者不得互相冒充。

### 2.8.3 老板重点画像（后台主视角）

**管理后台 `/users` 详情**是主载体，按三层组织：

| 层级 | 字段（现有真实来源） | 呈现 |
|---|---|---|
| 决策层（首屏） | 身份与编号、会员等级（`VipTier` / `BossType`）、已确认实销与成长差额、当前折扣、账号与封禁状态、可用券与积分 | 身份区 + ≤4 指标；明确「已确认实销用于会员成长，待确认金额未计入」 |
| 依据层 | 常用游戏资料（`CustomerGameProfile`：区服／昵称／UID）、推荐关系与分级、展示标签、生日、成就与签到进度、券与权益记录 | 分组卡，字段名即说明 |
| 明细层 | 订单与消费、钱包与流水、退款、赠礼、通知 | 现有列表与详情下钻，不占首屏 |

**老板端 `/mine` / `/membership` / `/profile` 是本人自助视图**，只展示本人会员、资料、积分与权益，不承载后台画像；后台画像中的推荐关系、封禁、他人订单归属等字段不得出现在老板端。所有金额按 4.5 口径，实销与充值本金分开。

### 2.8.4 自助统计汇总：现有可自主范围

| 自主维度 | 现有能力 | 界面定义 |
|---|---|---|
| 周期 | 榜单 `period = day / week / month`（`/orders/rankings/`） | 分段筛选，选中态明确，切换后重新请求、不保留旧榜数据 |
| 日期区间 | `/player-dashboard` 的 `start_date` / `end_date`；经营 ROI 月份切换 | 原生日期输入，起止校验、清空、应用三段；区间变化后立即隐藏旧数据 |
| 状态与范围 | 订单状态、礼物单、提现状态、券 tab、流水 `tx_type`、预约状态、权益状态、后台各列表筛选 | 只渲染服务端已支持的项；不支持的标「待开放」，不在当前分页内伪过滤 |
| 排序 | 目录价格／难度、陪玩价格、榜单周期、表格排序字段 | 选中态 + `aria-pressed`，排序由服务端返回 |
| 分页与粒度 | `page` / `page_size`、游标 `before` / `before_id` | 总数取接口 `total`；标「本页」的统计才从当前行汇总 |
| 指标 | 工作台 `/api/admin/dashboard/stats`（按权限）、`daily_new_orders` 趋势、状态分布、陪玩业绩三榜、净额／押金／钱包、经营 ROI | ≤4 指标卡 + 一张趋势图；每个指标标注口径与范围，缺成本／未确认薪资显示缺口而不是 0 |
| 陪玩业绩统计 | 后台 `/api/admin/dashboard/player`（`start_date` / `end_date`）、三榜、净额／押金／钱包；陪玩本人 `/users/provider-stats/` 提供今日接单、服务中、并发上限、累计完成、待处理、评分与评价数、累计收益、完成率、近 7 日收益趋势、接单状态 | 后台业绩看板为统计主载体；陪玩端工作台概况只是本人视图，不作为画像；不能用累计值冒充「本月净收益」（P-07 待开放） |

**交互形态**：条件区（一行）→ 指标区（≤4）→ 图／表区 → 明细下钻；条件变化后旧数据立即隐藏、加载中锁定、失败保留条件并可重试、空结果显示真实空态与清除条件入口。图表数据只来自服务端，不在前端二次聚合。

**口径规则**：净消费不含充值本金；退款净额与榜单一致；`APPROVED` 不等于已结算；暂估与已确认分开；薪资／投流／成本用人民币、门店币用浪花／星辉；跨店数据绝不合并。

### 2.8.5 需服务端新增 / 平台能力待定义

| 诉求 | 现状 | 界面处理 |
|---|---|---|
| 任意维度聚合、自定义公式、透视／拖拽报表、自定义报表保存与分享 | 代码未找到对应端点 | 标「平台能力待定义」，不摆放可点击占位、不做本地演算 |
| 导出 CSV / Excel | 代码未找到导出端点 | 不显示导出按钮 |
| 跨店／全平台汇总 | 每店独立业务库，禁止跨店混用 | 平台层只读目录与授权信息，不展示他店业务数据 |
| 画像字段扩充（结构化常用位置、声音标签、本人服务等级） | 后端序列化未提供 | 按待开放呈现（4.6） |
| 画像／统计的按档位开放范围 | License 判定结果尚不存在（2.5） | 见 2.8.8 |

界面依赖（若产品决定扩展）：可聚合维度白名单、聚合口径与权限、服务端返回的汇总结果快照、导出任务的幂等与结果待核对。这些是**设计依赖清单**，不是已具备能力。

### 2.8.6 简洁性与状态反馈

- 后台画像页页头只写任务名（陪玩名 / 老板名 / 编号），不写「360° 全景画像」「数据洞察」等标语；分区标题用字段名，不写引导句。
- 老板端榜单现存的「一起见证高光时刻」「每份支持，都有回响」类文案按 2.6.4 替换为任务名 + 周期 + 真实数据；这属于全局简洁性整改，不表示老板端承载画像。
- 指标卡 ≤4，口径用一行辅助文字（12px）标注；「本页」统计只汇总当前列表。
- 状态沿用第三部分：首载骨架、已有快照刷新、局部失败、空态、只读、禁用、结果未知；私有媒体签名加载骨架与失败重试；实时事件只局部重读画像与统计区，不清空用户已选条件与草稿。
- 深浅色、液态玻璃按 1.10：画像卡可用 L1 玻璃，但金额、评分、状态一律放在实色承载面上。

### 2.8.7 串联不变量

1. 画像与统计只改变**后台现有页面的信息组织与字段层级**，不改变路由、接口字段、动作、权限点与 `allowed_actions`。
2. 后台画像与老板端选人是**不同端的独立视图**，不串成一条操作链路：两者共享同一批公开字段口径（可约状态、资格、价格、评分），但后台画像用于管理，老板端详情用于选人；老板端「选择／预约 → 结算 → 订单」链路按原有参数与资格复核执行，不依赖后台画像页。
3. 统计下钻到订单／陪玩／流水时，使用明确的业务 `account_id` 与订单 ID，不猜 legacy ID；详情关闭返回原条件与位置。
4. 条件变化不复用旧对象数据；写后状态回读；幂等、版本、待核对、错误解包全部沿用（2.6.5）。
5. 门店隔离、私有媒体、WebSocket 订阅与异步任务上下文不变；平台层不读取门店业务数据；后台画像中的私有字段不得下发到老板端／陪玩端。

### 2.8.8 与 License 三档的对齐

**后台基础画像、老板端选人所需公开字段、陪玩端本人统计均属核心闭环依赖，三档全开**：老板选人需要可约状态、资格、价格与评分；陪玩工作台需要接单统计；后台审核需要档案字段。把这些按档位拦截会切断下单／派单／报单链路（2.5.2 红线）。

**可按档位差异化的是「进阶汇总」**：跨周期对比、自定义维度组合、画像字段扩充、导出与报表保存——这些尚属「平台能力待定义」，若将来开放，按 2.5.3 的数据能力分级处理；未开放前不显示为可用功能。

### 2.8.9 设计 QA

- 遮罩测试：遮住全部标语后，后台画像页仍能看出「这是谁、当前状态、下一步管理动作」；统计页仍能看出「当前范围、口径、结果」。
- 每页指标 ≤4、条件 1 行、主操作 1；待开放字段不伪造、不冒充；后台私有字段不出现在老板端／陪玩端。
- 三档 License 下基础画像、选人字段与本人统计均可用；核心闭环逐档可完成。
- 条件切换、刷新、返回、切店、断线重连后条件与草稿不丢；数据口径与流水、榜单、ROI 一致。

# 第三部分 · 状态与反馈

## 3.1 界面状态总模型

所有页面、列表、卡片、弹窗统一使用同一套状态词汇，避免「同状态不同表达」：

| 状态 | 触发条件 | 界面定义 |
|---|---|---|
| 首载加载 | 请求中且无有效快照 | 按页面真实几何显示骨架，不显示默认 0、空卡或占位金额 |
| 已有快照刷新 | 同条件请求中且已有真实数据 | 保留原数据与布局，只显示细「正在更新」条；锁写操作但不清空输入 |
| 切换条件加载 | 切换对象／筛选／页码／门店范围 | 立即隐藏旧对象数据并锁定加载，禁止把上一对象数据冒充当前对象 |
| 加载失败（首次） | 首次请求失败且无快照 | 页级或区域级错误卡 + 重试；保留原查询条件 |
| 刷新失败 | 已有快照的请求失败 | 保留真实旧快照 + 就近错误条 + 重试；区分「读取失败」与「写入失败」 |
| 空数据 | 请求成功且真实列表为空 | 分业务空态 + 明确下一步；不渲染默认卡片，不把空当失败 |
| 局部失败 | 页面内某一子资源失败（评价、玩法、动态、详情、元数据） | 仅该区块显示紧凑错误与重试，主体内容保留 |
| 分页／游标失败 | 下一页或更早页读取失败 | 当前页不混用、不追加旧页；错误 + 重试 / 返回最新，保留游标与筛选 |
| 禁用 | 资格、余额、人数、并发上限、报价中、未配置、只读 | 控件可见但禁用，紧邻显示原因与可执行的下一步 |
| 进行中 | 提交、保存、上传、审核、试算、核价 | 按钮与表单锁定，显示「处理中…」，隐藏关闭或保留 busy 保护；输入与草稿不清空 |
| 结果未知 / 待核对 | 网络中断、408 / 409 / 429 / 5xx、响应丢失 | 保留原金额、原积分、原凭证、原请求；提供核对／原请求重试／记录／客服；禁止新建重复交易 |
| 冲突 | `revision` / `expected_details` / `expected_status` / 版本不符 | 明确草稿冲突或状态已变化；允许复制草稿、读取最新、确认替换；不覆盖他处更新 |
| 待开放 | 服务端无对应接口或能力未启用 | 保留版式但明确「待开放／待公布」，可点击说明；不发写请求、不造数据、不模拟成功 |
| 只读 | 有查看权限无写权限、已完成权益、已转单预约 | 字段与按钮锁定并显示只读说明；不发隐式写（含已读、回复） |

### 3.1.1 状态优先级

**结果未知 / 待核对 > 冲突 > 权限只读 > 禁用条件 > 进行中 > 刷新失败 > 局部失败 > 首载失败 > 空数据 > 默认**。高优先级状态覆盖低优先级，但不得抹去已显示的真实数据；资金类状态一律高于普通视觉状态。

### 3.1.2 租户上下文与 License 状态

这两类状态属于平台层设计增补（2.4 / 2.5），优先级**低于任何资金与履约状态**，且不得阻断核心闭环：

| 状态 | 强度 | 界面定义 |
|---|---|---|
| 租户切换中 / 切换失败 | 中（局部） | 切换中禁用相关控件；失败保留原门店上下文并给出重试 |
| 租户待初始化 / 待配置 / 已停用 | 中（平台层） | 不可进入、不呈现为可营业；给出待办或恢复路径 |
| 许可有效 | 弱（可收起） | 顶栏轻量标识，不干扰主流程 |
| 将到期 / 宽限期 / 已过期 / 未授权 | 中（平台层 + 顶栏轻量） | 说明原因与下一步；**核心闭环不中断**，只阻止新增账号与增值功能 |
| 配额将满 / 已达上限 | 中（靠近新增账号入口） | 已用 / 上限与释放方式；已有账号继续使用核心功能不受影响 |
| 功能未授权 | 中（入口就地） | 可见但锁定 + 档位对比与升级引导；不隐藏、不静默失败、不跳空白页 |

规则：以上状态一律不使用 `destructive` 红；到期与配额信息常驻但可收起、不重复打扰；服务端判定为准，前端拦截只是表达。

## 3.2 加载态

- **首载骨架按页面几何分支**，不用通用三块替代：老板端首页／目录／套餐／订单详情／钱包／个人中心／转盘／交付／弹窗各有对应高度；陪玩端首载为四块 12px 圆角骨架；后台有 41 个显式骨架分支（工作台三列 224 + 四列 144 + 双栏 320 + 底部 288；订单 96/160/520；详情 144 + 双栏 720/520 等），并区分整页与局部作用域。
- **骨架不承载数据**：不显示 0、`—` 冒充的真实值、示例头像或示例余额；骨架内不放可点击控件。
- **刷新不整页重绘**：陪玩端自动刷新只更新订单列表，不替换上方统计、资料与预约侧栏；后台实时事件按当前业务页与运营 Tab 筛选，350ms 合并，读取期间最多保留一次后续核对；老板端实时重读保留未保存的会员标签与生日草稿。
- **保留输入焦点、滚动位置、已打开表单与草稿**：切换筛选后搜索节点常驻，新范围清掉旧卡但焦点不丢；列表翻页不丢已读范围。
- `aria-busy` 标记加载区域；骨架低频微光，尊重减少动态偏好。

## 3.3 空数据

| 空态类型 | 定义 | 必须提供的下一步 |
|---|---|---|
| 列表真空 | 服务端成功返回空数组 | 按业务命名的空态（暂无订单／暂无预约／暂无消息／暂无可接单／暂无流水／暂无评价…）+ 去创建、去目录、清除筛选或查看全部 |
| 筛选无结果 | 有数据但当前筛选不匹配 | 保留筛选控件，提供「清除查询」「查看全部」，不隐藏筛选 |
| 配置未就绪 | 转盘无活动、VIP 等级待配置、费率未配置、客服资料未配置、本期奖励待公布、正文准备中 | 说明当前不可用原因 + 可到达的相关入口；不生成示例内容 |
| 子区域为空 | 某一榜单为空、某一类动态为空、权益明细为空 | 只在该子区域显示空态，不影响同页其他真实数据 |
| 无权限／无对象 | 无关联对象、无详情 ID、他店或他人资料 | 错误或只读说明 + 返回来源列表；不伪造空记录 |

**规则**：空态与失败态严格区分；成功空态不得出现「重试」作为唯一动作；不得用默认卡片、示例数字或假日期填充空态。

## 3.4 异常与失败

| 场景 | 呈现 |
|---|---|
| 页面／列表首次失败 | 居中或区域错误卡，含真实错误摘要、重试按钮、保留的查询条件；不把失败当空列表 |
| 动作失败 | 错误靠近触发动作；页面 `ActionFeedback` 与确认框内同时显示；输入与草稿不清空 |
| 局部资源失败 | 玩法、评价、动态、详情、原流水、选项元数据、私图各自独立错误与重试，其余内容保留 |
| 分页失败 | 独立错误 + 重试 / 返回上一页或最新；不把上一页冒充当前页，不做模拟追加 |
| 私有媒体 | 签名加载骨架、刷新签名、失败重试、无材料状态；过期续签不覆盖新图，迟到响应不复活旧会话 |
| 未配置／能力不可用 | 企微客服链接非 HTTPS、钱包停用、门店待初始化、功能待开放；明确说明并保留备用入口（平台会话、客服） |
| 已受理但展示异常 | 明确「已受理」并给出核对入口，不重建请求、不重复扣款 |
| 权限错误 | 直接深链进入 `/403`；动态撤权后旧请求、WebSocket、图片续期不得继续泄露数据 |
| 带预览数据的业务错误 | 退款／协商／逐段退款／配置变更类 4xx 会同时返回 `errorCode` 与 `data` 载荷（剩余可退金额、缺口明细、重新试算预览）；界面须展示预览并提供「重新试算 / 返回修改」，不折叠成通用错误，也不当空态 |

错误文案必须包含「发生了什么 + 可执行的下一步」；不可逆后果与失败处理步骤不得藏进悬停提示；Toast 只承载轻结果，不承担错误恢复说明。

### 3.4.1 错误解包与限流的统一交互

错误响应有 **4 类载体**，界面必须统一解包，否则会出现「明明失败却没有错误码」或「把 HTTP 状态码当业务码」：

| 载体 | 形态 | 界面处理 |
|---|---|---|
| 视图内字面量 | `code` / `errorCode` / `msg` | 按 `errorCode` 匹配可执行下一步；领域异常被捕获后转字面量的（如价格／条款／资格变化）同样处理 |
| 异常对象动态透传 | `RefundError.code` + `data`，HTTP 状态按码分支 400 / 409 | 展示 `data` 中的预览与缺口，提供重新试算；不硬编码错误码表 |
| 自定义配置／认证异常 | 部分携带 `code` + `status` 转 `errorCode`；但 4 类配置异常（时钟、房间确认、预约截止、押金配置）**只返回 `code` / `msg`，没有 `errorCode`** | 配置类页面的失败态不得依赖 `errorCode` 才渲染；以服务端 `msg` 与字段错误为准；`PayrollConflict` 只落在 DRF `errors` 字段，不作为顶层码 |
| 全局异常处理器 | 把 DRF 异常包成 `code`（**HTTP 状态码，非业务码**）/ `msg` / `errors`；429 注入 `errorCode` 为 `ORDER_RATE_LIMITED` 或 `RATE_LIMITED`；3 处合成默认码子变体 `SEGMENT_REFUND_REVIEW` / `SETUP_UNAVAILABLE` / `WECHAT_UNAVAILABLE`（异常带 code 则透传，不带则合成默认码，普通校验失败也会返回）。部分错误只把码写进 `msg`（如薪资冲突、配置冲突），前端只能拿到 `msg` | 解包时区分顶层 `errorCode`、`msg`、`errors`；不把 `code` 当业务码展示；预览／建店类接口为合成码留「通用校验失败」兜底 |

**统一解包口径**：没有第五类载体。文案通道为 `errorCode → 后端 msg`，**后端 `msg` 优先**（同一 `errorCode` 在不同抛出点文案不同，且含动态变量，不可硬编码）；`errors` 单独走「`ValidationError` 字段级校验回填」通道，不作业务码兜底、不写 code 解析。按响应**形状**分派，优先级为 `fundResult`（原请求恢复）> `preview`（重新试算）> `shortfalls` / `remaining_amount`（差额说明与输入上限）> 429 限流 > 通用 `errorCode`。`data` 字段恒存在但可能为空对象，必须按字段判断而非按对象真假；仅退款异常路径填充 `data`。

请求层已保证 `ApiError.message` 就是后端 `msg`（429 用 `retry_after` 生成倒计时文案），因此**界面不为任何 `errorCode` 硬编码文案**：共用错误组件只按响应形状决定动作类型、在 `msg` 缺失时给通用兜底、并决定主动重拉哪个端点；完整中文 `msg` 全集只作兜底文案参考，不编译进界面。前端请求层已按此解包，缺口在**界面呈现**。

**三类共用反馈组件（界面定义，不新增页面）**：

| 组件 | 承载 | 呈现 |
|---|---|---|
| 通用错误提示 | `errorCode / msg / errors` | 就近错误条 + 重试；有字段错误时回填到对应控件；不吞掉 `msg` |
| 限流提示 | 429 专用载荷 | 倒计时 + 峰谷／动作说明 + 禁用触发动作；`retry_after` 至少 1 秒，`Retry-After` 响应头可用；倒计时结束前保留表单与草稿 |
| 资金结果提示 | `fundResult` / 预览 / 差额 | 原金额与凭证、重新试算、差额说明；优先于通用错误呈现，避免把「已受理待核对」显示为失败 |

**限流统一交互**：429 携带 `retry_after`、`Retry-After` 响应头、`traffic_mode`（`peak` / `valley` / `normal`，由配置化峰谷时段判定）、`traffic_action`（`pool` 抢单池 / `create` 下单 / `quote` 报价 / `grab` 接单）。

- 显示倒计时，期间禁用触发动作，不自动高频重发；区分订单限流与一般限流，前者靠近对应入口说明当前峰谷与动作。`traffic_mode` 必须**按后端返回值展示**（服务端按配置化峰谷时段判定），禁止前端用当前时间自行计算峰谷，避免与服务端限额不一致。
- 「自主下单关闭」是配置结果（403，无 `errorCode`，返回 `self_order_enabled=false`），不是限流；两者文案与下一步不同，不得混用同一提示。
- 倒计时只作展示，能否提交仍以服务端为准。

## 3.5 结果未知与幂等恢复（Pending）

这是本系统资金与履约体验的核心状态，界面必须完整保留原请求上下文：

- **Pending 卡片内容**：原金额／积分／凭证、原申请名称、原请求编号、原对象、当前阻塞状态（blocked 时禁用重试）、核对入口、原请求重试、查看记录、联系客服。
- **锁定范围**：禁止新建重复交易或重复下单；重试只沿用原请求；核对结果明确前不显示成功态、不播放成功动效。
- **跨页／跨会话**：按门店、角色、账号隔离保存；切换门店或退出后不得把原店待核对请求带入新店；恢复入口在首载失败与列表门控之外常驻。
- **后台集中待核对**：`trackReview` 在请求前按门店与身份保存结果待核对记录；业务字典、配置、审核、资金写操作统一纳入；网络／408／409／429／5xx 一律不当成功。
- **聊天场景**：原 `client_message_id` 查询状态；缺本机图片禁重传；放弃核对的最终确认须说明「可能已送达」的后果。

## 3.6 不可逆操作确认

| 要素 | 定义 |
|---|---|
| 触发 | 取消订单／预约、退款、驳回、封禁、停用门店、删除资源、放弃本地发送核对、覆盖最新交付资料、退出登录 |
| 确认内容 | 明确的**金额 + 对象 + 后果**（如订单号、服务、退款口径、券返还、押金、收款账户方式／姓名／账号） |
| 视觉 | 最终确认用 `destructive`；入口可为 `outline` 并带风险文字；不把支付行为一律标红 |
| 结构 | 标题与关闭区 / 可滚动正文（信息格呈现）/ 固定底部操作区；提交中禁用字段与确认并显示「处理中…」 |
| 草稿保护 | 关闭已修改表单前确认放弃；结构增删／排序用草稿快照判断；纯预览 Tab 不视为修改 |
| 版本 | 提交携带 `expected_version` / `expected_details` / `expected_status` / `terms_snapshot`；冲突时允许复制草稿、读取最新、确认替换 |

## 3.7 派单状态与关键信息易读

### 3.7.1 多状态并存

订单同时存在**履约状态**（5 值）、**支付状态**（4 值）、**派单路径**（公开／客服）、**报名／选中状态**、**报单状态**、**售后状态**（OPEN / RESOLVED / REFUNDED / PARTIALLY_REFUNDED）、**结算状态**（已结算／待结算／冻结中／已转出）。界面必须分层呈现，避免用一个颜色概括全单：

```
[强] 订单状态 Hero：状态文案 + 时间 + 34px 金额（实付 / 待核对分别标注）
  ├─ [中] 支付状态标签 + 派单路径（弱元信息）
  ├─ [中] 报名 / 履约 / 报单 / 售后 / 结算 各自独立状态标签
  └─ [弱] 时间线：真实时间戳 + 阶段名，付款未知不展示假履约事件
```

### 3.7.2 状态可视化规则

- **状态标签**：文字 + 语义色 + 可选图标，4px 圆角，内部居中；颜色不得单独承载含义。
- **进度**：订单履约、预约转单、权益交付、报单审核使用阶段进度或时间线；节点为 10px 圆点，最后节点强调，事件全部来自真实时间戳。
- **关键金额**：实付、退款、预计收益、核定金额、冻结、税额、实付人民币打款分开标注，不把「预计收益」显示为「已到账」，不把 `APPROVED` 显示为 `SETTLED`。
- **时钟**：72 小时售后窗口、预约确认与支付时限、通行证有效期、TAG 到期、待接单时限均显示真实北京时间与剩余时间；倒计时只作展示，不代替服务端判定。
- **终态**：`COMPLETED` / `CANCELLED` 订单与 `REJECTED` / `CANCELLED` / `CONVERTED` / `EXPIRED` 预约为终态，隐藏不可操作按钮，按 `allowed_actions` 呈现关联订单、重新预约或评价。
- **只读与禁用**：未授权游戏账号、已选人数已满、并发订单达上限、资格不满足、余额不足、钱包停用、活动未开启等均给出原因与下一步。

## 3.8 实时反馈

- WebSocket / 消息事件只作为**失效提示**，触发 HTTP 局部重读，载荷不直接作为账务或状态结果；HTTP 开发环境 `ws`、HTTPS 部署 `wss`。
- 按当前业务页、运营 Tab、门店与账号过滤事件；无关事件不触发读取；不按固定周期重读整页或健康队列。
- 重连、窗口重新可见时执行局部核对；断线恢复保留原筛选、滚动与草稿；同店换号／重登／退出／跨店使旧请求失效。
- 提示音：接单、后台派单、消息各自可开关并试听一次；正常通知静音、去重、门店会话隔离；应用内主音量默认 100%，不控制系统音量。
- 通知与私图：未读数、已读边界、私图续签、无权限签名与错店拒绝均有明确状态；通知不得发往真实外部接收人（隔离环境边界）。

## 3.9 反馈组件选择矩阵

| 组件 | 适用 | 不适用 |
|---|---|---|
| 内联说明 / Explanation | 字段旁规则、金额口径、必要但次要的说明，可点击／可聚焦 | 不可逆后果、失败恢复步骤 |
| Toast | 保存成功、已复制、轻结果，附真实回执 | 错误恢复、资金结果未知 |
| ActionFeedback / Notice | 动作失败、局部错误、重试，靠近触发点 | 整页首次失败 |
| 错误卡 / ErrorSurface | 首次读取失败、整页或整区失败 | 局部子资源失败 |

## 3.10 文案与信息密度

- 页面标题说明当前任务；压缩重复说明；只保留必要的业务结果、金额与错误。
- 次要规则收进关联字段旁可点击／可聚焦的说明；移动端不依赖悬停即可查看。
- 状态文案与服务端枚举一一对应，不自造同义词；「已通过」不得写成「已到账」，「暂估」不得写成「已确认」。
- 金额、编号、时间、对象名称完整呈现，不裁切；长标题完整换行。
- 明确标注「本页」的统计才从当前列表汇总，全量总数取接口 `total`；不复制原型演示的全店统计。
- 隔离验收环境、模拟数据、未启用能力、待开放功能必须在界面上明确标识，不得当作真实业务结果。

**文案预算（后台优先执行，见 2.6.4）**：标语 0；页面级说明 ≤1 条且可收起；次要标签只保留状态 / 单位 / 数量三类；字段级规则收进可点击、可聚焦的说明。错误、不可逆后果、资金口径、结果待核对恢复说明是例外，必须直接可见。

**遮罩测试**：遮住所有标语、提示文字与次要标签后仍能看懂并完成主任务的页面才算通过；做不到就改布局（列名、分组、默认值、位置、空态、状态标签），而不是补说明。这条裁决优先于任何装饰性视觉（1.11）。

## 4.2 状态流转 → 界面状态映射

### 4.2.1 订单状态机（服务端白名单，界面不得越权展示动作）

| 从 → 到 | 触发动作 | 三端界面 |
|---|---|---|
| `PENDING → GRABBED` | 抢单／派单 | 陪玩「确认接单」、后台「指派／转单」；仅已支付订单可进入，支付证据待核对禁止派单 |
| `PENDING → CANCELLED` | 取消 | 老板取消订单确认、后台取消；含券返还与退款口径 |
| `GRABBED → IN_SERVICE` | 开始服务 | 陪玩「开始服务」、上传入队凭证 |
| `GRABBED → PENDING` | 拒单／退回池 | 陪玩「拒单」+ 原因，订单重回待接单池 |
| `GRABBED → CANCELLED` | 取消 | 取消确认与退款预览 |
| `IN_SERVICE → COMPLETED` | 完成服务 | 陪玩「完成」、结单／战绩凭证；需满足房间确认与报单时限快照 |
| `IN_SERVICE / COMPLETED → CANCELLED` | 退款 | 售后退款、协商退款；`COMPLETED` 退款需显式允许已结算退款 |
| 终态 | `COMPLETED` / `CANCELLED` | 隐藏状态迁移按钮，仅保留评价、赠礼、客服、查看关联 |

界面规则：**动作集合由 `allowed_actions` 决定**，前端不依据状态自行推断可做什么；付款未知时隐藏派单进度并锁定危险动作；`REJECT` 回到 `PENDING` 的订单应在接单池中重新出现并保留真实原因。

**权威来源**：合法转换白名单为 `orders/state_machine.py` 的 8 条 `TRANSITIONS`；操作日志枚举为 `orders/models.py` 的 12 项 `OrderStatusLog.Action`（`CREATE` / `GRAB` / `ASSIGN` / `START` / `COMPLETE` / `REJECT` / `CANCEL` / `REFUND` / `NEGOTIATED_STOP` / `TRANSFER` / `AUTO_CANCEL` / `TEAM_WORKFLOW`）。历史迁移文件不是状态权威来源。**界面时间线由后端 `action_display || action` 数据驱动渲染**，前端不硬编码 12 项枚举，也不自行推断「人工 / 系统」；系统自动触发的事件按服务端展示字段区分。

### 4.2.2 其他状态机映射

| 对象 | 流转 | 界面要点 |
|---|---|---|
| 预约 | `PENDING → CONFIRMED / REJECTED / CANCELLED / EXPIRED`；`CONFIRMED → CONVERTED / CANCELLED / EXPIRED`；四类终态不可再流转；`ACTIVE_STATUSES = {PENDING, CONFIRMED}` 占用档期 | 待确认不显示「成单」；仅 `CONVERTED` 那一刻扣款建单；转单前必须取最新报价并校验 `expected_service` / `expected_amount` |
| 预约席位 | `VACANT → PENDING → CONFIRMED` | 双陪选人进度、队友确认、满员禁止追加 |
| 报名 | 等待老板选择 / 已选择 / 未选择 / 已撤回 / 队友待确认 / 报名结束 | 报名历史与详情，不把历史当可接单 |
| 报单 | `DRAFT → PENDING → APPROVED / REJECTED` | 「已通过」不等于「已结算」；驳回保留原文与重新提交入口 |
| 提现 | `PENDING → STORE_APPROVED / REJECTED / CANCELLED`；`STORE_APPROVED → PLATFORM_APPROVED → PAID / PAYMENT_UNKNOWN`；兼容 `APPROVED` | 门店初审与平台终审分离；`PAYMENT_UNKNOWN` 显示结果待核实；驳回精确还原余额与冻结 |
| 权益交付 | `PENDING → FULFILLING → COMPLETED / CANCELLED` | 完成后资料只读；TAG 审核／暂停；取消说明积分返还 |
| 售后 | `OPEN → RESOLVED / REFUNDED / PARTIALLY_REFUNDED` | 72 小时窗口、`RESOLVED` 不是 `OPEN`、退款与实销分别回读 |
| 陪玩接单 | `AVAILABLE / BUSY / OFFLINE` | 开关只发本人显式操作；`BUSY` 显示忙碌但可明确打开到 `AVAILABLE`；渲染不自动写 `OFFLINE` |
| 门店 | `PROVISIONING → CONFIGURING → ACTIVE ↔ DISABLED` | 非 `ACTIVE` 不得呈现为可营业；默认店禁停；新店不复制他店账户与资金 |
| 审核类 | `PENDING → APPROVED / REJECTED` | 注册、试音、评价回复共用状态语义但文案按业务区分（如注册为「需补充资料」） |

### 4.2.3 由系统自动触发的状态变化

定时任务驱动的状态变化不属于任何用户的界面动作：待接单超时自动取消、预约过期、收益到期释放、实销确认、售后窗口暂停与恢复、押金与通行证到期、试音链接过期、转盘与签到周期切换等。界面定义：

- 时间线中按 `OrderStatusLog.Action` 的 `AUTO_CANCEL` 等枚举区分「系统自动」与「人工操作」，并显示真实时间戳。
- 显示真实北京时间与剩余时长；倒计时只作展示，不代替服务端判定，也不在客户端自行改变状态。
- 自动变化通过实时事件触发局部重读，不提供对应的用户动作按钮；相关站内通知按真实事件呈现。
- 自动触发不得覆盖用户正在编辑的草稿，也不得重复记账、重复发放权益或重复发送通知。

## 4.3 接口约束 → 界面行为

| 约束 | 界面必须遵守 |
|---|---|
| **域名即门店边界** | `sl.esports.club/boss` / `sl.esports.club/player` → 声浪电竞；`xa.esports.club/boss` / `xa.esports.club/player` → 兴安电竞；`admin.esports.club` 独立管理入口。界面不提供门店切换按钮改变业务身份；未知域名不回落默认门店；门店切换器只做公开目录选择并整页进入目标店登录页 |
| **认证差异** | 老板端仅微信快捷登录（网页扫码 + 最小桥接页完成身份／手机号／短信确认）；陪玩端与后台为账号密码 + 动态验证码（TOTP）、首次绑定初始化与恢复码；三端会话按角色与门店隔离，不允许老板令牌进入陪玩端或后台 |
| **统一响应信封** | 成功与失败按服务端 `code` / `errorCode` / `msg` / `data` 解析；HTTP 401 单次刷新、刷新失败退出、迟到响应不复活旧会话；业务错误显示服务端文案与可执行下一步 |
| **权限点** | 后台菜单、按钮、详情字段、行操作、链接可见性由 `模块:动作` 权限点驱动（如 `order:dispatch`、`report:audit`、`withdraw:audit`、`salary:confirm`、`roi:view`、`engagement:fulfill`）；查看权与写权分离；独立删除权限单独判断 |
| **幂等与版本** | 资金、兑换、抽奖、派单、审核、消息发送使用稳定 `client_request_id` / `client_message_id`；编辑提交携带 `revision` / `expected_version` / `expected_details` / `expected_status` / `terms_snapshot` / `expected_updated_at`；重复原请求不重复扣款、建单、发消息或结算 |
| **结果未知** | 网络中断、408 / 409 / 429 / 5xx 一律进入待核对；保存原凭证与金额；后台按门店与身份集中登记待核对记录；不得乐观显示成功 |
| **分页与筛选** | 列表使用服务端 `page` / `page_size` 或游标 `before`；筛选参数只使用服务端已支持项；服务端未支持的筛选控件标待开放，不在当前分页内做伪全局过滤；真实总数取接口 `total` |
| **限流与配额** | 登录、短信、验证码、写操作可能返回 429；界面显示冷却与重试时机，不自动高频重发；查询预算不允许逐单 N+1 放大 |
| **私有媒体** | 陪玩证件、报单凭证、充值凭证、聊天图片使用短时签名票据；界面提供加载骨架、续签、失败重试与无材料状态；过期或错店一律拒绝，不缓存跨店图片 |
| **实时通道** | WebSocket 事件（订单状态、派单、预约、报单、钱包、通知、权益、聊天等）只触发局部重读；按门店、角色、账号、当前业务区过滤；HTTP 用 `ws`、HTTPS 用 `wss`；断线重连与可见性恢复各有局部核对 |
| **明确不存在的接口能力** | 无 `/api/v1/` 版本前缀、无 ETag、无 GraphQL、无独立抽成试算接口、无全量运营聚合接口、无公开试音招募列表、无结构化「擅长位置／声音标签／自由档期」字段；界面按待开放处理，不伪造请求或结果 |
| **特性开关** | 积分服务支付、直接支付／退款投递、房间协商等开关默认关闭；关闭时相关入口不呈现为可用业务，不得标为已上线 |
| **支付能力边界** | 系统**没有在线支付 API**：`POST /api/wallet/topup/` 固定拒绝，微信支付 v3 相关代码仅限测试且无生产端点；老板充值走线下企微客服收款，后台按 1:10 兑换人工入账；订单用门店币余额支付；押金是内部账务划转。界面不得出现收银台、支付渠道选择、支付中轮询或支付结果页；「充值」一律表述为「联系客服充值」，到账以钱包余额与流水为准 |
| **错误响应分两类** | ① 视图内字面量 `errorCode`；② 异常对象的 `code` 动态透传，且可能带 `data` 载荷（剩余可退金额、缺口、预览）。退款、补贴协商、逐段退款、配置变更以第二类为主，两者合起来才是完整错误码集合 | 界面按 `errorCode` + `data` 共同渲染：给出可执行下一步，必要时提供重新试算；不把带预览的失败折叠成通用错误，不硬编码完整错误码表 |

**权限数据源（不可由界面推断）**：登录响应 `profile.permissions[]`（多角色启用权限并集）+ `is_superuser` + `roles[]` 进入 `admin/src/lib/auth.ts::hasPerm`；`App.tsx` 中的路由→权限码映射只是前端硬编码的菜单映射，不是权限来源。角色权限树页面（`/roles`、`/admins`）按 `GET /api/admin/permissions` 返回的 `PERMISSION_GROUPS`（约 30 组 `模块:动作` + 中文标签）分组呈现，与后端 ViewSet `required_perms` 使用同一份 code。

### 4.4.3 门店隔离的界面体现

- 顶栏显示当前门店真实名称与币名（浪花／星辉）；薪资、投流、成本、费率、人民币打款始终显示人民币。
- 切店确认后整页重载，清理旧 hash、订单详情、表单草稿、未确认请求、消息草稿与实时订阅；不携带原店令牌或 Cookie。
- 同数字 ID 在不同门店是不同对象；详情链接只使用明确的业务 `account_id`，不猜测 legacy `user_id`。
- 未知／停用／待初始化门店显示阻断或状态提示，不挂载业务页面、不读取默认门店数据。
- 私有媒体、通知、WebSocket、图片续期与异步任务全部校验门店上下文；撤权后旧连接不继续泄露数据。

## 4.5 金额与口径

| 口径 | 界面规则 |
|---|---|
| 门店币 | 服务端整数账务单位换算为浪花／星辉；币名取当前门店元数据；不硬编码 |
| 人民币 | 薪资、投流、其他经营成本、支付费率、现金押金、提现实际打款、会员实销单独标注「元」；不与门店币混用 |
| 折扣链 | 原价 → 老板等级折扣 → 活动折扣 → 券抵扣 → 实付，逐项可见；双陪整套餐价不按单人重复乘除 |
| 抽成与收益 | 抽成率来自系统配置（缺省回落默认值）与商品／等级快照；订单拆账守恒；陪玩显示净额，不把预计收益当已到账 |
| 退款 | 普通／部分／协商退款、券返还、推荐佣金追回、转出个人收益、礼物退款分别列示；退款后不显示旧预计收益 |
| 提现 | 最低金额、税率（默认 2%）、税额、预计人民币打款由服务端试算；实付与冻结精确区分 |
| 结算 | 报单 `APPROVED`、订单 `COMPLETED`、实际入账、实销确认四件事分别回读；72 小时售后／冻结窗口显示真实北京时间 |
| 经营核算 | 净订单消费、投流投产比、经营 ROI 区分暂估与已确认；缺成本、未归属佣金、未确认薪资时显示缺口警告，不给虚假完整 ROI；充值本金与押金不计收入 |
| 薪资 | 岗位薪资与后台权限角色独立；夜班按配置的北京时间固定时段自动判定；考官每次 50 元为抽成前金额，扣 30% 后实得 35 元；核算只登记成本，不执行工资转账 |
| 充值与支付 | 无在线支付与收银台；充值由线下企微客服收款后后台人工入账（1:10 兑换），充值本金不计入订单收入；订单支付为门店币余额扣减；退款、券返还、佣金追回各自成账；人民币现金押金与门店币不混用 |
| 单位换算 | 门店币按 10 个账务单位 = 1 浪花／星辉显示；人民币由 `formatRmb`（元，100 单位 = 1 元）与 `formatRmbFen`（分）分别格式化；投流、薪资、成本、费率使用人民币；三端统一显示口径，不在界面自行换算 |
| 转盘与会员 | 转盘概率按万分比合计 10000、`expected_version` 乐观锁、单次／十连与日限额；保底阈值由服务端按目标奖项概率计算（`max(1, ceil(10000 / target_probability))`），**不是固定次数**；`draw_count` 来自服务端结果随机的十分之一，不由客户端累计；结果以服务端批次为准。会员等级只升不降，按会员周期与真实实销累计，展示当前等级／差额／下一等级；积分倍率与赛季配置取服务端字典 |
| 分段结算 | 按已确认段分摊收益、未确认段不计收入；功能开关默认关闭，关闭时相关界面不作为可用能力呈现 |

## 4.10 后台线下充值相关界面（领域层补充）

## 5.5 状态与错误契约

| 契约 | 规格 | 开发断言 |
|---|---|---|
| 14 类统一状态 | 3.1 的状态词汇与优先级 | 同一状态在三端同文案同强度；资金类状态优先于普通视觉状态 |
| 错误解包 | 4 类载体；文案 `errorCode → 后端 msg`（`msg` 优先、动态不硬编码）；`errors` 走字段级回填 | 不为任何 `errorCode` 硬编码文案；`data` 恒存在但可能为空，按字段判断 |
| 形状分派 | `fundResult` > `preview` > `shortfalls` / `remaining_amount` > 429 > 通用 `errorCode` | 带预览的 4xx 提供「重新试算 / 返回修改」；不折叠成通用错误 |
| 限流 429 | `retry_after`（≥1 秒）、`Retry-After` 头、`traffic_mode`（后端返回，不前端算）、`traffic_action` | 倒计时期间禁用触发动作、不自动高频重发；区分订单限流与一般限流；「自主下单关闭」是 403 配置结果，不混用 |
| 幂等与版本 | `client_request_id` / `client_message_id`、`expected_version` / `expected_details` / `plan_token`、结果待核对 | 重复原请求不重复扣款／建单／发消息；失败不清空输入与草稿 |
| 反馈组件 | 通用错误提示、限流提示、资金结果提示（3.4.1） | Toast 不承担错误恢复；错误靠近触发动作；成功用真实回执 |

## 5.6 交互动效与性能预算

| 项 | 规格 |
|---|---|
| 时长 | hover / active / focus 160ms `ease-out`；状态切换 200–300ms；弹层 300ms；实时事件合并 350ms |

| 降级 | `prefers-reduced-motion` 与持久「减少动态」直接呈现结果；`prefers-reduced-transparency` 与低性能／高对比模式玻璃退化为实色 + 1px 描边（需实测浏览器支持） |
| 玻璃预算 | 同屏玻璃层数受限；长列表、宽表、虚拟列表用实色；顶栏与 Dock 可常驻；不随滚动实时重采样 |
| 布局稳定性 | 全高用 `min-h-[100dvh]`；图片与骨架预留空间；目标 CLS < 0.1、INP < 200ms、LCP < 2.5s |
| 层级 | 5.1 的 z-index 契约；禁止随意 `z-50`；噪声／颗粒只用固定且 `pointer-events: none` 的伪元素 |

## 5.7 常见 UI 设计边界（反模式清单）

| 类别 | 禁止 |
|---|---|
| 色彩 | 纯黑、霓虹／外发光、AI 紫渐变、过饱和强调色、多个强调色、颜色单独承载状态、用红绿表达资金增减、状态色用于装饰 |
| 排版 | 后台使用衬线、换用 Geist/Satoshi/Inter、小于 12px 的文字、渐变文字大标题、emoji 当作图标、全大写小标签堆叠、装饰性编号 eyebrow、界面文案用装饰性破折号 |
| 布局 | 元素重叠、整页横向溢出、`h-screen`、placeholder 当标签、纯图标无文字、装饰状态点、三列等宽营销式卡片（后台指标网格除外，且须一致）、无必要的通用卡片包裹高密度数据 |
| 内容 | 示例账号／余额／订单／头像、假二维码、假精确数字、未标识的模拟数据、把隔离验收环境当真实业务、为解释不清楚而追加标语 |
| 反馈 | Toast 承担错误恢复、乐观显示成功、静默失败、空白页、禁用态不说原因、把结果未知显示为失败或成功 |
| 无障碍 | 低于 44px 的手机触控、低于 4.5:1 的正文对比、无 `focus-visible`、键盘不可达、表格横滚容器不可聚焦、忽略 200% 缩放与减少动态 |
| 业务 | 前端自行推断 `allowed_actions`、本地演算金额或统计、跨店合并数据、把待开放做成可点击占位、把审核通过当已结算、把暂估当已确认、把充值本金当实销 |

## 5.9 设计 QA 与验收清单（可勾选）

- [ ] **视觉一致性**：共享令牌唯一来源；无硬编码颜色；单一圆角系统；两模式对比度达标；玻璃近似已标注且有无模糊回退。
- [ ] **组件状态**：每个交互组件实现默认 / hover / active / focus / disabled / busy；骨架几何匹配；空与失败严格区分。
- [ ] **后台画像**：5.4.6 全部通过；私有字段不下发；待开放字段不伪造；遮罩测试通过。
- [ ] **业务串联**：下单 → 派单 → 报单 → 审核 → 结算 → 退款／提现在三档 License 下逐档可完成；`allowed_actions` 由服务端决定；详情返回位置与草稿保留。
- [ ] **数据口径**：金额按 4.5；实销与充值本金、暂估与已确认、`APPROVED` 与已结算分开；统计总数取接口 `total`；跨店不合并。
- [ ] **权限与门店**：菜单按 `permissions[]` 过滤；无权深链走 `/403`；平台⇄门店切换 5 态；切店后无旧店数据／草稿／订阅／未确认请求残留。
- [ ] **可访问性**：44px 触控、4.5:1、focus-visible、键盘全可达、200% 缩放、表格可聚焦横滚、减少动态、读屏标签完整。
- [ ] **性能与降级**：只动画 `transform` / `opacity`；同屏玻璃层数受控；长列表实色；CLS / INP / LCP 达标；`min-h-[100dvh]`。
- [ ] **内容诚实**：无假数据／假二维码／假精确数字；模拟数据与隔离验收环境明确标识；无误导性标语与重复说明。
- [ ] **文案自审**：逐条复读界面可见文案，无语法错误、无空洞营销词、无「看不懂靠提示补」的区块；错误文案提供可执行下一步。
- [ ] **回归基线**：三端类型检查与生产构建、共享测试、双店逐页读取、真实隔离链路；视觉演示数据不作为业务通过证据。
