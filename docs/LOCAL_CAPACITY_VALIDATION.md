# WSL 本地在线规模与热点查询验证

日期：2026-09-23。目标场景来自用户提供的高峰人数：100 名老板、50–60 名陪玩。本记录验证本机容器中的 100 老板 + 60 陪玩协议负载，不能替代腾讯云目标机器、真实网络和长时间稳定性验收。

## 环境与可复现方法

WSL 2 / Ubuntu 24.04，分配 4 个处理器、4 GB 内存；MySQL 8.0.46、Redis、Daphne、Celery、Caddy 及 H5，沿用 [本地部署记录](LOCAL_DEPLOYMENT_VALIDATION.md)。前几轮使用单个 Web 容器，最后一轮使用两个同镜像的 Web 实例，其余资源配置不变。压测程序运行在 Windows Node 24，经 `127.0.0.1:18080` 网关访问 WSL；没有绕过 HTTP 鉴权或改大 MySQL 连接上限。

```powershell
node scripts/verify-local-capacity.cjs
```

要求已启动本项目的 `XA-Ubuntu-24.04` 发行版和 local-validation 编排，已安装仓库开发依赖。脚本只允许本地 MySQL `xa_verify`，核对外部渠道开关已关闭；不支持传入任意远程目标。`--legacy-push` 用于复现修复前的逐条推送刷新方式，可能触发本机过载，只用于本地对照。

负载包含：

- 20 人（12/8）、80 人（50/30）、160 人（100/60）三个阶段，目标持续时间分别 20、20、60 秒，等待在途请求完成会延长实测阶段。
- 每人独立业务 JWT 和 WebSocket 连接，持续心跳；每个模拟客户端最多 6 条并行 HTTP 连接。HTTP 读请求采用闭环，每次返回后间隔 5 秒，初始错峰。
- 老板轮换浏览玩法、完整套餐目录、可选陪玩、订单和钱包；陪玩轮换读取公共池、看板、钱包、报单。
- 160 人阶段，10 名老板同时各发送两次相同请求编号的下单请求，验证每人只生成一单，再通过实际接口取消。60 名陪玩接收创建/取消广播，按陪玩端实际刷新调度器重新查询。
- 陪玩测试档案设置为黑卡，以立即读取公共池。通行证价格、延迟及其他业务配置未修改；不同档位的功能校验另见业务验收。
- 超过 20 个错误停止产生新的浏览压力，但会处理已发请求和本次未取消订单，核对全部测试钱包及流水。结果写入 `.tools/capacity/<run>.json`，不包含 JWT 或密码。

脚本是协议客户端，未启动 160 个浏览器。延迟从取得客户端连接槽位后开始，包含 HTTP 响应及解析，不含模拟浏览器槽位排队时间；报告同时记录并发量和实测 RPS。该闭环模型会随服务器变慢自动降低发起速率，不是恒定 RPS 极限测试。

## 已发现的问题及修复

最新版本数据见下文“实时权限修复后的复验”；本节及原“双实例复验结果”保留此前定位和优化过程。

初次探测出现 MySQL `Too many connections`，最高连接数触及默认 151 上限。将客户端并发限制到每人 6 条后仍能复现：对照运行 `4aeae20c090c` 在 160 人阶段 1,460 个请求中有 262 个错误，p95 为 13,485 ms；达到停止条件后没有跑满目标时长。10 单最终均取消，160 个钱包余额与流水核对通过。

陪玩订单页原本对每条公共广播同时查询订单和个人看板，连续状态变化不断增加并行请求。现已：

1. 合并 300–500 ms 内的连续推送，同类刷新最多一笔在途；期间再收到变化时，结束后补读一次最新数据。计时不会被后续消息无限推迟。
2. 公共池简要消息只更新订单列表；本人订单的完整通知继续更新个人看板。
3. 页面卸载释放待执行刷新，失败后可处理后续通知。定时检查通行证可见窗口继续保留。

只修复前端后的运行 `2d3bf7059ec5` 已达到 160 条连接、零错误且推送和账务检查通过，但 160 人阶段 p95 仍达 7,326 ms，因此继续优化热点接口。

真实 MySQL 查询剖析结果：

| 页面查询 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 61 名可选陪玩 | 128 次 | 7 次 |
| 1 笔待接单 | 17 次 | 9 次 |
| 5 笔待接单 | 33 次 | 9 次 |
| 10 笔待接单 | 53 次 | 9 次 |

陪玩列表批量读取档期，通过子查询复用已有接单名额规则；订单列表预加载关联资料和当前查看者的分账，并在单次响应中共用陪玩准入状态。没有跨请求缓存：下一次读取仍会检查新的档期、押金、资格和名额。实际抢单、派单、扣款继续在原事务和锁内校验。

查询剖析在回滚事务中进行，临时订单、余额与状态变更均未提交，提交后通知也未触发。记录为 `.tools/wsl-setup/capacity-queries-before.log` 和 `capacity-queries-after.log`。

## 双实例复验结果

查询优化后，单实例运行 `65ac2829f114` 无错误，但 160 人阶段 p95 仍为 5,164 ms；采样时 Web CPU 约 122%，MySQL 约 30%，存在大量在途请求。改为两个 Web 实例后，以相同脚本和刷新方式复验，运行 `958fa0009565` 结果如下。

| 阶段 | 请求数 | 实测 RPS | 错误数 | p50 | p95 | p99 | 最大响应 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 人 | 80 | 3.67 | 0 | 32 ms | 94 ms | 131 ms | 131 ms |
| 80 人 | 320 | 13.02 | 0 | 34 ms | 99 ms | 108 ms | 160 ms |
| 160 人 | 2,058 | 31.66 | 0 | 42 ms | 549 ms | 790 ms | 911 ms |

160 人阶段包括 60 秒发起窗口及在途等待，实测约 65 秒。160 条连接均有心跳回复，60 名陪玩均收到 10 单的创建和取消状态；10 组重复下单只生成 10 笔订单，最终全部取消，160 个钱包和流水核对通过。报告 `.tools/capacity/958fa0009565.json`，日志 `.tools/wsl-setup/capacity-two-web.log`。

同一场景的主要对照为：

| 配置 | 160 人阶段 p95 | 请求错误数 |
| --- | ---: | ---: |
| 原逐条推送刷新，单实例 | 13,485 ms | 262（触发提前停止） |
| 合并推送刷新，单实例 | 7,326 ms | 0 |
| 合并刷新及查询优化，单实例 | 5,164 ms | 0 |
| 上述优化及双实例 | 549 ms | 0 |

这是同一闭环场景的对照，实际请求数量会随响应及推送合并次数变化，不能当作恒定负载的吞吐倍数结论。双实例大幅降低了本轮延迟，但总 p95 仍高于部署方案中建议的 500 ms 读取目标，且没有执行 50 RPS、30 分钟的正式基线；因此不标记生产容量验收通过。

本地及 release 编排均固定两个 Web 副本，使用 Caddy 的动态 A 记录逐个解析内部实例并轮询分配请求，Web 不绑定固定宿主端口，Beat 仍只有一个。依据 [Caddy 动态上游与负载均衡](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#dynamic-upstreams) 和 [Compose 副本配置](https://docs.docker.com/reference/compose-file/deploy/#replicas)，已用实际 Docker/Caddy 解析验证配置。未部署腾讯云或申请公网证书。

实际 Web 日志统计显示两个实例分别处理 1,257 / 1,252 次 GET、各 15 次 POST，分别有 84 / 80 次 WebSocket 连接（包含本机其他连接）；未见数据库连接耗尽、死锁或 HTTP 5xx，原始含 token 的日志未输出。采样时两 Web 内存约 176 / 166 MiB，MySQL 约 846 MiB；这是时点数据，不是峰值。MySQL 全局历史最大连接数 152 来自较早失败探测，不代表本轮达到该值。

## 实时权限修复后的复验

在 [实时权限修复](LIVE_AUTHORIZATION_AUDIT_20260923.md) 部署后重新运行同一容量脚本，验证每次心跳及推送前读取当前账户状态的成本。2026-09-23 20:40 开始，运行 `3b529e54eeef`，仍为两个 Web 实例、4 CPU / 4 GB 的 WSL 和原数据库连接上限，未为本轮放宽权限校验或修改业务规则。

| 阶段 | 请求数 | 实测 RPS | 错误数 | p50 | p95 | p99 | 最大响应 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 人 | 80 | 3.68 | 0 | 32 ms | 97 ms | 116 ms | 116 ms |
| 80 人 | 320 | 13.03 | 0 | 34 ms | 96 ms | 108 ms | 154 ms |
| 160 人 | 2,936 | 45.25 | 0 | 95 ms | 730 ms | 904 ms | 1,696 ms |

160 人阶段实际约 65 秒，峰值在途 HTTP 请求 83 个，160 条连接均收到心跳回复。60 名陪玩均收到 10 笔订单的创建和取消通知；20 次重复创建请求只生成 10 单，全部取消并退币。160 个测试钱包与流水核对通过，测试账号及展示夹具已停用，保留订单与资金记录。报告为 `.tools/capacity/3b529e54eeef.json`，过程日志为 `.tools/wsl-setup/capacity-live-auth.log`。

推送阶段一次采样：MySQL 当前连接 25 个，两 Web CPU 约 108% / 118%、内存 177 / 179 MiB；这不是峰值资源统计。结束后的六分钟 Web 日志窗口未出现连接耗尽、死锁、锁等待超时或服务端错误关键词。数据库全局历史最高连接数 152 沿用早期探测，不能归为本轮峰值。

本轮总 p95 为 730 ms，较早一轮的 549 ms 更高；但实际请求数也由 2,058 增加到 2,936，推送时序与合并次数不同，不能据此单独计算权限校验造成的耗时或吞吐变化。取消接口的 10 次请求约 1.65–1.70 秒，成功退币且没有超时。当前证据证明最新权限策略下的本地短时功能及并发正确性，**没有达到云端 50 RPS、30 分钟持续测试及建议的读取 p95 ≤500 ms 目标**，不能据此标记生产容量验收通过。

## 60 人争抢同一单

```powershell
node scripts/verify-local-grab-race.cjs
```

复用同样的隔离、黑卡资格及合成账号，通过实际网关同时发出 60 个独立陪玩请求。运行 `563ef518e593`：1 人成功，59 人收到业务冲突，无 HTTP/传输失败；订单 83 只有 1 个有效分账关系、1 条成功抢单日志，赢家账号与数据库一致。随后由赢家走拒单接口回池，再由老板取消退款；160 个测试钱包及流水核对通过，夹具已隐藏和禁用。报告 `.tools/capacity/grab-563ef518e593.json`，日志 `.tools/wsl-setup/grab-race-two-web.log`。这是独立并发场景，不计入上面的容量请求数。

## 边界

这里的初始余额属于标记清楚的本地测试调账，不涉及收款或真实转账。每轮数据按独立编号创建，结束后隐藏测试商品、陪玩和客服，禁用测试登录；订单、退款和流水保留复核。

完整履约、报单审核、结算、提现及真实微信登录的证据在本地部署记录中，本容量脚本只对下单和取消施加写入压力。未覆盖长期运营历史规模、文件上传高峰、弱网、移动端渲染、微信/KOOK/企微外部限流或长时间持续负载。正式服务器仍需按相同业务场景复验，不能把本机结果称为生产容量承诺。
