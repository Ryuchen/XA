# 微信直付预支付与关单：测试态设计草案

日期：2026-10-27。本文是设计和验收边界，不表示预支付、关单、真实微信支付或公开 API 已经实现。当前直付领域受测试开关限制；本方案不接真实商户、真实渠道、生产路由或后台调度。

## 现有事实与边界

- `orders/direct_payment.py` 的 `prepare_direct_order` 使用账号、请求标识和请求指纹恢复同一个订单意图；`DirectPaymentIntent` 保存商户订单号、商户号、AppID、OpenID、金额与付款凭证。
- `DirectPaymentIntent.status` 目前只有 `AWAITING`、`PAID`、`REVIEW`，其中 `REVIEW` 的数据库约束要求已保存渠道交易号和付款时间。预支付超时、查单中或关单不明不能滥用这个状态表示。
- `confirm_verified_payment` 只有在渠道证据、金额、身份和报价快照通过后才令订单已付并进入待派；现有超时和接单截止从付款确认后开始。支付截止必须是独立时间，不复用接单截止。
- `require_cancel_channel_confirmation` 已阻止未付款的直付订单经旧余额取消入口直接关闭。未来仅有本地取消意愿或收银台关闭，均不足以证明微信订单关闭。
- 微信下单、按商户订单号查单、关单的低层网关已经存在；它们没有公开路由。请求返回与已确认付款、已关闭是不同事实。查询和关单的原始签名响应持久化尚需实现。

## 数据和状态

建议新建一个与支付意图一对一的测试态 `DirectPaymentSession`，不重写订单履约状态或已有付款状态。以下是**操作状态草案**，具体名称可随实现调整：

| 状态 | 含义与可做的事 | 不得推断 |
| --- | --- | --- |
| `CREATED` | 意图和不可变请求快照已保存，能证明没有任何发送尝试。 | 不代表微信已创建订单。 |
| `PREPAY_SENDING` | 单次下单尝试已登记并持有租约，外部调用可能尚未完成。 | 租约有效或过期都不能证明请求是否到达微信。 |
| `PREPAY_UNKNOWN` | 请求、进程、验签或响应结果不明；只能用原商户订单号受控查单或人工核对。 | 不能换订单号，也不能把结果当失败。 |
| `PAYABLE` | 收到认证预支付响应，会话及订单均仍有效，且没有关闭意图。 | 不代表用户已付款。 |
| `CLOSE_REQUESTED` | 记录老板或授权客服的关闭意愿，不再向新请求发放支付参数。 | 已交付的旧参数仍可能在微信收银台生效。 |
| `CLOSE_SENDING` / `CLOSE_UNKNOWN` | 原订单号正在关单或关单结果不明；后续只做受控查单及核对。 | 不能以超时、`NOTPAY`、本地取消或收银台返回当作已关闭。 |
| `CLOSED_UNPAID` | 有与原订单匹配的可信渠道关闭及未付款依据，或能严格证明该意图从未发送。 | 不代表产生过退款。 |
| `REVIEW` | 订单、交易、关闭结果或证据矛盾，需要人工核对；保存事实并停止自动新付款、派单与重新下单。 | 不覆盖既有已付款、已退款或已履约事实。 |

付款成功仍通过既有验签支付证据进入独立的付款事实。若已提交关闭意愿后收到可信付款，应保留付款事实并进入待核对或受控退款，不因订单恰好还是 `PENDING` 就派单。若渠道已确认关闭后又收到与该单匹配的可信成功，两份证据都需留存，视为冲突；不能抹掉任何一方。

新会话应冻结意图 ID、商户号、AppID、OpenID、商户订单号、渠道总额/币种、订单报价哈希、描述、回调地址、`time_expire`、请求格式版本及请求哈希；支付参数、有效期等敏感值仅限授权主体读取并按安全策略保存。若策略或账号后来变更，不得拿新参数重发旧单。

建议另建不可覆盖的 `DirectPaymentOperation` / observation 记录，每次记录操作类型（预下单、查询、关单）、尝试 ID、请求快照哈希、租约 token 与期限、是否进入可能发送阶段、认证响应摘要及其受控保存位置、错误分类与时间。数据库保证同一操作尝试唯一，并在会话行锁内串行决定是否可开启新的写操作。不得仅靠字段命名或部分索引假设跨数据库正确。

## 预支付、恢复与关单流程

1. 在短事务中按固定锁序读取订单、意图和会话，验证所有者、账号周期、OpenID 绑定、商户/AppID、金额、报价、未付款和未关闭意愿。持久化发送尝试和租约后提交；随后在事务外发一次请求。
2. 在新的短事务中核对尝试 token、当前订单及会话状态，保存可信响应事实。有效预支付响应可用于同一意图的继续支付；不能仅因为前端 `requestPayment` 成功回调就认定付款。用户重进页面、换设备或本地缓存丢失时，先经授权从服务端恢复原意图，不能创建第二笔。
3. 外部调用超时、连接中断、进程终止、超限、未验签或 5xx 均为未知。租约到期仅触发恢复和查原号；不能证明旧请求没有发送或不会迟到。要重试预下单，必须依据可靠渠道状态和确认适用的官方同号重入规则，并保持原参数；若无法证明安全，保留人工核对。
4. 若意图有已登记的可能发送尝试，即使暂时查到订单不存在，也不能由此证明旧请求之后不会到达。只有可以证明完全未发送时，才可本地结束未付款意图；否则须依赖可信渠道最终状态或人工处理。
5. 老板提出关闭意愿后，先持久化关闭意图，阻止继续发放新参数。按原商户订单号查单：`NOTPAY` 仍可付款，需执行关单；`SUCCESS` 保留付款并按取消意愿进入复核；`CLOSED` 按可信关闭处理；退款、失败或身份不一致则核对。关单响应未知时继续查原号，不换号、不显示退款成功。
6. 外部响应可能在租约过期、另一个 worker 运行或用户付款后迟到。过期 token 不得覆盖当前操作状态，但已经认证的事实仍须持久留证并触发冲突核对，不能因 token 失效丢弃真实付款或关闭证据。

微信官方小程序文档说明：`prepay_id` 有效期两小时，过期后应使用原下单参数重新请求；用户返回小程序后需服务端查单，`NOTPAY` 仍可付款，关单后才进入关闭状态。[微信支付小程序开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)

有效期不能仅按本机收到响应的时间简单加两小时：渠道生成可能早于响应送达。应保存发送/接收时间，采用经过确认的保守截止并留安全余量；不同设备时间不可作为最终证据。`time_expire`、预支付会话有效期和付款后的接单期限分别保存。

## 锁序、网络边界和隔离级别

- 现有支付收件箱处理遵循 inbox → order → intent；退款遵循独立退款 inbox → order → intent → refund。新会话与尝试行应排在 order → intent 之后，并与收件箱、派单 outbox 一起设计固定顺序。不能在持有 order 后倒序获取其他 inbox 行。
- 订单状态、会话变更和发送尝试预留在短事务中提交；网络请求、等待、重试或用户操作不能持有数据库事务及行锁。回写时重新锁定并验证状态和租约。
- 租约只防止系统重复领取；微信无法识别本地 fencing token。旧 worker 可能在租约过期后才真正发出网络请求，数据库无法撤回已发请求。任何无法证明安全的交错都进入未知或人工核对，不能声称租约单独保证绝不重复发送。
- 当前生产数据库配置及隔离测试配置使用 MySQL 8 `READ COMMITTED`。若实现依赖该隔离级别下锁后读取其他已提交记录，必须运行时检查实际会话隔离级别并 fail closed；不能在 `REPEATABLE READ` 下假定普通一致性读会看到竞争事务的新提交。设计应在 MySQL 8 真行锁下验证，SQLite 跳过的结果不能替代。

## 证据和隐私

通知应先验签、解密并受控持久化，只有成功落库后才可按渠道协议确认接收。查询/关单需要新增相同级别的认证响应证据能力：保留有界原始响应、签名头和可信密钥版本以供受控重验，或明确只保存摘要而不宣称可独立重验。HTTP 状态本身不在微信响应签名材料中，依赖 TLS 传输保护；`4xx`、`5xx`、验签失败与超时不能凭空变为资金终态。

原始响应可能包含用户信息。存储应加密、限权、设保留期限；日志和错误提示不包含私钥、Authorization、OpenID、原始响应或支付参数。只有经过账号与订单授权的老板能取回自己仍有效的支付参数，客服只获取权限范围内的脱敏审计信息。

## 最小迁移与验收

迁移只添加独立会话、操作及证据记录、约束和必要索引；对旧订单不伪造下单尝试、渠道关闭、付款时间或历史换算信息。旧无快照/V1 交易遵循当前待核对策略，已付款或已履约订单不得因新迁移倒退。待有真实数据后，迁移回滚不得静默删除不可重建的会话、凭证或换算快照。

测试使用本地生成密钥与 fake transport，且不开放生产入口：

- 连续点击、同请求重放、丢页面、换设备及重登均恢复同一意图；不同账号/业务周期/OpenID 不得读取支付参数。
- 在发送前、发送后、收到响应前后和回写前模拟崩溃；超时、未验签、5xx、`NOTPAY` 和暂时查无订单都不得自动换号或假定未付款。
- 验证旧支付参数与关闭意愿竞争、查单 `NOTPAY` 后用户付款、关单胜出与支付成功胜出的两种顺序；可信矛盾事实保留并阻断自动派单，已履约状态不倒退。
- 验证会话有效期、支付截止和接单截止互不混淆；手续费和换算快照变化不影响旧订单，用户确认金额与实际请求总额一致。
- MySQL 8 以双事务屏障覆盖并发领取、过期租约、迟到应答、支付通知与关单；fake transport 断言 HTTP 调用发生时事务和行锁均已释放。
- 验证失败留证、脱敏、失败重放及自动恢复；不以数据库测试、模拟网关或 UI 回调宣称真实商户上线。

## 0064 之后的模拟查单与关单设计

以下为下一步设计，**尚未实现**。这一切片只允许测试开关和显式注入的模拟网关，不提供公开接口、不发送真实商户请求，也不决定手续费退款或部分退款分摊。

### 会话、操作和可信事实

在现有会话旁新增独立的操作与观察记录：操作应包含会话与原支付意图、类型（查单或关单）、唯一尝试号、冻结请求摘要、发送可能性、持有者令牌、租约和时间；观察记录保存有限且脱敏的模拟证据、其来源与摘要，以及冲突处理状态。每个可能发送的写操作先在会话行锁内领取并持久化，禁止通过数据库不支持的条件唯一索引假设单次执行。租约只表明本系统中哪个工作进程持有处理权，并不能撤回已经交给渠道或仍可能被旧工作进程发送的请求。

会话状态需要区分取消意愿、关单处理中、结果未知、渠道确认关闭与证据冲突。扩展状态前必须一并修改 0064 中“取消时间与会话状态配对”的数据库约束，不能将已有取消意愿清空以迎合新状态。新增证据迁移需保护不可重建的记录，不允许自动回退时静默删除它们。

模拟证据仅能由服务端注入的假网关产生，不能从客户端输入构造可信事实。查单结果至少匹配原商户号、AppID 和商户订单号；`NOTPAY` 或 `CLOSED` 可能没有付款交易号或付款人字段，不得凭空补齐，但渠道若提供金额、币种或付款人且与快照矛盾，应保留证据并转入核对。`SUCCESS` 必须通过现有完整付款证据匹配金额、币种、付款身份和渠道交易号，并与回调走同一套冲突处理。正式接入还须验证响应签名，并受控保存可重验的证据或明确说明仅保存摘要的限制。[商户订单号查单字段](https://pay.wechatpay.cn/doc/v3/merchant/4012791900)

后台恢复与老板读取必须分开：老板读取支付参数仍须验证当前账号与绑定；系统对账不能依赖账号仍启用、OpenID 仍绑定或业务周期未变化。账号封禁、换绑或退役后，仍须按原冻结的商户身份查单并保留可信渠道事实；身份变化影响自动派单资格，不应导致真实收款或关闭证据丢失。

### 查询、关闭及迟到请求

1. 先在短事务中按订单、意图、会话、操作的顺序锁定并验证冻结快照，登记此次尝试；提交后才调用假网关，整个调用期间不得持有数据库事务或行锁。
2. 返回后在新短事务中先保存可信观察，再重新验证当前状态与令牌。令牌失效或被其他工作进程替代，只意味着该响应不能覆盖当前控制状态；已经可信的支付或关闭事实仍需保存和冲突核对。
3. 取消意愿提交后停止向新请求发放支付参数；之前已经交给用户的参数仍可能有效。对原商户订单号查单：`NOTPAY` 仅表示查询时尚未付款，需后续关单；`SUCCESS` 保留付款并进入取消冲突核对；`CLOSED` 留存关闭证据；`REFUND`、未认证响应、超时、字段矛盾或暂时查无订单都不能视作关单成功。查询到 `NOTPAY` 与发出关闭之间用户仍可能付款，关单报已付款或结果不明时须再次查原号。[微信支付关闭前查单指引](https://pay.wechatpay.cn/doc/v3/partner/4012082568)
4. 已进入可能发送阶段的旧预下单工作进程即使租约过期，也可能在查无订单或关单之后才发出请求。没有经确认的渠道终态、原号重入规则及旧进程停止证据时，不得据此释放新商户单号或声称该渠道单永远不能再付款；继续保留未知或人工核对。只有能证明从未进入可能发送阶段，才可考虑在本地结束未付款会话。
5. `CLOSED` 与 `SUCCESS` 不论先后顺序出现，都保存两份证据并暂停后续自动派单：先关后付时保留真实交易并进入待核对；先付后关时保留订单的真实已付及已有履约状态，将支付意图及待派事件转入核对。不得自动重写为未支付、重复退款或擅自取消已接单/服务中订单。没有付款交易号与时间时，应使用会话或操作的待核对状态，不能违反现有支付意图 `REVIEW` 的付款证据约束。

### 专项验证

在不连接真实渠道的前提下，至少覆盖：`NOTPAY` 后付款、关单超时、查询暂时无单、关闭与付款两种先后顺序、回调与主动查单冲突、响应在租约过期后到达、账号变更后后台留证，以及不同 worker 竞争同一关闭操作。假网关须断言调用时 `connection.in_atomic_block` 为 false；MySQL 8 `READ COMMITTED` 行锁测试须以屏障模拟旧预下单在查无订单甚至关单之后才发送，证明系统没有提前释放新单或虚报关闭。客户界面应能恢复原意图并查看核对状态；此设计不等于可用的自助取消恢复流程。

## 仅模拟查单的最小切片

本节是针对 0065 测试会话的下一步设计，**尚未实现**。本切片暂不实现关单，不发送真实 HTTP，不开放生产路由或自动调度，也不依赖手续费退款规则。现有 `DirectPaymentSessionObservation` 保存的是预下单模拟响应，不能将它当作查单结果或渠道付款证明。

### 尝试与观察

新增独立的查询尝试及观察记录。尝试需绑定原会话和支付意图，冻结商户号、AppID、商户订单号、支付总额、币种、原报价与会话摘要，并记录尝试标识、租约令牌、期限和时间。观察保存有界、脱敏的模拟结果及摘要，区分成功、结果未知、暂时无单、格式错误和身份冲突；保存摘要不能声称具备渠道原始签名重验能力。保护新增观察证据的迁移应禁止自动回退删除记录。

测试入口只接受受测试开关保护的显式假网关，不接受真实网关或由客户端构造的“可信”结果。内部恢复可通过独立方法读取冻结的原商户身份；老板查看原订单及取回任何模拟支付参数仍须通过现有账号授权。账号停用、换绑、业务周期变化或钱包不可用时，不应因客户已不能取回参数而丢弃系统已收到的模拟查询观察，也不能自动派单。

### 事务与锁序

1. 在短事务中按 `order → intent → session → query attempt` 锁定，校验原订单和会话快照，并持久化本次查询尝试和租约。查询不重新定价、不更换商户订单号。
2. 提交后再调用假网关；若调用方已经在数据库事务中，应拒绝发起。任何等待渠道的操作都不能持有数据库行锁。
3. 在新短事务中按同一顺序重新锁定，先记录有界观察，再比较令牌、快照及当前支付和取消状态。过期或被替代的令牌不能覆盖当前控制状态，但迟到的可信观察仍须留存并参与冲突检查。
4. 超时、进程中断、无效响应或查无订单保持未知。租约过期可触发针对**同一原单号**的受控再次查单，但不能重发预下单或关单，不能清除取消意愿，也不能创建新单。旧预下单工作进程仍可能迟发，查询不到或观察到 `CLOSED` 均不单独证明旧请求永远不会继续发送。

支付通知当前按 `inbox → order → intent → session` 获取锁。查询路径不能在持有订单锁后获取任何通知 inbox 锁，否则会与通知处理形成反向等待。应把现有通知处理中的付款证据比较与停派逻辑提取为只接受**已锁订单和意图**的共享领域操作：通知和查询各自保存来源证据，再在订单锁内调用同一比较规则。查询分支不得仅调用付款确认并捕获异常后继续派单。若实现依赖锁后读取其他已提交证据，须明确要求并检查 MySQL 8 `READ COMMITTED`，并用真实行锁测试验证。

### 查询结果处理

查询结果须匹配冻结的商户号、AppID 和商户订单号。`NOTPAY` 或 `CLOSED` 不要求渠道未提供的付款交易号和付款人；渠道若提供金额、币种或付款身份且与快照矛盾，留存该观察并进入核对。`SUCCESS` 则须完整匹配付款金额、币种、身份、渠道交易号及时间，不能从缺失字段推断实际现金或渠道优惠。[微信商户订单号查单字段](https://pay.wechatpay.cn/doc/v3/merchant/4012791900)

`NOTPAY` 是某次查询时的非终态观察：不得把它当成支付失败、退款或渠道已关闭，也不得覆盖已经确认的付款。`SUCCESS` 若与现有付款事实相同，应幂等处理，不重复创建派单事件或重置接单时限；若交易号、时间、实付金额或优惠等已知事实矛盾，保存两方证据并停止新派单。付款与取消意愿竞争时，先保存的取消意愿使随后确认的付款进入待核对；付款先确认则保留已付事实，不得重新描述为未付款取消。

查询观察到 `CLOSED` 时，只保留渠道状态观察并停止继续发放支付参数，不在此切片发起关单、自动取消订单、自动退款或释放新商户订单号。关闭观察与付款成功互相冲突时，两份事实都要保留并暂停派单；已付款或已履约订单的状态不得倒退。没有付款交易号和付款时间时，风险状态须放在查询或会话记录，不能违反支付意图 `REVIEW` 对付款证据的数据库约束。若新增会话风险标记，`_view`、预下单入口和付款确认都需在锁内共同检查，避免界面显示停用而后台继续派单。

### 验收清单

- 同一原单重复查单，以及两个工作进程竞争同一查询；请求超时、租约到期和迟到响应均不丢观察，也不自动换号。
- 已禁用账号、换绑 OpenID、业务周期变化和钱包不可用时，内部仍可留证；未授权客户无法取回支付参数。
- `NOTPAY` 在付款确认之后迟到时不回滚已付状态；取消意愿与 `SUCCESS` 按两种顺序竞争，均保留真实事实。
- 同一交易的主动查询与不同通知 ID 出现相同或矛盾证据；`CLOSED` 与 `SUCCESS` 两种先后顺序均留证并暂停新派单。
- 假网关验证自身调用期间 `connection.in_atomic_block` 为 false；异常和日志不暴露 OpenID、支付参数或原始敏感响应。
- MySQL 8 `READ COMMITTED` 使用双事务屏障验证通知与查询锁序、旧预下单迟发及多 worker 竞争。SQLite 中跳过的行锁测试不能计作通过。
