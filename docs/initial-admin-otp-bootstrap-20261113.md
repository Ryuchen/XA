# 新门店首位管理员 OTP 引导（2026-11-13）

平台独立超级管理员在统一后台调用 `POST /api/admin/platform/store-management/<门店ID>/initial-otp`，仅对已初始化、正在配置且有建库首位管理员记录的门店签发。返回一次性 `token`、`expiresAt`、`username`；十分钟有效，重发使旧凭据失效，平台和门店审计关联 operation_id。已绑定 OTP、账号禁用或无法核实首位管理员时不签发。

管理员在统一后台调用 `POST /api/admin/auth/initial-otp`，请求体 `token`、`username`、`password`，验证成功后仅首次返回 `otpSecret` 和 `otpUri`；再次提交同一凭据、账号、密码及 `otpCode`，校验真实动态码后返回仅一次的 `recoveryCodes`。客户端应安全展示及传递凭据并清除响应；绑定后使用现有密码加 OTP 登录，绑定接口不签发登录令牌。凭据由签名中的门店标识定位业务库，不能使用门店 header/query；门店记录只存凭据散列和 OTP 密文。密码变更、过期、失败次数过多或重发会使凭据失效；账号行锁将重发与绑定串行化，OTP 和凭据消费同事务提交。

采用 [PyOTP 官方说明](https://github.com/pyauth/pyotp) 中保护密钥和阻止已使用验证码重放的原则，复用项目已有 OTP 密文、计数器及恢复码实现，不引入其身份或数据库模型。

新增 `club_accounts/0011_initial_admin_otp_grant` 结构迁移，仅编写未执行。开发期间未执行测试、迁移或建库。最终需在隔离环境联调签发/重发/过期、并发单次消费、真实验证器与正常登录、统一后台跨店隔离、跨库审计故障及日志脱敏；短信和微信通道仍按现有真实服务状态处理。本功能不支持缺少建库管理员事实的门店或重置已绑定 OTP。

## 首次开业管理员检查

首次开业核验现在单独检查本店有效超级管理员的真实已绑定 OTP（密码可用且密钥可解密），或已验证手机号及短信服务配置，或与已配置入口对应的微信绑定。建库和开业前配置仍沿用原有初始化检查，允许首位管理员先完成 OTP 引导；未验证手机号或仅填写手机号不再使开业检查通过。微信及短信仅表示已配置并具备绑定事实，不能证明外部渠道申请已获批或消息成功送达，须在隔离环境最终联调。

微信开业检查以当前平台配置的 AppID 为准：小程序绑定需属于该 AppID，H5 微信身份还须保持账号实际绑定状态。此调整未运行测试或迁移。
