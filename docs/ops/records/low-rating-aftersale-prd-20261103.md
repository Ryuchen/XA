# 低星评价触发售后与结算暂缓：需求设计草稿

日期：2026-11-03。状态：**设计草稿，未开发、未验收**。本文件承接用户最新决策；历史实现和历史测试不能作为本功能已完成的证据。

## 已确认决策与本次目标

- 老板评价的**综合、技术、态度、沟通任一评分为 1–2 星**时自动创建售后工单；售后处理完成前暂缓结算，处理后恢复。
- 用户确认：自动触发只处理功能上线后的新评价；上线前已有的低星评价保留供查询，不为其批量追溯创建售后。上线切换时点、并发评价及部署重试的可审计界线须在七角色评审中明确。
- 评价发生时收益已到账的，仍自动创建售后工单；**已到账收益不自动追回**。未结算部分按售后暂缓处理。
- 只要评价在现行规则下有效，低星按同订单工单状态创建或追加售后；已结案时低星评价不再开启新一轮。不以现有老板主动申请售后的窗口或已结算状态过滤。评价本身是否有效仍按现行评价规则判断；此决定不自动改变老板主动重新申请售后的现行资格规则。
- 双陪订单只暂缓被差评打手的未结算收益，另一位打手的收益按现有条件处理；售后处理中同订单新增低星评价追加到现有工单，工单已结案则不再开启新一轮，仍需保留关联评价。
- 老板主动售后继续适用各结算路径现有的限制；只有低星来源的暂缓限制差评对象。同一开放工单同时有主动售后与低星来源时，不能因合并来源而放松主动售后的既有限制。现有 `REPORT_APPROVAL` 模式的 `settlement_ready` 对开放售后按整单阻断；`COMPLETION`、补贴和转单等路径条件不同，不能笼统断言所有模式已有相同的整单阻断，须在技术设计评审中逐条核对。
- 推荐人、平台收入及老板权益的原有发放时点不因部分打手先入账而提前；退款承担沿用既有已确认规则。遇到无法安全按既有规则处理的具体分支，先提出决策。
- 售后工作仅在老板主动发起售后或订单评价不好时开始。正常评价不因此启动售后；差评不自动批准退款。
- 老板当前原生评价页面只有一项综合满意度，尚不能分别填写技术、态度、沟通。为使用户确认的四项触发条件可实际使用，原型与需求须补齐四项评分输入及其校验和反馈，再经七角色评审。现有评价 API 的三个单项可选，未传时分别回填综合分；旧客户端不得被误解为默认单项均为 5 分。评分必填方式及新界面的初始值须在设计中明确，不能静默更改旧端语义。
- 恢复是解除该售后造成的结算暂缓，仍须满足订单现行的审核、售后窗口、资金与其他结算条件；不得将“处理完成”展示为收益必定立即到账。
- 全系统品牌统一为“声浪电竞”，原“兴安币”称谓改为“浪花”；用户确认仅更名，沿用原换算比例和历史余额，不进行余额换算或迁移改值。本功能新文案采用新品牌与单位，品牌替换的全系统范围需单独盘点并执行，不能以本稿完成代替。


## 源码事实与差距

1. `orders/models.py` 的评价有 1–5 星综合分及技术、态度、沟通三项评分，订单和陪玩组合有唯一约束；双陪可分别评价。用户已确认任一字段为 1–2 星即触发。
2. `orders/views.py` 的 `EvaluateOrderView.post` 当前创建评价、更新评分、通知打手与刷新订单；其中综合分 `>= 4` 分支用于广播，不能倒推低星售后规则。该入口静态阅读未见创建售后；仍需完整检查其他入口和本轮容器行为，不能仅凭本段断言全系统均无此能力。
3. `orders/models.py` 中 `AfterSale` 按订单唯一，状态包括 `OPEN`、`RESOLVED`、`REFUNDED`、`PARTIALLY_REFUNDED`；`orders/aftersale.py` 老板主动申请入口可新建或在符合条件时复用旧记录，并校验请求与订单。该模型当前没有明确评价来源/关联字段，来源留存方式需设计。
4. `engagement/confirmation.py` 的 `settlement_ready` 对订单存在未处理 `OPEN` 售后时阻断订单结算；`process_order` 还核对订单、报单等条件。**必须解决差异：订单级阻断会阻止双陪中未被差评者按规则获得未结算收益，与用户只暂停被差评打手的决定冲突。** 需设计按打手份额阻断与恢复，覆盖各结算模式、订单锁和流水幂等，同时保留既有老板主动售后的适用规则；不能仅修改页面。现有判断不证明低星自动建单及并发安全已实现。
5. [业务覆盖工作底稿](business-coverage-20261103.md)记载已结算退款、服务中转单及双陪分摊等专项，处理结果依各自规则；不得用新触发条件自行改写追回、退款、钱包或分配规则。
6. 静态核对 `CreateEvaluationSerializer.validate_order_id`：仅本人 `COMPLETED` 订单可评价，该校验没有按付款/退款状态过滤；`OrderSerializer.get_allowed_actions` 的 `EVALUATE` 分支同样未按支付状态过滤，但要求非礼物、存在可评价对象且尚未评价。因而**已退款但仍为完成状态的订单可能可评价**；实际对象、入口、权限和退款后状态仍需容器实测。不能概括为所有已退款订单都可评价，例如现有部分协商退款路径会将订单置为 `CANCELLED`。
7. `engagement/confirmation.py` 的 `process_order` 初始允许 `PARTIALLY_REFUNDED`，但未结算且为 `REPORT_APPROVAL` 模式时调用的 `orders/services.py::settle_order` 要求 `PAID`；同文件的报单审核也要求 `PAID`。这是需结合退款方式、订单状态与既有专项核实的代码分支差异，尚不能认定所有部分退款都可以恢复结算，也不能仅凭静态阅读认定缺陷。
8. 研发静态复核：当前 `settle_order` 按整单一次结算，并使用整单结算标记；只暂停受差评者时，另一成员先结算需要明确逐份额状态、重试幂等和最终整单标记的关系。现有普通退款核验涉及已结算收入完整性；先结一部分再退款时，必须保证分配、钱包、流水及退款承担依据原规则守恒，不能绕过退款校验或自行推定追回规则。此为实现前必须完成的技术设计和验收边界，尚未在本轮容器验证。

## 流程及三端状态草图

本节为功能和信息原型，非真实页面截图或视觉验收。各页面基于已批准视觉方向及现有原型补齐，真实字段和权限须在开发前与源码及岗位授权核对。

```text
老板：完成订单 → 提交评价（命中已确认低星条件）
      → 评价提交结果 + 售后已创建 / 可查看进度
      → 售后处理中 → 处理结果（以及有退款时的实际结果）

售后后台：待处理列表 [订单号 / 触发来源 / 当前状态]
      → 核对评价、订单及既有售后 → 按获授权动作处理
      → 记录处理结果 → 完成；如需退款，沿现有退款确认流程

打手 H5 / Web：订单与收益看到售后处理中、未结算收益暂缓
      → 售后处理完成 → 结算状态按实际规则更新
      → 已入账或可提现只以真实钱包与流水为准
```

| 使用者 / 场景 | 应能看到和操作 | 失败与状态反馈 |
| --- | --- | --- |
| 老板 | 对本人完成订单评价；命中低星后可辨识已创建售后、查看处理进度和处理结果。 | 提交结果未知时核对原订单及评价/售后结果，不能提示成功却遗漏自动工单；退款需展示真实结果，不能由低星推断已退款。 |
| 打手 | 在本人订单、收益相关页面看到与本人相关的售后和结算状态；查看本人评价及按原权限回复。 | 被差评打手未结算收益暂缓；未被差评的打手不因该低星售后被暂停，其他规则仍适用。已有收入以实际流水展示，不能暗示自动扣回或可以提现。多打手售后详细内容可见性待明确。 |
| 客服 | 在实际授权内查看订单、评价、客户咨询和相关进度。 | 无权限的操作不可提交，状态变化后显示可核对的信息。是否承担具体售后动作由实际授权确定。 |
| 售后 | 在实际授权内查看低星触发来源、订单、评价、售后记录及处理结果，按允许动作处理并留痕。 | 有既存工单、并发修改或处理结果未知时提示核对；不可将未确认退款显示为成功。 |
| 财务 | 在实际授权内查看未结算状态、退款及相关流水，按既有规则处理被授权的财务动作。 | 准确区分暂停结算、已结算、退款及待核对；不凭评价直接改余额。 |
| 管理员 | 在实际授权内查看角色和权限配置、操作记录与问题处理状态。 | 无权限、状态冲突等信息可定位；不假定该岗位均有所有业务动作。 |

售后通知应以订单及工单服务端状态为准。站内通知和实时刷新与持久结果分别验收；外部渠道不可用时不把通知投递当作工单事实。权限通过当前服务端校验，不能只依赖页面隐藏。

## 四项评分交互与兼容设计（待评审）

在现有订单详情和已批准视觉方向上扩展评价面板；保留文字选填、匿名开关及现有单人/双人评价入口。按用户要求，**综合、技术、态度、沟通任一项 1–2 分都触发对应打手的低星处理**；不能只检查综合分、平均分，或将低维度覆盖为高综合分。每项以 1–5 的整数分表达，并显示当前数值与关联名称；老板提交前必须能清楚区分四项各自的值。四项的控件形式、长文案、移动触控、加载/失败/空状态须由 UI/UX 制作本地网页可审阅原型，使用 mock 数据并对照现有视觉；微信端的最终实现仍采用原生组件。

| 环节 | 候选产品行为及必须保持的边界 |
| --- | --- |
| 初次进入 | 已完成且服务端允许评价的本人订单才显示入口；展示订单与被评价打手。四项需让老板理解是不同评价维度。每项是否默认、默认数值及是否要求显式操作由七角色审议，候选见下表；不得把未操作的展示当作已经真实单独选择。 |
| 双陪选择 | 逐位选择尚可评价的打手，明确姓名及已评价标记。每位打手独立持有四项分数、文字和匿名草稿；切换、重载或刷新时不得将甲的分数提交给乙。页面重进后的草稿持久范围按最终设计声明，不承诺现有内存草稿跨设备保存。 |
| 输入与提交 | 每项只能是 1–5 整数，文字仍最多 500 字且可留空；提交时带订单与服务端认可的目标身份，发送四项、文字及匿名选择。输入非法时在对应项附近说明并保留其余草稿；提交中阻止同一面板重复点击。新界面如果允许未填写单项，必须明确是否依现有 API 回填综合分，不能显示为独立人工评分。 |
| 低星提示 | 提交前与提交后应让老板看懂会进入售后及如何查看进度；不得暗示自动退款或改变其已完成订单的履约状态。预提示、文案和是否需要额外确认由产品/UI/研发评审，不能使已确认的自动触发悄然变成必须另选或可关闭。 |
| 结果确认 | 低星评价与所需的工单创建/关联须共同成功；响应应使客户端能够按服务端真实结果区别新建、追加现有处理中工单、已有结案工单不重开。高分或无触发则显示评价已提交，不误称售后已创建。老板查看订单及售后时以服务端状态为准；历史聊天与评价原文、上传凭证按用户已确认规则保留。 |
| 网络或状态变化 | 网络失败且确定未保存时保留草稿并显示可执行的重试；提交结果未知时先核对该订单、打手的评价与工单，不提示已失败或盲目创建第二条。目标已评价、订单状态变化或权限失效时以服务端结果提示刷新/查看既有评价，并防止草稿写入另一账号。此处为目标体验，现有接口无幂等回执，须在技术设计中明确恢复机制。 |
| 服务端与其他角色 | 验证当前订单归属、评价资格和目标打手，并在事务内与现有工单、订单及结算竞争检查保持一致；打手只能看到本人相关评价和收益状态，后台在实际权限内核对来源和处理。匿名身份及双陪可见范围按既有权限和待确认的隐私设计执行，不因网页原型演示放宽访问。 |

### 新界面的评分初始值候选

这些是**交七角色评审的产品候选，尚非新业务规则**：

| 选项 | 新页面行为 | 权衡及待确认 |
| --- | --- | --- |
| A（team leader 推荐，待七角色评审） | 四项初始均未选择，逐项选择 1–5 后才提交。 | 能明确每项是老板主动选择，避免默认值让未选择的维度触发售后；但相比当前默认综合 5 分增加三项输入和逐项确认成本。未完成项须就近提示；低分提交结果应说明已创建/追加售后或已有工单已结案不重开，具体以服务端返回为准。旧客户端仍允许缺省单项回填。 |
| B | 综合保留现有初始 5 分；三个单项未选择时明确显示“沿用综合分”，老板可分别修改。 | 更接近当前单项提交体验，但须清楚标识哪些是自动回填，不能将回填值宣传为老板独立评价；需核对显示、接口和历史记录是否能可靠区分来源。 |

Team leader 推荐 A 是评审建议，**不是用户已额外确认或七人已通过的决定**。产品、UI/UX、研发及测试应基于现有真实业务和用户体验比较以上方案并提交七人评审；若影响老板评价义务或历史评分口径且无法由现有授权判断，再由 team leader 汇总交用户决定。新客户端字段与反馈确定之前，不应开发四项界面或声称此功能已通过评审。旧客户端仍按现有 API 协议：只传综合分时，三个维度分别回填综合分，再依据用户确认的任一字段触发规则判定；不能因新页面要求单项而直接拒绝旧客户端。现有模型是否能区分历史独立录入与回填仍待核实，不能倒推用户当时选择过每一项。

## 待决策及设计边界

| 情况 | 已知事实 / 必须保持 | 待业务决策或进一步核实 |
| --- | --- | --- |
| 评分字段 | 用户确认综合、技术、态度、沟通任一评分 1–2 星触发；旧 API 缺省单项逐项回填综合分。 | 新页面初始值、是否逐项显式选择及历史值来源标注待七角色评审；历史值不可擅自宣称独立录入。 |
| 同订单已有 `OPEN` 售后 | 用户确认追加评价，数据库订单售后唯一；不能产生重复并行记录。主动售后与低星同时存在时保留对应路径的既有限制。 | 设计来源分类、评价关联、原理由与处理历史保留方式，逐模式核对既有限制、老板主动申请与评价并发时的展示和接收人。 |
| 已处理或已退款工单再次低星 | 用户确认同订单工单结案后不再开启新一轮；现有模型只允许一条记录。 | 设计结案后新增评价的可追溯关联和展示；不得重新打开、静默丢失来源或更改既有退款结论。 |
| 双陪及多次低星 | 用户确认仅暂停被差评打手未结算收益；同单多条低星关联同一工单。 | 设计每位打手份额的暂缓、恢复和幂等；保留老板主动售后的原有规则，核对其他成员可见细节。 |
| 评价发生在结算之后 | 用户确认仍自动创建售后；已到账收益不自动追回，未结算部分暂缓。现有结算模式不同，某些订单或份额可能已结算。 | 涉及后续协商退款或其他人工资金处理时，依据既有规则和实际授权逐项核实，不擅自新增追回规则。 |
| 售后窗口外评价 | 用户已确认有效低星评价仍自动创建售后，不受主动申请窗口或已结算状态过滤。 | 核实窗口外及已确认消费订单的现有评价资格、工单后的处理时限；不能悄然丢弃有效低星。 |
| 处理完成与恢复 | `OPEN` 是当前结算阻断条件之一，结算还依赖其他条件。 | 哪些处理结果算完成、再次打开如何恢复暂缓、部分退款后待结算份额如何恢复，以及解阻后由现有任务还是其他机制重新触发结算；不跳过现行条件。 |
| 打手及后台权限/隐私 | 现有权限点按动作授权，通知避免暴露客户私人售后内容。 | 各岗位具体授权、双陪能否看到对方评价/售后细节和老板匿名信息展示，需结合现有规则核实。 |
| 待结算与钱包冻结展示 | 低星只暂停受影响打手尚未结算的收益；到账后的收益不自动追回。 | 需由产品、研发和财务评审分别说明待结算份额、已到账冻结金额及流水口径，避免将尚未入账的份额直接计入钱包冻结余额或暗示已发生资金流水；最终展示和账务须以实际模型及已确认资金规则为准。 |

上述待决项涉及用户明确决策范围之外的商业与资金规则，应整理选项由用户决定；不能以静默丢弃、创建多个互相矛盾的工单或自动追回资金替代决策。
