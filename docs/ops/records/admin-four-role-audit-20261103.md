# 管理后台四岗位：权限与业务核对底稿

日期：2026-11-03。用户明确后台主要由客服、售后、财务和管理员使用，后台按桌面 Web 场景设计。本表为源码静态盘点和后续设计输入，不是岗位授权决定、实际数据库配置或测试通过证明。

## 现有机制与证据

- `services/backend/console/models.py` 中 `AdminRole` 保存权限点，`AdminMembership` 可关联多个角色。`console/permissions.py` 的 `get_account_permissions` 合并启用角色的有效权限；后台账户必须符合启用、可登录、STAFF 身份及有效后台成员资格等条件。
- `services/backend/console/migrations/0002_seed_roles.py` 的历史种子包含超级管理员、运营、财务和客服，并未列独立售后种子。迁移种子不代表当前数据库角色、成员或授权；角色名称相同也不能推断其现在权限相同。
- 功能动作在 `console/views.py` 和 `orders/aftersale.py` 声明权限；前端还会根据权限决定入口可见性。具体操作仍需满足状态和业务约束，不能仅凭持有权限认定一定能成功。
- 既有业务记录 [核心业务基线](../../development/topics/misc/CORE_BUSINESS_WORKING_BASELINE_20261027.md) 描述客服派单和异常处理、人工核实收款、报单审核等流程，但不足以决定四岗位完整的组织分工或资金审批责任。

## 后续权限验证

在已确认本轮功能与测试计划后，使用部署到本地 WSL 的独立容器、合成账户及隔离数据，记录实际角色和权限点。对首轮相关动作逐项验证：

1. 有对应权限且符合业务前置条件时，可看到并执行动作，结果与关联三端、流水和审计一致。
2. 无权限时，核对菜单/按钮及直接 API：不得以隐藏按钮代替服务端拒绝；只读账号不能写入。
3. 多角色叠加、角色停用、账号停用或权限变更后，核对权限实际并集、后续请求与必要的实时访问行为；不得推断已有历史测试覆盖本轮部署。
4. 分开核对售后查看、解决、退款，以及提现领取、释放、审核；核对实际页面是否还要求其他查看权限，记录测试账号、权限、动作、响应、数据结果和未覆盖项。
5. 管理员变更角色和查看审计仅在合成账户中执行；现有业务角色、真实客户及生产资金不作为测试对象。

## 待产品和业务负责人处理的决策

- 各岗位实际负责哪些订单、报单、售后、充值、提现与对账操作，哪些只需查看；是否允许同一人员兼任多岗位。
- 退款、调账、充值、提现审核和线下打款由谁发起、核对和执行，是否需要分人复核；现有实现与期望有无差异。
- 售后解决是否应与订单结单共享授权、售后退款是否应与订单退款共享授权；若需拆分须先定义权限和兼容方案，不能将现状直接认定为缺陷。
- 哪些人员可维护角色、员工与审计，管理员是否对应现有超级管理员或另建受限角色；已部署环境的现有角色需由授权人员及隔离方式核实。

仅当具体业务设计依赖上述尚无依据的决策时，由 team leader 整理影响和选项交用户决定；在此之前不创建、重置或重新分配现有角色。
