# VIP 停用后配置与重新启用：试验实现

状态：隔离测试中的功能，`VIP_THRESHOLD_RECALC_ENABLED` 默认关闭；并非已部署。此文记录实现范围，不替代 PRD 的产品规则。

- 在试验路径中停用 VIP 时，按门店保存当时等级、门槛等基线；停用期间调整门槛、新增、启用或停用等级，只保存配置，不立即更改老板等级和升级权益。
- 重新启用前先预览并校验当时的门店数据，使用基线与当前有效消费计算变更；提交期间数据变化则要求重新预览。已有月券按确定的条款保护，等级、升级权益及审计记录在同一事务中处理。
- 如果接手时门店已停用而无法还原基线，按当前净消费重算等级，将无法确认的等级权益列入本店人工核对。授权员工填写依据后，可以记录历史已发或确认未发并按当前配置补发；两者均留审计，不凭空生成历史发放流水。普通消费、等级变化不会绕过待核对或已确认历史发放的记录自动重发。
- 对已确认历史发放但缺少安全箱券记录的情况，系统不会据此自动创建安全箱券；需要根据实际历史进一步核实。人工确认的权益名额保守地保留防重复标记，不等于已交付凭证。
- 停用期间消费的会员成长按既有实现排除。审核是门店级数据，不共享其他门店的账户、配置和记录。

启用条件与限制：先在专用测试数据库验证迁移 `engagement.0026`、`0027` 及实际历史数据，再结合对应开关和部署流程安排上线；本次没有修改或迁移现有门店数据库，也没有重启后端。锁和并发在隔离 SQLite 测试中通过，但 MySQL 下的并发锁、容量和迁移耗时尚待验证。已有部分升级权益、券和安全箱逻辑仍引用六级固定规则，不能将此次修改视为完整实现任意等级配置；继续开发时需统一配置、迁移和验收。停用前历史数据不完整的真实人工核验和安全箱记录恢复流程尚未验证。

后台等级编辑器已接入每月券数量、月券支付比例及安全箱券支付比例；仅当本店已建立月券切换记录且新规则开关启用时显示。月券数量从下次发放生效，符合条件的未用券按对应新条款使用，已使用或已固化原条款的券保持原记录。升级权益尚待人工核对时，已存在的未用安全箱券仍可按规则更新，但不因此新发券。设置变更会提示在线老板刷新券信息；目前对隔离测试数据验证，不能推断现有门店已切换。

扩展回归发现 `coupons.test_coupon_availability_workflow.CouponAvailabilityWorkflowTest` 中若干旧陪玩样本未满足当前现金押金要求，无法进入原来的派单流程。以仅影响该次测试进程的方式为默认陪玩测试数据补足押金后，20 项中 19 项通过，另一项仍按旧规则期待陪玩分配后自行拒单，与用户确认的新规则冲突；该探查没有更改生产逻辑或测试文件。这组旧场景需要按现行资格和客服协调转单流程更新后，才能作为完整回归依据。
