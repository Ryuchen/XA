# 低星售后与按打手份额暂缓结算：技术设计交接

日期：2026-11-03。状态：**开发前设计稿，尚未实现或测试**。产品规则见 [低星售后 PRD](low-rating-aftersale-prd-20261103.md)，发生冲突时以用户最新明确决策为准。金额规则、优惠权益及历史数据不因品牌从“兴安电竞 / 兴安币”更名为“声浪电竞 / 浪花”而改变。

## 已确认的合同

功能上线后，老板新提交的有效评价中，综合、技术、态度、沟通任一项为 1–2 星时触发售后；上线前已有评价保留查询，不追溯批量建单。评价是否有效沿用现有评价校验，不按老板主动售后窗口或是否已经结算过滤。无工单则创建；同订单工单处理中则追加评价来源；已结案则记录评价关联但不重开新一轮。符合触发范围的评价已产生时不能丢失对应低星来源。低星售后只暂缓被差评打手未结算收益，已到账收益不自动追回；处理完成后解除此暂缓，其他结算条件继续生效。双陪仅一人低星时另一人的未结算收益不因**低星来源本身**被拦截。

老板主动售后继续维持各结算路径现有限制；同一开放工单同时有主动售后与低星来源时不得因来源合并而放松这些限制。`REPORT_APPROVAL` 的 `settlement_ready` 对开放售后整单阻断；`COMPLETION`、补贴及转单的具体条件须逐条核实，不能假定与其完全相同。不同来源及处理历史不可互相覆盖。退款、已到账收入、推荐人、平台收入、积分和老板权益按现有已确认规则，不因一位打手先入账而提前发生或自动追回。

## 现状与实现边界

- `orders/views.py::EvaluateOrderView` 在事务中先锁订单，创建每单每打手唯一评价并推送事件；`orders/models.py::Evaluation` 保存综合与三维评分。当前低星路径未在该入口创建售后。
- `orders/models.py::AfterSale` 对订单有唯一约束，当前有状态与 JSON 历史，没有明确、可可靠查询的多来源及评价关联；主动申请、处理、退款分别在 `orders/aftersale.py`。`OPEN` 目前参与订单级结算拦截。
- `engagement/confirmation.py::settlement_ready` 对任何订单级 `OPEN` 阻断；`orders/services.py::settle_order` 先检查订单级 `settled_at`，一次结算未结算的打手份额、推荐和平台收入，末尾标记整单 `settled_at` 并发放积分；份额已有 `settled_at`。直接复用整单拦截或提前写整单已结算都违反本需求。
- `orders/refunds.py::posted_settlement` 可根据份额及流水识别已结算；部分结算转单协商退款是现有限定路径，不应自动将任意新部分结算套入。`process_order` 对 `PARTIALLY_REFUNDED` 与 `settle_order` 对 `PAID` 的判断存在路径差异，需结合实际退款状态复核。
- 历史订单可能无份额明细而使用订单级主打手兼容路径；零收益、转单、补贴、旧身份映射和直付隔离域不能凭常规双陪推断。先通过场景矩阵和源码确认；不能安全计算或证明守恒时阻止资金写入并形成待核对结果。

## 数据与来源设计

在现有订单唯一工单基础上设计**持久、可追溯的来源关联**：至少能区分老板主动申请和每条触发低星的评价，记录关联订单、评价、被评价打手、四项评分快照或可靠引用、产生时间及对应工单。评价来源必须按评价唯一去重；订单、评价、打手和工单关联在服务端核对，不能信任客户端提供的打手或金额。老板主动申请的理由与历史保持原样，追加低星不得覆盖。

#### 评价对象与结算份额映射（待评审）

`orders/evaluation_targets.py::evaluation_targets` 当前只列未释放的参与成员；仅当没有参与成员记录时才回退到旧单订单级打手。`CreateEvaluationSerializer` 对账户 ID 和旧用户 ID 使用不同匹配条件，`EvaluateOrderView` 在订单锁内重新核对这两个身份并按订单及旧用户 ID 防止重复评价。不能把客户端名称、订单的主打手字段或当前所有历史成员直接当作受影响份额，也不能在存在成员记录但均已释放时擅自启用旧单回退。这些是源码事实，实际多种历史数据及资金路径仍须容器核对。

方案需明确评价创建时锁内确认的目标如何对应到同订单的待结算份额，并在身份迁移、历史旧单无成员记录、成员已释放或转单、同一账号/旧用户映射不唯一及零收益时给出可审计判定。若无法证明某个评价只对应确定的本人份额，记录来源并使受影响资金进入待核对，不能静默指向主打手、误暂停另一人或跳过来源；正常路径不得因此默认整单暂停。目标变化或权限变化时应按服务端真实结果反馈，不将旧页面已显示目标视为可提交的凭据。对应前端及消息仅展示该角色按授权可见的信息，不以历史昵称充当身份标识。

这是逻辑数据合同，不限定必须采用 JSON 或新表。实现选择须证明数据库唯一约束、可查询性、迁移、并发原子性和历史兼容；按评价持久关联可避免同订单两位打手的低星互相覆盖。工单结案后发生低星时只追加审计关联，不重开、不可凭旧工单新建并行工单；老板与后台能区分来源和处理状态，不把新评价伪装为新的处理轮次。

为结算建立可从**活动来源与被评价打手**导出的阻断事实：主动售后活动时遵循对应结算路径的既有限制，`REPORT_APPROVAL` 的现有整单阻断不得因合并来源放松；否则低星工单活动期间只拦对应打手份额；结案后只释放该工单仍有效的阻断，不能无条件清除其他来源或独立资金限制。关联来源/阻断的存续、处理动作和审计应可在锁内一致核对。状态不明时禁止资金写入并标记待核对，而非推断可结算。

### 售后记录复用与处理轮次（设计候选）

静态源码显示，`AfterSaleView.post` 在符合主动售后条件且已有记录时，会复用同一工单并将状态改回 `OPEN`；处理前调用 `append_history`，重置本轮理由、处理结果及时间。因而工单主键和当前 `OPEN` 状态不足以区分历史低星来源与本次主动申请。用户禁止**低星触发**重开已结案工单，并未取消符合现有资格的老板主动再申请；两者不能混成“工单永不再打开”。

评审方案须为每次实际处理轮次建立稳定、可审计的边界，并将每条来源及其是否在该轮形成有效阻断明确关联；来源是否单独存表由研发决定。已结案后、老板再次主动申请前到达的低星仅保留审计关联，不得自行开启或排队一轮售后；后续主动申请复用工单时，不能仅因工单再次 `OPEN` 就把这些旧来源自动变为新一轮低星阻断。已创建的新一轮主动售后仍按该结算路径原有规则生效，不能借此绕开其限制。主动售后重开后收到的新低星，应按用户已确认的“处理中追加”归入当前处理状态；最终应影响的被评价者及其他来源的限制分别计算。历史工单没有足够轮次证据时不猜测来源或覆盖旧理由，应保留可核对状态并设计兼容方案。

独立测试使用至少两笔分别包含甲乙两位打手的隔离订单，每笔订单各自沿用一个工单：第一笔按甲低星创建 → 结案 → 乙低星仅留关联、不重开 → 在既有资格允许时老板主动再申请的顺序，核对旧低星不变成新来源、主动售后限制仍生效；第二笔按甲低星创建 → 结案 → 老板主动再申请 → 乙低星的顺序，核对乙的评价追加至当前处理记录并分别检查两位份额。两笔订单分开是因为现行规则每单每位打手只能评价一次，不能在第一笔中再次使用乙的评价构造第二条路径。另以独立订单覆盖评价、主动重开和结案的竞争及请求重试。每一步核对工单数量、轮次和来源、原理由/历史、各份额与钱包流水、各端状态及操作审计；真实状态和模型可用字段以评审后设计为准。本节不改变已确认的售后资格、退款或已到账收益规则。

## 事务、幂等和竞争顺序

1. 评价入口必须由服务端按已验证的四个分值判断，三维缺省按 `CreateEvaluationSerializer` 现有规则回填后再判定。订单、打手和分数取自服务端验证结果。
2. 评价创建、低星来源关联、无工单时创建工单及对结算阻断生效，应在同一数据库事务内完成；若失败则事务回滚并向老板返回可重试/核对的结果，不出现评价成功但无对应应处理记录。唯一约束加事务内重查处理同评价重试、双陪并发、主动售后并发与已结案场景。
3. 保持现有锁体系：先锁目标订单，再按已有资金锁顺序取得 `lock_order_money`、钱包/档案等锁；工单及份额锁在统一顺序中获取。不要在另一入口先锁钱包、评价或工单再等订单。完整锁顺序须研发核对转单、退款和补贴现有调用后固定，不能只依据文档更改资金锁次序。
4. 结算任务、后台结算、评价、老板主动售后、售后处理和退款竞争时，以同一订单锁内读取最新工单来源、份额与资金状态为准。先结算已提交的份额按已到账处理，不自动追回；低星先提交的对应未结算份额必须阻断。工单结案与新评价先后发生时必须遵循当前提交后的状态与已确认不重开规则，保留评价。
5. 结案/退款结果写入后，在事务提交后发送订单、报单、钱包与站内通知，按现有机制安排重试或重新计算；重复消息、worker 重启或请求重试不能导致重复关联、重复结算或重复退款。通知失败不能回滚已提交事实或视作操作未发生。

### 上线切换方案候选（待七角色评审）

先部署兼容新旧数据结构的版本并确认所有处理评价的服务实例均已具备新规则，再在服务端以可审计的统一切换记录启用；不要让仍运行旧评价路径的实例在启用后继续处理请求。切换事实、操作者和时间必须可追踪；切换中的请求和开关变更应有确定的串行顺序，以实际服务端事务结果界定新旧范围，不能依赖客户端传入时间。重复部署不得回填启用前评价或再次激活造成边界漂移。回滚前先评估新版本已产生的评价、来源和工单兼容性，避免旧版本继续接受评价却绕过已启用规则；无法证明安全时应中止切换并报告，而非清除已产生数据。以上是技术候选，需研发核对现有多实例发布与锁机制、测试隔离环境中的切换和回滚后才能定稿。

## 逐份额结算及财务约束

研发需在设计评审中明确份额级可结算、已入账和订单整体完成的持久状态与唯一幂等键，复用可证明安全的现有 `OrderProvider.settled_at`/账务事实，必要时设计受控迁移。对历史无份额订单保留可验证的单人路径；不能把两个打手的钱合并成一个可回放整单动作。

每次结算在订单锁和原资金锁下重算实际待结算份额、有效售后阻断、已入账/冲正、退款及剩余分配；校验整个订单累计的已入账、拟入账及剩余分配和退款按既有方案守恒。不能只对当前批次校验，或把已发放部分、推荐及平台收入重复计入。钱包入账、份额标记和幂等记录必须同事务提交；零收入及既有冻结/押金规则仍要准确处理。仅在所有必要份额和整单相关处理满足现行条件时写入与现有含义一致的整单完成标记；不能提前释放对后续份额的幂等保护。

涉及“另一位先入账 → 低星售后退款 / 部分退款 → 剩余份额”的计划和执行，需逐项审查现有普通退款/协商退款准入、确认令牌、历史流水、承担分摊、已结算追回授权、钱包余额不足及优惠/权益冲回。沿用已确认规则，不将本功能自动追回或新增承担方式。无法按现有规则安全处理的具体路径应返回可核对状态，记录缺口并由 team leader 提出用户决策；不能绕过现有退款一致性校验或造一条默认退款规则。

### 部分入账后的退款兼容性：评审必须闭合

静态证据：`orders/refunds.py::posted_settlement` 在订单总标记、正额成功入账流水或正额已结算份额任一成立时即识别为已结算；`build_refund_plan` 的普通已结算路径还要求原成功入账总额与原支付相等，否则返回 `REFUND_LEDGER_INCOMPLETE`。因此，双陪中一人因低星等待、另一人已入账时，即便用户看到“部分已结算”，现有普通退款也不能被假定可直接执行。`is_partially_settled_transfer` 又限定 `COMPLETION` 等条件，不能直接把它当作所有低星场景的退款许可。以上是静态代码发现，实际分支、附加校验和接口结果仍需研发及独立测试复核。

评审材料必须逐一给出以下组合的服务端动作、余额与流水结果和操作人员反馈：①尚无任何正额入账时申请全退或部分退；②一位陪玩已入账、另一位因低星尚未结算时申请全退或部分退；③结案解除低星阻断后再发起退款；④请求退款与另一份额结算并发；⑤此前已有部分退款或资金冲正。每个组合分别覆盖普通退款、现有协商退款是否具备准入、退款预览令牌过期或事实变化后的重算，以及退款结果未知后的查询。不能用“先暂缓所有退款”作为已确认的业务决定，也不能仅用现有转单协商路径掩盖普通低星售后的缺口。

对第 ② 类情形，设计须说明已入账份额、未入账份额、推荐与平台留存、老板退款和原支付之间如何核对；系统不得因评价自动追回已到账收益。若主动发起退款依照现有规则可能产生追回，其授权、确认内容及可用余额不足的处理必须与现行产品约定逐项核对，不能将“低星不自动追回”扩展解释成退款永不追回。若现有规则无法覆盖某一组合，记录具体冲突、候选方案及对应业务影响，交 team leader 决定是否需要用户决策后才能通过评审；不要伪造可退款结论。

推荐人及平台收入、积分、老板权益沿用原发放时点和去重约束：某个打手份额提前入账不应提前发放，也不能在后续整单完成时重复发放。要检查 `award_order_points`、消费确认、会员及券的调用点，按各自真实条件实施；不把所有权益强行改成同一时间点。

## 客户端与权限接口合同

- 打手 H5 和 Web：从授权的服务端字段显示本人是否受阻、对应收益待结算/已入账/待核对与售后处理结果；另一打手不可见私密细节的边界按现行权限与最终确认设计。不能将订单有售后直接推断本人收益必然受阻。
- 后台 Web（桌面及 iPad Pro 12.9 英寸横屏，约 1366 × 1024 CSS 逻辑视口）：客服、售后、财务、管理员按实际权限看到必要的订单、来源、被评价打手、处理记录和对应结算/钱包结果，平板保留触控空间；修改、退款和角色配置各按注册权限点与实际授权限制，操作结果及冲突可核对。视图中的来源不应泄露老板匿名评价身份或售后私密内容给无权用户。
- 接口须同时提供可区分的工单状态和本人份额结算状态，并保证旧客户端对新增字段兼容；具名字段、权限检查位置、通知事件和错误码由研发基于既有接口出具契约，不应以页面文案作为唯一权限或账务依据。

## 迁移、部署和待核实问题

迁移须兼容现有订单唯一工单、旧账号映射、已结案记录、既有审计和已入账流水；历史已有主动售后不得默认转换成低星来源，也不得重新开户或改动账户余额。对可可靠识别的旧数据采用可重复校验的迁移；来源无法确定时保留未知而不猜测。用户已确认只处理上线后的新评价，上线前历史低星评价保留查询，不追溯批量创建售后；须设计可审计的服务端上线切换边界，并处理切换附近的并发、重试和部署回滚，具体方案经七角色评审后实施。迁移前备份、预检约束和迁移后核对只针对隔离测试及授权环境；不可覆盖当前用户工作区。

开发前由研发将已确认的资金规则与现有普通退款路径逐个映射，明确可支持和不可安全支持的具体组合；确认“已结案后新增低星”的前台表述、处理结果展示及权限边界。任何需改变资金承担、追回、历史追溯或权益时点的分支先交 team leader 和用户决策。用户已确认的四项评分、各打手暂缓及已结案不重开，不需要重复提问。

合成场景与本地单元数据分工见[测试数据与证据设计草案](low-rating-aftersale-fixture-plan-20261103.md)；这是准备方案，尚未构成测试执行或数据创建记录。

独立测试人员基于 PRD 的全部验收矩阵（当前为 L1–L23，评审时以锁定版本为准）编制可复现用例。构建当前工作区快照并记录镜像 ID、源码哈希与迁移，在本地 WSL 独立 Compose 启动实际 MySQL、Redis、ASGI、worker/beat 和打包 Web；验证数据库、消息和支付隔离。只用合成老板、打手、后台岗位、钱包与凭证；微信工具和浏览器作宿主客户端，指向隔离容器。不得把历史非容器测试、内存队列或示例原型列为本轮通过。
