# XA 团队接手与瀑布迭代工作底稿

日期：2026-11-03。状态：接手及设计中；更名代码已有改动，正式 PRD 评审前发生的改动列为流程偏差，尚未通过本轮验收。

## 团队与职责

- Team leader：核对业务规则、确定迭代优先级、分析完整测试报告及调整建议；资料不足以决定的业务问题交用户决断。
- Product leader：梳理老板、打手以及客服、售后、财务、管理员四类后台人员的操作、状态和反馈，形成可评审 PRD、原型及验收条件；根据复盘设计下一轮。岗位权限以现有配置和用户确认的业务为准，不自行假定四类岗位的授权范围。
- UI/UX leader：依据 PRD，使用用户指定的 impeccable 与 huashu-design 技能设计三端产品原型，负责视觉和交互审查并参加每轮评审。用户最新决定放弃 Figma，改用本地网页原型，数据可完全 mock；Figma 历史文件仅供追溯，不再是本轮交付依赖。
- 本地网页原型使用已确认的视觉方向和三端对应组件规范；各页面分别设计加载骨架与有数据状态，区分请求完成后的真实空态，并显著标注模拟数据。原型不连接真实业务数据，也不能作为功能验收证据。
- 用户明确三端当天已有视觉更新，本地网页原型应以现有实际界面和源码为基准忠实迁移，逐页、逐 Tab、关键弹层和状态核对；代表性样稿不等同于全量覆盖。管理后台以桌面和 iPad Pro 12.9 英寸横屏为布局目标，并保留触控空间。
- Develop leader：依据已确认的需求和设计拆分任务、协调接口与文件归属，审查开发交付并移交测试。
- 开发 A：后端、陪玩 H5 和协调后的管理后台；开发 B：老板微信原生小程序；测试 C：独立准备隔离环境、执行验收和提交报告，不自行修改业务代码。

当前会话最多同时运行三个子 agent，因此七个角色按阶段轮换；这不代表七个角色同时在线或已完成共同评审。共享文件、接口和迁移必须先指定唯一负责人。工作区已有大量未提交内容，均作为现有成果保留，不重置或覆盖。

## 每轮关口

1. **盘点与设计**：核对用户最新确认、当前代码和带日期的证据；产品整理三角色流程、业务规则、异常、权限、资金结果、原型与验收标准。存在业务分歧或缺失规则时交用户决断，不能自行发明。
2. **PRD 与原型评审会**：每轮开发前，team leader、product leader、UI/UX leader、develop leader、后端及陪玩端开发、小程序开发和测试人员共同审查同一版本 PRD 和原型。原型必须细致到可指导开发，覆盖对应字段、操作、权限、加载/有数据/适用空态和异常反馈。记录每人的意见和确认；七人全部确认、阻塞问题解决后才开始开发。当前同时在线子 agent 数有限，各角色轮流审阅同一份记录并互相复核，不将未回复视为确认。
3. **开发**：评审通过、需求和必要决策明确后，开发负责人协调文件和接口，按范围实现；需求发生变化时返回设计与评审。
4. **测试**：开发完成后，由测试人员在 WSL 中部署打包后的容器，用隔离的真实业务代码、接口与合成业务数据执行功能验收，提交结果和证据。另准备独立的单元测试数据供研发本地快速验证，不能替代容器业务验收。不得接触生产资金、真实客户或真实消息接收人。
5. **复盘和下一轮**：team leader 分析完整报告、确认问题及调整，product leader 更新设计后再启动下一轮。测试失败不是验收通过，模拟数据不能充当业务验收。

## 首轮候选范围

优先核对已实现的余额订单、接单/派单、履约报单、审核结算、提现，以及已有确认规则的售后；先定位最小具体缺口，再冻结本轮设计和测试边界。此范围是工作假设，并非声称所有分支已经设计或完成验收，也不自动引入微信直接支付。

基线入口：[业务覆盖与待核对清单](business-coverage-20261103.md)、[三端订单状态与原型验收基线](../订单派单三端状态与原型验收基线.md)、[业务工作基线](../CORE_BUSINESS_WORKING_BASELINE_20261027.md)。历史 PRD 与当前实现存在技术栈、视觉和业务口径差异时，应逐项核对，不以旧文档覆盖最新用户指令或实际代码。既有原型使用示例数据，不能视为业务验收。

已发现的验证缺口包括：部分小程序售后、预约、会员和 TAG 交互尚未在微信开发者工具或实机验证；提现页面曾间歇出现 401，原因未证实；外部消息投递和真实线下打款不在已有隔离测试的证明范围。微信直接支付测试域未接入真实网关。

## 环境和交付边界

用户最新明确：老板使用微信原生小程序下单；打手使用陪玩 Web，陪玩端原型及布局只考虑桌面，不要求手机适配；客服、售后、财务和管理员使用 Web 管理后台。原有陪玩 H5 技术与业务代码仍须盘点，桌面限定不意味着删除功能。按 2026-11-03 项目协作约定，后台布局目标为桌面及 12.9 英寸 iPad Pro 横屏（约 1366 × 1024 CSS 逻辑视口），保留平板触控空间，不要求手机端适配。老板端当前只交付微信原生小程序。每次打开微信开发者工具模拟器验收或截图前，最大化窗口并确认完整屏幕可见，目标为回读的 iPhone 12/13 (Pro)、390 × 844。测试和截图应记录实际环境，不把宿主替身称为开发者工具验收。

用户补充并确认：售后仅针对老板发起售后或订单出现差评时开始处理；1–2 星评价自动创建售后工单，售后处理完成前暂缓结算、处理后恢复。评价出现时收益已到账的，仍自动建工单，但不自动追回已到账收益；该决定也不等于自动退款。重复触发等边界须按现有规则和具体场景明确后设计。静态审查显示目前评价不会自动创建售后，尚需开发与容器验收。

进一步确认：综合、技术、态度、沟通任一评分为 1–2 星即触发；双陪仅暂缓被差评打手的未结算收益。已有售后处理中追加评价，已结案则不再开启新一轮。当前订单级售后拦截可能同时影响其他打手，必须设计并验证符合新规则的结算范围。

用户随后确认：低星自动售后只处理上线后的新评价，上线前已有低星评价保留查询，不批量追溯建单。上线边界及多实例并发切换方案需要评审，并按低星售后 PRD 的 L21 在隔离容器验收。

品牌更新：全系统“兴安电竞”改为“声浪电竞”，“兴安币”改为“浪花”。用户确认仅更名，沿用既有换算比例和历史余额。域名、第三方账号和历史记录需盘点后确定处理方式，不能将更改展示名称直接等同于已完成外部迁移。

用户进一步确认：历史聊天和评价原文照常显示，上传凭证保留原件；系统文案及运营内容改用新名称。原始记录保留供追溯，不能机械替换客户原话或证据。

研发只读核查：可评估 `deploy/local-validation.sh` 与对应 Compose 配置作为本地 WSL 打包部署入口，但其持久验证库不能直接视为全新隔离库，脚本可能加载本机微信凭证，测试前必须核对合并配置并禁用真实外部渠道。现有容器测试配置将部分 Redis、队列和 Channels 替换为内存，不能证明真实跨进程链路；端到端验收需要隔离数据库、Redis 和实际 worker。微信开发者工具及浏览器是宿主交互客户端，业务服务和被测打包产物运行在 WSL 容器中，报告须明确这一边界。上述为静态审查，尚未构建或验证。

持续场景库使用固定独立 Compose 项目和持久数据卷，跨迭代保留合成业务及媒体数据；单元测试库与场景库隔离。每轮迁移前先备份并核验，禁止以重建或重新初始化替代保留数据。每轮部署后打开对应容器页面供用户查看，标明隔离场景数据及构建版本。

本地网页原型完全使用 mock 数据，原型页面及交互不连接真实业务接口、业务数据库或外部服务；展示数据、状态切换和操作结果均须标为示例，跨端数据是否同步也应说明。原型预览与 WSL 容器中的隔离业务验收是两套独立用途：原型交互检查不能作为业务功能验收证据，持续保留的 WSL 场景数据也不注入网页原型。
