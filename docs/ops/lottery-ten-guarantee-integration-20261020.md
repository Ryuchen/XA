# 十连非积分奖保底补充验收 · 2026-10-20

按用户最新确认，增加**每次十连至少获得1份非积分奖**，并保留68体验单240抽保底。基础概率继续留在后台配置；本地活动仍为原来的13个奖项、全0概率和关闭状态。

## 已确定的规则

| 场景 | 结果 |
| --- | --- |
| 十连前9抽全部是积分奖 | 第10抽从基础概率大于0的非积分奖中，按原权重归一抽取 |
| 前9抽已自然获得非积分奖 | 已满足十连保底，第10抽正常抽取 |
| 前9抽已获得240保底68体验单 | 已满足十连保底，不再额外补奖 |
| 第10抽同时达到240抽保底 | 240规则优先，必得68体验单；本次十连也满足非积分奖保证 |
| 68体验单基础概率为0 | 仍可触发240抽保底，不进入十连兜底候选池 |
| 没有正基础概率的非积分候选 | 十连在扣费前完整拒绝，单抽仍按普通奖池规则校验 |
| 连续进行10次单抽 | 不触发本次新增的“十连批次保底”，但共用240抽进度 |

非积分奖包括专属服务、冠名、TAG等，68体验单也计入。自然抽中68仍重置240抽进度。十连消耗10倍入场积分和10次每日额度，没有额外保底费用。中奖积分不能垫付本次十连入场费。

十连兜底会提高实际获得非积分奖的机会，奖池公示仍标明**基础概率**及额外保底规则，不再使用“单抽与十连概率相同”的文案。若要开放十连，后台除配齐总和100%的概率外，还需至少一个正概率非积分奖。

## 实现与原子性

后端沿用整批事务、奖品／钱包／积分锁顺序和幂等批次。第10抽兜底时只从正权重非积分候选中选择；240硬保底优先。新增 `is_ten_guarantee` 与实际 `selection_pool` 审计快照，保留原基础概率快照。硬保底记录单一目标权重1、票号0，避免把指定奖误记为基础随机命中。

库存不足或任一交付、积分、广播写入失败会回滚整批，不留下部分扣分、奖品或保底进度。重放返回原中奖及保底标记，不重复扣分或追加奖励。历史批次不改写、不补发。

原生页显示“十连至少1份非积分奖”、本次非积分奖数量、实际末抽“十连保底”标记，以及240抽标记。标记仅使用后端持久结果；自然SR或240奖不会被误标为末抽兜底。后端报告不可用时只禁用十连，保留正常单抽入口。逐张揭晓、跳过／简化动画和底部五项导航继续保留。

微信开发者工具另验证3个页面场景：末抽SR兜底，第5张240硬SSR且不误标十连兜底，以及无候选时十连禁用但单抽可用。两轮十连各只发1个POST，10张结果与跳过动画一致，底部导航保留，退出演示后回到原首页。

**界面演示拦截了全部HTTP请求，使用测试数据，没有在真实账号上扣积分或发奖。** 实际抽奖事务、库存、随机边界和并发由隔离数据库测试验证；演示截图不代表实际获奖，也不代表后台已采用截图中的概率。

## 本地更新与数据保护

迁移0017已应用，只增加中奖记录的两列，未回填历史奖品。两个Web进程及Celery worker／beat已更新，9个普通本地容器均运行，Django系统与迁移检查通过。更新前已另做整库备份；最终对25张资金、积分、奖池及批次／保底表的旧列、原行进行只读核对，全部不变。真实本地小程序读取到十连最低1份非积分、240抽优先的新规则，活动仍关闭、基础概率仍为0。

本轮保留所有基础概率和活动关闭状态，不切换原小程序账号，不进行真实抽奖。独立MySQL测试容器及匿名卷已精确清理；旧版无十连额外保底的验收档案作为历史记录保留，以本报告为最新规则。
