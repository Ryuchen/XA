# 声浪更名：存量内容可审计处理设计

日期：2026-11-03。状态：供七角色评审的确定方案；仅设计，未开发、未访问数据库、未进行功能测试。适用用户已确认的范围：历史聊天、评价与回复照常显示原文，上传凭证保留原件；系统文案与运营内容改名；资金、历史余额、兑换比例不变。任何来源不明的内容不得自动归类为系统消息，也不得先批量替换再倒推来源。

## 内容边界和具体机制

| 对象及字段 | 处理方式 | 不处理的内容 |
| --- | --- | --- |
| `announcements.Announcement.title/content` | 在运营确认来源、预览原文和拟改文后，以原对象行锁和原文字段哈希比较，通过现有公告编辑操作保存新运营文本；同一事务追加不可覆盖的内容版本事件。 | 不改公告 ID、排序、状态及历史事件；导入命令按标题查找的兼容性须单独处理和测试，不能因改标题重复建公告。 |
| `orders.ServiceItem.name/description/rules/details_html/purchase_note/highlights`，以及 `orders.Gameplay.name/subtitle/rules/details_html` | 分对象、分字段人工确认并通过现有对应编辑权限写入；同一事务保存变更前后版本事件及哈希。`highlights` 按完整 JSON 值处理；富文本继续走现有净化规则，不修改 URL、HTML 属性、模板变量、金额或游戏专名。 | 商品键、价格、抽成、订单快照、媒体路径和其他字段不因改名变化；服务回落玩法内容时分别核对真实来源，不能只改服务表。 |
| `console.KookDispatchConfig.routes[*].template` | 使用现有 `dispatch_config:view`/`dispatch_config:edit` 配置流程，逐路由预览并修改模板，复用现有 `revision` 比较和锁；另以同事务的版本事件保存经过权限保护的模板前后值/哈希与路由 ID。仅修改模板文本，保留频道、开关、变量、URL 与密钥。 | 不重新发送历史消息、不操作真实接收人；不记录 token 密文或完整配置。现有外部频道无法访问时是未完成依赖。 |
| `site_messages.Message.title/preview/detail` 中**有证据确认由系统生成**的历史消息 | 不更新原 `Message`。由授权人员在后台按消息 ID 与允许字段逐条核实后，创建只用于展示的覆盖版本：消息 ID、字段、原文哈希、展示值、来源证明、审核人/时间与原因；覆盖仅在原文哈希仍匹配、覆盖有效时生效。若某条消息多个字段一起更名，作为同一原子版本发布，避免标题和正文来自不同次变更。 | `Message.type`、关键词、`related_order_id` 单独不足以证明来源；来源不明、客服/老板/打手原话一律不自动覆盖。`action_url`、接收人、阅读状态、历史投递及发送动作保持原样；不改历史通知原文或重新发送。 |
| 老板/打手聊天、评价、回复、上传截图/凭证、财务流水和审计原始记录 | 原始值、权限及页面原文保持不变；结构化金额由原有格式化入口显示“浪花”。 | 禁止为消除旧称而改写用户原话、证据、资金流水备注或审计记录。来源不明的财务自由文本不覆盖，列入人工核查。 |

公告/服务版本事件采用同一通用 `ContentChangeEvent` 的对象类型与主键、字段、操作类型、前后值（限授权读取）、前后 UTF-8 SHA-256、操作者业务账号与名称快照、时间、原因和请求 ID；事件只追加不覆盖，事务回滚不留半条事件。仅保存实际改变的白名单字段，不保存凭据、收款账号或未授权消息正文到通用日志。消息覆盖版本另保存来源确认依据和预览文本，管理员按原消息访问范围才能查看其内容；角色、字段白名单和授权均在服务端执行。对象被删除后历史事件仍可追溯，不得让级联删除抹去版本记录；身份删除时保留非敏感操作人快照。日志/报告默认输出对象类型、合成 ID、哈希及结果，不输出私密正文。

## 权限、审阅和发布

沿用公告 `announcement:view` + `announcement:edit`、商品及玩法 `service:view` + `service:edit`、KOOK 配置 `dispatch_config:view` + `dispatch_config:edit`；以上操作仍须满足 `IsConsoleUser`、账号启用及当前数据可见性。历史消息覆盖不是发送消息：新增独立 `message:brand_override`，只允许同时持有 `message:view` 和该权限的后台人员逐条核对、预览、发布和撤销；不将它等同 `message:push`，不以此改变消息原有接收者授权。新权限默认不向既有角色自动授予，由用户认可的权限管理员在隔离环境中明确配置；不得凭客服、售后、财务、管理员岗位名称推导授权。无权限时 API 拒绝并且不返回原文或候选文本，前端隐藏入口并显示可执行的权限提示。

后台提供候选清单、原/拟显示值对照、来源依据、理由与发布操作；候选扫描只定位，不自动生成有效覆盖或自动认定来源。按对象白名单提交 ID、字段、预期原文哈希、拟显示值及原因；服务端重新读取并校验类型、字段、权限、长度和富文本安全，逐条拒绝非白名单对象。确认范围仅限被选中的合成或获授权数据；不能跨客户广播或自动批量批准。系统历史消息审核人与操作者可以是同一人：此处只定义已有授权核对，不凭空增加双人审批业务规则。

## 一致性、冲突与回退

1. 采用数据库中的**原始字段 UTF-8 字节的 SHA-256**；不对字符、空白或 HTML 做隐式归一化。`null`、空字符串和 JSON 的区分应由带类型的稳定编码明确，JSON 使用固定键顺序、无损值的确定性序列化。提交与读取使用同一版本的编码规则；同时记录算法/编码版本，防止升级后误匹配。
2. 发布/编辑时锁原对象；若原字段哈希与预览时不同、对象已删除或权限改变，整组不发布，返回 409/权限错误与“刷新后重新核对”，不覆盖别人修改。对象键及覆盖类型范围受数据库唯一约束；并发两次发布仅一次成为当前有效版本，另一方以版本冲突返回，不能生成重复有效覆盖。成功后的重试应使用请求 ID 返回同一结果，不能重复追加历史版本。
3. 读取消息时先执行现有 `recipient_account=request.account` 的列表/详情过滤和访问授权，再对已授权对象批量加载有效覆盖。每次对原字段重算哈希：不匹配则跳过整组覆盖、按原始消息显示并记录受控的待核对状态，不静默套用过期文本；原始返回可能仍包含旧称，此时该条列为未完成而不是验收通过。非授权者不得借覆盖查找、错误码或日志推断消息存在。覆盖不改变已读状态、消息顺序、分页游标、未读统计或通知推送。
4. 撤销覆盖是追加事件并把当前版本标记为停用，不删除原值或审核轨迹；恢复旧显示只对仍匹配的同组原文有效。公告/商品的回退通过同一编辑入口提交经授权的旧值，比较当前字段哈希，追加新事件，不抹去历史。原始数据已被其他人修改时不得强制回退，必须重新预览并确认。静态文件、图像或外部模板另维护旧资源与新资源的引用和内容哈希，不能将历史凭证作为可替换素材。
5. 页面列表、详情、后台预览和系统通知读取应由同一服务端展示规则产生；只读搜索、排序、分页与现有数据授权保持语义，禁止把全局字符串替换放在 `__str__`、数据库写入钩子或微信客户端。服务/公告编辑是实际内容变更，核对对应检索、详情回退与导入键兼容，不能改变活动、商品和金额业务。若事件或覆盖版本迁移失败则停止上线；禁止以不记录版本的直接 SQL 作为替代。

## WSL 场景及单元验收

使用固定 WSL Compose 项目的隔离合成场景库和媒体卷；开始前备份数据库与媒体并在独立卷演练恢复，禁止重建或覆盖持续场景库。容器镜像、迁移、小程序副本哈希和 UI 版本与案例对应；研发本地单元数据与容器业务场景分开。

1. 为公告、服务/玩法回退、系统消息三字段、KOOK 合成路由分别创建含旧名称的数据；通过真实后台接口核对预览、授权、发布和撤销。检查原始历史消息不变、当前显示新称、有效版本和操作事件匹配；聊天/评价与上传凭证含旧名称仍原文展示，数据哈希不变。
2. 分别验证只读账号、无 `message:brand_override`、账号停用、他人消息、非白名单字段及缺少来源证据的拒绝和无内容泄露；来源是否真实由有权限人员根据证据核实，系统不能仅凭填写的文字证明其真实性。覆盖不能代替原消息权限，也不能自动获得发送权限。
3. 两个独立 MySQL 连接交错提交、原文编辑与覆盖发布、版本撤销与重新发布；校验仅一个有效版本、过期原文不会被覆盖、返回 409、失败事务无半条审计、请求重试不重复事件。管理员删除/恢复与导入重复执行需核对对象与事件保留。
4. 核对 `ServiceItem` / `Gameplay` fallback、富文本净化、JSON 值、图片链接、筛选/分页、旧标题导入兼容和 KOOK 变量/频道/版本；仅用隔离接收端或将外部投递标未覆盖。验证列表、详情、后台及微信原生页面结果，微信开发者工具截图前最大化并确认 iPhone 12/13 (Pro) 390 × 844 和完整屏幕可见。
5. 在相同合成账本和迁移前后快照核对订单、钱包、退款、押金、收益、提现、优惠券、流水、金额与关联；字段缺失须失败或标无法比较，不能只验文案或新空库。检查消息已读、分页、实时更新与服务原有权限不变。记录各场景通过/失败/阻塞、日志与截图；真实客户、外部资金及正式消息不在本轮隔离证据内。

## 实施范围和待评审事项

候选修改仅限上述内容模型/迁移、对应后端权限和序列化/视图、后台审核界面、现有小程序与陪玩展示，以及针对该机制的单元和容器验收；共享模块及接口由研发负责人先指定唯一负责人。设计不改变资金、报价、业务状态、消息收件人或客户原话。`ContentChangeEvent` 和消息覆盖的数据模型、权限名、审计可见范围及批处理规模均为本稿具体提案，需七角色针对同一版 PRD 和本设计确认；该设计本身不是开发授权或验收报告。
