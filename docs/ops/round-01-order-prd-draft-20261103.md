# 第一轮候选 PRD：单陪余额订单的三角色闭环

状态：**草稿，待业务确认**。日期：2026-11-03。本文用于评审首轮范围、页面信息和验收条件；不代表发现的问题已经修复、测试已通过，亦不改变已有资金和售后规则。

## 目标与范围

以同一笔隔离测试订单贯穿下单老板使用的微信小程序、打手使用的陪玩 H5 和 Web、后台 Web：余额报价与下单 → 公开直接抢单或有权限人员指派 → 履约 → 报单与审核 → 按现行规则核对收益。后台主要面向客服、售后、财务、管理员四类岗位，具体操作以实际权限为准。另以独立订单验证待接单取消、超时和驳回重提。先逐端走查当前代码及真实接口，记录差异，再确定本轮最小修复；未经需求与设计确认不进入开发。

首轮建议限定为**单陪、余额支付、非礼物订单**，覆盖公开直接抢单和客服待派两条路径。公开报名后老板选人、指定陪玩、双陪、转单、部分及已结算退款、提现、微信直付属于已有或后续独立链路，保留兼容，并按走查结果安排后续迭代；需新增或有冲突的业务规则再交用户决断。退款路径仅使用现有允许状态，不以旧文档中「终态一律不可退」代替现行售后规则。

## 三端文字线框

以下为待核对的信息和动作，不断言已有页面已完整实现；在现有页面和已确认设计方向上做最小必要调整。老板端以 iPhone 12 Pro（开发者工具回读 iPhone 12/13 (Pro)，390 × 844）为目标；后台 Web 以桌面和 12.9 英寸 iPad Pro 横屏（约 1366 × 1024 CSS 逻辑视口）为布局目标，并保留平板触控操作空间，不要求手机端适配；按用户最新要求，陪玩端以桌面为唯一布局和原型目标，不要求手机端适配，现有陪玩 H5 的业务能力仍需保留和核对。

### 后台四类岗位：权限及待核对操作

岗位名称是使用场景，不自动等于权限模板。当前 `services/backend/console/permissions.py` 注册订单查看、派单、退款、报单审核、钱包及管理等细分权限；`services/backend/console/migrations/0002_seed_roles.py` 是历史初始化角色，实际账号可配置多个角色，不能用迁移中的初始权限推断现有授权，也不能假设现有数据库已有单独“售后”角色。以下为结合首轮流程需要核实的操作，不是授权决定：

| 岗位 | 需结合实际授权与现有流程确认的操作及反馈 |
| --- | --- |
| 客服 | 接收咨询、查看订单及待派，按获授权的动作指派；核对处理结果、失败原因和订单更新。 |
| 售后 | 查看相关订单与售后进度、按获授权动作处理问题；核对限制原因、处理结果和三端反馈。转单及协商售后不属于本轮候选核心范围。 |
| 财务 | 查看涉及余额、退款及流水的记录，按获授权动作核对账务；确认金额、支付状态、流水和结果待核对反馈。 |
| 管理员 | 查看并配置人员角色及权限，核对敏感动作权限、操作记录和异常；具体权限以当前账号配置及服务端为准。 |

测试需分别用实际配置的隔离岗位账号核对可见菜单、允许及拒绝动作、操作人与可执行的错误反馈；如缺少岗位与权限对应关系，先核对现有配置或向用户确认，不能预设默认授权。

### 售后启动边界（用户最新确认）

售后仅在老板发起售后，或订单出现符合规则的低星评价时开始；普通正常履约不进入售后流程。用户已确认上线后的新评价中，综合、技术、态度、沟通任一项为 1–2 星时自动创建或关联售后，并暂缓受差评打手尚未结算的收益；这不自动意味着退款、终止服务或追回已到账收益。处理动作仍按已确认规则与实际授权执行。

现有证据：`services/backend/orders/aftersale.py` 的 `AfterSaleView.post` 处理老板针对本人订单提交售后，并检查已有记录与申请条件；`services/backend/orders/views.py` 的 `EvaluateOrderView.post` 创建评价并通知更新，代码中 `score >= 4` 用于评价广播，**不能把该条件反推成差评定义或售后触发阈值**。本次只读静态检查不能证明所有评价入口均已触发售后，也不能证明现有功能已经满足用户最新要求。

用户已进一步确认：双陪仅暂缓被差评打手未结算收益；已有处理中工单则追加评价，已结案不因低星开启新一轮；历史低星保留查询、不批量追溯建单。详细规则、兼容及尚需评审的资金与权限边界以[低星售后 PRD](low-rating-aftersale-prd-20261103.md)为准。不得据现有 `score >= 4` 广播逻辑自定阈值，也不得将低星视为退款批准。本轮如涉及该功能，须在详细设计和七角色评审通过后开发；正常余额订单路径仍须遵循其自身评审与验收门槛。

### 1. 老板：确认订单 → 订单详情

```text
确认订单
服务 / 套餐 / 数量 / 游戏资料
安排方式：[公开给陪玩接单] [客服安排]
公开时按现有能力选择直接抢单
报价：原价 / 适用优惠 / 实付 / 当前余额
[确认提交]    余额不足：联系客服

订单详情
订单号 / 服务 / 已支付金额
当前安排、接单或履约状态；适用时显示服务端截止时间
待接单且服务端允许取消时：[取消订单] → 明确金额与退回余额
结果未知：核对原请求 / 查看订单与余额 / 联系客服
```

报价和金额以服务端为准；重试使用同一未决请求，不将网络中断直接表述为扣款失败。取消按钮是否可用按当前服务端状态决定。

### 2. 后台获授权人员：待派列表 → 指派 / 审核

```text
待处理订单
订单号 | 老板身份 | 服务 / 人数 | 截止时间 | 状态 | [查看 / 指派]
指派：核对订单与陪玩身份、资格，提交后显示服务端结果
失败：已被处理 / 资格或名额变化 → 刷新后处理

报单审核
订单号 / 陪玩身份 / 业务状态
入队截图 / 结单截图 / 战绩截图
收益口径与结算状态（以服务端核定为准）
[通过] [驳回：填写原因] → 操作结果 / 待核对
```

只读与审核权限按当前后台权限控制。审核与售后相互影响时展示服务端限制；不从已完成履约推断收益已可提现。

### 3. 陪玩：接单 → 履约 → 报单

```text
订单工作台
公开可接订单 / 本人已接订单
服务要求 / 订单号 / 收益信息（标明口径） / [抢单或查看]
已接单：[开始服务，上传入队截图] → 服务中：[完成服务，上传结单截图]

报单
关联订单 / 已提交的入队截图和结单截图 / 补充至少一张战绩截图
[提交审核] → 待审核
驳回：显示原因 → 补充材料 → [重新提交]
收益：待审核 / 待核对 / 已核定或已入账，以实际钱包状态为准
```

公开订单可见性、资格、容量、可见延迟和操作状态由服务端校验；客服待派订单在指派前不向公共池开放。入队、结单截图分别伴随开始和完成服务操作提交；报单提交需要服务完成且三类凭证齐全，驳回后的补充操作以服务端允许项为准。依据：`apps/provider-vue/src/views/Orders.vue` 的履约动作、`apps/provider-vue/src/views/Reports.vue` 的缺失凭证及提交条件；实际提交及异常处理仍需容器验证。

## 单陪订单状态、责任和异常矩阵

此矩阵限定本轮候选余额单；订单状态、支付状态、报单状态和结算状态是独立维度。以下状态与允许动作按当前源码及[订单状态基线](../订单派单三端状态与原型验收基线.md)整理，页面展示与真实操作结果仍待本轮验证。

| 阶段与转换 | 老板 | 后台获授权人员 | 陪玩 | 异常和核对 |
| --- | --- | --- | --- | --- |
| 报价 → 下单成功，订单 `PENDING` | 确认服务端报价、余额及公开/客服安排；结果不明时核对原请求。 | 按权限查看订单和客服待派队列。 | 仅在公开、符合资格与可见规则时可见。 | 报价变更重新确认；请求结果不明不能断言扣款失败或盲目再付。核对订单、钱包和原请求回执。 |
| `PENDING` → `GRABBED` | 查看实际安排及接单结果。 | 可在有权限及服务端允许时为订单指派合资格人员。 | 公开直接抢单成功，或获得客服指派后查看本人订单。 | 提交时重查资格、容量、期限和订单状态；已被处理或过期时以服务端结果为准。客服待派在指派前不可从公开池、抢单或报名取得。 |
| `GRABBED` → `IN_SERVICE` | 查看服务进度。 | 查看履约进度，按现有权限处理异常。 | 开始服务并提交入队截图。 | 上传、网络或状态变化导致结果不明时核对订单和截图；不要将页面按钮状态当作业务成功。 |
| `IN_SERVICE` → `COMPLETED` | 查看服务完成结果，售后状态另行展示。 | 查看订单及报单；审核按权限执行。 | 完成服务并提交结单截图，再补充战绩截图并提交报单。 | 售后等限制以服务端允许动作为准；订单完成不等于报单通过或收益可提现。 |
| 报单 `DRAFT` / `REJECTED` → `PENDING` → `APPROVED` 或 `REJECTED` | 按现有订单页面查看本人可见结果。 | 查验凭证，记录通过或驳回原因。 | 补齐至少一张战绩图和缺失凭证后提交；被驳回可按允许项补充并重提。 | 重复提交/审核不能重复产生收益；结算方式、售后窗口、流水及可用/冻结以实际订单和服务端为准，不假定审核即到账。 |
| `PENDING` → `CANCELLED` | 订单所属老板在服务端允许时主动取消；查看实际退款。 | 核对取消原因、订单和账务。 | 不能再接取已取消订单。 | 待接单到期也按既有规则取消。退款只退实际余额支付，优惠券恢复受原有效期约束；取消和超时竞争时不能重复退款。 |

订单枚举见 `services/backend/orders/models.py`，报单枚举见 `services/backend/wallet/models.py`；老板主动取消入口仅允许本人 `PENDING` 订单，见 `services/backend/orders/views.py` 的 `CancelOrderView`；优惠券约束见[核心业务基线](../CORE_BUSINESS_WORKING_BASELINE_20261027.md)。不能把其他状态下的售后或退款归入该取消入口。

## 验收场景（待测试人员据代码细化数据与预期）

| 编号 | 场景 | 预期及证据 |
| --- | --- | --- |
| R1 | 老板对单陪服务取报价并用余额下单 | 服务端成交金额与订单、余额流水对应；同一请求重复提交最多创建一单、扣款一次；三端以同一订单号核对。 |

| R8 | 角色边界 | 老板只能查看本人数据；陪玩仅操作本人或当前合资格公开订单；后台客服、售后、财务、管理员以各自实际授权核对菜单、动作、拒绝反馈及审计，只读角色不能审核或指派。 |

所有本轮功能测试，以及开发过程中的运行验证，均使用**打包后部署到本地 WSL 的容器**执行；记录镜像版本或摘要、构建来源、部署配置、数据库和服务地址及执行结果。先核对隔离边界，再创建测试数据。数据库、账号、钱包和凭证使用与生产隔离的测试资源；金额、订单状态、权限及并发采用真实业务代码和真实接口，MySQL 行锁验证不以 SQLite 跳过项冒充通过。外部支付、真实消息和人工打款只在安全的测试环境单独验证；未接入或隔离范围须写入报告。历史非容器测试、原型演示和以往专项结果单独列作历史参考，不计入本轮容器验收通过证据。

## 待核实与决策门禁

1. 当前工作树存在大量未提交变更；由研发先记录本轮测试版本、实际陪玩入口、配置和迁移状态，不覆盖现有工作。
2. 三端现有具体字段、文案、错误提示及实时刷新要以实际页面和接口逐项走查，形成差异清单；文字线框是候选要求而非已验收截图。
3. 核对当前服务类型的入队、结单、战绩凭证要求、售后窗口、收益冻结与结算调度；特殊订单和历史订单不能套用本候选范围。
4. 当前计划仅走查已确认路径；如发现必须新增客服转公开池、指派二次确认或其他商业规则，整理影响和选项交用户决定后再设计。直付手续费实际费率、取整、退款处理亦须单独确认。
5. 产品、业务、研发和测试评审本草稿及实际原型，确认现有规则、需求、设计和验收条件清楚后才开发；不能由已有资料决定的实际业务分歧交用户决策，不把每个已确认规则重新提交审批。测试人员完成报告后，由负责人归纳问题和调整，再由产品进入下一轮设计。
