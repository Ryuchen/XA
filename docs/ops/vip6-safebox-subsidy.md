# 六级会员免费安全箱：平台承担陪玩报酬

## 2026-11-03 已确认的业务规则

- 六级会员使用免费安全箱券时，老板仍为零实付；陪玩报酬按该安全箱项目原价及现有分成规则计算，由平台承担。
- 达到结算条件而平台钱包余额不足时，暂缓结算；平台补足余额后继续。
- 用户确认：管理员核实线下补入后，在后台登记平台入账；线下凭据编号与操作人保留在流水中。
- 服务开始前取消时不产生陪玩报酬；券的归还与补发沿用已有流程。
- 服务开始后因售后协商终止时，客服根据实际履约与各方协商填写陪玩报酬，每人不得超过其原预计份额；免费安全箱券视为已使用，不退还。
- 用户确认：协商终止后，待全部协商报酬结算完成，再发下一张六级免费安全箱券；平台余额不足期间不发，原券仍为已使用。
- 工作台按服务端业务时区展示当日平台补贴净支出及支付、追回明细：以平台钱包成功入账的补贴流水发生日为准，净支出＝支付－追回；跨日追回可能使当日净支出为负。待结算金额单独展示，此指标不代表平台利润，仅有钱包查看权限时显示。
- 当前会员安全箱券仅适用于明确绑定的端游／手游单陪安全箱主套餐；权益配置选项与服务端校验使用相同条件，双陪套餐不会出现在可绑定列表中。
- 已绑定套餐后来停用或不符合条件时，会员权益配置会提示并允许逐项移除；有效已选项超过初始 500 项时仍保留，搜索通过服务端查找完整目录。
- 在老板停留结算页期间更改安全箱绑定时，报价与最终下单均重新核对当前会员券范围；真实 Redis／WebSocket 验证了旧券从打开的结算页移除、价格重新计算并保留已填写信息。

## 现状和实施注意事项

订单级分账守恒校验以老板实付为上限，平台钱包余额不允许为负。实现使用独立补贴依据、份额和平台支出流水，保留老板零实付及普通订单分账口径。

平台钱包同时存放陪玩押金：可用于补贴的余额为平台总余额扣除押金池，不能将押金当作平台补贴资金。钱包管理提供平台资金余额和线下补入登记，待结算报酬由现有定时任务重试。

平台资金页显示已完成订单、协商终止订单和完成结算模式转单中尚未支付的补贴份额，支持分页、按订单定位与刷新；已完成订单可能仍需审核或等待售后期，不能仅凭该统计判断资金不足。具有钱包查看权限但无订单查看权限的人员仅能看到汇总，不显示订单明细。隔离 MySQL 验证汇总和补款业务，11 笔真实创建的订单验证分页，375px 浏览器验证订单定位和补款。

有流水查看权限的人员可从平台资金页直接进入该钱包的补贴流水；追回流水在列表中单独标记，并可查看原流水和关联订单。375px 浏览器已用实际补款与结算验证入口、筛选及支出订单金额。

隔离 MySQL 已验证真实缴押金、平台补贴不足、管理员登记线下补入及重试到账；同一凭据和同一请求不能重复入账。375px 实际浏览器已验证客服补款登记及陪玩待结算展示。

当前代码已实现新订单的补贴快照、派单与公开接单收益、转单分配、余额不足暂缓和补足重试，补发成功后事务提交再通知钱包刷新。2026-11-03 已先备份并演练，再对本地独立预览数据库应用迁移并启用功能；其他运行配置默认关闭。历史订单不自动补发。

老板仅有新业务账号、没有旧用户映射时，也可领取普通券和会员券。隔离业务流程验证该账号完成免费安全箱下单、转单、协商终止、平台报酬结算和下一张券补发，全程不创建旧账号。此能力依赖 `coupons/0011_usercoupon_user_optional`；本地预览已备份并应用迁移，其他环境需先迁移再启用对应代码。

新账号自然升级流程已在 SQLite 和独立 MySQL 验证：客服凭凭证充值后不立即升级；老板下单、陪玩服务并报单、客服审核后，达到确认时间才计入消费并发放升级券和安全箱券。测试将隔离订单及报单时间调至 73 小时前，会员门槛只为测试设置；管理钱包等级和陪玩钱包收入也在 SQLite 接口测试中核对。
