# 已转单预约的参与人展示与权限

客服在服务中将预约订单转给其他陪玩后，预约记录保留原预约人员；老板和后台可同时看到原预约人员和订单当前未转出的履约人员。接替陪玩可从订单打开原预约时段，并可在自己的预约列表与详情查看该预约；没有关联的陪玩不能查看。已转换预约仍用订单的当前参与人判断占档，原预约事实不被覆盖。

隔离测试覆盖了实际预约、付款、服务中转单、原时段冲突与释放、原／接替陪玩和无关账号权限；另外使用两个独立测试库检查相同编号下的门店隔离。三端浏览器展示采用隔离测试库中的合成订单和人员，验证真实网页与接口，没有触及真实客户或资金。

后续新增了试验性服务前改派：开启 `PRESTART_HANDOFF_ENABLED` 后，授权客服可对已付款、尚未由被更换者开始履约的订单更换陪玩；重新校验资格、容量和预约冲突，原付款不变，新陪玩保存接入时抽成快照，每次更换独立留痕。免费安全箱平台补贴、双陪另一人已经入队、双陪固定抽成尾差、转回及后续结算已在隔离场景核验。预约仍按原记录与当前人员计算时段占用；未来预约不占当前接单名额。

该能力默认关闭，新增迁移 `orders.0097`、`orders.0098` 尚未应用到现有门店数据库，现有后端没有重启。已有游戏抽成范围快照的订单，可在商品目录变更后按原购买范围匹配接替时的门店抽成；新游戏订单还会保存服务家族和最低等级的排序快照。旧游戏订单没有保存最低等级且没有独立的游戏资格快照时，授权客服可在改派时记录人工核对的原要求、依据和对应等级；该记录随改派审计保存，不改写原订单快照。MySQL 行锁竞争仍需在符合项目隔离约定的专用测试库验证；多人安全箱补贴的分摊基数未形成可靠快照，暂不处理。双陪预约、积分抵扣后的分账以及服务中每次参与履约的完整模型仍需继续按 PRD 开发，不能将此试验能力视为所有转单已完成。

后台订单详情在试验开关开启时可查看每次服务前改派的人员、原因、操作人和收益／抽成快照；安全箱补贴单的预期收益同时包含其平台补贴份额。开关关闭时不查询未迁移的审计表。

当原商品的游戏、玩法或技能范围发生变更时，仅有指向同一商品编号的技能关联不足以证明接替陪玩具备原服务技能；试验改派还须验证可独立核实的原范围技能和资格，无法核实时拒绝改派并提示核对。隔离测试覆盖了目录改动后仅持原商品关联被拒绝、补充原范围资格与同家族技能后允许改派，原订单付款和范围快照保持不变。

新增独立、默认关闭的 `PRESTART_SCOPE_SNAPSHOT_ENABLED` 试验开关：老板普通下单、预约转单和客服代单会在同一付款事务保存原服务范围和最低等级顺序；付款前商品或等级发生变化则拒绝旧请求。启用后改派优先读取这份快照；无游戏抽成快照且无原服务范围记录的历史订单拒绝自动改派，不依据现行目录倒填。快照写入失败时订单与资金一起回滚。功能启用前必须先在全部目标门店应用并核验 `orders.0098`；完整历史服务范围核对入口和真实 MySQL 锁竞争仍待实现与验证，该开关不代表服务前改派已具备上线条件。

对已有旧版游戏服务范围、仅缺最低等级的订单，后台转单界面要求填写原要求、核对依据以及对应本店最低等级或明确不限等级；仅授权派单人员可以执行。通过后原始核对、操作人、等级及顺序随改派审计写入，同一订单快照未变化时后续改派可复用；订单快照变化后需重新核对。验证覆盖等级不符拒绝、审计记录、重复改派、快照变化，以及隔离 ASGI 和临时库连接真实后台页面的人工核对流程。**无游戏抽成快照且无付款服务范围的历史订单仍需另行建设完整服务范围核对入口。**

试验快照开启时，现有单陪抢单池列表、抢单、报名与老板选人、客服单人／双人指派的资格检查使用付款范围；旧订单没有付款范围时维持现有处理。列表按付款时游戏筛选，有效资格在最后分配时再次检查；商品归属变化后，仅持同一可变商品编号不足以证明原游戏技能，须有可核实的原范围技能。隔离 SQLite 覆盖等级与游戏变更、报名后资格变化、异常快照和客服指派；两套完整迁移临时库验证了同编号订单各按本店要求显示。此处尚未实现 PRD 的完整抢单窗口、通行证逐级可见快照、自动排序及双陪抢单池；列表对新快照候选逐条核验，规模与 MySQL 性能亦未验证，不能视为完整抢单功能已交付。
