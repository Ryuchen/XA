## 提现手机页面验收环境补充

2026-11-03 对上述间歇性认证失败继续复测：内存 SQLite 运行期间还出现 `LegacyAccountMap.MultipleObjectsReturned`，该表的账号关系在数据库中是唯一约束。Django 官方测试文档说明内存 SQLite 的实时服务器和测试线程共享连接，重叠查询可能引发随机失败（[Django testing tools](https://docs.djangoproject.com/en/4.2/topics/testing/tools/)）。这是需要排除的测试环境因素，但不足以证明两次 401 的直接原因。

已让 `console.test_dashboard_withdraw_browser.DashboardWithdrawalBrowserTest` 在启用浏览器验收时拒绝内存 SQLite，并提示使用隔离文件库或 MySQL；前端测试账号的 ID 采用与实际登录相同的字符串格式，并在发生 401 时保留不含令牌的响应信息。切换独立文件 SQLite 后，该手机联调在加限制前后各通过一次；独立 Redis/WebSocket 的陪玩钱包验证也已通过。尚不能据此排除生产环境中的其他认证问题。

管理后台改为 iPad 横屏后，在隔离文件 SQLite 和真实 HTTP 下复核工作台按领取状态进入待审列表、管理员核实未打款后释放、另一客服领取并登记打款凭证、陪玩查看回执；另核对待审按时间先后排序，以及领取最后一页唯一记录后的分页回退，三项页面测试通过。打款凭证为隔离测试数据；本轮 HTTP 页面测试未验证 WebSocket 实时连接，也未实际打款。此前间歇性 401 仍不能仅凭本次通过排除。

## 服务中转单售后规则

适用已付款、按完成结算的历史订单：服务中转单后存在已结算与未结算份额时，老板可提交售后；客服协商退款时按各方确认的承担处理。退款成功后，售后按全额或部分退款结束；资金不足或方案失效时保留售后处理中，不发生退款或结算。用户 2026-11-03 确认：售后未处理时暂不允许结单；客服处理为继续服务后恢复结单。普通未转单订单和零实付补贴单仍沿用各自规则。陪玩端在订单上提示原因；服务端同时阻止单陪、双陪及后台完成操作，避免页面状态未刷新时仍提交。

隔离文件数据库、真实 Redis/WebSocket、后台及陪玩 H5 验证：老板原生页面控制器提交售后后，接手陪玩页面显示不可结单；客服协商退款后老板控制器及陪玩页面实时更新。另一个真实浏览器流程保持陪玩页面打开，客服处理为继续服务后自动恢复结单入口。小程序运行使用微信宿主接口替身，未在开发者工具中实际操作。SQLite 真实业务测试覆盖追回不足、全额与部分退款、双陪和推荐人；本地预览为热更新，其他环境需要同步新前后端代码。

同一笔隔离协商退款中，后台工作台在售后打开时显示 1 条待办，退款完成后通过真实 WebSocket 自动移出待办；老板与两位陪玩页面、订单金额及陪玩收入排行同时核对。用户随后确认：该类付费订单售后未处理时先处理售后，再次转单须等待处理完成。服务端在订单锁内核对；后台订单卡片显示原因并禁用转单与结单，客服处理为继续服务后恢复操作。隔离真实接口验证期间无额外转单及资金流水，处理后可再次转单。

该再次转单流程也在使用真实迁移的独立 MySQL 中通过：售后开放时转单被拒、记录与资金不变；客服处理后转单成功。真实 MySQL 并发 3 项通过：①售后先持锁并提交后，等待中的再次转单和结单均被拒，订单、钱包及流水不变；②再次转单先提交后，等待中的售后关联最新接手陪玩，该陪玩不能结单；③结单先提交后，等待中的售后按已完成订单成功创建，已结算收益保持原值。这些结果针对上述操作顺序，不能推及其他并发场景。

客服从售后详情的“退款结案”也能进入服务中转单的协商分摊；原入口只对订单列表退款开放。真实 375px 与 1440px 后台页面验证从售后详情进入、分项试算、确认退款及两位陪玩收益回执，售后记录正确结束。

老板订单列表现在直接提示“售后处理中”，保留原履约状态，售后结案后提示消失；支付尚未确认的订单不显示该提示。隔离文件 SQLite、真实 HTTP、Redis 和 WebSocket 下，从老板原生控制器发起售后，客服使用 iPad 横屏后台协商部分退款，两位陪玩 H5、老板订单、后台工作台和收益榜同步更新，核对退款及两人收益后连续两次通过。微信宿主使用适配器，尚未在开发者工具内核验渲染。参考 [Saleor 订单异步处理状态更新](https://github.com/saleor/saleor-dashboard/blob/main/CHANGELOG.md)，现有履约、支付和售后状态继续分别展示。
