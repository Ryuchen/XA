# 微信直付订单退款：三端状态与展示契约草案

日期：2026-10-27。本文件是设计草案，不代表微信支付、退款接口、渠道通知、查单、运营处理或三端展示已经上线。当前 `orders/direct_payment.py`、`orders/direct_refund.py` 是受测试配置保护、未对外开放的领域实现；真实渠道结果必须由可信服务端验签、核对与查单后确定。

2026-10-30 增量：隔离测试域可对已持久化的退款通知按原退款号执行一次验签查单，通知和查询事实匹配后推进退款状态，并通知订单页面刷新；查单结果未知时保留原退款号等待再次核对，查询期间出现冲突时不更新为成功。测试环境可显式配置测试网关并执行 `reconcile_test_refund_inbox` 命令扫描待处理通知；回调仅负责可靠入库，不在回调请求内同步查单。该命令只接受测试传输，不提供生产 API、退款提交、自动调度或真实渠道证据留存；手续费退款、部分退款和商户联调仍未开放。

## 基本原则

- 订单履约状态、支付状态和渠道退款状态分别表示不同事实。`CANCELLED` 只能说明订单停止履约，不能表示微信退款已到账。余额支付的现有退款口径保持不变。
- 微信支付订单金额以人民币分为渠道单位，页面展示人民币元；兴安币是余额展示单位，不能沿用 `core/ui.js` 中的兴安币换算方法展示人民币。避免将预期退款、渠道受理和实际成功合并成一个“已退款”。
- 非终态或结果未知时保留原支付/退款请求标识，先查询权威状态；不得因为小程序回调、网络超时或关闭页面而新建另一笔退款。渠道退款申请需要通过可靠异步任务、查单和对账恢复，不能在持有数据库事务锁时等待外部网络。
- 已经确认的原始支付、退款编号、金额、状态、时间、处理人和异常处理轨迹须可追溯。客户和陪玩只能看到自身有权查看的信息；客服的操作及审计受后台权限控制。

## 按资金事实展示，而不是按订单状态猜测

| 服务端已核验事实 | 老板订单列表和详情建议 | 客服订单详情与待办建议 | 陪玩订单建议 |
| --- | --- | --- | --- |
| 尚未支付，订单待支付 | “待支付”；展示应付人民币、支付截止、继续支付和关闭操作（以服务端许可为准） | 未支付，不能派单；可查看支付确认状态和有效期 | 不进入公开池，不产生可接单操作 |
| 支付结果尚不确定 | “支付结果确认中”；提供刷新/核对入口，不再创建一笔新支付 | 可按原商户单号查渠道状态，展示上次核对时间及失败原因 | 不显示为已付款或可接单 |
| 渠道付款已确认、订单正常待派 | 按公开/客服路径显示待安排，开始展示该单的待接单截止时间 | 可按已支付订单派单；展示支付来源及服务端规则快照 | 按原有资格和可见性规则显示/接单 |
| 订单取消后，渠道退款已预留、受理或处理中 | “订单已取消，微信退款处理中”；展示申请金额，不能写“已到账”或“退回余额” | 展示原支付与同一商户退款号、申请时间、受理/处理中状态、下次查询或处理入口 | 订单不可再接；不展示老板的支付凭证或退款账户 |
| 退款结果未知 | “退款结果确认中”；展示订单及金额，提示可刷新，避免重复申请 | 保留原退款号，展示渠道结果未知、最近核对/失败信息和人工处置入口 | 已取消订单不可继续履约 |
| 渠道退款成功 | “微信退款成功”；展示渠道确认金额和时间，到账时间以微信/银行为准 | 展示微信退款编号、成功时间及核对状态 | 按实际履约/分账规则显示，不因单独的退款弹窗暴露客户敏感信息 |
| 渠道退款关闭 | “退款未完成，平台处理中”；不能展示退款成功 | 标明关闭原因与处理结果；仅在验证渠道最终关闭及业务允许后，以新退款号发起新的尝试 | 维持订单停用状态 |
| 渠道退款异常 | “退款处理中，需要平台核对”；不能暗示款项已退 | 标记异常待人工处理，提供渠道核对和处理记录；不能盲目新建退款 | 维持订单停用状态 |
| 取消后收到迟到付款 | “付款已确认，订单状态异常，平台核对中”；不能显示未付款、已退款或可继续派单 | 将支付事实和订单状态冲突列入待处理队列；核实后按渠道退款或其他明确规则处理 | 不进入公开池、不提供履约按钮 |

上述“待支付”“结果确认中”等词是产品展示建议，不要求直接添加同名订单履约状态。显示优先级应由服务端提供的资金事实决定：已核验退款成功高于较早的退款处理中信息；迟到或矛盾事件不能覆盖更可靠的终态。`ABNORMAL` 与 `CLOSED` 都不是退款成功；微信官方描述 `CLOSED` 可在特定条件下使用新商户退款号重新申请，而 `ABNORMAL` 须核对并按平台流程处理。参见 [微信支付退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)。

## 建议的三端数据边界

当前尚无直付退款的公开接口。下列字段和接口能力是待设计契约，不是现有 API 承诺；最终命名由实现和接口测试确定。

### 老板端

- 订单详情及列表提供经授权的支付来源、应付/已付人民币金额、支付状态、支付截止时间、退款金额、退款状态和安全的下一步操作。支付与接单截止时间分开，不以客户端本地计时断定渠道结果。
- 不把渠道退款流水展示成钱包退款流水；提供“查看微信退款进度”或订单内状态说明。只有服务器确认成功时才显示退款成功，用户取消微信收银台后仍需服务端查单确认。
- 目前 `apps/boss-miniapp/native/core/orders.js` 按履约 `PENDING` 展示“待接单”，`pages/orders/index.wxml` 与 `pages/order-detail/index.wxml` 按兴安币展示实付；接入直付前须按支付渠道和资金状态调整。`pages/order-detail/index.js` 中余额取消提示不可用于微信订单。
- 现有 `core/order-intent.js` 与 `core/api.js` 负责余额下单恢复和封止，不能当作微信支付事实；新渠道的本地恢复信息须与服务端支付意图绑定，同账号切换、页面销毁及迟到响应不能覆盖新会话。

### 管理端

- 在现有订单详情中清晰分开订单状态、原支付来源、退款金额、退款渠道状态和核对时间；可按异常/待核对状态筛选，并在未授权时隐藏操作与敏感字段。
- 由服务器统一判断本单是否可申请、查询或重新尝试退款。操作前说明金额和实际去向；状态未知不提供使用新编号重试的快捷操作。变更记录同时保留操作人、前后状态、时间和服务端结果。
- 当前 `apps/admin-web/src/views/order/index.vue`、`services/backend/console/serializers.py` 与既有余额退款预览仅覆盖已有资金链路；不得用余额退款按钮或余额回执充当微信退款结果。

### 陪玩端

- 继续按订单归属和服务端许可动作展示；退款处理中、订单已取消或付款未确认时禁止接单/开始/完成。仅显示为履约必要的订单处理状态与本人收益影响，不展示老板微信账号、渠道退款号或其他人的资金信息。
- 已分配、部分履约、部分退款、已结算后的渠道退款和收益追回须单独设计。现有 `orders/direct_refund.py` 当前只预留未指派订单或迟到支付的全额退款，不能推断这些场景已支持。

## 实时更新与恢复

1. 数据库提交后的事件应作为“请重新读取订单/退款”的提示，而不是唯一真相。老板和客服在页面进入、重新连接、网络恢复及应用恢复前台后重新查询；失联期间可通过列表找回处理中事项。
2. 读取或推送时重新校验当前登录身份、归属和权限；账号切换、权限撤销、页面关闭后的迟到响应不能覆盖新的会话。重连查询应合并，失败退避，未知状态不能显示为零或成功。
3. 微信已确认退款成功后，需持久化渠道凭证并更新订单资金事实，再发送通知；失败不能回滚已发生的外部退款，也不能因此重复申请。签名不符、金额或交易号不匹配、终态冲突必须记录并进入人工核对。
4. 当前直付测试域尚未接入这些通知与恢复能力；也未验证真实渠道回调、Worker、用户真机或生产消息投递。
5. 如果旧退款已关闭后出现与该终态矛盾的可信渠道结果，系统应持久化冲突并进入人工核对；在发送任何已预留的新退款请求前，执行器须检查该支付意图及其他退款是否处于冲突处理状态。此检查不能撤回已经发往微信的外部请求，已发送或结果未知的请求仍须按原退款号查询、对账及人工核对，不能仅凭本地冻结状态认定没有发生退款。

## 必须通过的场景

- 支付成功但小程序返回失败、关闭页面或请求超时：重新打开只能查到同一订单，不能重复付款或误称未付款；未确认付款不得进入派单池。
- 退款受理、处理中、网络结果未知、重复与乱序通知、成功、关闭、异常：三端展示与可用操作分别正确；成功不能被较早状态覆盖；错误请求不能触发另一笔退款。
- 支付成功与关单、取消与接单、超时与接单、退款查询与通知、相同及不同退款号并发：以真实 MySQL 独立连接验证最终状态和金额；不允许渠道退款与余额退款重复发放。
- 订单与支付/退款回执所属账号不同、员工缺权限、用户换号、连接断开重连、应用进出后台：禁止越权或迟到数据污染，断线恢复后能找到未处理订单。
- 老板、客服、陪玩分别走查可理解性；验证人民币与兴安币、退款去向和预计状态，不把模拟支付或本地测试当成商户实测。正式联调应与日对账、异常工单、资金追踪和人工补偿流程一起验收。
