# 企业级 SaaS 重构实施计划

版本：2026-11-17；状态：**实施计划（规划），未开始执行**。目标设计见 [SAAS_TARGET_ARCHITECTURE.md](SAAS_TARGET_ARCHITECTURE.md)；阶段与验收治理见 [26-企业级总体规划](../development/26-企业级总体规划.md)。

**执行前提**：2026-11-15 仓库重组期间用户要求停止业务功能开发及测试；本计划全部波次须先获用户明确复工确认（M0），且不得重置、覆盖工作树中他人未提交变更。当前分工只负责后端与接口；涉及前端契约的条目须与前端开发协调排期。

## 0. 总体执行原则

1. **绞合式渐进**：每波次独立提交序列、独立可回退；禁止一次性大爆炸重构。
2. **测试先行的行为锁定**：动任何资金/状态逻辑前，先补 characterization tests 固化现有数值与状态行为；重构后逐分/逐状态比对。口径争议停手上报，不得借重构改业务口径。
3. **零迁移优先**：子包拆分、视图拆分不改 app_label 与表结构，`makemigrations --check` 必须无新增；确需迁移的条目（七态建店、entitlement 控制面表）单独列出并按 B3 门禁执行。
4. **契约不变**：现有 URL、请求/响应结构、WS 事件在过渡期保持兼容；变更走 dev/09 契约流程并同步 PRD 08 追踪与前端开发。
5. **进度单一口径**：执行记录写入 dev/16、18、19 与 T/G/D 追踪，不另建进度文档。
6. 每波次退出门禁（通用）：`pnpm run typecheck`、后端全量测试（SQLite＋迁移检查＋MySQL 并发子集）、`manage.py check`、`deploy/dev.ps1 Verify` 五入口健康；资金相关波次加隔离 MySQL 对账。

## R2 领域解耦与金额内核（对齐 M3/M4，E03–E08）

执行顺序严格如下，前项未绿不启动后项：

1. **R2.1 金额内核 characterization tests**：对 `orders/refund_math.py`、`orders/points_redemption_math.py`、`console/payroll_calculation.py`、`wallet/refund_priority.py` 现有纯函数建立边界用例矩阵（T07/T08 取整、部分退款构成、积分冲正、工资绩效口径），锁定当前行为。
2. **R2.2 内核落地**：新建 `common/money_kernel/`，四处公式逐处迁入并替换调用；每替换一处跑全量比对，数值逐分一致。与前端 `packages/money` 口径对齐（10 单位=1 店币），后端为唯一计价事实源。
3. **R2.3 orders→wallet 单向化**：定义 wallet 资金服务接口（付款/退款/冻结/结算/补差，入参订单侧值对象）；`wallet/income.py:213-389` 对 orders.models/financial_lock 的反向依赖改为调用方传参或 outbox 事件（依赖 R4.1 的事件注册，可先以接口传参过渡）；`wallet/deposit_applications.py:68` 派单锁协调归 common/financial_lock 锁序协议。
4. **R2.4 业务层去 console 依赖**：`orders/views.py:20,778` 改依赖 R1.4 共享权限注册表；payroll_event_barrier 接口下沉 workforce 服务层。
5. **R2.5 子包拆分**（零迁移）：orders 按 ordinary/points/grab/reservation/negotiation/addon/room 归位；console/views.py 拆 `console/views/` 域模块；stores 拆 licensing/platform/tenancy。models 不动、URLconf 不动、`__init__` 兼容导出过渡；测试文件随包归位但命名后缀体系（_mysql/_multistore 等）不变。
6. **R2.6 依赖门禁**：CI 增加 import 方向静态检查（业务 app 禁 import console；orders/wallet 禁双向），违规即失败。

**回退**：R2.1–R2.4 每处替换独立提交可单独 revert；R2.5 拆分提交按包分组，兼容导出保证回退不破坏调用方。

## R3 权益统一裁决与开关治理（对齐 M5，E02/E06）

1. **R3.1 entitlement 服务**：`stores/entitlements` 模块，裁决顺序＝角色权限→License/配额→平台增值配置→门店开关；拒绝返回原因码。**含控制面迁移**（权益目录/增值配置表，已有配置沿用不重建）。
2. **R3.2 快照扩展**：现有签名授权快照增加 feature 维度；控制库故障读快照，无有效快照新增账号/增值 503、核心业务保留；离线授权与物理断库演练（与 M5 合并）。
3. **R3.3 入口清单与接入**：盘点全部新增账号入口与增值发放入口（券/积分/安全箱/成就/礼物权益/BOSS_H5 可购模块），逐项接入统一裁决；清单与接入证据登记 dev/18。陪玩显式注销释放名额随本波接入。
4. **R3.4 开关三层治理**：133 处 env_bool 按架构文档 §5.1 分类登记；功能级开关迁平台增值配置（双读期配置优先）；门店级归系统字典；每个迁移开关须有行为一致测试后才退役 env。
5. **R3.5 绕过防护**：新增发放入口必须声明 entitlement 键的静态检查纳入 CI。

**回退**：裁决服务带旁路开关（仅开发环境）；生产拦截不可配置关闭核心订单资金（硬约束）。

## R4 事件与任务收敛（对齐 M3/M5，E04/E10）

1. **R4.1 outbox 统一派发器**：common/outbox 统一表结构/派发/重试/死信登记；各领域注册事件类型与幂等处理器；逐店扇出沿用 StoreTask。现有分散 outbox 用法逐类迁移，迁移期双写对账。
2. **R4.2 持久化时钟贯通**：预约到期、抢单窗口、收益冻结、售后计时统一持久化时钟来源（18 文档"正式持久化时钟未贯通"清偿项）；禁止内存时钟。
3. **R4.3 补偿扫描合并**：30+ 个 *_NOTICE_RECOVERY_ENABLED 及同类 60s 扫描合并为通用补偿框架（单任务按事件类型注册表逐店扫描）。**逐类迁移**：每类先跑对应通知恢复专项（dev/development 无编号专题）回归，通过后切新框架、退役旧开关；61 条 beat 收敛目标登记于 dev/18。
4. **R4.4 聚合采集**：配额用量/平台汇总日快照任务，失败标注缺失不补零，不复制客户明细入控制库。

**回退**：每类补偿切换独立开关，旧任务保留至新框架稳定一个观察期后删除。

## 波次依赖与排期约束

```
M0 复工基线 ─▶ R1 ─▶ R2（R2.3 可先接口传参，R4.1 后改事件）
                └─▶ R3（依赖 R1 权限底座；与 M3 业务清偿并行）
R2.1/R2.2 ─▶ R4（金额内核稳定后才动资金事件）
R3 ─▶ R5（错误契约含 entitlement 原因码）
R1–R5 ─▶ R6（配置与观测收口）─▶ M7 统一联调 ─▶ M8 上线
```

- 业务功能清偿（M3/M4 组合场景、开关启用）与重构波次交织时，**同一文件不并行改动**；按 M0 文件分工冻结协调。
- 每波次完成后更新 dev/16 进度、dev/18 剩余清单、T/G/D 追踪；未验证项标"待联调"。
- 51 个遗留脚本清偿（26 规划 A3）穿插 R2/R4：等价覆盖补齐后移除，期间不作验收依据。

本计划完成的判据（逐项证据）：

1. R1–R6 各波次退出门禁全绿，记录于 dev/16。
2. 依赖静态检查、entitlement 绕过检查、覆盖率门禁（阈值首轮基线测定）在 CI 生效。
3. 资金内核替换前后数值逐分一致的对账报告；补偿合并逐类回归记录。
4. 物理断库＋隔离 MySQL 全流程演练记录（M5）；`ISOLATED_CONTROL_PLANE` 生产常开验证。
5. T/G/D 追踪无未解释缺号；26 规划 §6 调整项 A1/A2/B1/B3 及本文各波对应项登记完成证据。
