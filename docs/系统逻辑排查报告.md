# 兴安电竞陪玩平台 · 系统逻辑排查报告

| 项目 | 内容 |
|------|------|
| 排查范围 | 老板管理、人员管理、陪玩管理、订单流转、金额流转 |
| 排查方式 | 后端源码静态审计（`services/backend`），逐条追踪资金与状态变更路径 |
| 报告日期 | 2026-08-03 |
| 结论 | **存在 3 个 P0 级资金/可用性缺陷，6 个 P1 级严重缺陷，5 个 P2 级问题** |

---

## 0. 总体结论

系统的**骨架设计是好的**：订单状态机集中收口、行锁 + 原子事务覆盖全部资金写入、下单金额完全由服务端计算、报单审核明确禁止对已结算订单二次入账。这几点避免了陪玩类平台最常见的重复付款和价格篡改事故。

但**资金分账的算术口径**和**钱包实体的寻址口径**这两处存在系统性缺陷，属于会直接产生真金白银损失或让用户无法使用的级别，必须在上线前修复。

严重度定义：

- **P0 — 致命**：直接造成资金损失，或让核心功能对用户完全不可用
- **P1 — 严重**：业务结果错误、权限失效、账目不平，需要人工介入纠正
- **P2 — 中等**：健壮性与体验问题，可排入常规迭代

## 1. P0 致命问题

### P0-1 双陪订单超额分账，平台每单净亏

**位置**
- `orders/models.py:376-382`（`OrderProvider` 设计注释）
- `orders/views.py:836-856`（陪玩端完成结算）
- `console/views.py:1292-1315`（客服后台完成结算）

**现象**

`OrderProvider` 的设计注释白纸黑字写着「每个打手以**订单实付金额**为结算基数」。双陪订单会生成两条 `OrderProvider`，每条都以完整 `amount` 计算 `provider_income`。结算时逐条入账，两名陪玩各拿一份全额分成，之后再按订单级字段给推荐人分佣、给平台留存。

**复现路径**

1. 老板下一笔双陪订单，实付 `amount = 1000`（分），抽成率 20%
2. 两条 `OrderProvider` 各算出 `provider_income = 1000 × 80% = 800`
3. 订单级 `shop_income = 160`、`inviter_commission = 40`
4. 完成订单 → 陪玩 A +800、陪玩 B +800、推荐人 +40、平台 +160
5. 合计流出 **1800**，老板只付 **1000**

**为什么现有约束拦不住**

```python
models.CheckConstraint(
    condition=models.Q(provider_income__lte=models.F('settlement_base')),
    name='order_provider_income_lte_base',
)
```

这条约束只校验**单条**记录不超过自己的结算基数，两条记录各自都合法，汇总起来就穿透了。数据库层没有任何跨条汇总校验。

**影响**：每笔双陪订单平台净亏约 `amount × (1 - 抽成率)`。抽成 20% 时每单亏 80% 的订单金额。平台钱包会被持续掏空至余额约束报错为止。

**修复建议**

1. 明确双陪的商业口径。两种合理方案二选一：
   - **均分制**：`settlement_base = amount // provider_count`，余数归平台
   - **加价制**：双陪下单时价格翻倍（`amount = 单价 × 2`），每人各按自己那份基数结算
2. 在 `settlement.py` 增加统一的分账校验函数，结算前断言：
   `SUM(row.provider_income) + inviter_commission + shop_income == amount`
3. 补一个服务层守卫：任何 `OrderProvider` 批量创建后立即校验汇总，不通过直接抛异常回滚

### P0-2 `provider_income or amount` 回落，抽成 100% 时陪玩拿走全款

**位置**
- `orders/views.py:858` — `provider_income = order.provider_income or order.amount`
- `console/views.py:1318` — `income = o.provider_income or o.amount`

**现象**

Python 中 `0 or X` 求值为 `X`。当 `provider_income == 0` 时，这行代码不会入账 0，而是**回落到订单全额**。

**为什么 `provider_income` 会是 0**

`commission_rate = 100`（平台全抽）是完全合法的配置：

- `EscortLevel.commission_rate` 校验区间是 `0-100`
- `CommissionConfigView`（`console/views.py:1891`）允许设置 `0-100`
- `compute_split()` 在 `rate=100` 时算出 `provider_income = 0`、`shop_income = amount`

**后果叠加**

陪玩拿到全额 `amount`，同时 `shop_income = amount` 也照常入账平台钱包 → **系统凭空创造了一倍订单金额**。这个漏洞可被运营误操作触发，也可被恶意配置利用。

**修复建议**

```python
income = order.provider_income if order.provider_income is not None else order.amount
```

更稳妥的做法是彻底删掉这个回落逻辑：`provider_income` 在下单时就已由 `compute_split` 落库，不存在为空的合法场景。旧数据兼容应写成一次性数据迁移，而不是留在热路径上。

### P0-3 钱包寻址维度不一致，触发唯一约束冲突 500

**位置**

`Wallet` 模型（`wallet/models.py:14-21`）同时持有两个 `OneToOneField`：

```python
user    = models.OneToOneField(AUTH_USER_MODEL, ..., related_name='wallet')
account = models.OneToOneField('club_accounts.ClubAccount', null=True, ..., related_name='wallet')
```

系统里存在**两套互不兼容的取钱包方式**：

| 维度 | 调用点 |
|------|--------|
| `account` 维度 | `wallet/views.py:25-30`（`_get_wallet`）、`orders/views.py:388`（下单扣款） |
| `user` 维度 | `orders/views.py:842 / 859 / 872 / 1374`、`console/views.py:473 / 1298 / 1319 / 1336 / 1443 / 1631 / 1813` |

**复现路径（陪玩场景）**

1. 新陪玩完成第一笔订单，结算走 `get_or_create(user_id=...)` → 创建 `Wallet(user=X, account=NULL)`
2. 该陪玩首次打开钱包页，`_get_wallet` 走 `get_or_create(account=A, defaults={'user': X})`
3. 按 `account=A` 查不到（那条记录 account 是 NULL）→ 进入 create 分支
4. 插入 `Wallet(user=X, account=A)` → 撞上 `user` 的 **OneToOne 唯一约束** → `IntegrityError` → **HTTP 500**
5. 该陪玩此后**永久无法访问钱包、无法提现、无法缴押金**

老板侧同理：先被后台充值或收到打赏（user 维度建钱包），再下单（account 维度）就崩。

**佐证：团队已经踩过这个坑**

```python
# console/views.py:441
Wallet.objects.filter(user=user).update(account=account)

# console/views.py:1126
if wallet.account_id != customer_account.id:
    wallet.account = customer_account
    wallet.save(update_fields=['account'])
```

这两处是明显的事后补丁，但只覆盖了后台两条路径，`orders` 和 `wallet` 侧的入口依然裸奔。

**修复建议**

1. 收敛为**唯一一个**钱包工厂函数，全系统资金入口只准调它：

```python
def get_wallet_for_account(account, *, for_update=False):
    qs = Wallet.objects.select_for_update() if for_update else Wallet.objects
    legacy_id = account.legacy_mapping.legacy_user_id
    wallet = qs.filter(Q(account=account) | Q(user_id=legacy_id)).first()
    if wallet is None:
        return Wallet.objects.create(account=account, user_id=legacy_id)
    if wallet.account_id is None:
        wallet.account = account
        wallet.save(update_fields=['account'])
    return wallet
```

2. 写一次性数据修复脚本，按 `LegacyAccountMapping` 回填所有 `account IS NULL` 的钱包
3. 回填完成后把 `account` 字段改为 `null=False`，从数据库层杜绝回归

## 2. P1 严重问题

### P1-1 押金与提现税金凭空消失，全系统资金不守恒

**押金**（`wallet/views.py:462-477`）

```python
wallet.balance -= amount
profile.deposit_paid += amount
Transaction.objects.create(..., amount=-amount, tx_type=DEPOSIT, ...)
```

陪玩钱包扣了钱，`EscortProfile.deposit_paid` 加了个计数，但**没有任何账户收到这笔钱**。资金在系统内蒸发。同时押金**没有退还入口**——陪玩离职或解约时无法退款。

**提现税**（`wallet/views.py:206-213` + `console/views.py:1952`）

申请时冻结全额 `amount`，`actual_amount = amount - tax_amount`。审核通过时 `frozen_amount -= amount`，实际只打款 `actual_amount`。差额 `tax_amount` 同样**没有任何账户承接**。

**影响**：`SUM(所有钱包 balance + frozen)` 与 `SUM(充值) − SUM(实际打款)` 永久对不上，财务无法出具正确的资金报表，也无法核对平台真实收入。

**修复建议**：押金与税金都应转入平台钱包（或独立的「押金专户」`Wallet`），每笔都写配对的正向流水。押金另需补一个「退还押金」的后台操作。

### P1-2 `can_view` 权限开关完全没有生效

`ClubAccount.can_view` 与 `CustomUser.can_view` 有字段定义、有后台编辑表单（`console/serializers.py:62, 87`）、有 admin 列表过滤（`club_accounts/admin.py:13`），但**全代码库没有任何一处鉴权逻辑读取它**。

对比之下 `can_login` 是正常生效的：`club_accounts/authentication.py:41`、`club_accounts/permissions.py:25,36`、`console/permissions.py:264,282` 都有校验。

**影响**：运营在后台勾掉「允许查看数据」后，界面显示已限制，实际该账号仍能读取全部数据。这是**功能欺骗 + 数据合规风险**。

**修复建议**：要么在 `IsClubAccountAuthenticated` 的只读路径上补校验，要么直接从模型和后台表单里移除这个字段——留一个假开关比没有开关更危险。

### P1-3 并发抢单可突破同时接单上限（写偏斜）

**位置**：`orders/views.py:59-68`（`count_active_orders`）、`694-720`（`GrabOrderView`）

```python
def count_active_orders(account):
    return Order.objects.filter(...).distinct().count()   # 无锁 COUNT
```

`transition()` 只对**目标订单行**加 `select_for_update`。两个陪玩同时抢**两笔不同订单**时，两个事务锁的是不同的行，互不阻塞，各自 `COUNT` 到 2 → 都判定未超限 → 提交后实际变成 4 单，超过 `MAX_CONCURRENT_ORDERS = 3`。

`pre_check` 里的「二次校验」在同一事务内执行，看到的还是快照，无济于事。

**修复建议**：抢单前先对陪玩账号加行锁（`ClubAccount.objects.select_for_update().get(pk=account.id)`），把并发抢单串行化；或在 `EscortProfile` 上维护 `active_order_count` 计数器字段，用数据库 CHECK 约束兜底。

---

### P1-4 陪玩状态在多单场景下被错误重置为空闲

`MAX_CONCURRENT_ORDERS = 3`，但以下四处都**无条件**把陪玩置为 `AVAILABLE`：

| 位置 | 场景 |
|------|------|
| `orders/views.py:901` | 陪玩端完成订单 |
| `orders/views.py:1031` | 陪玩拒单 |
| `orders/views.py:1094` | 客服强制退款 |
| `console/views.py:1366` | 后台完成订单 |

陪玩手上有 3 单、完成其中 1 单，状态就变成「空闲」，实际还在服务另外 2 单。派单和抢单池的展示会因此失真。

**唯一做对的是** `AssignOrderView`（`orders/views.py:1287-1293`），它按 `count_active_orders` 动态判断 BUSY/AVAILABLE。

**修复建议**：抽出统一的 `refresh_escort_status(account)`，按在途单数决定状态，四处调用点全部替换。

### P1-5 报单创建维度不一致，可能撞唯一约束 500

`ProviderReport` 有**两条**唯一约束（`wallet/models.py:305-311`）：

```python
UniqueConstraint(fields=['provider', 'order'],         name='uniq_provider_order_report')
UniqueConstraint(fields=['provider_account', 'order'], name='uniq_provider_account_report')
```

但两个创建入口用了不同的查询键：

| 入口 | 查询键 | 是否写 `provider_account` |
|------|--------|--------------------------|
| `orders/views.py:783`（开始服务） | `provider=legacy_user, order=order` | 否 |
| `orders/views.py:910`（完成订单） | `provider=legacy_user, order=order` | 否 |
| `wallet/views.py:324`（陪玩端建草稿） | `provider_account=account, order=order` | 是 |

前两处创建的记录 `provider_account` 为 NULL。陪玩之后在报单页点「创建报单」，第三处按 `provider_account` 查不到 → 进 create 分支 → 撞 `uniq_provider_order_report` → **IntegrityError 500**。

**修复建议**：统一封装 `get_or_create_report(order, account)`，三处调用同一个函数，创建时两个字段都写。

---

### P1-6 双陪订单副陪无法自助流转，报单金额展示错误

**副陪被挡在门外**

`StartOrderServiceView`（`orders/views.py:776`）和 `CompleteOrderView`（`830`）的 `pre_check` 都只判断：

```python
if order.provider_id != request.legacy_user.id:
    raise IllegalTransitionError('仅订单关联的大神可开始服务')
```

`order.provider_id` 只记录主陪。副陪调用这两个接口直接被拒，双陪订单只能靠客服后台 `console complete` 兜底，而后台完成**不校验入队/结单凭证**，等于绕过了整个凭证风控。

**报单金额口径错误**

`console/views.py:1796`：

```python
report.payout_amount = report.order.provider_income   # 订单级字段
```

双陪时每人实际入账的是各自 `OrderProvider.provider_income`，但报单页展示的是订单级口径。陪玩看到的金额和钱包实际到账对不上，会引发大量客诉。

**修复建议**：`pre_check` 改为校验 `order.providers` 中是否存在当前账号；`payout_amount` 按 `OrderProvider` 行取值。

## 3. P2 中等问题

### P2-1 已完成订单没有正规退款通道

`RefundOrderView` 限定 `GRABBED / IN_SERVICE`，`console._do_refund` 限定非终态。订单 `COMPLETED` 后发生纠纷无法走退款流程，只能用 `wallet:adjust` 手工调账（`console/views.py:1590`）。而调账写的 `tx_type` 是 `REWARD` / `WITHDRAW`，**语义错误、无法对账**，也不会回滚陪玩已入账的收入。

建议补一个「完成后退款」流程：冲正陪玩收入 + 冲正平台留存 + 退款给老板，全部写配对流水。

### P2-2 审核接口取钱包无异常保护

`console/views.py:1949`、`1991` 使用 `Wallet.objects.select_for_update().get(user_id=...)`，钱包不存在直接 500。虽然申请提现时必然已建钱包，但叠加 P0-3 的维度错乱会显著放大故障面。

### P2-3 退款回退优惠券不校验有效期

`orders/views.py:1389-1392` 把 `USED` 券无条件回滚为 `UNUSED`。若券已过期，回滚的是一张死券，用户看到券回来了却用不了。建议过期券改为补发或明确提示。

### P2-4 人员编号生成方式在规模上升后不可靠

`users/models.py:9-17`：`XA` + 6 位随机数，查库校验冲突后重试。10 万级用户后碰撞率显著上升；且「查询」与「插入」之间没有锁，高并发注册仍可能撞 `unique`。建议改用数据库序列或雪花算法。

### P2-5 订单超时自动取消依赖 Celery，投递失败被静默吞掉

`orders/views.py:1400-1410`：

```python
except Exception:
    pass   # 注释：Celery 未启动时由 management command 兜底
```

需确认兜底的 management command 确实配置了定时调度。否则 Celery 异常期间下的订单会**永久停留在 PENDING**，老板的钱一直被占用且无法自动退回。

## 4. 设计中做得好的部分（建议保留并加固）

| 项 | 说明 |
|----|------|
| 状态机统一收口 | `transition()` 是唯一状态切换入口，白名单 + `select_for_update` + `@transaction.atomic`，重复完成/重复退款天然幂等 |
| 报单不二次入账 | `console/views.py:1792-1804` 对有 `order_id` 的报单只更新审核状态，明确避开了「完成入账 + 报单再入账」的双倍付款陷阱 |
| 服务端定价 | `CreateOrderSerializer.validate` 用 `compute_order_amount` 全量重算并覆盖 `attrs['amount']`，客户端无法篡改价格 |
| 优惠券防并发 | 下单时对 `UserCoupon` 加行锁并校验 `UNUSED`，杜绝同券多用 |
| 提现三态闭环 | 申请冻结、通过解冻、驳回退回，三条路径都正确维护 `frozen_amount` |
| 提现税额双保险 | `actual_amount = amount − tax_amount` 在模型 `save()` 强制 + 数据库 `CheckConstraint` 双重校验 |
| 抢单二次校验 | `pre_check` 内复查接单上限，缩小了拉列表到点击之间的窗口（虽仍需行锁根治，见 P1-3） |

## 5. 修复优先级建议

**上线前必须完成（阻断项）**

1. P0-3 钱包寻址统一 + 存量数据回填 —— 影响面最广，且是其他问题的放大器
2. P0-2 删除 `or amount` 回落 —— 改动量最小，收益最直接
3. P0-1 双陪分账口径重定义 + 汇总校验 —— 需先与业务确认商业规则

**首个迭代内完成**

4. P1-1 押金/税金入平台账户，补押金退还
5. P1-5 报单创建维度统一
6. P1-6 双陪副陪流转 + 报单金额口径
7. P1-2 `can_view` 落地或移除

**排入常规迭代**

8. P1-3 抢单并发行锁
9. P1-4 陪玩状态统一刷新函数
10. P2 全部

## 6. 建议补充的回归测试

| 用例 | 断言 |
|------|------|
| 双陪订单完成 | `SUM(provider_income) + inviter_commission + shop_income == amount` |
| 抽成率 100% 的订单完成 | 陪玩入账为 0，平台入账为 `amount` |
| 陪玩先结算后首次访问钱包 | 返回 200，余额与结算金额一致 |
| 老板先充值后首次下单 | 返回 200，无 `IntegrityError` |
| 单陪玩并发抢 4 单 | 成功数不超过 `MAX_CONCURRENT_ORDERS` |
| 陪玩持 3 单完成 1 单 | `EscortProfile.status` 仍为 `BUSY` |
| 开始服务后在报单页建草稿 | 返回 200，命中同一条 `ProviderReport` |
| 缴纳押金前后 | 全系统钱包余额总和不变（押金进入平台账户） |
| 提现通过前后 | `SUM(balance + frozen)` 减少额 == `actual_amount + tax_amount` |
| `can_view=False` 的账号访问数据接口 | 返回 403 |
