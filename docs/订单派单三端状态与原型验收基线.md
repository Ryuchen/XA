# 订单与派单：三端状态、原型和验收基线

日期：2026-10-27。范围是老板微信小程序、客服管理后台和陪玩 H5 的一笔服务订单。本文件用于讨论和验收，不代表提议已经实现或运营规则已经确认。现状依据本工作区源码静态检查及既有文档；没有在本次检查中执行真机、生产环境或支付联调。

**本轮决策与开发增量：** 用户已确认由老板在每笔适用订单选择公开接单或客服指定。本地老板原生结算页已增加选择，未指定的单陪及双陪订单可提交 `PUBLIC` / `STAFF`；已指定陪玩按既有指定流程处理。双陪客服指派要求一次选择两名陪玩。待接单时限已增加全局配置，并为新订单冻结时限快照；老板订单列表及详情显示该订单服务端返回的实际截止时间。后端增加路由隔离和请求核对/封止接口，具体本地测试结果见第 7 节；真机、真实 Worker 和真实消息渠道尚未验收。

## 1. 现状与本次目标

**现有：** 老板原生结算页支持服务端报价、余额支付、指定陪玩或平台安排，并有「老板选人 / 直接抢单」两种请求模式。余额不足时页面提示联系客服充值；当前基线没有自助微信支付。已支付订单按选择进入公开接单或客服待派路径；后台可为符合条件的单陪或双陪待派订单指派。陪玩完成服务后可提交报单，后台处理审核和退款。

**现有边界：** 自主下单开关、流量限制和全局待接单时限可以配置，但不等于所有派单策略都可配置。待接单时限默认 30 分钟，可设为 1–1440 的整数分钟；陪玩接单并发上限当前仍为代码常量 3。直接抢单仅允许单陪，公开路径的老板选人模式涉及公开报名；客服待派路径不进入公开池。

**建议：** 在已实现的两种安排路径上继续完善运营体验；是否允许有权限人员把待派订单转入公共池仍需确认。任何时刻同一履约名额最多归属一名有效陪玩。

**待确认：** 余额不足是否需要新增微信支付或自助充值，及商户资质、退款回原渠道还是余额、赠币处理；后续是否需要陪玩确认指派、按商品配置可选路径及其他阶段时限。不得以本文件自行改变已有资金规则。本轮客服待派对陪玩公共池隐藏，未接单到期退款回余额；双陪沿用当前不支持成员自行拒单，开工前由客服处理退款，服务中按现有规则转单。

**待接单时限与历史订单：** 新订单读取当时已提交的全局配置并冻结分钟数；有待接单期限的订单以服务端保存的 `auto_cancel_at` 为准。后台修改配置不改在途订单当前截止时间，也不重写其已冻结时限；新订单在允许拒单后按本单快照重新计时。历史无快照订单保留原截止时间，之后允许拒单时按 30 分钟回退重新计时。原本无抢单期限的已指定或预约订单不因配置更新增加当前截止时间。报价可返回当前分钟数，创建请求可带预期分钟数并在配置变化时要求重新确认；老板原生页面不把报价时配置当作承诺，提交后显示实际截止时间。

**后台权限与审计：** 查看配置需 `order:view`；修改需同时具备 `order:view` 和 `order:timeout`，使用配置版本防止覆盖他人更改。每次修改记录操作人、变更前后分钟数和版本；查看历史需 `audit:view`。

源码参照：`apps/boss-miniapp/native/pages/checkout/index.js`、`index.wxml`；`apps/provider-miniapp/src/pages/orders/index.tsx`、`report/index.tsx`；`apps/admin-web/src/views/order/index.vue`、`TrafficConfig.vue`；`services/backend/orders/views.py`、`applications.py`、`serializers.py`、`services.py`、`models.py`。历史基线见 [当前 PRD](PRD_CURRENT.md) 和 [订单流程验收](ORDER_FLOW_AUDIT_20260922.md)；较早文档与当前源码有时间差，具体实现及结算条件需以现行代码和专项记录复核。

## 2. 同一订单的三端状态矩阵

下表是原型和验收应覆盖的用户状态，并非新增数据库状态枚举。订单状态、支付、履约、报单、售后和结算是不同维度，页面不应把其中一个状态当作其他状态的证明。

| 阶段 | 老板小程序：看到什么 / 可做什么 | 管理端：看到什么 / 可做什么 | 陪玩 H5：看到什么 / 可做什么 | 标记和约束 |
| --- | --- | --- | --- | --- |
| 选择与报价 | 选服务、数量、游戏信息及安排方式；看到服务端报价、优惠、实付和余额；价格变化需重新确认。 | 配置上架及价格；报价应反映当前有效配置。 | 不展示未付款订单。 | **现有**余额结算及重新报价；**建议**在付款前说明安排方式和等待/超时规则。 |
| 支付结果待核对 | 提交过程中防重复；网络结果不明时先查订单和余额，不提示已失败或要求盲目再次付款。 | 可用订单号和账务流水定位。 | 无可抢订单，直到服务端确认已支付并满足规则。 | **现有**幂等回执及查询机制的设计；真机弱网体验仍需验证。 |
| 已付款、等待安排 | 显示已支付金额、订单号、当前等待路径；有期限时展示服务端实际截止时间及到期退款去向。 | 列表可查看待接单并对合资格人员指派，区分需客服处理和已公开订单。 | 自动入池时，符合条件者看到可操作订单；客服专属待派不可见。 | **本地已实现**公共池、报名、客服待派和后台指派；真实三端消息待验收。 |
| 接单竞争 / 指派 | 看到已接单人员或继续等待；不因过期消息误显示多名已接单人员。 | 接单结果和操作人可查；同一订单被其他人接走时刷新并展示原因。 | 抢单、报名或接收指派的结果以服务端为准；失败显示已接走、资格变化、容量不足或期限已到等原因。 | **现有**提交时检查状态、资格和容量；**待确认**指派是否需要接单确认，不能预设当前指派为待确认。 |
| 已接单 / 履约中 | 查看陪玩及服务进度，必要时发起售后或联系平台。 | 可按权限处理拒单、转单及退款；操作需有原因和记录。 | 按允许动作开始、完成或拒单；拒单结果应说明后续安排。 | **本地已实现**单陪客服待派拒单回客服并按订单时限快照重计时；双陪不可自行拒单。 |
| 履约完成 / 报单与售后 | 区分服务完成、售后处理与退款进度；不把陪玩收益结算当成老板付款状态。 | 查看各必要成员的报单、审核结果、售后与结算条件。 | 补充凭证、提交、查看驳回原因及重新提交；收益应区分预计、冻结和实际到账。 | **现有**报单、审核与收益展示；结算窗口、投诉和部分退款等现行细则须以最新代码及专项记录核实。 |
| 超时 / 取消 / 退款 | 清楚显示原因、退款金额、去向和进度；余额退款不表述为原支付渠道退款。 | 可查触发原因、金额、流水和失败待核对项；有权限时处理异常。 | 订单不可继续抢或报单；已完成的服务及收益依据实际账务展示。 | **本地已实现**全局可配置待接单时限、快照及钱包退款；**待确认**外部支付退款去向。 |

## 3. 两种派单路径与后续体验建议

两种路径的基础路由已在本地实现；以下表格中涉及提醒、人工转池及渠道补偿的内容仍是产品建议，不代表已交付。

| 情形 | 自动入池：建议体验 | 客服待派：建议体验 |
| --- | --- | --- |
| 支付成功 | 老板看到「等待陪玩接单」，陪玩池按资格、可见时间和容量过滤；后台能查看订单及剩余时间。 | 老板看到「平台正在安排」；后台待办显示服务要求、等待时间和可操作项；未经释放的订单不出现在陪玩池。 |
| 抢单 / 指派 | 陪玩点击抢单时重新校验；成功后更新三端。客服如可介入，需受同一归属约束。 | 客服选择陪玩前展示资格及原因，提交时重新校验；成功后陪玩收到站内结果。是否要求陪玩接受须确认。 |
| 超时 | 展示明确处理：继续等待、转人工、取消退款等只能采用已确认规则；不要让用户自行猜测。 | 在约定时限前提醒并升级处理；若允许转入池，需记录操作者、时间与新的期限。不能静默丢单。 |
| 拒单 / 转单 | 说明回池条件、可见时间是否重新计算、订单已支付金额和期限是否变化。 | 明确回客服队列还是释放入池，及新一轮派单期限；避免陪玩仍占用原名额。 |
| 消息失败 | 订单状态仍以服务端为准；页面刷新可恢复，通知失败要有可核对记录及重试机制。 | 客服可看到待处理任务；不能把消息送达当作订单已派出或已接单。 |

## 4. 可配置范围与规则护栏（建议）

配置应有作用范围、优先级、版本、操作人、生效时间和变更记录；订单保存当时适用的关键规则快照，避免配置变更改写历史承诺。当前已实现的全局待接单时限及权限、审计规则见第 1 节；以下其余内容不是现有后台能力清单。

| 配置域 | 可讨论项 | 护栏与待确认事项 |
| --- | --- | --- |
| 入口与路由 | 按服务/套餐决定自动入池或客服待派；是否允许老板选择、客服释放至池。 | 不同路径不得互相绕过；已付订单改路径需记录原因。默认规则和优先级待运营确认。 |
| 时限与升级 | 已实现全局待接单时长；可进一步讨论提醒、其他阶段时长及升级。 | 现有新单冻结配置、历史单保护与退款去向见第 1 节；其他策略需单独确认。 |
| 接单资格 | 认证、游戏项目、档期、名额、通行证可见延迟等。 | 列表过滤只是展示优化，执行时必须重新验证；指派能否覆盖资格应明确，不默认允许。 |
| 通知 | 客服及陪玩的站内消息、渠道启用与发送范围。 | 不承诺外部消息已送达；失败、重试、结果未知需区分，不能触发重复派单。 |
| 资金及售后 | 报价、优惠、支付、退款与结算规则。 | 由已批准的财务口径单独控制；支付、退款和分账均要求幂等及流水，不因派单配置变更而重算历史订单。 |

## 5. 可操作验收场景

| 场景 | 操作 | 预期证据 |
| --- | --- | --- |
| 自动入池 | 老板付款后，合资格和不合资格陪玩分别刷新订单池。 | 成功扣款一次；符合规则者看到订单，不符合者不可抢；三端订单号和金额一致。 |
| 客服待派隔离 | 老板选择待派路径并支付，陪玩刷新池；客服打开待办并指派。 | 指派前陪玩池不出现订单；后台能查到待处理订单；指派结果及操作者可追溯。本轮本地已实现，数据库专项和并发结果见第 7 节，真机及真实通知尚未验收。 |
| 指派与抢单竞争 | 对同一单分别从客服和多个陪玩会话同时提交；另测两单争同一人最后名额。 | 每个履约名额至多一个成功归属，容量不超限；失败者看到明确结果；扣款不重复。需真实数据库独立连接。 |
| 资格变化 | 列表加载后封禁、改变档期或占满名额，再提交抢单/指派。 | 服务端拒绝过期动作，订单和钱包不发生错误变化；刷新后状态一致。 |
| 超时与接单竞争 | 临近截止时并发接单、超时任务和兜底扫描。 | 只产生一种一致结果：成功接单或按规则超时处理；不出现已接单又退款，重复任务不重复退款。 |

| 通知不可用 | 测试环境关闭或模拟消息渠道失败，执行已支付订单派单。 | 订单与账务不因通知失败回滚；刷新能查到真实状态；待设计的通知监控能定位并处理失败。 |
| 售后和结算 | 服务完成后提交必要凭证，测试驳回重提、退款与审核竞争，以及涉及转单成员的情况。 | 不重复结算或退款，资金流水平衡；已完成、待审核、待结算与实际到账分别展示。按最新退款和售后窗口规则执行。 |
| 三角色可用性走查 | 老板、客服、陪玩各按原型独立完成正常和异常场景。 | 记录任务完成率、误操作、耗时和困惑；由实际运营者确认文案、待办归属和处理规则。指标阈值先与运营共同约定。 |

## 6. 需要业务确认的决策

1. 自助资金路径：是否新增微信支付/自助充值？退款是回余额、原支付渠道还是依不同资金来源处理？
2. 派单路由：本轮由老板选择，客服待派期间对陪玩公共池隐藏；后续是否允许商品配置可选路径，以及客服是否可以转入池？
3. 指派语义：指派后立即算接单，还是陪玩确认后才算接单？拒绝和超时各回哪里？
4. 多人服务：当前公开路径按既有组队报名、老板选人处理；客服路径要求一次指派两人。后续是否支持逐人补位，以及成员退出等新规则，需另行确认。
5. 时限、升级与售后：待接单时限和在途订单规则已按第 1 节实现；其他阶段等待多久、是否通知或升级处理需确认。
6. 权限和证据：待接单时限的查看、修改和审计权限已按第 1 节实现；其他策略、指派、释放、退款的后续权限及对账字段需逐项确认。

这些决策应由实际老板、陪玩、客服和财务参与，以真实业务数据、小规模试运行和可复现验收共同检验；当前无法仅凭设计文档证明某个商业策略是唯一正确答案。

## 7. 本轮本地验证与资金恢复边界
