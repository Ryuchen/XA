# 核心业务工作基线与验证计划

日期：2026-10-27。本文用于指导后续工作，不覆盖已经确认的资金规则，也不将设计建议当成上线事实。业务代码和对应日期的实际验收记录优先于历史文档；本文中的新方案以最终代码及验证结果为准。

## 目标和现有边界

老板通过微信小程序购买服务，陪玩通过 H5 接单及履约，客服通过管理端处理派单和异常。目标是减少非必要人工介入，同时保证客户知道订单进度和钱的去向。

现有代码和历史验收资料表明，项目已有三端、余额下单、订单状态机、接单、客服指派、凭证审核和结算。现行发布口径为客服核实收款并在后台充值，余额不足仍须联系客服；微信支付和外部自动退款不在已有一期范围内。因此，余额充足时的自助下单不能被当作首次购买已完全自助的证据。接入支付前应核实商户资质、服务类目、支付和退款方案，以及现有余额、赠币与退费关系；不能未经确认就将余额退款描述为原路退款。

现有下单选择中的 `BOSS_SELECT` 指陪玩报名后老板选择，`AUTO_GRAB` 指单人订单直接抢单；它们不是“客服待派／公开池”策略。待接单默认时限为 30 分钟，已增加全局配置；陪玩并发上限仍为代码常量 3。公开路径、多人组队和历史订单必须在改造中保留既定语义。

用户已确认：**每笔订单由老板选择派单方式**。本轮工作将“公开给陪玩接单”和“由客服指定陪玩”作为独立派单路径；客服待派不能从公开池或直接请求绕过。待接单到期取消并退回钱包的资金去向沿用现有规则；可配置时长默认 30 分钟。已有截止点不随配置变化而修改，新的单陪拒单轮次使用该订单冻结的时长；无快照的历史单拒单回退 30 分钟。

### 本轮本地交付与证据

- 客服待派列表及提醒在分页前核对直付报价，异常或超出单次 500 笔直付核验上限时显示“部分待核对”，可进入全部待派订单；余额订单不受该上限影响。后续仍需受数据库保护的可查询资格状态、支付异常工作台及生产负载验证。后台派单与群发按钮分别使用服务端动作判断，现有规则下公开双陪可在 H5 报名，但不支持一键群发。
- 陪玩与客服收益展示区分核定、待核对和内部钱包已记账；后者不等于可提现，冻结与可用金额以钱包为准。双陪缺少本人份额或身份映射冲突时不回退显示整单收益，退款、冲正或流水不一致时保守显示待核对。无退款报单列表的收益核验按批查询；历史退款摘要仍有逐单查询，报单列表尚未分页，不能宣称所有场景性能已优化。陪玩端订单/报单专项 40 项和后台提醒相关 67 项通过，均未替代真实设备或 WebSocket 验收。
- 已修复陪玩封禁与派单的竞态：普通/强制封禁先取得派单名额锁，在锁内重查在途订单再修改账号；派单和报名相关入口在锁后重新验证资格。MySQL 8 空库迁移后 99 项通过、无跳过，包含派单先完成时封禁被拒、封禁先完成时客服派单被拒及老板指定下单不扣款；H5 抢单、双陪、转单等入口尚未逐一完成 MySQL 并发验收。
- 隔离测试态微信回调可从 ASGI 原始请求完成验签、解密与持久收件；不能处理的已验签报文加密留存。与客服队列关联回归在 MySQL 8 空库完整迁移后 121 项通过、无跳过；生产回调、真实收款和异常重放仍未开放。

- 未指定陪玩的单陪和双陪订单可由老板选择公开接单或客服派单；客服待派不进入公开列表、报名、抢单或群发，客服可在后台筛选和指派。单陪拒单后退回客服处理；双陪由客服一次指派两人，保留现有不能自行拒单、需联系客服处理的规则。已有订单默认保留原有路径，已指定陪玩的订单继续直接安排。
- 老板暂时指定陪玩后再清空选择时，恢复先前选择的公开或客服派单方式；公开双陪在付款前说明组队报名、队友确认与老板选人。接单期限由服务端判定，过期时不再提供选人动作，老板端显示等待处理。小程序相关回归 112 项通过；真实微信直付尚未开放。
- 管理后台在线时通过实时事件提示有权限的客服，并可查看待派截止时间。离线通知与真实消息渠道投递尚未验收；断线期间需从待派列表核对。
- 老板端在本设备保留未确认的原订单请求；可重试相同请求，也可请求服务端核对或封止。封止和下单共用钱包事务锁，已成功的请求返回原回执；已封止的请求不能再扣款。旧交易无可信回执或请求内容冲突仍须人工核对。本机保护不保证换设备、清除存储或旧版本客户端上的跨设备防重。
- 验证：单人客服待派及相关并发组合在隔离 MySQL 空库真实迁移后 12 项通过；请求封止及相关回执组合 24 项通过；加强版封止专项另在 MySQL 空库真实迁移后 7 项通过，包含先下单及先封止两种钱包锁竞争。双陪客服派单关联回归在 MySQL 空库迁移后 32 项通过，最新专项 6 项通过，包括竞争最后名额、指派与退款并发、两人履约结算及部分入队后退款；均无跳过。老板端专项 33 项、核心回归 72 项、陪玩交互 13 项，以及后台提醒和双陪管理相关测试通过；陪玩和后台类型检查通过，后台构建通过，微信原生 49 个 WXML、52 个 WXSS 通过官方编译检查。上述结果只对应本地版本，不代表真机、生产、真实外部通知或全部业务场景均已验收。
- 生产发布需要先完成新数据库迁移，再同步发布配套服务端和三端；本轮未执行部署。自动充值、微信支付、外部原路退款以及真实场景验收仍未完成。
- 资格快照仍有边界：明确的端、玩法及档位要求使用订单快照；缺少该快照的旧式等级准入和技能关系仍可能读取当前商品配置。不能把本轮金额与固定抽成快照的测试，扩展解释为所有资格都已冻结。
- 时限配置的生效点是创建订单时读取到的已提交配置；并发修改尚未提交时，正在创建的订单可能采用旧值。后台对修改权限、版本冲突和时限前后值历史做了控制；实际可见时间、员工角色授权和系统负载仍需要运营验收。
- 最终时限配置、权限及审计版本在 MySQL 空库完整迁移后，连同双陪和资金恢复相关回归共 26 项通过、无跳过，覆盖未提交配置时下单不阻塞、配置与订单快照一致、角色迁移及历史分页。管理端配置与审计界面相关 53 项测试、类型检查和构建通过；老板端相关回归 105 项及原生模板编译通过。测试环境的 Celery eager 模式会立即执行延时任务并出现重试日志，不能据此认定真实 Worker、Beat 的延时和重启恢复已验收。
- 同步修复超时兜底管理命令的旧扫描竞态：订单锁内重查当前待接单状态及期限，防止接单、拒单后新期限被旧扫描取消。新增确定性竞态模拟和正常退款防重，与既有业务闭环共 17 项 SQLite 测试通过；这一专项不等同于真实 MySQL 并发验收。

## 专家会补上的工作

1. **业务与运营**：还原从购买到退款的真实过程，记录客服介入原因、未接单原因、争议与对账操作；区别老板选人、客服指派和公开抢单，确认异常归属和运营责任。
2. **产品与体验**：沿同一订单制作老板、客服、陪玩三端状态矩阵；为等待、无合适陪玩、拒单、超时、退款和网络结果未知设计下一步，而不是仅做成功页面。
3. **研发与测试**：枚举所有能改变订单的入口，包括公开列表、抢单、报名、客服指派、取消、延时任务与群消息；从服务端限制越权、重复提交、过期请求和并发竞争。
4. **财务与风控**：核对实收、赠币、订单支付、退款、陪玩分账、平台留存、提现和账务流水；将资金去向、权限、凭证和审计留痕纳入验收。
5. **运营可靠性**：验证通知投递失败、任务积压、服务重启、订单长时间无人处理及人工接管；定义值班责任和恢复步骤。

## 先从业务不变量出发

| 核心问题 | 应保持的约束 | 验证重点 |
| --- | --- | --- |
| 报价与支付 | 服务端决定成交价；用户确认的报价变化时不能按旧确认静默扣款；重试不能重复扣款 | 改价后提交、重复请求、断线后恢复、券规则 |
| 派单归属 | 客服待派订单未公开前不能被陪玩通过列表、报名或抢单获取；每个可用名额最多有一个有效归属，团队单按实际成员数检查 | 列表及直接 API、客服指派与并发抢单、容量锁 |
| 状态与资格 | 操作人、订单状态、资格、容量和时限在服务端提交时重新检查，不依赖按钮是否隐藏 | 资格变化、过期页面、取消与指派竞争 |
| 退款与结算 | 不重复退款或结算；退款、结算和订单状态相互一致；优惠券恢复仍受原有效期约束 | 退款与审核并发、取消与超时并发、断线重试 |
| 金额守恒 | 按成交及已批准退款的具体规则核对客户、陪玩、邀请人与平台流水；多成员和转单不能重复分配完整订单金额 | 小额舍入、部分退款、转单、对账差异 |
| 配置生效 | 影响价格、可见性或时限的策略应明确范围、生效时间与在途订单处理方式，并保留可追溯快照 | 修改配置前后下单、并发变更、回滚及旧单 |
| 通知与恢复 | 通知只是状态变化的提示，不能代替订单事实；失败或结果未知可核对和补偿 | 延迟任务、重复通知、服务重启、过期消息 |

## 方法与开发手段
 
- 用事件风暴梳理「用户意图 → 业务事件 → 状态与资金变化 → 责任人」，再写出各角色的正常路径与异常路径。
- 以状态机、决策表和不可变约束描述允许的转换及其前置条件，建立入口到规则、规则到测试的追踪矩阵。配置先明确优先级、默认值、历史快照与修改权限，再开发界面。
- 以场景驱动验收（Given / When / Then）覆盖越权、重复、错序与失败；对资金和订单竞争使用与生产同类型的数据库、独立连接与真实事务，而非把 SQLite 跳过的行锁测试算作通过。
- 支付及外部通知需设计幂等标识、可靠状态记录、结果未知的查询和对账，避免把超时直接视为失败。发布前用隔离环境演练回滚、任务重启、消息重放与人工补偿。
- 产品、业务、设计、开发和测试交叉审查同一份订单场景；产品核实文案与策略，开发说明实际约束和取舍，测试尝试绕过规则，运营核对是否可处理异常。AI 多角色协作只相当于内部交叉检查，不替代真实运营人员、客户或独立审计。

## 除团队判断以外的证据

没有单一证据能证明商业规则“唯一正确”。应以相互独立的证据持续检验，并让业务负责人明确验收阈值：

1. **历史业务数据**：抽样核对真实订单生命周期和财务流水，统计付款成功到接单、人工介入、拒单、超时、退款及对账差异。定义样本期间、口径、排除项与隐私处理；先测基线再设目标，不虚构行业标准。
2. **真实角色走查**：邀请老板、客服、陪玩分别在真实设备演练正常单和异常单，记录是否理解等待时间、操作后果及退款去向。样本量和通过标准由运营共同确定。
3. **可重复的工程证据**：由独立审查者根据业务规则编写反例；在 MySQL 验证并发、资金守恒与权限，在隔离环境验证 Worker、Beat、消息和重启恢复。记录版本、环境、命令、结果及跳过项。
4. **外部平台约束**：核实微信商户、产品及相关官方文档的最新适用要求；在真实商户与测试环境中验收，不能用本地模拟代替平台验收。
5. **受控试运行**：条件满足后由运营安排小范围试运行，核对订单与资金，并观察介入率、接单耗时、超时退款和投诉；发现偏差时停止扩量并复盘。

OWASP 的 [业务逻辑安全指南](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html) 提供服务端重算、状态转换、并发和业务不变量测试等独立工程参考；它不能证明某个俱乐部的具体派单政策最适合其客户。

## 分工与交付门槛

| 角色 | 责任 | 交叉验证 |
| --- | --- | --- |
| 业务/运营 | 规则、异常处置、真实数据和决策确认 | 验收原型、对账和试运行结果 |
| 产品 | 状态矩阵、配置和验收场景 | 与业务确认含义，与研发核对实际实现 |
| 设计 | 三端信息、操作反馈、移动端可用性 | 由真实角色走查，覆盖空、错、等状态 |
| 后端/前端 | 各入口统一规则、权限、事务和三端反馈 | 互审接口契约，验证旧订单和兼容路径 |
| 测试/质量 | 独立反例、并发、资金对账、故障恢复 | 复核代码与实际运行证据，不将跳过记为通过 |

交付顺序：先完成老板选择派单路径的可验证闭环及历史兼容；再根据实际使用结果细化可配置的时限、资格和异常处理；支付自助化单独完成商户和资金规则确认、方案设计、开发、对账及真实平台验收。每次交付保留具体版本、变更范围、验证结果和未验证项，不以历史专项的通过数字代替本次结果。
