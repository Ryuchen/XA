# 02 数据模型与迁移

本节是逻辑模型建议，名称与索引是待实施方案；实际 migration 以既有字段、MySQL 版本和 `makemigrations --check` 结果为准。所有业务表在各店库各自创建；目录与平台主体仅在 `default`。跨库只存稳定平台主体标识和原门店标识，不建立跨库外键。

## 2. 类型与数据一致性

- 保留当前 `Wallet.balance` / `Order.amount` 的内部整数单位，展示换算不得用二进制浮点；仅在已确认的服务／适用加购标价、预约／折扣报价、老板支付、退款店币和陪玩承担分摊等金额域执行相应整店币规则，不对历史余额及普通收益一律加整除约束。用户已确认普通收益沿用现有最小记账单位，可保留 0.1 店币，如 202.4 店币；不足该内部单位的计算沿用现有分成代码的取整方向，除非另有明确业务规则。薪资 `*_fen` 是人民币分，与业务内部分换算关系单独标明并经测试。
- 比率用整数分子／分母、基点或精确 Decimal，存储使用 `BigInteger` 时预先评估现有 `IntegerField` 的最大值；积分以 0.01 积分计数。各域 DTO 显式带单位或固定字段含义，禁止把两种整数直接相加。
- 原订单 `amount`、结算约束及 `OrderProvider.settlement_base` 目前以同一个基数工作；按支付、分成、积分补贴建立新恒等式并改写所有调用，不能只放宽 [order_split_not_exceed_amount](../../services/backend/orders/models.py#L476) 而忽略计算、报单和退款。
- 现有 [OrderFinancialLock](../../services/backend/orders/financial_lock.py#L1) 是避免多钱包互锁的门店级互斥。跨多钱包的订单资金操作沿用已有 `订单行 → 本店资金互斥行 → 资金／画像行` 方案，其他行按稳定类型与 ID 排序；明确核查提现、收益释放、预约、积分和押金不存在反向锁链。生产瓶颈以测试和监控证明后再优化，不在此阶段擅自拆锁。

## 3. 迁移步骤与历史语义

1. 扩列、新表和索引，均先允许旧记录为空；逐店执行有版本的 schema migration，先验备份、容量、锁时长和恢复演练。
2. 按流水恢复老板来源；无法判断的历史可用余额和已付款未知来源均归本金，记录迁移批次、金额与证据。可识别的赠送、赔付不能混入本金；迁移前后钱包总额与历史流水不变。
3. 对旧人／单回填一个最小履约段，使用可证明的抽成、接单／报单时间；无法可靠复原的内容标为未知，不能捏造细分历史。已结算与已退款流水保留，不能因为新规则重新发钱。
4. 读路径先兼容新旧对象，再用受控切换使新写仅走统一服务。全量迁移校验：钱包总额、冻结、押金、积分、订单应收、已退款、在途提现逐店逐对象一致，所有差异入异常队列而非强行修正。
5. 新旧流程不允许对同一笔业务双重记账；切换后原路径返回可理解错误或转发到统一服务。开始之前保存按店的切换水位、计时快照与配置版本；迁移与回滚细节见 [08](08-房间加购与历史切换.md) 和 [10](10-测试发布与回滚.md)。
