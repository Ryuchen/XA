# 工资退款确认与流水屏障

积分退款的实际退币由 `OrderPointsRefund.coin_transaction` 关联，普通协商退款由 `NegotiationExecution.customer_transaction` 关联，加购退款由 `OrderAddonRefund.buyer_transaction` 关联；普通直接退款另有 0263 的逐笔关联。工资核对这些流水的真实钱包、金额、订单和发生月，不把返还积分再次扣作退币。加购工资核对补充退款方案的付款、金额及退款操作人和真实入账操作人的一致性。

店内工资确认和离职结清现在与平台工资确认一致：启用退款工资核算时必须启用工资事件屏障；启用屏障后先在本店事务内获取工资独占锁，再执行既有核算与保存。主单、加购付款／退款的主要业务入口已有对应共享锁，工资确认后业务按已有迟核补发、退款发生月绩效及下一期扣回记录处理，历史工资快照不改写。

本次没有新增迁移，未运行测试或迁移。现有事件模型仍要求退款事实与真实钱包入账处于同一自然月；同一事务跨月写入两者的边界目前会要求核对，尚未完成按实际入账时点贯穿所有工资来源的改造。屏障配置和所有资金写入调用栈还须隔离环境逐项联调，重点覆盖积分零店币退款、同额多笔、加购、各轮协商、确认并发、跨月、补发与退款扣回、重试及门店隔离；不能据此宣称全部入口已验证。

## 后续：退款跨月时点

有直接退款流水关联的普通、积分、协商和加购退款，工资月度绩效、已确认工资退款扣回、迟核派单及加购补发统一按经过核验的老板钱包入账时间筛选、排序及计算截止时间，退款记录与流水跨自然月不再仅因此阻断。积分零店币退款不产生负店币工资事件；历史工资快照及已关联扣回记录不改写。

没有直接流水关联的旧事实仍只能通过原有唯一流水核验，候选事件不能可靠跨月定位；不作历史数据推断或迁移。跨月事务与工资确认竞争仍依赖工资事件屏障实际启用和资金入口取得共享锁。本轮未运行测试或迁移，须在隔离环境核验跨月、跨工资确认、多个同额退款、晚核实及下一期扣回、幂等、并发回滚和双店隔离。
