## 2. 身份和访问模型

- 店内 `ClubAccount` 仍为本店用户／员工身份，数据库内 ID 只在该店有意义；任何平台展示与审计统一用 `(store_slug, local_id)`，不能仅按数字 ID 汇总。
- 在平台目录新增独立平台账号及职能授权：平台超级管理员管理门店、汇总与薪资；平台财务在获授权范围内审核提现及配置／核算薪资。身份与店内岗位、角色分离；不得因店内超级管理员自动获得平台权限。账号停用、权限撤销对已有会话实时生效或按短有效期和撤销列表校验。
- 研发建议旧 `StorePlatformGrant` 保留审计及兼容过渡，逐人完成身份核验、显式迁移平台授权，不复制或伪造密码，不自动把全部店内超管升级。平台账户与存量店内账号可建立已验证的映射；映射和权限是不同事实。
- 老板和陪玩请求由已允许域名绑定门店，令牌声明、域名与目标资源必须一致；未知域名失败。后台从凭证或已签名的平台身份认证确定主体；平台选择目标门店仅用于受授权操作上下文，绝不接受任意 header/query 充当身份证明。
- 一家门店不可用时，后台无前缀登录若无法排除该店存在同凭证，不得静默选另一店；平台聚合逐店查询，明确成功、失败、统计时间与口径，不以 0 伪装缺失值。平台默认多店聚合，不将多库钱包／订单复制到平台库。
- 店内门店财务不作为新职能配置；保留历史账户、流水及权限审计，调整现有权限组合。门店客服初审提现；平台财务终审和登记打款；充值、售后和押金仍按本店明确权限处理。

## 3. 三端认证和接单资格

统一入口支持账号密码，绑定 OTP 时默认 OTP 验证并可切换短信，未绑定 OTP 使用短信；绑定本人微信后可使用扫码或快捷登录。手机号经短信核验，微信身份不得使用伪造授权。后台未绑定微信可以先通过密码加第二因子进入；成功绑定后微信直接授权登录。频控、验证码重放防护与第二因子重置必须同时覆盖三端。

接单判定统一服务调用，覆盖公开抢单、双陪、试音报名与选人、客服安排、指定、转单、预约确认；在授权和最终分配时按场景核对本人微信绑定、新入驻者已真实取得微信头像、押金、技能、可用状态、并发和档期。普通新接单与押金缺口放行单须检查当前并发；未来预约的提交、确认和付款转单不因当前在服单已满被拦，预约开始时可按已确认例外暂超上限，仍须检查档期冲突和其他适用条件。历史已绑定陪玩的旧头像可继续使用，不能伪记为真实微信头像。微信账号类型与实际头像获取能力需用真实渠道核验；不可行时阻断新入驻者首次接单并给出明确操作提示。

## 4. 新店初始化状态机

建议控制面持久化 `REQUESTED → RESOURCE_READY → SCHEMA_READY → ADMIN_READY → CONFIGURING → READY → ACTIVE`，任一步可为 `FAILED` 并记录可重试步骤、操作人、时间和错误。必须完成域名、库唯一性、首位管理员和下单、资金等核心配置校验才能营业，非核心项可明确停用。不要沿用现有 [initialize_store](../../services/backend/stores/provisioning.py#L40) 完成迁移即置 `ACTIVE` 的行为。

网页发起授权后的工作流由受限部署执行器完成库名分配、资源创建、迁移、连接与健康验证。已有 `create_database` 只面向预先存在的配置别名，不等于可动态注册任意库；其 `CREATE DATABASE IF NOT EXISTS` 也不能证明已存在库属于本次建店。新设计必须验证库所有权、多进程数据库别名注册、连接刷新、重启恢复及密钥安全；已存在但非本次申请持有的库禁止接管或迁移。库名、主机、权限由平台策略生成，禁止前端自由提交连接参数或执行 SQL；不得覆盖、清空或克隆现有门店。建库、迁移、目录更新互不具备分布式事务，应按步骤持久化并可恢复，失败不显示营业成功。

## 5. 事务与消息

单店资金事件：校验店上下文 → 店库事务及稳定顺序行锁 → 状态、资金流水、幂等结果和待发送事件同库提交 → 提交后唤醒任务；后台定时扫描未投递事件并幂等重试。`on_commit` 只避免提前消费，进程在提交后崩溃仍可能漏派，因此资金关键任务不可仅靠内存回调。通知失败不回滚已成功支付。

平台财务操作先验证平台主体及门店范围，再在目标门店单库持久写入业务动作与平台主体标识；平台汇总或独立审计异步同步并对账，不依赖跨库外键或跨库事务。实际线下付款状态不明一律停留核对状态，禁止自动重付或解冻。
