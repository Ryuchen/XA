# 续单核实与奖励

新增 `POST /api/orders/orders/{续单ID}/continuation/`，老板提交 `original_order_id` 和 `client_request_id`，建立独立续单申请；`GET` 同路径供老板和该单陪玩查看状态及本人奖励。原单与续单须属于同一老板业务周期，礼物订单及赠礼来源订单不能作为续单。请求重试使用原编号。

具备订单查看和客服处理权限的人员通过 `GET /api/admin/continuations/` 查看队列，`POST /api/admin/continuations/{ID}/` 提交 `decision`（`VERIFIED` 或 `REJECTED`）、`note`、`client_request_id`。核实时保存当前陪玩与各自业务周期；同一续单只能建立一条申请，相同审核请求可重放。

每店任务扫描已核实且已结算续单，持锁核实付款、积分凭据和补资、人员与实际收益流水；积分订单取原积分抵扣凭证的成交额，其他订单取实际成交额，严格大于 18800 账务单位才发奖。每人一次写入 500 账务单位的 `REWARD` 钱包流水与 `OrderContinuationReward`；本次续单转单、改派、退款或取消后不发，原单转单不影响，发奖后退款不冲销奖励。发奖同事务写所有受影响人，任务失败逐店重试。

受控路径包括可通过现有逐人结算及加购结算凭证核验的续单；有加购不直接取消奖励。加购退款与发奖持同一订单锁：尚无奖励时核对原加购付款、退款流水和双方确认，事实完整则标记不符合发奖，事实不完整则待核对；已有完整奖励记录的后续退款不追回。收入流水、账号缺失、所属周期或其他凭证不一致时，客服列表的 `reward_state=REVIEW` 和原因可见，任务会继续重试。授权人员可调用 `POST /api/admin/continuations/{ID}/retry/` 并提供 `reason`，留审计后重新核验并按实际结果返回状态；不能向新业务周期冒发，无法证明原账户合法收款时继续待核对。当前尚无人工裁定跨周期补发接口。`ORDER_CONTINUATION_REWARD_ENABLED` 默认关闭；依赖逐店 Celery 扫描和各店应用 `orders/0260` 及依赖。未运行测试或迁移；上线前须隔离联调单陪/双陪、188 元边界、积分前成交额、加购先退款及发奖后退款、退款与发奖并发、提前核实和结算后补发、跨周期、双店、重复请求及回滚；经营报表成本接入须另行验证。

续单查询增加 `reward_state_reason` 和每笔奖励的 `evidence_status`、`notice_status`；已发状态须核对对应陪玩、原周期和 500 单位的真实钱包流水，否则显示待核对。老板只能查询本人原周期；陪玩只能查询本人本周期席位，且只看到本人奖励。客服列表可查看待核对原因。可确认的不符合原因区分退款、转单及金额门槛；新字段供前端对接，未改前端。

续单奖励区分已付款加购和未付款意向：只有实际付款的加购需要核验加购结算；仅创建、但未支付的加购不会凭空要求加购收益流水或阻止符合条件的续单奖励。积分服务的资金作用域仍根据实际存在的意向选择，不绕过原有资金门禁。本次未运行测试或迁移，最终联调需覆盖普通和积分续单的未付款意向、已付款加购以及付款与结算竞争。

每笔奖励事实本身作为通知待发送记录，发奖提交后尝试创建该陪玩原周期的站内消息；失败由现有每店续单任务重试，单笔奖励最多关联一条消息。发送时重核奖励与钱包流水；来源不明保持待核对，账号离店或重入后终止旧待发送通知。启用前须各店应用 `orders/0261` 及依赖、运行逐店任务；通知发送不代表客户端已读。本轮未运行测试或迁移，须最终联调消息失败恢复、重复扫描、周期变化、同店身份权限和双店同号隔离。

普通补资或积分续单使用独立逐人结算凭证时，奖励任务按该凭证、本人报单和真实收入流水核对，并要求整单实际结算；不再等待该路径不会填写的旧陪玩分配行结算时间。原先使用分配行结算的订单仍按其既有凭证判断。此修改未执行测试或迁移，最终联调须覆盖普通与积分、单陪和双陪、零收益、加购、重复发奖及不同门店。
