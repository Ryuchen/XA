# 09 接口契约与工作包

### 陪玩名称的门店展示

预约 `provider`、双陪 `seats` 及转单后的 `current_providers` 增加当前 `avatar_url`，继续提供本店前缀展示名；列表批量读取头像，预约席位与订单的原姓名快照不被头像变更改写。代码未经测试，最终联调需覆盖双陪替换、已转单改派、仅业务账号、微信同步及自行上传头像。

订单 `provider`、`participants` 与双陪 `team_progress.members` 增加当前头像地址 `avatar_url`；参与人及进度使用本店前缀的 `display_name`，原昵称和业务快照不变。`provider.account_id` 返回本店业务账号，只有业务账号而没有旧用户映射时仍可返回陪玩信息。订单列表按当前页面批量读取陪玩头像，头像同步及上传仍由现有账户接口处理。代码未经测试，最终联调须覆盖双店、微信头像、上传后更换、双陪及仅业务账号。

订单接口增加 `provider_display_name_snapshot`，当前陪玩、参与人、抢单／试音报名人员、评价对象和评价记录分别增加 `display_name` 或 `provider_display_name`；预约接口的原陪玩、席位和当前陪玩也提供 `display_name`。展示值使用当前请求门店配置的英文前缀，原昵称与订单、预约中的原名快照保留，供前端在老板端使用展示字段。未设置姓名时保持为空，未配置合法前缀时返回原名。本批接口尚未联调，最终需核对声浪、兴安和第三门店的域名隔离、双陪及转单展示。

新生成的礼物、评价等运营播报，`{provider}` 按所属门店生成带前缀的名称；赠礼冠名播报内的陪玩名称也使用同一规则，既有权益记录与原始姓名不变。

本文件的字段和新增接口是**拟议契约**，并非现有实现承诺。保留现有 URL 和兼容响应字段；真正实施时以 OpenAPI／自动化契约验证命名、数据类型、授权和迁移版本。现有入口以 [路由总表](../../services/backend/config/urls.py#L7)、[订单路由](../../services/backend/orders/urls.py#L53)、[钱包路由](../../services/backend/wallet/urls.py#L1)、[后台路由](../../services/backend/console/urls.py#L1) 为准，完整盘点见 [PRD 接口清单](../prd/09-后端接口清单.md)。

## 1. 公共约定

- 店内对象标识只在认证后绑定门店内解释；平台接口显式目标门店只是授权检查的输入，不是可覆盖凭证的选库参数。
- 兼容现有 `client_request_id`。新资金写入口要求客户端生成唯一请求号，服务端保存请求摘要与原响应；同键同内容可查询／重放原结果，同键不同内容返回 `409 IDEMPOTENCY_CONFLICT`。历史接口的拒绝重复语义需做兼容迁移，不擅自声称现有代码已支持回放。
- 请求金额采用明确后缀：`*_coin` 仅用于对应业务规则已确认以整数店币表示的金额，`*_raw` 为现有内部整数、`*_fen` 为人民币分、`*_point_centi` 为 0.01 积分。分账、冻结、历史余额等不能全部强转为整数店币；普通收益沿用内部最小单位并按现有分成方向取整。旧字段先保持现有单位并声明版本；不能静默改义。
- 报价、配置、售后计划、房间和会话动作携带版本；状态变化冲突用 `409` 提示刷新。常见可执行错误含 `STORE_CONTEXT_INVALID`、`PERMISSION_DENIED`、`QUOTE_EXPIRED`、`INSUFFICIENT_BALANCE`、`POINTS_INELIGIBLE`、`QUALIFICATION_CHANGED`、`AFTERSALE_EXPIRED`、`PAYMENT_UNCERTAIN`。详细响应与实际 DRF 错误格式保持一致。
- 实时事件只含获权字段、门店上下文、对象和事件版本；重新连接以后按授权回读，不能用推送代替交易成功的查询。

## 2. 定价与支付契约示例

继续使用已有 `POST /api/orders/quote/` 与 `POST /api/orders/create/`，以下是需要协商增加的字段示意，并非当前已返回：

```json
{
  "quote_id": "q-example",
  "config_version": "store-config-v8",
  "expires_at": "2026-11-06T10:05:00Z",
  "original_coin": 2500,
  "discounted_coin": 2000,
  "points_redeemed_centi": 10000,
  "points_discount_coin": 300,
  "payable_coin": 1700,
  "source_coin": {"principal": 1500, "gift": 100, "compensation": 100},
  "discount_choice": {"kind": "member_or_activity_or_coupon", "id": "example"},
  "coupon_id": null,
  "rules_version": "pricing-v2"
}
```

示例仅展示字段关系，不指定门店真实积分汇率；若配置每 100 积分抵 300 店币，则上例消费 100 积分。创建时提交 `quote_id`、`client_request_id`、用户选中的来源／优惠及必要的确认记录，服务端从可信报价和锁内数据重算；不得信任客户端提供的金额或由客户端声称已付款。服务端要能区分老版 `amount` 与新增字段，并返回订单号、真实支付构成、积分消耗、等待安排状态。客服代单补 `customer_confirmation` 的来源、时间及可追溯证据，不能让客服代为捏造老板选择。

此示例仅为老板服务单：礼物只允许老板本金来源；陪玩通行证以陪玩本人钱包和本人积分支付，不应要求陪玩提供老板三类余额字段。统一支付核心必须按订单类型和付款人身份校验相应来源。

历史有效安全箱券可形成零实付订单，其补贴路径单独验证；本条不适用于使用积分抵扣的订单。礼物和特殊加购拒绝积分；体验单保持其专价及资格券限制。

## 3. 关键入口改造映射

### 门店加购关系配置（已实现，尚不支持购买）

- `GET /api/admin/config/service-addons/{service_id}/`：读取本店主服务下已配置的加购关系；返回 `status=CONFIGURATION_ONLY`、加购名称、当前价格和计价单位，以及各关系版本。价格仍是现有内部账务单位（10 内部单位为 1 店币），不是订单报价。
- `PUT /api/admin/config/service-addons/{service_id}/{addon_id}/`：请求为 `{"version":0,"enabled":true,"conditions":"条件说明"}`。新配置版本为 0，之后提交上次读到的版本；冲突返回 409。仅本店后台具备服务编辑权限的人员可修改，操作与前后版本写入审计。主服务和加购须属于同一游戏，不能是礼物或把加购当主服务。
- `GET`／`PUT /api/admin/config/service-addons/{service_id}/{addon_id}/price-options/`：读取或整体更新此关系的单位与单价，`PUT` 请求示例 `{"version":1,"options":[{"unit":"HOUR","price":500,"enabled":true},{"unit":"ROUND","price":400,"enabled":true}]}`。单位为 `HOUR`、`ROUND`、`ITEM` 或 `PACKAGE`；价格使用内部账务单位，必须是 100 内部单位（即 10 店币）的整数倍。此处与关系配置共享版本，保存同时替换单位列表、递增版本并记录前后审计；不是下单报价或付款。
- `conditions` 仅为文字记录，`enabled` 是门店配置状态，并非已经可以自助购买或能自动执行玩法条件；需待玩法条件、定价、支付及结算接通后重新在锁内验证。当前不会自动上架任何加购，也不修改既有价格。

当前试验路径增加 `POST /api/orders/orders/{id}/participation-evidence/`：陪玩本人在原价参与记录开启、本人兼容报单可编辑时，为已开始且已转出的指定 `segment_id` 上传 `completion_image`；可带 `client_request_id` 重放，同键不同内容冲突。订单与账号由已认证门店限定；图片通过现有私有媒体票据读取。此接口仅保存截图，不等于逐段提交、审核或结算；部分退款与协商终止等尚未接通旧报单编辑状态的情形仍需改造。

三端界面优先复用：老板端 [`fronted/boss/src`](../../fronted/boss/src)、陪玩端 [`fronted/provider/src/pages`](../../fronted/provider/src/pages)、后台 [`fronted/admin/src/pages`](../../fronted/admin/src/pages)。老板／陪玩桌面及手机均可操作；后台至少适配 1366×1024 横屏及桌面。保留现有界面，先保证成功、等待、失败、冲突和刷新后回读，不进行视觉重设计。

### 旧协商入口的兼容状态（2026-11-11）

- 旧转单的 `negotiated-refund-preview/` 保留历史资金核对信息；`funds_eligible` 仅表示旧账面资金是否充足，`eligible` 为 `false`，并返回 `execution_block_code=LEGACY_NEGOTIATION_AGREEMENT_REQUIRED` 与原因。旧 `negotiated-refund/` 对新请求返回同一错误码，不能仅凭客服的 `reviewed` 字段退款。
- 安全箱旧 `subsidy-negotiation-preview/` 保留 `recovery_available` 等资金事实，但返回 `execution_available=false`、`execution_block_code=SUBSIDY_NEGOTIATION_AGREEMENT_REQUIRED` 和原因；旧确认入口对新请求返回同一错误码。
- 已完成的旧请求仍按原操作编号和意图识别重试，不重复记账。上述两类历史协商的当事人确认、现行退款分摊及结算衔接仍待实现，不能把普通新协商流程通过的测试等同于这两类历史场景已接通。前端应展示服务端原因，不应自行把资金充足解释为可执行。

### 退押金等待期接口补充（2026-11-11）

后台 `GET /api/admin/escorts/{profile_id}/deposit-refund/` 在现有资格和阻断原因基础上返回 `wait_status`、`cleared_at`、`eligible_at`。`READY` 表示已满 7 天，`WAITING` 表示尚在等待，`BLOCKED` 表示仍有未结业务，`REVIEW` 表示历史结清或缴清凭证无法核实，`NOT_APPLICABLE` 表示无已缴押金；仍以 `can_refund` 及对应数量、原因作为操作依据。`cleared_at`、`eligible_at` 是时间戳或 `null`，不应由前端自行推断是否可以退款。`POST` 执行时在锁内重新核验，不允许仅凭旧预览出账。

退押金资格增加 `pending_addon_income_count`，表示本人尚未结算的加购收益段数，并计入 `pending_income_count`。加购实际结算及本人承担的加购退款影响七天起算；主单份额为零也不能跳过未结加购。后台和陪玩端共享同一资格计算。该代码尚未联调。

后台退押金在锁内重新核对七天资格后、占用资金幂等键之前，也核对退还金额入账后是否超过钱包记账上限；超限返回可核对的业务错误，不写资金流水。退还金额仍以已缴押金为限，不以现有钱包余额为限。当前已确认的七天规则由资格计算和后台执行承接，尚无单独申请、自动执行或到期通知的已确认流程；本次未运行检查、测试或迁移。

陪玩本人 `GET /api/wallet/deposit/` 的 `data.refund_eligibility` 提供同一资格预览及等待状态；它只展示当前账号的本店押金，正式退还仍由授权后台人员在事务内复核并执行。钱包归属异常时仅返回不可退还及核对原因。该新增接口字段尚待最终联调。

已付款且尚未分配的单陪和双陪公开试音订单，对符合本店资格和可见时限的陪玩显示在待接单列表。列表和详情用 `allowed_actions` 的 `GRAB` 表示可报名，用 `required_team_size` 指定报名人数。陪玩报名须提交本人 `recording_id`，双陪的队友在本人确认时提交自己的录音。可先上传新录音，再用返回的 ID 报名。老板选人前重新检查每人的录音。普通抢单仍由独立的自动窗口处理，`audition_recordings_required` 对普通抢单返回 `false`。历史报名已确认但缺录音时，两人可各自补录，老板须等两份有效录音齐备后选人。生产媒体与真实通知待最终联调。

### 2026-11-12：主单退款后的指定加购售后

- 主单已完成一次协商部分退款，且该退款影响了加购负责人时，有 `support:edit` 权限的本店客服使用 `POST /api/admin/aftersales/open-negotiation/`，提交 `order_id`、`affected_provider_account_ids: [加购负责人账号 ID]`、`reason`、`client_request_id` 和 **`addon_payment_id`**。这里的付款 ID 是加购付款记录 ID，不是加购意向 ID；必须属于该订单。单陪主单终止后，订单须已完成、仍在原售后期且未结算；双陪时另一名陪玩仍须处于履约中，订单及人员均未结算。

- 每部分最多一次退款，支持这项加购的部分或全额退款；原付款来源、本人前次主单退款后的剩余待结算收益、钱包及押金均在执行事务内重新核对。部分退款后仍需处理加购剩余履约时，使用现有 `/api/admin/orders/{order_id}/addons/payments/{addon_payment_id}/completion/` 发起完成确认，老板和加购负责人通过对应 `/{completion_id}/decision/` 确认；全部退完无剩余份额。加购不产生推荐佣金。`execution_available` 表示当前范围可执行，最终结果仍以锁内资金核验为准。
