# 08 房间、加购与历史切换

> 当前首版基线：不接管历史订单或旧站业务数据，下文历史切换内容仅供追溯。通用房间的申请、老板确认及自动确认三个 `ROOM_*` 开关当前代码默认启用；下文早期记录中“默认关闭／尚未接通”描述的是当时阶段，不代表当前配置。涉及积分、加购、转单的资金闭环仍按对应能力限制执行，须在最终联调核验。

客服核实结单申请通过或驳回时，申请陪玩可收到站内消息及核实说明；通过时老板收到待确认消息。以上通知与核实同事务写入，未完成本阶段联调。

通知处理参考 [Django 事务提交回调](https://github.com/django/django/blob/main/docs/topics/db/transactions.txt)：先在本店事务写入站内消息，提交后再触发实时刷新；该参考不替代门店身份、权益权限和实际送达判断。

## 1. 特殊加购

服务进行中，满足该玩法条件时老板从订单发起加购。加购保存主单、实际负责该加购的履约段、项目、数量／单位、项目单价、原价、支付来源、费率与配置快照；转单后 B 负责的加购使用 B 接入时主单费率。老板选择小时数／局数，系统按对应单价计算，不测量实际服务时长。支付前服务端重新校验订单状态、玩法条件、价格和资格；不使用会员／活动折扣、优惠券或积分，但按确认的三类钱包来源支付。

加购作为可逐项退款的资金明细与订单关联，按实际负责人跟随主单的报单、售后、冻结条件结算；售后分别确定主单和每项加购退款范围。下单额、派单额、陪玩接单额及抢单排序按原价与既定归属计入，VIP、工资按各自实付与时点规则计入。瓦罗兰特 1 陪 2／1 陪 4 由一名老板付款，其他人只是游戏队友、无需注册。

初始化价目保留逐店可编辑：百万房卡 40 店币，银行手游绝密加仓参考 1080 店币，预言家端游绝密／机密参考 680／480 店币；其他项目必须逐项核对历史价格，禁止统一乘 10 或未经核验上架。兴安黄金矿工钓鱼版保持既有停用，具体项目以 [PRD 特殊加购](../prd/31-特殊玩法订单加购.md) 为准。

## 2. 通用房间

当前已实现第一阶段：后台可在主服务上配置 `room_enabled`；新订单保存是否需要房间的快照，在已付款订单完成单陪或双陪人员安排时，于派单事务内自动创建唯一关联房间。`GET /api/orders/orders/{order_id}/room/` 按当前门店认证身份及订单关系返回房间入口信息：老板本人、当前履约陪玩和有订单查看权限的后台员工可读取。转出陪玩返回 `FORMER_PROVIDER` 及仅查看本人消息的权限。旧订单没有快照，不自动补开房间；具体玩法、待确认或结单能力尚未实现。

`GET`／`POST /api/orders/orders/{order_id}/room/messages/` 提供分页纯文本消息，发送字段为 `content` 和 `client_request_id`；同一发送人重复编号须保持相同内容。老板、当前陪玩和有订单查看权限的后台可读取共同沟通；后台发送还须有客服编辑权限。转出陪玩只能读取本人消息、不能继续发新消息；转入陪玩按当前分配获得权限。消息提交后通过 WebSocket 发送仅含订单编号的 `room_message_update` 刷新通知，客户端须重新调用 HTTP 接口，服务端在推送时再次校验门店及身份。玩法事件、其他附件类型和转出人员个人玩法历史尚未接通。

图片消息使用 `POST /api/orders/orders/{order_id}/room/messages/image/`，以 multipart 提交 `image` 和 `client_request_id`；支持 5 MB 以内的 JPG、PNG、WebP，并按实际图片内容校验及去重。消息列表通过 `content_type` 和短期 `image_url` 表示图片；图片票据每次读取都会重新核验本店身份和消息权限，转出陪玩不能继续使用他人图片的旧票据。此能力用于房间共同消息，不用于未经角色隔离的玩法私密凭证。

图片文件写入前保存独立提交的上传意图，再在订单事务中写入消息、附件和意图的关联。若结果不明，接口提示使用原请求编号重试，不立即删除可能已成功关联的文件；读取和重试也会核对图片摘要，文件被更改或缺失时拒绝读取并提示核对。每店定时恢复任务仅处理超过一小时的待处理意图，锁定意图并核对专用相对路径、文件指纹及数据库引用；无关联且证据一致的文件才删除，证据异常转待核对。该机制不扫描或自动清理未建立上传意图的历史文件；图片上传要求当前数据库连接没有外层事务。

房间异议已接入独立入口：老板可对本人房间通过 `GET`／`POST /api/orders/orders/{order_id}/room/objections/` 分页查看或提交异议；提交须带 `reason` 和 `client_request_id`。本店同时有订单查看和客服编辑权限的员工，可使用 `GET /api/admin/room-objections/` 查看待处理队列，并以 `POST /api/admin/room-objections/{id}/resolve/` 提交 `resolution` 和 `client_request_id`。异议保留完整记录及处理审计，重复请求不重复生成记录或通知；未处理异议阻止订单状态机进入已完成。异议不是正式售后、退款或老板确认结单。玩法条件、确认倒计时以及暂停后恢复剩余时间仍未接通，不能将异议关闭等同于已完成订单。

门店可通过 `GET`／`PUT /api/admin/config/room-confirmation/` 配置确认时限，请求格式为 `{"minutes":30,"version":0}`；平台超级管理员可在门店初始化接口的 `setup/room-confirmation` 配置同一项。版本冲突返回 409，修改留审计，缺失时不使用猜测的默认值。初始化证据中可单独核对该配置；当前确认倒计时尚未调用该配置。

用户确认通用房间达到条件时，由陪玩提交结单申请，客服核实通过后交老板确认。新增试验接口 `GET`／`POST /api/orders/orders/{order_id}/room/completion-requests/`，提交 `description` 和 `client_request_id`；`GET /api/admin/room-completion-requests/` 查看待核实项，`POST /api/admin/room-completion-requests/{id}/review/` 提交 `decision`（`VERIFIED`／`REJECTED`）、`note` 和 `client_request_id`。请求保存当前参与人，客服通过前校验人员与异议／售后状态，核实结果与审计同事务保存。核实不代表老板已确认或订单结束；因自动完成和异常路径尚未全部接通，`ROOM_COMPLETION_REVIEW_ENABLED` 默认关闭。不能在当前状态下启用房间订单并投入营业。

试验流程现在可收集单陪及双陪原有结单凭证，不结束订单或结算；双陪各自提交必要凭证后才可申请核实，核实通过后不得从订单或报单入口修改结单截图。核实通过同时保存本店时限和版本快照并通知老板；确认前提交异议会保存剩余时间并暂停，处理时由客服明确选择条件仍满足并恢复剩余时间，或不满足并作废本次核实。发生转单则在转单事务中作废旧核实，接替陪玩须重新申请；已暂停的异议仍须处理，不能恢复被转单作废的旧等待。旧结算模式的房间订单暂不允许转单，以免提前向转出陪玩入账。用户确认超时后、自动确认执行前仍可提出异议；若剩余时间为零，异议处理后恢复为立即到期。

老板主动确认试验接口为 `POST /api/orders/orders/{order_id}/room/completion-requests/{id}/confirm/`，携带 `client_request_id`。系统重新核对本店老板、核实状态、当前参与人、凭证、未处理异议／售后和订单结算快照，确认记录与订单完成、报单草稿和站内提醒在同一事务中保存；重试同一请求不重复结单。此时收益仍须按报单、售后和冻结规则结算。双陪中一人经已核验的协商退款终止后，继续履约者可以提交本人结单凭证、申请核实并由老板确认；人员变化使先前核实失效。积分订单对应分支仍需专项联调。自动确认任务按门店扫描并复用同一完成校验，单条异常不阻断其他订单；手动和自动流程的功能开关均默认关闭，尚须完成真实 MySQL 并发和外部任务验证。

定时任务发现待确认订单过期后，持有本店订单锁并重新检查异议、履约凭证、参与人、售后和结算条件；确认记录和订单完成在同一事务保存，不直接发放收益。校验失败进入有权限的客服可见的 `GET /api/admin/room-confirmation-problems/` 待核对列表并发送一次站内提醒；异常订单不会阻塞其他订单，条件恢复后由后续扫描再次核验。任务按 30 秒调度，三项功能开关默认均关闭；不因此声称已运行生产定时任务。

房间订单中，若老板与所有受影响陪玩已分别确认整单协商终止方案，客服执行时可依据已核验的协商和资金凭证结束订单，无须老板再次确认房间；普通退款、零退款及积分退款均保留原协商确认时间和后续结算等待。若房间有未处理异议，整单协商结案时同步关闭异议并关联协商方案，零退款也适用；仅部分陪玩终止而其他人继续履约时，异议仍须处理。异议处理、退款、确认计时作废及关联审计须同事务提交或回滚。

本期建设订单房间框架，不实现旧游乐场九种具体玩法。已付款且所需陪玩全部安排到位时自动创建，可在正式开始前进入；进入校验已登录账号、门店、订单和参与者。履约中按房间规则记录事件；进入待确认时存该店确认时限快照，老板确认结束或无异议超时自动确认。老板从房间或订单提异议，暂停计时并通知客服；异议解决后若仍满足结单条件，继续剩余时间；若修正后不满足，回到履约，再次满足时按当时新配置重新计算完整时限。

转单保留房间及已发生进度，接替者获得后续操作权限，原陪玩仅查看自身历史；加购由实际负责人员归属。房间事件、成员权限与订单状态变更须具备并发版本和幂等，不能因为重复回调产生两次结单或两笔收入。后续接入各玩法时沿用对应旧玩法的人／客服核验流程，但具体玩法规则及门店差异仍须逐项设计和验证。

## 3. 未结订单切换

> **2026-11-11 范围变更：** 本节旧数据迁移与接管流程不再是本次交付或上线验收要求，仅保留历史记录。按用户最新决定线上全清后从空数据重新部署；不自动清理本机隔离开发／测试库。房间与加购的新订单功能仍须完成。

历史普通服务单的时钟切换提供 `GET`／`POST /api/admin/orders/{order_id}/legacy-clock-cutover/`。有订单查看和押金规则编辑权限的本店员工先读取只读预览，核对订单状态、参与人、原抽成、报单、已有冻结和本店配置；提交时携带预览指纹与请求编号。系统锁定订单、资金互斥和本店配置，重新核验后保存切换时的售后／冻结时限和版本；没有原单抵比例时保存切换时比例，已有原比例则保留。原付款、抽成、钱包与冻结流水不改写；旧冻结已开始或归属不明、已部分退款或已发生收益、关键资料不完整等情况暂不自动切换。新快照下有效报单的冻结仍从本人最后有效提交时间起算，切换前已过去时间计入。

当前实现只覆盖已接单或服务中、售后时钟尚未开始且可核验的普通历史服务单；已完成、待抢、积分及其他复杂历史单仍需对应切换方案。切换记录和审计保存原事实及配置来源，重复请求可恢复结果，配置或订单变化后需重新预览；本项不是整店历史迁移已完成的证明。

针对仍在旧游乐场履约的历史单，新增本店客服核实接口 `GET`／`POST /api/admin/orders/{order_id}/legacy-room-completion/`。提交老板账号、当前陪玩账号、旧站老板确认时间、人工核实依据和请求编号；仅允许有订单查看和客服编辑权限的员工操作。系统校验本店订单、账号映射、旧站确认时间、未结售后及售后／收益时钟快照；通过后记录人工核实事实和审计并完成原订单，不创建旧站房间与订单的系统关联，老板不需二次确认。重复请求读取同一结果，核实和订单状态变更失败一起回滚。完成订单不直接结算，后续仍需报单、审核、等待期及资金条件。

目前该入口仅接收身份和钱包可核验、仍在服务中、原服务付款完整、未有已结算人员且已保存结算时钟的历史服务单。资料不足、已部分退款、旧收益已部分结算或时钟尚未迁移时进入人工核对，不假定迁移已经完成；该范围不能替代逐店完整历史切换。

逐店形成切换清单，按订单与每名陪玩列出原付款、来源、券／积分、报单、售后、冻结、转单、提现、原价份额与房间情况；只处理切换时未结订单，已完成历史交易不重开。保留原付款、流水和原参与人的抽成快照，后续新接入人员按其接入时新规则。未知历史付款来源退本金并记录依据，不能篡改原凭证。

| 切换时状态 | 接管处理 |
| --- | --- |
| 已开始售后或收益冻结 | 保留原真实截止时间；不得按新配置重新缩短或延长 |
| 服务中、售后未开始 | 保存切换时本店新售后时限，完成后从适用事件开始，即使门店之后改配置也不变 |
| 已有效报单、旧冻结尚未开始 | 以最后有效提交时间起算，切换前已过去时间计入；时限取切换快照；旧冻结已开始则保留旧截止 |
| 已付款仍待抢 | 从切换时开始新完整抢单窗口与总等待；合资格旧候选保留可核验的原提交等级和时间，证据不足按 [04](04-抢单预约与履约.md) 处理 |
| 旧游乐场房间进行中 | 继续在旧站玩完，不建立系统级订单房间关联；客服人工核验旧站本人结单与本店对应订单后，在新系统完成订单并留证据，不要求老板再次确认 |

迁移前先对每个目标店做只读核对及隔离环境演练，保存切换水位和可回溯报告；无法还原的历史字段标未知并进入人工核验，不能伪造原始事件或跨店归集。迁移期间对同单暂停写入或采取可证明的版本／水位机制，避免旧新两套流程并发收钱或结算。旧站与新系统不自动同步意味着人工核验依赖真实证据，并非已联调完成。
