# 预约历史与本人操作周期

预约列表和详情保留原有可见历史。序列化新增 `viewer_business_cycle_status`：`CURRENT` 为本人的当前周期，`PREVIOUS` 为已知旧周期，`UNKNOWN` 为缺少可信周期，后台人员为 `NOT_APPLICABLE`。旧周期与未知周期的本人 `allowed_actions` 为空。转单后当前有效履约席位以该席位保存的周期判断，同一账号新周期接替不因原预约旧席位被误标为旧周期。

本人确认、拒绝、取消、双陪重选、预约报价和付款转单按原预约或本人席位周期核验。确认、拒绝沿现有事务核验；取消、重选及付款在锁内重新核验账号和预约周期，后台操作继续使用既有权限。报价按请求时周期判断，实际付款仍在事务内重验。无法证明周期时不把当前周期当成原周期。

不增加结构迁移。尚需在隔离环境联调预约重入、席位重选、转换后接替、并发注销及报价与付款竞态；本次未运行测试或迁移。预约历史原有按账号可见的查询范围未改，其他订单或消息入口不在本次覆盖范围。

## 受邀人退出后的历史

双陪邀请事件新增 `provider_business_cycle`，创建邀请时保存当时本人周期；拒绝、超时或重选清空席位后，本人仍可按邀请事件查看预约历史摘要。`viewer_participation_status` 区分 `CURRENT`、`HISTORICAL` 与非陪玩的 `NOT_APPLICABLE`：即使历史邀请处于当前账号周期，历史受邀人也不能操作该预约。历史摘要不包含老板资料、其他席位、订单和游戏账号等信息；当前席位或转单后当前履约席位仍沿原授权展示。后台权限不变。

新增结构迁移 `orders/0275_reservation_seat_event_cycle`，依赖 `orders/0274`；首次部署须执行结构迁移，本轮未执行。旧事件没有周期快照时显示 `UNKNOWN`，不以当前周期推测；最终需联调超时、重邀及重新入驻交错场景。

## 新预约与老板退店并发

单陪及双陪预约创建在既有服务、陪玩档期及冲突检查锁之后，锁定预约老板账号，核验实际在店、可登录及请求周期，再以锁内周期写入预约。客服代约也校验所选老板，员工权限沿用原规则；不改变已确认预约的付款或陪玩押金缺口规则。此项无需新增迁移，尚需隔离数据库联调老板退店/重入与本人或客服创建并发。
