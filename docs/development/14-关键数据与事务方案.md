# 14 关键数据与事务方案

本页把 [02](02-数据模型与迁移.md) 的逻辑对象展开成可拆 migration 与服务任务的数据契约。以下字段名、索引名为**建议**，不是现有表的断言；实现前须复核 `makemigrations`、当前数据库版本和已有迁移链。所有新业务记录属于一个门店数据库；控制面条目注明在 `default`。

## 1. 单店持久对象

| 逻辑对象及归属 | 建议字段与类型 | 约束、索引与用途 |
| --- | --- | --- |
| 订单金额快照，扩展 `Order` 或一对一表 | `original_raw`、`discounted_raw`、`points_offset_raw`、`paid_raw`、`coupon_snapshot`、`pricing_version`、`pay_time`；金额 `BIGINT`，快照 JSON | 同订单唯一；原字段不改含义；`discounted_raw = points_offset_raw + paid_raw` 仅适用于该明确价格结构，历史、免费券及其他补贴路径须独立表达，不能用此式强套所有订单 |
| 老板余额来源及支付分配 | `wallet_id`、本金／赠送／赔付各自 `available_raw`；支付分配记录 `payment_id`、`kind`、`amount_raw` 与原流水 ID | 同老板钱包每种来源唯一；可用来源非负且总和等于老板可用钱包；写锁同钱包。礼物仅本金；陪玩钱包不套老板分类 |
| 积分抵扣与返还 | `payment_id`、`group_point_centi`、`group_coin`、`group_count`、`spent_point_centi`、`offset_coin`、汇率及开关版本；退款累计返还独立行 | 成功抵扣的组数为非负整数；保存原配置不可约分；每次退款唯一关联退款 ID，最终不超过原消耗 |
| 每次参与 `FulfillmentSegment` | `order_id`、`provider_account_id`、`sequence`、`accepted_at`、`started_at`、`ended_at`、`original_share_raw`、`settlement_base_raw`、费率／固定额快照、状态和来源 | `(order_id, sequence)` 唯一；索引 `(provider_account_id, accepted_at)` 供近 30 天统计；同人同单允许多段；旧 `OrderProvider` 保留聚合兼容头 |
| 段报单／版本 | `segment_id`、`version`、证据引用、`submitted_at`、`review_status`、`reviewed_at`、`freeze_deadline`、`validity` | `(segment_id, version)` 唯一；段上记录当前有效版本 ID 或用锁内状态管理，不能依赖 MySQL 不支持的条件唯一索引；旧 `ProviderReport` 作为兼容汇总头 |
| 收益、补贴与释放 | `segment_id`、`entitled_raw`、`subsidy_required_raw`、`subsidy_funded_raw`、`released_raw`、`state`、实际流水引用；礼物另关联礼物单 | 用稳定的收益份额／加购／释放分片 ID 建立唯一入账业务键；版本仅控制状态并发，不能当防重复付款键，否则版本变化会再次付款。累计实际拨付不超过已确认应付；应得、应补、已补、已付分别核对，负经营贡献不写入现有无符号 `shop_income` |
| 退款与回收 | 复用 `OrderRefund`、历史 `RefundRecoveryLine`；新增按退款＋履约段＋资金来源的责任／占用明细，记录原支付分配、退币／退分、待结收益／钱包／押金来源及门店取整差额 | 原 `RefundRecoveryLine` 的两条交易外键非空，但未结收益可能尚无入账流水，不能虚构原交易；待结应得冲减和已有钱包／押金流水回收分别留证。`(order, client_request_id)` 唯一；老板累计收到限于原付款，陪玩累计承担可因逐笔取整超本人原价；差额仅入账一次 |
| 押金缺口 | 陪玩、来源退款、`initial_raw`、`remaining_raw`、允许补缺服务单 ID、状态、每笔补款／收益抵扣流水引用 | `remaining_raw >= 0`；关联实际扣押金事件；同人占用补缺单至多一个，且不突破普通并发上限；礼物补缺不占该名额 |
| 抢单轮与候选 | 轮次 `order_id`、`round_no`、入池时间、截止、总期限、可见配置快照、版本、状态；候选保存队员、提交卡级、提交完成时间和实际履约指标比较所需快照 | `(order_id, round_no)` 唯一；轮内个人／队伍防重复；只有完整队伍是候选；候选提交和分配写入在订单锁内同步检查轮次版本 |
| 预约成员与占档 | `reservation_id`、陪玩账号、确认状态及时间、`start_at`、`end_at`、确认／付款截止快照、版本 | `(reservation_id, provider_account_id)` 唯一；在账号互斥锁下检查时间交集；锁外预览仅供提示，不能当最终占档依据 |
| 录音与报名快照 | 所属账号、媒体对象 ID、格式、时长、版本、状态；报名保存 `recording_version_id` 与本人身份 | 本人录音库可逻辑删除；已提交版本的对象及授权仍可供规定人员读取，不能指向可被后续覆盖的同名文件 |
| 售后事项与受影响人 | `order_id`、状态、方案版本、原因、受影响段、老板确认、各受影响人确认、截止及完成时间 | 每个事项及确认版本可审计；只查询本人事项，权限过滤覆盖序列化、消息、附件和收益阻断 |
| 提现审核与付款记录 | 现有提现扩展初审、终审、线下付款状态及操作者；`actual_paid_at`、`recorded_at`、`payment_reference`、`client_request_id` | 系统登记键去重；外部批次可包含多项明细，不能全局唯一；渠道明细疑似重复提示核实；未知付款不能释放冻结 |
| 会话、订单关联与权限 | 会话 `assigned_staff_id`、`version`，流转记录及 `session_id/order_id` 关联；消息卡片及引用版本 | 事务内只有一名普通客服领取；列表预览不能泄露正文；转交后 socket 与私图权限同样撤销 |
| 配置版本与事务 outbox | 配置 `domain/code/version/effective_at/value`、校验和；事件 `event_id/store/object/version/type/payload/status/attempts` | 配置发布版本唯一、快照可回读；业务与事件同库提交；`event_id` 唯一，按待发送状态索引并幂等消费 |
| 平台目录 `default` | 平台主体、角色／门店范围授权、数据库资源归属、初始化任务步骤、公共薪资 | 平台主体 ID 与店内账号 ID 命名空间不同；不得通过跨库外键关联，平台公共工资仅入公共成本一次 |

建议主键、金额和业务时间有明确最大值及精度，所有表按数据量评估索引和迁移锁影响；真实 `Decimal` 比例先精确运算再按业务规则取整，不能将浮点数写入账本。普通陪玩收益允许 0.1 店币：253 店币成交、门店抽成 20%，应得 `2024 raw = 202.4 coin`；老板付款、店币退款及陪玩承担退款分摊仍分别按已确认整店币规则。

## 2. 支付事务建议

```
绑定已认证 store、真实操作人 actor 与经授权的付款人 payer
本人下单时两者可相同；客服代单时 actor=客服、payer=老板，保存老板明确确认依据
验证本店代单权限、付款目标、请求号格式、订单类型及报价引用
只读查询同请求号是否已有可恢复的成功结果；同键异摘要返回冲突
with 本店 transaction.atomic():
    按现有协议获取订单／服务和本店资金互斥锁（已有订单先锁订单）
    读取并锁定适用钱包、积分、券、配置引用与必要资格记录
    验证报价版本、状态、合法优惠、积分完整组、余额及支付来源
    在第一次动钱前，同事务 claim 幂等键；摘要覆盖 actor、payer 及交易内容，并发冲突按已保存结果恢复
    创建或更新订单快照、按来源扣款、积分流水、券使用及对应资金流水
    写本店 outbox 和幂等响应
commit 后唤醒通知；结果未知按相同请求号查询或重试
```

这是锁边界与业务顺序示意，不可按伪代码机械加锁：新建订单、预约转单和已存在订单持锁路径不同。占用幂等键后的失败必须抛出可回滚异常或显式回滚；Django 的 `atomic` 内直接 `return` 会提交，不能留下占键但未付款的假成功。实现前应绘制实际调用链，保留 [financial_lock.py](../../services/backend/orders/financial_lock.py#L1) 与 [reservation_services.py](../../services/backend/orders/reservation_services.py#L396) 的约束；对多陪玩产能锁先在事务外按既有规则准备锁记录，事务内按账号 ID 排序获取。所有事务必须验证无钱包／画像先锁后反向等待订单或全店互斥，使用隔离 MySQL 压测死锁及重试。

两次相同请求可能都在事务外查不到回执；第一笔提交后，第二笔因余额变化在 claim 前失败。可变规则校验失败或 claim 冲突时，应在能看到最新提交的事务边界再次查请求摘要与成功回执：同意图返回原结果、异意图返回冲突；确无回执才返回余额或资格错误。可参考已有 [receipts.py](../../services/backend/wallet/receipts.py#L57)，并用并发测试证明失败前重查不占键。

## 3. 退款与释放事务建议

退款预览只计算不记账；执行时锁订单／财务互斥及涉及的来源记录，验证原付款构成、售后方案、确认版本、计划摘要和已退上限，按本次退款重算老板店币、积分及每名陪玩承担。先检查各人本单未结算应得、钱包、押金合计足够；任何一人不足即整体失败，不先改其他人余额。满足后同事务写老板退款、积分返还、消费赠分冲回、各人回收、押金缺口、门店取整差额、工资／实销事件和幂等结果。已发推荐佣金不逆转，由本店承担。

收益释放以每段唯一业务键锁住订单、本人段／有效报单、相关售后、资金与押金，复核整单已结束、两时钟、审核、售后及真实补贴；整单已结束包括正常完成，以及经双方确认、退款完成并保留有效履约金额的协商终止等合法终态，不能只检查旧 `COMPLETED` 枚举。各类适用的可释放收益先补退款造成的押金缺口；仅当该陪玩为单抵且该收益按规则适用普通单抵、目标仍未缴足时，再按**余下收益**与订单付款时比例抵扣，不超过目标，余额才入可用。现金押金陪玩补缺后不套普通单抵，礼物是否适用普通单抵依既有规则核验，不能擅自扩大。分段释放与本人已释放标记、账务流水和事件同事务，重试不重复。礼物不需要报单，使用支付时起始的两个期限。

## 4. 平台操作和恢复

平台财务先验证独立平台主体、职能、目标店及授权版本；在目标店事务内写提现状态、平台主体引用和审计事实，不能直接保存默认库账号外键。线下付款不是数据库动作：登记前记录状态、收款快照及确认事实，真实付款可能成功而响应丢失；通过凭证核验、唯一请求结果和人工复核恢复，不重付。平台端列表及公共账目从各店独立读取／异步汇总，失败店显示缺失，不以跨库事务或零值掩盖故障。
