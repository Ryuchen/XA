# 04 抢单、预约与履约

> **2026-11-11 转单上限：** 每个订单席位累计最多更换陪玩两次，服务前改派和服务中转单统一计数；转回也计一次。双陪分别按席位计数；失败或回滚不计入。

## 1. 抢单现状与调整

当前 [GrabOrderView](../../services/backend/orders/views.py#L1223) 抢单后立即转换状态；[applications.py](../../services/backend/orders/applications.py#L21) 的报名与组队主要服务老板选人，不能直接当自动排序。保留现有资格检查、订单状态机、[ProviderDispatchLock](../../services/backend/orders/models.py#L35) 与异步框架，新增抢单轮、候选及队伍成员记录。试音仍由老板选人，普通未指定订单及客服安排新单进入自动抢单池。

客服直接指派旧入口 `POST /api/orders/orders/<order_id>/assign/` 及后台 `POST /api/admin/orders/<order_id>/assign/` 不再更改订单或指定陪玩；订单存在时返回 HTTP 409，提示使用抢单池，已安排订单另走改派或转单。支付后的真实开池仍由付款事务记录及开池任务处理，这两个接口不会假称已成功开池；老板招募试音仍由老板选人。该调整未经测试，需在最终联调中覆盖客服安排新单、试音、已安排订单改派、关闭开池开关和双店权限。

### 状态及事件

同一订单同一轮中，每名陪玩只能参加一支队伍；双方完成确认才形成双陪候选。陪玩退出后可以再发起或加入其他队伍，旧队伍及成员确认记录保留；并发换队须在订单与参与人锁内验证，不能同时占据两支队伍。

| 状态／事件 | 处理 |
| --- | --- |
| 首轮 `OPEN` | 入池立即开始配置的完整窗口；保存入池时间、订单总等待截止、各通行证可见延迟配置版本。没有合资格在线人员也照常计时 |
| `CANDIDATE` | 同一订单可能有多个单人或双人候选；双陪只有两人确认完成才是完整候选。队长可提前邀请尚不可见队员，队员到本人可见时间才能确认 |
| `DECIDING` | 到期时在订单锁内取得完整候选、冻结必要统计和排序，复核获胜者实时资格；成功只分配一次 |
| `PARKED` | 一轮无人完整参与且订单总等待未到：继续留池，仅当前合资格人员可见；之后首个合资格单人或首个完成的双人队直接获得 |
| `REOPEN` | 首名失去非通行证资格且总期限未到，或各排序项含完成时间完全相同：所有当前合资格人立即同时可见，重开完整窗口并重新提交；必要时延长总期限 |
| `CANCELLED` | 无人抢到且总期限届满时取消退款；首名失去资格、重开时原期限已届满也取消退款。完全同分重开是例外：即使原期限已到仍延长并重开 |

首轮各人可见时间按其**入池时**通行证状态及当时延迟配置判断，后续买卡或过期均不改变该订单的可见时间；从未在线者上线后按同一入池快照规则判断，不能因为他上线延长窗口。若旧通行证事实不可可靠重建，应显式记录证据缺口并走受控处理，不以当前状态冒充历史。排序等级按**本人提交时**的通行证快照，提交后过期不使该候选失效；其他接单资格在最终分配时仍需核验。重开轮不再使用通行证可见延迟。

单陪重开后，同一陪玩用原 `client_request_id` 重试，原轮及时登记返回原 `receipt_id` 和 `NOT_WON`，迟到或时间待核仍按原分类返回。参加新轮须重新提交。单陪仲裁任务入队时保存目标轮号，旧轮仲裁重投返回 `STALE_ROUND`。升级前只有订单号的仲裁任务归属首轮。订单级超时兜底仍在订单锁内核对当前轮次及其截止。

单双陪重开时，若新轮激活区间与旧窗口截止重叠，须核对同店旧轮的重开状态、签封截止和收件摘要，以及保存的重开决定发生在旧总等待期限前。证据相符时，以旧签封给新激活区间提供更晚的下界，再按冻结窗口长度计算新截止。原始激活样本和上界留存。缺少证据或采样反序时保留待核对。

录音库与抢单池不同：老板选择招募试音并付款后，陪玩可以选择本人已上传多段录音之一，或上传新录音；新录音保存本人库的同时关联报名。双陪两人必须分别确认各自录音才是完整可选队伍，老板试听后选人。录音记录保存所属门店、本人账号、对象引用、格式／时长和上传状态；提交时固化音频版本与播放所需引用，后续从个人库删除或更换不能破坏已提交报名。只有本人、该订单老板和有权限的本店后台可获取短期授权播放地址；不可提前泄露尚未可见订单或跨店文件。上传、报名及选人分别去重，音频无效、上传失败、报名截止或资格变化时给出状态并保留可恢复操作。

排序字典序：通行证等级高者 → 本店最近 30 天已开始履约的个人**原价份额净额**高者 → 最近 30 天有效评价中综合 4–5 星占比高者 → 提交完成时间早者；无评价按 0%。最近 30 天按该履约段接单时间归属，尚未开始不计；转出再接入分段计算。退款按受影响份额冲减，个人指标最低为零。比较好评率时应使用分子／分母交叉相乘，不能先对显示百分比取整。双陪队伍每一维独立取两人最高值，队伍提交时间取两人均确认完成之时。

实现口径：窗口截止后以实际仲裁时的同一门店数据库一致快照和统一时点计算接单额及好评率，并在分配事务内重新校验资格；通行证等级仍取各人提交时的快照。窗口截止用于判断报名和取消是否及时，不要求回溯重建截止瞬间的全部经营指标。仲裁与并发退款、评价及资格变化的行为须在最终联调验证。

双陪原价等分后各自向上取整到整数店币，统计超出的部分单列，例如原价 101 店币则两人各记 51 店币、超出 1 店币单列。履约中转单时，原陪玩及接替人员的个人原价份额由客服协商并留痕；单陪原价 1000 店币时，涉及各段份额合计为 1000 店币。同一陪玩转回使用新的履约段。首名失格或完全同分重开时，仍使用本单入池时保存的窗口长度，不受门店随后改配置影响。

双陪邀请的实际确认入口在双方生命周期锁内核对邀请登记保存的队长与被邀人业务周期；任一方退出后重新入店，旧邀请不能由新周期确认，须重新邀请。邀请列表也不向新周期展示旧邀请。轮次窗口、可见延迟和排序规则不变；最终仍须联调退店与确认并发、重试及邀请列表，开发期未运行测试或迁移。

### 双陪邀请登记与查询

- 队长用 `POST /api/orders/orders/<order_id>/grab-team/` 提交本店队友的业务账号 `partner_id` 和本次 `client_request_id`。原登记已提交、时间证据仍待确认时，HTTP 409 返回 `GRAB_INVITE_PENDING` 和原 `receipt_id`。继续用相同请求号和队友查询。同号换队友返回 `REQUEST_ID_CONFLICT`，即使抢单轮次已重开也只读原邀请。明确截止返回 `GRAB_INVITE_CLOSED`，证据不明返回 `GRAB_INVITE_REVIEW`，由本店后台核对原记录。
- 被邀请人通过 `GET /api/orders/grab-team/invitations/` 读取本人周期内的邀请。收件待确认时 `visibility_state` 为 `PENDING`，时间证据待核对时为 `REVIEW`。两种情况 `order_visible` 均为 `false`，`visible_at` 为 `null`，订单编号及服务名不返回。时间证据核验通过后，仍须复核当前可见时间和接单资格才返回订单信息。已证实逾期的邀请不出现在列表。[并发验收](16-开发进度.md#2026-11-21-双陪邀请并发与回执待确认)

客服代下积分抢单时，即使门店未开启赠送／赔付选择或折扣组合，也必须记录老板明确确认内容及确认方式；付款、订单确认快照和入池意向仍在同一门店事务内。按已确认规则，积分抵扣上限必须低于 100%，每笔符合抵扣条件的消费都须支付一部分店币；纯积分零实付不是待开放功能。须最终联调单陪、双陪、付款重试与超时原路退款；本次未运行测试或迁移。

每次服务中转单，对被转出段尚待分配的成交额按客服确认的两方原价份额比例拆分；原陪玩所得基数向下取整到 0.1 店币，剩余基数全部分给接替陪玩。双方收益分别按各自抽成快照计算，接替段使用接入时的门店规则，积分抵扣不减少成交分成基数。该次分配保存原始基数、两方基数、原价份额及尾差，后续转单仅拆接替段基数，已转出段不重新计算。双陪个人原价统计向上取整的差额不视为新增成交额或资金；须按各原始席位实际成交额分配，不将统计差额纳入整单成交金额。

整单固定抽成按该段成交基数占整单成交额的比例分摊，各段使用各自接入时的固定额规则；门店之后修改规则不追改已有段。双方规则相同时，原陪玩的固定扣额向下取到 0.1 店币，原席位已分配固定扣额的余下部分分给接替陪玩，双陪另一席位保持原扣额；接替者的扣额以其成交基数为上限，超出的差额由门店承担，不从接替者的钱包另扣。规则不同时，原陪玩按本人旧规则计算并向下取到 0.1 店币，接替陪玩按本人新规则和自己的成交份额计算并向上取到 0.1 店币；两人适用的整单固定额不同，合计不要求等于其中某一个固定额。例：成交 900、双方基数 300/600、旧固定额 200、新固定额 203，则分别扣 66.6 和 135.4 店币。

历史候选可迁入新首轮：原提交等级可验证且仍合资格才迁入；等级无法核实时要求重新抢；同分比较先后时若原完成时间无法验证，该候选本轮落选，继续下一位，不构造时间。需要完整同分重开的判断应在剔除无可靠比较时间者后进行。

抢单提交、窗口到期、重新开抢、最终分配及到期退款均锁订单及轮次，复核状态版本；队员确认与撤销锁队伍，分配锁住两人资格／并发记录，避免一人同时胜出多单。定时任务按 `store_slug + round_id + version` 幂等执行，并逐店扫描逾期遗漏；WebSocket、站内通知及群消息只在提交后发送并可重试。KOOK／企微混合群等待所有等级及无卡的可见延迟后发送完整内容，消息仅写原价与要求，双陪标注需组队；发送前检查订单仍在有效状态。

### 同时到期和取消的确定性顺序

故障后若无法可靠确认抢单或取消登记是否赶上截止，该订单进入待客服核对，暂停自动派单与自动退款；保留请求和可用证据，处理留痕，不将不明时间默认视为超时。

用户已确认：抢单窗口与订单总等待同时到期，且截止前已有完整合资格候选时，先排序及最终资格复核；无完整候选，或首名最终失格且判断重开时原期限已届满，则取消退款，不能因其他候选仍合资格而自动递补。老板也在同一截止时刻有效提交取消时，老板取消优先并退款。四项完全同分时仍按 D159 重开完整窗口；首名最终失格按 D97 和当时总期限处理，不能把两种重开混在一起。历史候选原提交时间不能核实、比较先后时落选并继续下一位是 D160 的独立例外。

候选、老板取消和窗口结算应进入同一店库、同一订单的可靠串行化命令入口。**以服务器成功完成持久化登记的时点判断是否收到**：请求先到达服务器、但登记成功发生在截止之后的，不能算作截止前收到；数据库事务提交前写入的时间戳本身不能证明提交已经成功。截止前候选为 `< deadline`；用户授权且在截止时刻或之前成功登记的取消优先处理。定时结算须在截止之后确认截至截止的已登记命令均已处理，避免 Celery 任务因抢先取得锁而偶然胜出；后于截止才登记的请求按当时真实订单状态处理。不得采用客户端时钟或仅凭进程内队列判定。设计验收须覆盖提交跨越截止、相同时间戳、任务并发、重复提交和进程崩溃；实际启用前须证明持久登记时间、顺序和处理水位的可靠性。

老板通过 `POST /api/orders/orders/<order_id>/cancel/` 转人工核对时，本店订单仅登记一份申请。首笔申请保存老板账号、去除首尾空白的原因和显式 `client_request_id`（最长 64 字符）。同号同原因可读取 `PENDING` 或 `CANCELLED`，同号改原因返回 HTTP 409 `REQUEST_ID_CONFLICT`。换号重查只读已有申请。旧申请及省略请求号的人工申请保留空编号，重查保留原原因。定时取消已证实逾期的原收件仍按原号返回 `GRAB_CANCEL_CLOSED`。客服核对沿用有权限的原退款入口，经办请求号独立保存。

MySQL 的 binlog `immediate_commit_timestamp` 表示写入 binlog 的时间，[官方文档](https://dev.mysql.com/doc/refman/8.4/en/replication-delayed.html)并未把它定义为应用收到事务提交成功的时间；[二进制日志文档](https://dev.mysql.com/doc/refman/8.0/en/binary-log.html)说明记录发生在存储引擎提交之前。因此不能未经部署环境和崩溃恢复验证就把该时间视为用户要求的成功登记时间；也不能仅凭事务内取时或成功回调的较晚观察时刻声称能精确复原提交时点。

正在验证的方案是在独立事务提交前、提交成功返回后分别读取同一门店数据库时钟，按时钟精度形成保守区间。只有在数据库时钟连续性、服务器身份和切换行为得到证明的前提下，整个区间都位于截止之前或之后时才能给出对应结论；跨截止、时钟不可信、连接变化或确认丢失均不得猜测，应进入待核对。这个区间不是精确提交时间：即使能证明赶上截止，也不能直接用于比较候选完成先后或判断完全同分。意向登记不等于资格通过或命令已应用；尚无命令处理水位时，零条登记也不能视作可以结算。

已在隔离 MySQL 验证首轮与总等待同刻截止的情况。老板取消上下界跨总截止时，原收件保存为 `REVIEW/CROSSED_CUTOFF_INTERVAL`。签封仍保留首轮候选，仲裁返回 `WAIT_REVIEW`，暂停分配和自动退款。客服按现行权限核对原付款后可取消，保留原时间证据。首窗和总等待相隔 48 秒的隔离实测也保留了留池候选。单陪的取消上界若已经证实早于总截止，晚于总截止补存原样本后，按原号自动取消并原路退款。[实库验收](16-开发进度.md#2026-11-21-抢单取消登记跨过总截止) · [分开期限的实测](16-开发进度.md#2026-11-21-首窗封存后的取消与总截止竞争) · [积分订单和任务重跑](16-开发进度.md#2026-11-21-抢单积分退款后的任务重跑)

## 2. 预约

### 门店预约配置接口（首版）

本店后台 `GET/PUT /api/admin/config/reservation-deadlines/`，平台配置期使用 `PUT /api/admin/platform/store-management/<store_id>/setup/reservation-deadlines`。读取需预约／字典查看权限，修改需 `dictionary:edit`；平台接口另需平台授权。请求须完整提供整数 `confirmation_minutes`、`payment_minutes`、`slot_minutes`、`min_duration_minutes`、`max_duration_minutes`、`max_advance_days` 和 `version`。前两项为 1–43200 分钟；时间粒度可选 1、2、3、4、5、6、10、12、15、20、30、60 分钟，最短／最长时长须为该粒度整数倍，且 `slot_minutes ≤ min_duration_minutes ≤ max_duration_minutes ≤ 43200`；最长提前期为 1–365 天。起止时间可以跨天，时长按实际时间差计算。

未保存时 GET 返回版本 0，时间范围参考值依次为 15、15、720 分钟和 30 天，确认／付款时限为空；这些参考值不会自动启用预约，必须完整提交保存。PUT 使用当前版本，成功后递增并写审计；版本不匹配返回 409，非法或缺字段返回 400，调用方应重新读取后核对提交。开业配置确认覆盖所有字段，保存任何变更后须重新确认；没有预约配置的门店不因此被要求启用预约。已有预约的确认／付款截止使用创建和确认时的快照。首次开业总开关仍默认关闭，实际启用还须完成其他开业依赖验收。

保留 [Reservation](../../services/backend/orders/models.py#L861) 与 [现有预约接口](../../services/backend/orders/reservation_views.py#L116)，扩展双陪成员与占档。用户选择的起止时段可以跨午夜；陪玩未设置档期默认全天可接，但仍须满足上线、绑定、头像、押金、技能等。普通新建时距离开始时间不得短于本店确认时限，提交时保存时限快照；从提交起占用该时段，只有陪玩本人可以确认或拒绝。

双陪 A 已确认而 B 拒绝／超时：保留 A 的确认与占档，允许重选 B，即使剩余时间不足普通确认时限也可选；新 B 最迟在预约开始前确认，直至开始仍未完成则取消并释放 A。全部确认后支付截止 = `min(全部确认时间 + 当时快照付款时限, 预约开始时间)`；超时取消释放，修改配置不影响已保存截止。未付款预约不形成已付款服务单。

预约转单重新报价、支持合法普通券及积分；选择的预约时长与购买时长一致，按报价规则收取，不实时计时。已付款后继续锁占档直到履约结束／取消；允许提前开始。未来预约未开始不占当前并发名额，到开始时可暂时超过上限。已付款陪玩不能自行拒单，客服协调转单或取消退款；转单时释放原人档期并检查、锁定新人同一时段，失败则原状态不变。

实现中应对陪玩固定资源行加锁后，检查有效占档的半开区间 `existing.start < new.end AND new.start < existing.end` 并写入；多陪玩按稳定 ID 顺序拿锁。不能依靠 MySQL 普通唯一索引表达时间区间不相交，也不能先查询后无锁插入。时间统一存 UTC、展示北京时间，特别测试跨午夜和截止边界。

## 3. 履约、转单和评价

以订单为整体流程、履约段为人员与资金事实：开始、完成、报单、售后分别维护，转出后再回来的同一人新增段并使用再次接入时配置快照，之前已发生的费用和报单不被覆盖。普通及特殊订单都遵守此规则。整单结束前转出段不结算；历史已经发生的结算流水保留，不做伪造撤回。

续单须有与前单不同的正式关联和客服核实记录；符合条件时按积分抵扣前成交额判断是否严格超过 188 元，待结算条件满足后给每位陪玩 5 元奖励。本次续单转单或发奖前退款取消奖励，已经发放后退款不追回；每次核实和发奖以原单及人员去重并记录依据。

评价四项由老板分别选择才能提交；低星仅在售后有效期内建立／关联售后，期后只记录提醒。匿名隐藏昵称、头像但保留订单号；授权后台可关联真实老板。授权人作废评价必须填写原因并留痕，作废不计好评率、不撤销已建立售后，也不能对该陪玩重新评价。排行榜按实际履约的每人每单一次，归属本人最后一次履约结束或转出时间；全退但已履约仍计单。

通用房间的普通双陪订单若首轮协商先于首次转单，后续继续履约或追加协商后，双陪结单截图进度、陪玩房间申请和客服核实/老板确认复用真实转单前正退款或零退款、原始履约快照及后续连续协商凭证识别当前人员；此前转单或人员终止作废的申请仍需重新提交。老板确认或无异议超时自动确认规则不变。尚未测试、迁移或隔离 MySQL 并发及失败回滚联调。

普通双陪转单后，若协商仅终止某人旧履约段而该人已以新段转回，订单部分退款且两名当前陪玩仍有真实进行中段时，房间结单申请、客服核实、老板确认及异议恢复可在核验连续协商和当前两段均未终止后继续；旧段不重开。原申请因转单或人员变化失效时仍需重新提交，老板确认或无异议超时规则不变。尚未运行测试、迁移或隔离 MySQL 并发及失败回滚联调。

客服安排零实付安全箱：老板明确确认用券后，单陪未指定订单复用已用本人周期券、原价补贴和零额付款事实进入正式抢单池；老板端选择客服安排同样适用。待分配抽成按中选陪玩快照确定，既有取消退券和未转单补贴结算不改。依赖正式 MySQL 时钟、抢单、服务范围、原价归因及安全箱补贴/分段捕获开关（默认关闭）；转单和复杂售后仍有各自能力限制。未运行测试或迁移，需最终双店、并发和资金联调。

补充：上述客服代单安全箱补贴创建适用于单陪、本人抽成待分配的零实付正式抢单路径。客服代下新单按已确认规则统一进入抢单池，当前接口拒绝客服指定陪玩；中选后的补贴份额由实际分配流程生成。其他非待分配代单及安全箱售后和转单不因此认定已完成。
