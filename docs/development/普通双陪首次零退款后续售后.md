# 普通双陪首次零退款后的后续售后

新增受控 MySQL 链路：普通未转单双陪订单中，A 经老板和本人确认零退款终止后，保留实际零退款协商、原付款与 A 的收益；B 继续完成服务，可在原售后期内由客服登记本人售后，或按既有低星规则建单。B 与老板确认后复用既有追加协商事务、原付款来源退款、门店补资和逐人结算，B 为零退款时不制造退款流水。A 已终止范围不得重开。

首次零退款后的补资及 A、B 后续结算接入原普通退款资金服务；有实际 B 退款并需释放共享到账时，以 A 真实零退款确认和 B 实际退款为界回放到账用途。支持 A 确认前多笔已付款加购及其此前真实退款、已确认接替，按原退款凭证、双方或三方确认、履约责任、已扣主单收益和付款构成计算净额；之前本单真实释放须逐笔核验来源、发生时点和对应到账用途事件，再按该分配的实际净额处理。A 已在整单完成后结算的场景，核对其原报单、等待时限、本人真实入账及主单和加购收益补押金流水；B 退款只核对 B 的承担，不改写 A 的流水。同一到账由其他订单分配或释放时按各自分配编号核对。A 确认后发生的加购退款或接替、仍待确认的接替及其他不符范围的情况仍待核对；其他积分、直付、安全箱和转单等场景继续使用各自规则。

`ORDINARY_ZERO_FOLLOWUP_MYSQL_ENABLED` 默认关闭，还依赖原普通资金、追加协商、零退款及结算等开关和逐店 MySQL 结构、worker/beat。开发阶段没有执行测试或迁移，尚未完成真实 MySQL 资金、各来源、A 先结算、两个零退款、B 正退款、低星、自动结单、到账并发及失败回滚联调；这些未完成前不得开启新开关。无数据库结构变更。

## A 终止后 B 新增加购的开发进度

已增加对 A 的真实零退款确认、B 当前继续履约席位以及加购付款与退款实际凭证的核对；付款和退款的资金释放调度已开始复用现有到账账本，退款执行审计在退款事务内先于凭证回放写入，失败时与退款一同回滚。历史时点回放只读取当时已经付款的加购。重试沿用原退款记录与原审计，不应再次记账。

新增独立开关 `ORDINARY_ZERO_POST_ADDON_MYSQL_ENABLED`，默认关闭；资格判断、付款可用性及客服发起加购售后限定继续履约的 B，真实退款与补资释放沿原事务，每笔退款仍由老板和受影响陪玩确认。退款 RELEASE 回放和 B 后续主单退款的账本核对已增加零协商后的真实加购事件分支。退款没有释放金额时，直接核验真实退款资金版本；从未分配到账时，在订单和资金锁内核验空分配版本，不创建虚假到账或释放。后续才发生的到账不会回填历史。

代码接入范围为普通、未转单、无积分及直付的双陪订单：A 完成首次零退款终止，B 在服务中负责新增加购、付款及本人加购退款；A 终止前已付款且由 A 负责的未完成加购，可经老板、A、B 分别确认后按实际工作份额交由当前 B 接替，B 可对本人真实剩余接替份额另行协商退款，A 已确认保留的份额不重开。接替后的资金版本按实际确认时点和本订单分配到账记录；B 完成后的主单售后与逐人结算复用现有路径。

接替前已有多笔真实退款时，最终确认事务按原付款、逐人责任和资金版本逐笔回放，按实际剩余份额接替；无到账分配时核验空资金版本。复杂跨付款责任、涉及 A 已确认保留份额的争议，以及后续主单转单后由第三人接替、积分、直付等场景仍有门禁，不能视为已支持。两个零退款开关及原普通资金、追加协商、结算、到账用途账本开关均须满足，且须使用已初始化结构的逐店 MySQL 环境。

这一场景尚未完成验证，不得开启新开关；须在隔离 MySQL 环境联调真实付款来源、两人确认、零分配、零释放、后续退款及结算、并发重试和失败回滚。本轮未执行测试或数据库迁移。

## A 终止后 B 转给 C

转单事务已增加对转单前零协商、原双陪履约快照及 A 保留收益的核验，并在普通转单资金版本中保存真实零协商执行编号；本店尚无到账分配时也保存空分配版本。转单后加购接替的历史回放会核对同一原协商。若尚未接通零协商先于转单的逐段结算版本，结算计划会阻止将 A 已终止的履约段当作零收益。

已接入 B→C 后加购付款、实际三方确认接替及加购退款的事务资金版本更新；结算代码按最新本店真实版本重新核对补资、逐段收益、A 的终止时点和本人报单。C 的加购售后复用实际剩余份额和双方确认路径。

已增加 C 对本人实际履约段的主单追加协商、双方确认、真实退款和逐轮资金版本；多轮正退款导致共享到账释放时，按首协商、每轮实际确认/结案、本人履约段和承担、原付款及本单既有分配与释放逐笔回放；退款后逐段结算继续核对本店补资、本人报单和售后等待。A 原已终止段始终不可重新选择。追加正退款或零退款后仍有活动席位时，再次转单按原每席两次上限记录真实新段和资金版本，不为零退款创建退款流水。A 可以按真实转单新建履约段后转回；原协商终止按原段时间核验，新段通过实际入队、报单和逐段资金路径处理，不把两个段混为一笔。多轮共享到账回放覆盖普通订单零协商先于转单，以及转单后首笔正退款或零退款的真实首协商；仅使用逐店真实到账用途账本，积分和直付继续使用各自路径。

现有代码未经真实数据库、并发及失败回滚联调，不能宣称已验收或开启开关。开发阶段没有运行测试或迁移。

## 正退款先于首次转单

普通订单首次正退款结案后仍有活动席位时，已增加原付款、原退款与本人承担流水、真实确认/终止、原履约段及原价份额核验；通过后只解除该笔协商退款造成的特定原价 REVIEW，在实际转单事务中创建带原退款执行编号的资金版本。后续受影响段、追加协商、实际共享到账释放及逐段结算沿相同的已确认事实处理，旧已终止段不得重开，同一人可以以新履约段转回。

普通已转单订单的接单额统计已按真实履约段和每笔受影响人承担计算：同一账号转回时新旧段分别归属；多个受影响段按可核验的剩余原价份额比例分摊本人已取整承担，各段最低为零，超出部分另列。老板榜单 `order_rank` 新增 `excess_refund_amount_raw`，与 `total_amount` 一样使用账务最小单位；其他尚无逐段超额事实或证据不完整时返回 `null`，不是零，也不改变资金退款或钱包。

该路径尚未进行真实 MySQL、跨轮加购退款、共享到账、并发和失败回滚联调。相应开关保持默认关闭，本轮不运行测试或数据库迁移。

正退款完成后、首次服务转单前若已真实发生加购退款，其既有共享到账释放在后续转单、多轮售后和逐段结算时，按该次退款时的原入段抽成及各陪玩收益快照回放；后续席位拆分、同人转回及后来发生的主单退款不改写旧资金事件。该时序尚待真实 MySQL 联调验证。

主单退款前已确认的加购接替，在后续正退款、转单及多轮售后中，原加购付款和接替的历史补资版本按当时真实履约段、入段抽成、三方确认和审计回放。若接替前后另有真实加购退款，逐笔核验原付款来源、各人确认和实际剩余收益；回放本笔退款时仅排除它自身的同刻事件，其他同刻事件仍要求核对。此代码复用真实退款、到账 RELEASE 和逐段结算事务，尚需最终 MySQL 并发、共享到账及失败回滚联调。

多项加购分别接替并退款、随后主单退款和服务转单的普通订单：首轮及多轮共享到账回放逐项检查每笔加购的真实接替确认、资金版本及实际释放；即使后续退款不需 RELEASE，最终逐轮资金计划仍会核验主单协商前的各笔加购退款及接替，不将零释放当作到账。

普通订单首次服务转单后新增的多项加购，可以按各自实际支付、受影响人确认、接替和退款事实进入后续主单协商及逐轮资金计划；历史本人主单收益按退款时实际转单段及入段抽成重建，不读取后来的席位金额。转单后加购退款发生时尚未分配到账的真实空分配版本可以回放，不伪造 RELEASE；存在其他不可证明的跨付款责任或后续接替组合仍保留待核对。该路径尚未进行隔离 MySQL、共享到账并发和失败回滚联调。

主单首次协商前的加购退款跨付款承担，现按该笔退款时本人全部真实主单履约段、此前逐段扣减和当时执行顺序核对已持久化明细；不同加购责任段与主单承担段可以不同，不重算或修改已发生退款。此补充只覆盖主单首次协商前，协商后复杂跨付款和后续接替交错仍需继续接通；真实 RELEASE、资金版本及逐段结算须最终隔离联调。

首次主单协商后、追加主单协商前的普通加购退款，资金版本回放按各次真实服务转单与加购接替核验付款责任，并按本人原履约段、首次协商已确认保留收益及历史逐段扣减核对跨付款承担；原终止段只保留其已确认收益，不能重新履约。复用真实退款版本、共享到账 RELEASE 和逐段结算，不创建虚假流水。追加主单协商之后的复杂跨付款承担仍待接通；默认关闭的开关、真实 MySQL、并发和失败回滚联调要求不变。

逐轮资金计划现在按被核验资金事件之前的真实加购退款扣减计算；这只是后续能力的准备。追加主单协商后的加购退款独立资金版本、到账锁内逐笔 RELEASE 回放与最终结算仍未贯通，现有门禁保持。

已新增仅供订单资金事务内部调用的追加协商后加购零释放版本写入与核验，快照此前各类真实 RELEASE；公开退款入口尚未调用。非零释放、到账锁内无反向加锁回放和最终结算尚未接通，不能视为此场景完成。

随后已将上述内部版本接入真实加购退款事务，并支持按真实分配生成非零 RELEASE、登记到账用途及逐轮结算核验；当前只覆盖有到账用途账本、首次追加主单协商为正退款且本人承担完全来自实际加购待结收益的转单普通订单，逐付款逐段核对确认与收益。缺少先前追加协商资金版本、未分配到账、零追加协商、多轮追加，或需要扣主单收益、钱包、押金的情况继续待核对。前段关于该内部版本尚未接线的描述已被本段覆盖。上述实际链路未经隔离 MySQL、并发、失败回滚及前端接口联调，相关开关保持默认关闭。

首次追加正退款或零退款后，如真实尚无到账分配，可在订单资金事务内核验协商和加购退款并记录空分配、零 RELEASE 版本，不伪造到账。首次追加零退款且已有到账分配仍未接入到账锁内回放；主单、钱包、押金承担及多轮追加继续待核对，前述测试与上线门禁不变。

首次追加协商后的退款承担现依次核对各实际加购待结收益、本人历史主单段待结收益、钱包流水和押金凭证；押金不足继续由实际退款事务拒绝并回滚。已有到账的首次追加零退款、多轮追加及未能证明先前资金版本的组合仍待接通；此前仅支持加购待结收益的限制以本段更新。所有分支未经隔离 MySQL、并发、失败回滚及接口联调，默认开关维持关闭。

已有到账分配的首次追加零退款也增加到账锁内核验：以真实零协商确认及终止、先前主单资金版本或零协商、当时履约段和扣减为依据；缺少必要前序版本时仍待核对，不造退款流水。此更新覆盖前述该分支未接入的记录，仍须隔离 MySQL、并发及失败回滚联调。

实际执行入口已将普通转单、追加协商后的加购退款直接分流至独立资金版本，避免通用转单刷新提前截走；需要押金时补充原周期零余额钱包事实，余额和押金均不足仍由原事务报错回滚。最终逐轮结算核对该退款版本并分项扣除此前真实释放，避免重复计入。完整链仍须最终隔离联调，默认开关未打开。

多轮追加后，最新追加为正退款且已有对应真实到账版本时，后续加购退款可复用多轮协商 receipt-local 凭证，核验各轮终止段、本人承担及前序释放，再写入该笔实际 RELEASE 和逐轮结算。多轮最新零追加、未有前序到账版本或其他无法核实的组合仍保持待核对。以上尚未测试、迁移或最终联调。

多轮最新零追加及协商当时没有到账版本的情形，也按实际逐轮确认、终止、主单来源、本人承担和分配时点重建；确实没有分配时不虚构前序 RELEASE，已有分配却缺少真实版本仍待核对。此更新覆盖前述多轮门禁记录；仍须最终 MySQL、并发、回滚及端到端联调，开关保持默认关闭。

多轮加购回放中，若首协商前的真实加购退款发生时尚无到账分配、原执行未创建释放版本，后续使用逐笔真实付款、确认、退款和履约段承担核验，不为旧事件补造 RELEASE；当时已有分配而缺少版本仍待核对。未进行测试、迁移或最终联调。

多轮追加后，前一笔加购退款若由通用转单资金事务生成 ADDON_REFUND 修订及 RELEASE，后续接替或再次退款的到账回放现可读取真实修订及对应释放；重复资金版本、事件时序异常或当时已有分配但缺版本仍拒绝。该调整接入已有公开退款事务和逐轮结算，须最终隔离 MySQL、并发及回滚联调。

普通转单订单在多轮已确认协商之后，退款若实际改变待确认加购接替的原付款份额或本人收益，现按真实各轮确认、终止、履约段及退款时点核对后写入失效凭证；客服可基于实际剩余份额重新发起接替，再由既有资金版本、到账 RELEASE 和逐段结算处理。未实际涉及的其他待确认方案不因该笔退款失效。该路径尚未执行隔离 MySQL、并发和失败回滚联调。

本轮涉及后台真实接口：POST /api/admin/orders/{order_id}/addons/payments/{payment_id}/refund-proposals/{proposal_id}/execute/ 执行已确认退款并记录受影响待确认方案的失效；POST /api/admin/orders/{order_id}/addons/payments/{payment_id}/handovers/ 按真实剩余份额重新发起。接替确认、逐店到账 RELEASE 和最终结算沿现有事务链；当前只覆盖有真实连续协商凭证、退款确实改变方案责任的普通转单单，身份/时序或原付款凭证缺失仍待核对。既有默认关闭开关、隔离 MySQL、并发、失败回滚和三端接口联调要求不变。
