# 05 售后、结算、押金与提现

## 1. 售后及退款

目前 [refunds.py](../../services/backend/orders/refunds.py#L142) 未结算订单普通部分退款受限，而目标允许售后期内协商部分退款；[AfterSale](../../services/backend/orders/models.py#L1088) 还是一单唯一。需修改业务状态机、受影响人员／履约段、资金计划及权限，不能仅放开按钮。

普通售后在订单结束后的本店时限内创建，默认 72 小时，付款时存规则版本；到期不能新建售后／退款，期内已建立的继续处理。中途终止由客服建立协商售后，老板及受影响陪玩各自确认方案，双陪只影响 A 时 B 无须确认也看不到 A 的售后详情；确认时间作为 A 的等待起点，但结算仍须整单结束。双方协商、实际退款完成并满足适用等待和报单后，保留的实付可计会员实销、消费积分与非礼物成就。

双陪 A 与老板已确认协商终止后，A 的已确认方案不重开，B 完成整单后也不能再次针对 A 的已终止服务登记售后；B 未经协商终止的独立问题可在适用售后期限内处理。老板申请须明确选择可申请人员，整单范围不能把已确认终止人员重新纳入；凭证异常须先核对。正在处理的历史请求按原幂等凭证查证，不因后续规则造成重复提交。

B 完成后在售后期内收到老板的 1～2 星评价，应单独针对 B 自动登记售后，保留 A 的原协商与结案记录；期限届满后只记录低星提醒。针对 B 的部分退款方案，须老板与 B 分别确认，再由授权客服执行，不能覆盖原完成时间或重复结算 A。

退款按 [03](03-定价钱包与积分.md) 的店币／积分来源与取整计划执行。陪玩承担依次冲本人本单未结算收益 → 钱包可用 → 可扣押金；总额仍不足时**整个退款不执行**，提示等待陪玩补足，不能已退老板一部分又假装成功。退款预览生成计划摘要，执行时重锁、重算、校验版本和请求摘要；沿用 [OrderRefund 幂等](../../services/backend/orders/models.py#L1104) 和现有计划校验能力，扩展逐段来源和逐笔向上取整。门店取整差额有真实对账流水。

## 2. 两个重叠时钟与逐人释放

服务订单售后等待从整单完成开始；协商终止受影响人的等待从双方确认终止起。每名陪玩收益冻结从本人最后一次**有效**报单提交开始，驳回重提重新起算；两项默认各 72 小时，由门店分别配置，并使用订单付款时快照。礼物无需报单，两项从礼物支付时间同时开始。转出段即使自身等待已满，也要等整单完成；例外仅限历史已实际结算的事实保留。

每个履约段可释放条件：`整单已结束 AND 对本人未结售后已关闭 AND 售后等待到期 AND 本人有效报单审核通过 AND 本人冻结到期 AND 应付资金已落实`。整单已结束既包括正常完成，也包括双方确认且退款完成、仍保留有效履约金额的协商终止等合法终态，不能只检查旧 `COMPLETED` 枚举。礼物以支付完成替代报单审核；零售后或零冻结仍须运行押金补足逻辑。分别以本人时间计算：双陪 A 满足可先释放，B 不满足继续等待。**不得先等 72 小时再从入账起冻结另一个 72 小时。**

现有 [confirmation.py](../../services/backend/engagement/confirmation.py#L20) 使用全员汇总闸门，[income.py](../../services/backend/wallet/income.py#L22) 又会在收益入账后起冻结；须按段改造并兼容历史时钟，消费实销与收益释放事件也要区分。正常服务会员实销按已确认实销处理；礼物实付本金付款成功立即计会员成长，之后退款按退回本金冲回。付款或实销确认任一时点 VIP 停用时，按 PRD 不计相应成长／消费赠分。

## 3. 押金及缺口

现金和单抵目标由门店配置，初始参考人民币 400／800 元；保留历史已缴数。线下现金补差由客服核验证据后直接登记已缴押金及原因，不经陪玩可用余额，也不是充值。押金退款前须核实没有进行中订单、未结售后、待结收益及未释放冻结。

普通单抵按该订单付款时保存的收益抵押金比例计算，最高抵至本店目标；之后门店修改比例不影响本单，收益冻结为零也不能跳过抵扣。它与退款扣押金形成的缺口是不同事实：同一笔可释放收益同时涉及两者时，先补退款缺口，再以**补缺后的剩余收益**为基数按该单比例计算普通单抵，仍不超过剩余目标。例如可释放 100 店币、退款缺口 20、单抵比例 60%，且普通目标足够大：先补 20，再从剩余 80 抵 48，共补押金 68，剩余 32 正常结算。

因退款扣押金形成缺口时，已接订单继续履行；按本店普通并发上限，只可另放行一个用于补缺口的服务单，若本来已满则等空位。**该补差单未开始履约就取消时立即恢复一次机会；已经履约则等待该单收益结算。**该单完成但收益仍冻结时，不再放行下一单；已进行中的单以**最先满足结算条件**者优先补缺。礼物收益到期也优先补缺，不占服务单名额。某单结算补完后仍不足，才允许在符合并发条件时再接一单。补足状态、来源、资金流水、允许名额与订单归属须同事务更新。

## 4. 提现状态和线下打款

| 状态 | 允许动作与资金事实 |
| --- | --- |
| `SUBMITTED` | 申请金额至少达到本店单笔最低额，可用余额**严格大于**本店余额门槛；估算扣费后实付须大于零。锁钱包并冻结申请额，保留费率快照；初审前本人可取消并解冻 |
| `STORE_APPROVED` | 本店客服初审通过，平台财务可见；拒绝解冻并留原因；此后取消由工作人员先核实尚未打款 |
| `PLATFORM_APPROVED` / `PAYMENT_PENDING` | 平台财务终审并线下处理；分别保存审核人和付款证据，不因按下审核按钮即扣除钱包 |
| `PAYMENT_UNKNOWN` | 可能已付款但结果或登记不确定时冻结保留，人员核对真实付款凭据；禁止自动重付、重复登记或擅自解冻 |
| `PAID` | 经财务确认实际打款后，以系统内唯一登记／请求键和原提现请求在店库原子解冻、记提现支出及手续费；记录实际线下付款时间与系统登记时间，重试返回原结果。外部同一付款批次可含多笔收款明细，不能把批次号当全局唯一键；疑似重复的渠道明细提示核对 |
| `REJECTED` / `CANCELLED` | 有权人员确认未付款后处理；冻结原额准确释放，保留审计，不记已打款 |

平台列表聚合仅返回有权限门店的待处理单，动作时以签名的平台主体、目标店及该店内申请 ID 重新授权，拒绝客户端冒充本店员工。平台库与目标店库之间不假设原子性，目标店业务状态为资金事实，平台审计和聚合通过持久事件可恢复对账。历史申请要逐笔区分待审核、已付与不明，禁止批量解冻或补记没有证据的付款。
