# 积分首次退款后转单待接替责任版本

新增 `PointsTransferAddonLiabilityRevision` 和结构迁移 `0279_points_transfer_addon_liability`（依赖 orders 0278），保存真实加购退款对转单冻结的待接替付款造成的责任变化。版本绑定原转单、具体退款、实际加购付款、原事务资金 RELEASE run、逐段退款前后责任、实际扣减及释放记录；同付款多次退款以真实前后版本连接。退款执行在既有 RELEASE 完成后、原事务退出前调用写入，失败整体回滚。原转单快照及已有流水不改写。

现已将版本链接入转单待交责任计算及首次接替核验：按实际退款事件重建剩余基数，全额退款不再保留待交责任；首个接替及其重试按重提时的真实版本核对。版本回读可传入已持锁到账见证核对资金 run，未回写原转单数据。

已扩展首退后转单的 STANDARD 待确认接替失效事实：按真实转单冻结责任、未完成三方决定、实际退款与逐段扣减生成独立失效种类；事务写入口将此时序交给该事实记录。后续校验要求该失效记录关联同一退款、资金释放 run 与 0279 对应付款的责任版本，并可带到账见证回读。

已接入首退后转单的单个 STANDARD 待确认接替退款预核：绑定本单付款及转单待交责任，原事务执行实际退款、失效事实、资金 RELEASE 和责任版本后互相核验；提交前检查退款后的责任历史可重放，失败整体回滚。后续三方重提按当时剩余责任核对；普通历史能力识别使用版本提示，持到账锁后重新核验退款、失效与资金事件，最终逐段结算继续使用该订单资金版本和原整单补资规则。

预核现支持同一真实转单版本中不同付款各有一个 STANDARD 待确认接替：逐项核对当前责任；退款按双方确认的实际逐付款、逐段承担计划扣减，受影响方案分别记录失效、退款 RELEASE 和责任版本，无关待确认方案保留。每笔失效与对应付款责任版本在同一事务互证，事务提交前核对剩余待交责任可回放。

当前仍要求没有已付陪玩或已建结算清单，同一付款不得存在多个待确认接替；不同转单版本的并发待接替以及其他上游未支持的资金组合继续受限。代码尚未经联调，不能当作业务验收结果。

本轮静态追踪发现，积分双陪提交结单截图先经过转单报单能力域，未传待确认 STANDARD 付款范围时不会放行；房间结单要求完成证据，而接替创建不允许受影响本人已有完成事实，接替接受也要求订单进行中。因此目前不能证明待接替与整单完成可由正式入口并存，不放宽履约规则，也不为该状态增加不可达的先结算凭证。房间和其他入口仍需最终联调验证。

首退后转单的 STANDARD 接替入口现将同单其他待确认付款一并纳入到账预核提示，在取得订单及资金锁后逐项重新核对原转单冻结负债、当前责任、目标履约段及每笔付款唯一的待确认方案。当前接替的创建或决定事务中，整单资金计算可读取这些已核对的待交责任；接受后仍由原确认事务写入该付款真实资金版本和 RELEASE，其他付款方案不因这次操作改变状态。该作用域仅在事务中生效，不授权跨单资金或已付人员场景。

这一接线尚未执行端到端联调；其他付款同时待确认时的共享到账本地回放、逐笔确认、退款失效和最终逐段结算仍须在隔离环境核实。首退预核的已付人员门禁及不属于同一转单版本的负债门禁继续保留。

追加主单退款的资金链现识别另一条真实结束方式：转单冻结的加购待交责任，经真实独立退款全额退还后，若 0279 逐笔责任版本在追加退款发生前核实剩余基数为零，无须虚构已接受接替。该判断接入二次退款预览、执行、资金版本、逐段结算共用的事件链，以及共享到账本地回放；回放使用本店本单实际到账见证核验原退款与 RELEASE。退款未全额、责任仍为正或版本不足时仍要求实际接替。此项未运行测试，尚须最终联调确认公开请求到结算全链。

跨转单版本的中间步骤：真实加购退款事务的 0279 写入现按每笔受影响付款选择退款时最近冻结该付款责任的转单版本；如果该版本对应的接替已真实接受，则不再给这段已结束责任写退款版本。每笔仍绑定原退款、逐份额扣减和同事务资金 RELEASE，原转单快照不改写。这不是跨版本业务开放：第二次转单、待交接替、上游退款作用域与到账回放仍有仅支持最新版本或要求旧责任完成的限制，必须全部接通后才能放行。

同一中间步骤中，三方接替历史核验和退款导致接替失效的事实核验，按实际付款、原段、目标段与创建时点查找冻结来源，不再把其他席位后发生的转单误作本付款的来源。该查找仅提供真实来源，仍须执行既有责任、决定及资金版本校验；跨版本创建、确认、退款和到账链尚未开放。

继续接入不同席位的跨版本流程：再次转单事务锁内按原版本核验待交责任和具体方案，允许其他席位尚未完成的责任保留；新转单冻结自己的付款责任，仍禁止同席旧责任未交时再次转单。历史资金捕获分开首次转单之前与其后的实际加购资金事件；到账本地回放按首次转单时点核验前史，再使用原加购事件回放。三方接替和待确认方案退款预核按付款所属冻结版本选择来源，确认时的资金 RELEASE 使用当时最新整单版本；已接受旧责任不再误要求 RELEASE 仍指向旧整单版本。现有资金及结算仍要求所有待交责任真实结束、整单补资足额和本人条件满足。

这些改动尚未执行真实数据库联调，不等于跨版本端到端验收通过；同一付款存在多个同时未交责任、同席旧责任未交即再次转单、已付人员以及二次主单退款后的跨版本组合仍受限。需要最终在隔离环境核对并发创建、不同顺序确认/退款、共享到账、失败回滚和逐段结算。

本轮新增结构迁移 `0280_points_followup_pending_snapshot`（依赖 0279，未执行），在二次主单退款的真实资金版本写入事务保存当时待接替方案、原付款、转单版本、剩余责任和决定，并纳入资金摘要。正常回读及持到账锁的回放按退款发生时点重建快照，不用后来的确认或失效覆盖原事实；逐段结算历史读取也使用该快照。仅允许快照中的待接替人与主单退款受影响人不重叠。

客服建案、方案与退款事务现将真实待确认 STANDARD 方案纳入本单作用域，要求售后受影响人不包括接替的来源及目标陪玩；退款时按 0280 保存三方决定和剩余责任。二次退款后，仅对 0280 中同一付款、原方案、原转单和未变份额允许原已转出履约段继续完成三方接替；目标仍须在本单履约。接受后使用二次退款资金版本写入真实加购 RELEASE，原转单责任回读核验该事件与 0280 的关联。未经三方确认、没有方案的待交责任、涉及接替双方的退款及已付人员仍受限。

以上仅为代码接线，未运行测试或执行迁移，不能作为业务验收。最终需在隔离环境逐项联调客服建案、各方确认、跨付款承担、真实退款、共享到账 RELEASE、方案失效或后续确认、本人报单与逐段结算，并验证并发与回滚。

二次主单退款的受影响人若同时是待接替来源或目标，可在明确选择其其他、实际存在且已开始的履约段时继续：所选段须与待交来源段和目标段均不同，且所选段的账号集合与协商范围一致。方案预核、真实退款时点快照与到账回放使用相同逐段规则；没有明确段、选中目标段或无法证明归属仍拒绝，选中来源段另按下述限定处理。接替本人完成事实按对应履约段判断，避免其他历史段结束误封当前段。

进一步接入已转出来源段的主单退款：来源段须在原待接替方案创建前真实转出，退款明确选中该段，不扣改独立加购责任；原目标段及其陪玩在退款时仍在履约且未结算。原加购方案、已完成份额和三方确认继续使用 0280 时点事实，后续接受、RELEASE 及逐段结算沿用原资金链。

主单二次退款全退但独立加购未退时，在仍有原目标陪玩履约的范围内，也允许继续确认 0280 已记录的原 STANDARD 待接替方案；全退状态不自动授予任意新建或更改接替方案的权限，退款失效后的受控重提见下文。退款及接替预核均校验目标段和该席位当时仍在履约且未结算，主单全退不自动退加购。选中目标段终止、目标不再履约或无法证明原方案的范围仍受限。本段尚未联调，需最终验证真实客服确认、原路退款、补资共享到账和收益守恒。

二次主单退款前已在 0280 保存的待确认 STANDARD 方案，二退后对该付款的独立加购退款现按实际双方确认和退款时点处理：变更责任的原方案在原退款事务中失效，实际退款 RELEASE 后同事务写入其原转单的 0279 剩余责任，并互相核验失效事实。剩余责任需要重提时，入口要求能追溯 0280 原方案、真实退款及其 RELEASE，重新三方确认后使用二退后资金事件和逐段结算。全额加购退款按真实零剩余处理，不凭空接替。主单全退后的其他新建接替仍受限；跨付款、已付人员及其他未证明组合不能据此视为开放。本轮未测试、未执行迁移，必须最终联调验证实际入口、共享到账、并发与失败回滚。

主单已全退后，如果上述 0280 原方案又因该付款的真实部分加购退款而失效，现可在本单锁内重提该付款的实际剩余责任：须核验原失效、对应退款及 RELEASE，目标仍为原方案中当前履约的陪玩；新方案仍须老板及双方陪玩确认，接受后沿用二退后真实资金事件和结算。全退状态不因此开放任意新加购接替、变更目标或零剩余重提。此范围尚未执行测试或数据库联调。

二退后真实加购退款已使 0280 原待接替方案失效时，同一退款方案的执行重试可在订单及资金锁内回读：必须匹配原订单、付款和已接受方案，核验 0280、对应失效事实、0279 原转单剩余责任及真实 RELEASE，然后返回原退款，不再入账或改变后来重提的方案。整单已最终结算时，先进入既有结算核验作用域，核对最终逐人清单及真实流水，之后才回读该原退款；不开放已结算订单的新退款。其他时序仍需独立接通和最终联调。

已付加购份额回放与真实结算口径统一：先逐笔核对退款边界、付款及真实责任份额，再仅将同付款、同陪玩、同履约段的多份收入相加，与既有已付清单比较；重复付款条目直接拒绝。该回放用于后续主单退款版本、共享到账及结算核验，不重写已付流水、不合并不同付款或不同段。其他上游未开放组合仍按原门禁；未运行测试或执行迁移，需最终联调已付与未付人员、退款及并发回滚。

二退后原 0280 接替方案已因首笔独立加购退款失效、尚未重提时，同一付款的剩余加购可再次发起独立退款。正式作用域先核对原方案的真实失效、首次退款及 RELEASE、0279 逐笔余额链和目标仍在本单履约；每笔仍须按当次售后方案完成老板及实际承担陪玩确认，原路退款和 RELEASE 后在同事务追加对应 0279 责任版本。后续重提按实际剩余责任，全部退完则无需虚构接替。已接替、已结算、目标离场及跨付款等其他组合不因本项放开；代码尚未联调，需验证多次部分退款、全退、共享到账、重试及事务回滚。

原 0280 方案因退款失效后，若客服已按真实剩余责任重提且新方案尚未确认，同一付款再次退款的作用域也会核验原失效及 RELEASE、新方案当前来源与目标；实际退款在原事务使受影响的新方案失效，写入 RELEASE 及下一笔 0279 责任版本，并核验原失效与本次失效。未受影响方案不因此失效；该项不改变目标离场、已结算或跨付款的既有门禁。未运行测试或迁移，需最终联调两次部分退款、二次全退、重提、三方确认、共享到账及失败回滚。

该退款的共享到账预锁使用同一订单已固定的退款预核与待确认付款集合回读接替历史；没有对应退款预核时不扩展到账范围。后续结算仍读取真实退款与责任版本，未完成接替和整单补资不足均不放行。

未运行测试或迁移。后续需依次以实际退款版本计算待交责任、校验退款及到账用途、在原锁序下接通三方重提和最终逐段结算，并在隔离环境验证多付款、跨付款扣减、完整退款、重复请求、共享到账、并发与失败回滚。
