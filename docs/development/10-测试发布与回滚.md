# 10 测试、发布与回滚

## 1. 环境边界与执行方式

开发环境按 [deploy/README.md](../../deploy/README.md) 使用 `deploy/dev.ps1` 的标准操作，复用登记的双店隔离测试库和 Redis；本研发文档未启动服务或执行业务测试。上线前先核实目标库、连接和资源归属，不触及真实客户、生产资金、其他 WSL 项目；不执行清库、重建或对共享 Redis 的全局清理。模拟或隔离真实短信、微信、银行及群发时，要在报告标明替代范围，不能据此声称真实第三方链路已验收。

优先扩展真实 Django 业务与接口测试，数据库并发和行锁使用隔离 MySQL；SQLite 测试只验证非 MySQL 特定行为。已有基础可参考 [test_settlement.py](../../services/backend/orders/tests/test_settlement.py)、[test_transferred_team_refunds.py](../../services/backend/orders/tests/test_transferred_team_refunds.py)、[reservation_mysql_concurrency](../../services/backend/orders/tests/test_reservation_mysql_concurrency.py) 和 [双店资金隔离](../../services/backend/stores/tests_financial_boundaries.py)。执行具体命令前检查相应测试 settings 与测试库授权，不直接照搬并连接未知资源。

## 2. 必测链路与不变量

| 层次 | 核验重点 |
| --- | --- |
| 域名、认证、角色 | 同数字 ID 跨店；错域令牌／WebSocket／文件；平台独立身份、店角色不可跨店；单库不可用不能错误消歧 |
| 建店与配置 | 并发建同店／同库、库已存在但非本门店所有、迁移中断、权限缺失、重试、核心项未填、非核心停用；不复制业务数据 |
| 报价与资金 | 多种支付入口共用同一规则；报价失效、重复请求、同一余额／积分并发；优惠互斥与合法最低组合、整组抵扣、旧零实付安全箱 |
| 承担与退款 | 原价 2500／成交 2000／积分抵 300／实付 1700 店币，陪玩应得 1600；退 500 等值含店币 425、积分等值 75，原价净额 2000、实付净额 1275；消费赠分只按退本金冲回 |
| 多陪玩取整 | 每次退款 51 店币，A／B 各承担 26，老板收到 51，门店实际得 1；两次退款逐次取整；余额和押金总额不足时整笔不发生 |
| 抢单、预约 | 首轮立即计时、可见快照、最后胜者失格、完全同分即使超总期重开、双陪组合、后上线、旧候选时点不明、双陪预约转单及并发占档；窗口与总期同时到期先排序，有老板同刻取消则取消优先 |
| 售后、报单和收益 | 两时钟重叠、双陪不同提交、驳回重提、部分协商、整单未完禁止结算、礼物双计时、期后低星、单人售后不泄露给另一人 |
| 押金与提现 | 每店目标、退款缺口一单放行、最先结算／礼物补足；100 店币收益先补 20 缺口、剩余 80 按 60% 普通单抵，共抵 68；零打款不可提现；初审、财务终审、付款未知、重复回执、停权与跨店同 ID |
| 会员、运营、薪资 | 支付／确认时开关、券版本与降级、抽奖保底、签到退款、积分负余额；跨月退款、已确认工资补扣／补发、离职结清、平台公共成本仅一次 |
| 消息、房间与切换 | 领取前无正文、主管可回复、转交撤权；订单卡权限；异议暂停恢复；旧房间人工核验；每店迁移中重复任务及崩溃恢复 |

补充精度及礼物向量：253 店币成交、抽成 20%，陪玩收益 202.4 店币，账内记 2024 个现有内部单位；不能因老板支付要求整数店币而将陪玩收益改为 202／203。购物篮中每款礼物分别与人民币 20 元门槛比较，分别测 19.9 元和 20 元等值，不能按购物篮总价合计后套用抽成。

每次结果核对状态、钱包来源、积分、订单／段、资金及补贴流水、售后、工资、审计和三端展示。金额核对不能只比较总余额：`支付来源合计 = 店币实付`；每次退款已退店币与积分不得超过原构成；本金、赠送、赔付的可用余额之和等于相应老板钱包可用金额，冻结另核对；提现冻结、已付和解冻不能重复。陪玩应付款、门店承诺补贴、实际可用资金和真实入账分开对账。

## 3. 锁、并发与异步可靠性

验证沿用的全店资金互斥锁、订单行锁、预约／陪玩产能锁和钱包行锁的完整次序，包括 MySQL 外键隐式锁。覆盖新建订单、充值、提现、售后、双陪转单、收益释放及退款相互交错，故障注入进程崩溃、任务重复、网络超时、配置修改及响应丢失。新增资金逻辑不得在持有钱包后反向等待订单或全店资金互斥；预约的产能锁初始化和事务内锁定须遵循现有服务要求。监控死锁、重试次数、锁等待和门店级锁吞吐；若瓶颈被证明，再单独评估缩锁。

关键异步任务使用同店持久化 outbox、按对象／版本的幂等与定期扫描；测试提交后进程退出、消息先到／重复、消费者宕机、门店停用及无租户旧任务的受控处理。平台汇总允许部分失败，但明示各店数据时间与缺失，不能发起跨库回滚。

## 4. 逐店上线

1. 备份及恢复演练，完成只读盘点：订单、钱包分类、押金、冻结、积分、报单、提现、工资和既有截止。形成基线与需人工核验清单。
2. 隔离环境执行扩展 migration、历史回填和双读；核对数量与金额，演练中断恢复、重试和最大数据量；历史不确定来源按已确认规则留痕归本金。
3. 配置平台主体、门店核心字典、测试授权及开关。完成业务单据、时钟、旧任务和路由的切换水位。灰度切换时，对同一订单锁定或停写，防止旧新两个 worker 同时处理。
4. 先对授权测试账号做三端纵向场景，核对日志与账本，再逐店放量。每店、每配置版本记录时间、负责人、结果和异常；关键对账不平、越权或重复资金动作立即停止继续放量。
5. 比较新旧报表并解释已知口径差异；处理未完成订单和待支付提现清单；真实渠道在允许的测试环境单独验证。所有 G/T 场景完成与否均应记录证据，见 [11](11-需求与验收追踪.md)。

## 5. 回滚和恢复

扩表、开关未引入新业务事实时，可在验证兼容前提下关闭新入口或恢复旧读路径；不能假设回滚 schema 不影响正在运行的旧实例。切换后如果已经支付、退款、线下打款或释放收益，**不得**通过回滚代码、覆盖余额或删除流水消除事实：暂停相关操作、核对外部凭证与店内流水，通过补偿交易或前向修复处理，并保存审计。结果不明的线下付款始终先核实，不能为了回滚自动重付或解冻。
