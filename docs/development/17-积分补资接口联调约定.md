# 积分补资接口联调约定

> 后续开发说明：本文下方的“仅限隔离 SQLite”“尚未接通”等状态描述是建立本文时的历史记录，不代表当前代码的完整能力。当前代码已准备受 `SERVICE_POINTS_MYSQL_ENABLED` 等开关限制的 MySQL 积分业务及更多退款、转单和加购处理，但相关组合并未全部接通，也未完成最终联调；开关默认关闭。具体接线及尚受限的业务时序以 [后端剩余任务盘点](18-后端剩余任务盘点.md) 和 [积分接替退款进度](topics/points/积分接替退款本轮进度.md) 为准，不得据此认为真实资金链已验收或可以开放。本文接口格式仍供前端对接参考，实际可用状态以服务端返回为准。

状态：**仅限隔离 SQLite 测试**。这些接口和字段尚未在登记门店上线，不应据此开放真实资金操作。老板端积分下单、派单、履约与结算也尚未完整接通。前端可以据此准备交互和错误处理，最终启用以完整资金链路及隔离验收为准。

幂等冲突处理参考 [Formance Ledger 的幂等设计](https://github.com/formancehq/ledger/blob/main/docs/technical/architecture/subsystems/admission/idempotency.md)：同一编号与不同请求内容冲突。该项目采用不同的账本架构，本项目仍使用现有门店独立数据库和跨库恢复凭证，不直接引入其代码。

## 身份、门店和金额

- 使用 `admin.esports.club` 和已授权的**平台财务**身份；店内客服、门店管理员和仅具超级管理员权限的账号不能执行补资。路径中的 `slug` 是该平台财务已获授权的门店，例如 `shenglang`、`xinan`，不能替代身份或突破授权范围。
- 所有金额为整数内部记账单位：10 内部单位 = 1 店币，人民币 1 元 = 10 店币；展示时使用该门店的店币名称。`amount` 不能是小数、字符串或布尔值。
- 一笔实际到账只登记一次，可分配给本店多笔普通或积分服务订单以及通行证退款缺口；所有用途的分配合计不得超过到账金额。不能跨店分配。

## 测试流程

1. 沿用现有平台到账登记接口 `POST /api/admin/platform/pass-refund-repayments/{slug}/register` 登记外部流水和凭证，再使用 `POST /api/admin/platform/pass-refund-repayments/{slug}/{claim_id}/verify` 核实。核实动作带独立 `request_id`；未核实或证据异常不得分配。
2. 使用 `POST /api/admin/platform/pass-refund-repayments/{slug}/{claim_id}/points-allocation`，请求体为 `{"request_id":"UUID", "order_id":1, "amount":300}`。`request_id` 是本次操作的唯一 UUID；服务器检查积分订单支付证据、个人成交额与抽成快照、待补缺口和到账可分配余额。订单分配金额可低于缺口，余款可继续分配。
   普通服务订单可使用同格式的 `POST /api/admin/platform/pass-refund-repayments/{slug}/{claim_id}/service-allocation`；这两个入口共用操作编号及到账额度。
3. 成功响应为 `{"code":0,"data":{"operation_id":"UUID","status":"COMPLETED","receipt_id":1,"allocation_id":1,"order_id":1,"amount":300}}`。这个结果表明**分配记录完成**，不代表陪玩已经结算或提现；整单补资足额且本人结算条件满足后才可结算。
4. 若请求超时或收到 `POINTS_FUNDING_UNCERTAIN`，先使用**完全相同请求体及 request_id** 重试；不要换编号重复提交。其他内容发生变化而复用编号会返回 `REQUEST_CONFLICT`。请求编号也不能与通行证核实或核销操作复用。

## 核对与恢复

- `GET /api/admin/platform/pass-refund-repayments/{slug}/reconciliation` 返回通行证操作与 `points_operations` 列表；后者为兼容保留的字段名，包含普通和积分订单补资操作，并提供 `operation_id`、`request_id`、`claim_id`、操作人、时间及状态。隔离测试中系统交叉核对平台意图、门店操作、分配和核实凭证；凭证不一致为 `REVIEW`，存在待确认操作为 `PENDING`，余额字段为 `null`。不能把 `null` 显示为零或作为可继续分配的余额。
- 原请求丢失时，授权平台财务可调用 `POST /api/admin/platform/points-funding/{slug}/{operation_id}/recover`，请求体 `{}`。系统必须找到并核对门店侧分配、操作及原到账证据；找到匹配证据才恢复完成状态，不另做分配。
- 若原请求丢失、已核实门店库没有对应操作，调用同路径的 `/void`，请求体 `{"reason":"核实原因"}`，原因不超过 200 字。门店不可访问、存在任何对应分配或操作记录、已有结果时不能作废；作废后旧请求不能再执行，需要新请求并保留审计。
- `REPAYMENT_BUSY`、`POINTS_FUNDING_REVIEW` 和 `POINTS_FUNDING_UNCERTAIN` 都不是成功，也不能据此重新登记线下到账。`POINTS_FUNDING_REJECTED` 表示该次操作被拒绝，应修正原因并使用新请求；`POINTS_FUNDING_VOIDED` 表示旧操作已留痕作废。

## 尚未具备的能力

本期测试只验证未退款、未转单、无加购且快照完整的服务订单；隔离数据库中已执行普通订单及积分订单服务报单、按整单补资和个人等待期入账及押金抵扣，没有真实门店资金写入。另在隔离试验中接入积分订单的实销确认及本金积分发放；转单或售后改变收益后如何调整已分配补资和实销，还须按真实凭证和业务状态接通并验证。对账目前一次最多读取每类 5,000 条记录，超出时拒绝不完整结果；MySQL 并发和生产部署尚未验收。

陪玩订单接口在隔离测试中可向本人返回经凭证核验的 `expected_income`；异常时为 `null`，不代表钱包已入账。单独启用隔离结算试验后，报单状态可在核对补资及个人钱包流水后显示 `SETTLED`；未启用时仍阻断。不能依据隔离测试开放真实门店操作。

## 积分协商预览与权限

- 正式 MySQL 的服务主单首次协商退款涵盖已付加购且未转单的主单，以及符合原执行门禁的转单主单。`negotiation-preview` 中的 `execution_available` 表示当前退款路径和经办权限，金额核对由 `negotiation-funding` 提供。具备 `support:edit` 的客服可按 `agreement_available` 确认是否能登记方案。
- `negotiation-funding` 要求 `order:refund`。`read_only_points=false` 表示当前正式退款路径可用。正式转单首退的执行范围为一至两名受影响陪玩，超出时仍可核对各人账面承担。`executable=true` 还要求账面资金可承担，若预计需要扣押金，押金扣款与后续补差均须开启。店币以内部单位返回，积分以百分单位返回。执行时仍校验最新方案、当事人确认和资金凭证。
- 正式服务主单首次积分退款的资金预览返回 `execution_check_required=true`。未转单且有已付加购的主单还须核对 `conditional_combined_funding`，`remaining_units=0` 才可提交。符合门禁的无加购转单主单可在门店补资仍有缺口时办理退款，整单补足后才能发放陪玩收益。后台发起新退款须使用当前方案和金额的预览，并核对 `executable=true`。预览禁止提交时展示服务端原因。已有请求号先查询同一方案的回执，只在查无记录时用原载荷提交。
- 协商方案中的 `refund_units` 是店币及积分抵扣合计的退款等值；服务端根据原付款凭证保存 `refund_coin_units`、`refund_points_hundredths` 和是否全额，不能由客户端指定。老板和授权后台可另查看 `refund_coin_sources`（本金、赠送、赔付），陪玩只看到退款总构成及本人收益。
- `POST /api/admin/aftersales/{case_id}/negotiation-proposal/` 以及老板、受影响陪玩的 `/api/orders/orders/{order_id}/negotiation-proposal/` 使用现有方案与确认格式。双陪仅受影响的人参与确认。旧方案、退款构成损坏或证据不可用时，系统拒绝确认。经办客服通过 `negotiation-execution` 取得实际结果并按原请求号核对回执。
