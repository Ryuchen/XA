# 12 研发评审与待核实事项

评审方式：主研发分析 PRD 与当前工作树，另由研发代理独立只读复核租户、资金、履约、抢单及切换。以下结论是对现有代码的静态证据与设计讨论，不代表已执行测试。源代码行号随工作树改变可能移动；实施时重新核实。

## 1. 分歧、证据与结论

| 讨论点 | 源码证据和备选 | 结论与原因 |
| --- | --- | --- |
| 多库事务能否直接使用默认库 | [stores/db.py](../../services/backend/stores/db.py#L17) 已按门店路由 `atomic`、`on_commit`，而 [context.py](../../services/backend/stores/context.py#L22) 可默认回落 | 复用现有事务封装，新增资金操作缺门店时失败；平台目录使用原生 Django `default`，不要把封装的 `using='default'` 误认作固定目录库 |
| 平台财务能否直接用店内员工身份 | [permissions.py](../../services/backend/stores/permissions.py#L7) 的平台授权目前依赖默认库店内超管；[console 提现](../../services/backend/console/views.py#L3634) 写入店内人员外键 | 增加独立平台主体和授权，目标店记录真实平台主体引用和快照；不使用同 ID 店员冒充，也不跨库直接挂外键 |
| 只改报价能否支持积分 | [订单约束](../../services/backend/orders/models.py#L474)、[结算聚合](../../services/backend/orders/settlement.py#L153) 将分账限制在订单金额内；多个入口各自扣款 | 按原价、成交、实付、积分和补贴分别建模并覆盖所有入口；保留可继续成立的“本人应得不超过本人成交份额”约束，不简单删除所有金额校验 |
| 补贴是否可用已有模型 | [subsidies.py](../../services/backend/orders/subsidies.py#L16) 已有余额检查和成对流水，但旧模型针对安全箱 | 抽取共通能力，独立区分积分补贴应付／实付／待结；不把原安全箱补贴改义，零实付安全箱继续按其规则处理 |
| 奖励积分能否沿用预存批次 FIFO | [engagement/services.py](../../services/backend/engagement/services.py#L204) 沿用充值批次及倍率 | 保留批次作为历史来源证据；新消费按用户选的来源和付款 VIP 快照，仅本金赠分，不继续以预存批次倍率决定新单赠分 |
| 同一陪玩转出再回是否直接删除唯一约束 | [OrderProvider](../../services/backend/orders/models.py#L629) 人／单唯一，[ProviderReport](../../services/backend/wallet/models.py#L465) 报单同样依赖此假设 | 保留人／单兼容聚合，新建每次接入的履约段和报单版本。删除唯一约束会使既有 `.first()`／`get_or_create()` 等语义失效 |
| 退款能否只更改前端入口 | [refunds.py](../../services/backend/orders/refunds.py#L142) 对未结算部分退款和累计分摊有旧限制，且原反冲范围包含已发推荐收入 | 改退款计划、逐人逐笔取整及门店差额；已发推荐佣金不追回、由店承担；未发部分按有效基础重算。保留原幂等键和计划重验 |
| 收益能否继续订单级释放 | [confirmation.py](../../services/backend/engagement/confirmation.py#L20) 聚合全部报单；[income.py](../../services/backend/wallet/income.py#L22) 入账后另开冻结 | 改为整单结束且各人时钟／审核／售后／资金分别满足时释放，两个时钟重叠；保留实际发生的历史时钟与流水 |
| 是否先重构所有锁 | [financial_lock.py](../../services/backend/orders/financial_lock.py#L1) 已防止订单跨钱包锁环；[reservation_services.py](../../services/backend/orders/reservation_services.py#L396) 已有预约产能互斥 | 沿用既有保护并补齐各路径的统一锁顺序、死锁测试和监控；不先为了理论吞吐取消已有全店锁 |
| 时间冲突是否由任务先后决定 | 原待抢单任务和自动取消可竞争；原 PRD 未明确同时到期与取消 | 用户已补充：窗口与总期同刻、有合法候选先排序；老板同刻取消则取消优先。用可恢复的服务端命令顺序、截止水位和锁内判定实现，详见 [04](04-抢单预约与履约.md) |
| 是否引入统一巨型字典或第三方多租户框架 | 现有 [业务字典](../../services/backend/console/dictionary_models.py#L7)、`SystemConfig`、会员与薪资各有表和校验 | 做统一配置目录与版本服务，领域表仍为事实源；不为统一界面删除现有数据或更换一店一库架构 |

## 2. 近似开源实现与适用范围

- [Django 6.0 多数据库文档](https://docs.djangoproject.com/en/6.0/topics/db/multi-db/) 说明别名及路由；本项目还须处理平台控制面和一店一库的业务事务，不能假设跨库外键和事务可直接使用。
- [django-db-multitenant](https://github.com/mik3y/django-db-multitenant) 采用一租户一库，但项目自身也提示动态数据库连接的风险；本项目已有路由、上下文、通道和文件隔离，直接替换会增大迁移范围，仅参考风险与测试思路。
- [django-tenants](https://github.com/django-tenants/django-tenants) 面向 PostgreSQL schema，和现有 MySQL 独立数据库边界不一致，不选其作为本期实现。
- [Capone](https://github.com/counsyl/capone) 展示 Django 复式记账的借贷平衡与证据关联；本项目已有钱包和流水，只借鉴对账思想，不直接引入或替换既有账簿。是否演进为完整总账属于后续独立评估，不能把店币余额当人民币现金。
- [Celery 的 Django 集成文档](https://github.com/celery/celery/blob/main/docs/django/first-steps-with-django.rst) 解释事务提交后再触发任务；关键任务还需本地持久事件和补偿扫描，以应对提交后进程退出。上述参考未审计到可直接用于生产的程度，不作为引入依赖的建议。

## 3. 尚需实际核验或上线时确定

1. 微信服务号／网页实际支持的账号授权、手机号与头像获取链路；需要真实受控账号及微信能力验证。新陪玩首次头像不可得时不得伪造成功，也不能直接跳过该产品前置。
2. 每店积分兑换组、上限、核心字典、实际收费标准、有效员工、押金已缴数、线上历史钱包来源和上线时间由门店配置或逐项核对；不能从种子、截图缺失或代码默认值推断真实业务。
3. 本轮薪资参考图原件未复核，按既有文字记录设计；每岗位具体工资和实际人事数据需要实施前核对，不能编造。
4. 新门店 MySQL 用户权限、密钥管理、DNS／证书、部署执行器、多进程别名注册和目标环境备份恢复能力须实测；现有开发配置已预设别名，不能证明生产可自动分配。
5. 历史候选提交时点／通行证状态、陪玩多次履约与旧付款来源如果没有可靠证据，按 PRD 的待核验／本金归类／需重新抢规则处理，不伪造历史。
6. 具体特殊玩法规则本期不实现，通用房间不等于旧九种游戏已被重做。既有玩法、价格和门店上架状态应依 [31](../prd/31-特殊玩法订单加购.md)、[32](../prd/32-特殊玩法订单房间.md) 逐项核实。

如研发再次发现会改变用户权益、资金或职责的歧义，应携带现有代码证据、具体示例和互斥选项向用户确认；纯技术细节可在满足已确认结果的前提下自行设计。本目录没有把待核验项目写成已完成。
