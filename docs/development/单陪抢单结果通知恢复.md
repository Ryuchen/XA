# 单陪抢单结果通知恢复

单陪抢单池实际分配或重开时，若同时启用 `PROVIDER_LIFECYCLE_INTEGRATION_ENABLED` 和 `GRAB_RESULT_NOTICE_RECOVERY_ENABLED`，在原业务事务中按参与人的抢单回执和老板订单来源周期保存逐人通知意图。分配提交后尝试投递；失败由逐店任务重试，不重复分配或回滚已成功的订单操作。投递在账号锁后核对回执、轮次、获胜事实、账号类型和原业务周期；不可核验或周期已变化时记录跳过。每个意图独立记录结果，重复任务不会重复创建消息。

恢复开关默认关闭，关闭时沿用原有通知路径。结构迁移依次包括 `orders/0253_single_grab_notice_intents`、`site_messages/0016_grabresultnotices`；上线须按各门店数据库应用依赖迁移，配置两个开关并运行带门店上下文的 Celery worker 和 beat。恢复任务每分钟逐店扫描。启用前须联调双店隔离、赢家及未中签人、重开、账号退店重入、并发及通知失败重试；消息创建不代表客户端已收到。

本次不覆盖资格失效即时通知、双陪抢单结果及其他业务通知的持久恢复。客服直接指定派单不是本次实现范围；正式陪玩注销仍关闭。未执行测试或迁移。

## 普通单陪周期和结果复核

单陪真实抢单请求现在无论生命周期总开关是否开启，均在本店陪玩生命周期共享锁内核验请求身份并保存原周期；不调整请求接收时钟、窗口截止、留池或仲裁排序。关闭恢复开关时的即时结果通知也使用该原周期，老板使用订单周期；缺少可信来源或周期已变化时不向新周期发送，并记录待核对日志。客服安排的新订单仍须进入抢单池，不恢复人工直接指派。

启用上述两个开关后，既有逐店恢复继续按业务事务保存的逐人意图运行：对老板和获胜陪玩核对真实抢单状态记录、获胜回执、当前未释放席位及付款和订单状态；重开结果核对当前轮次仍开放或留池，不以首轮截止单独判定失效。未中奖通知仍按原回执发送。来源、周期或状态不符的意图留下跳过原因，不伪造新周期；投递异常可由任务重试。已跳过意图不是自动重试成功，需人工核对。

单陪回执的生命周期锁依赖本店 MySQL 及 `club_accounts/0010_provider_lifecycle_lock` 等首版结构和账号锁初始化；抢单实际入口仍受原有开池、单陪窗口和可信数据库时钟开关约束。`GRAB_RESULT_NOTICE_RECOVERY_ENABLED` 和 `PROVIDER_LIFECYCLE_INTEGRATION_ENABLED` 默认均关闭，必须按门店完成结构初始化、配置及 worker/beat 后，才具备可靠恢复；关闭时即时路径没有持久失败重试。本轮未新增结构迁移，未运行测试或迁移，跨周期、实际分配、留池及失败恢复仍需最终联调。
