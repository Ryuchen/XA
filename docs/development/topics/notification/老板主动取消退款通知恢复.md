# 老板主动取消退款通知恢复

老板主动取消未分配且已付款的订单时，普通取消入口及单双陪抢单池取消回执均在原取消与退款事务内保存老板通知意图。客服核对并完成老板已登记的人工申请后，也在同一笔退款事务内保存通知意图和确切的经办审计引用。两条路径共用 `PROVIDER_LIFECYCLE_INTEGRATION_ENABLED` 和默认关闭的 `CUSTOMER_CANCEL_NOTICE_RECOVERY_ENABLED`。只有实际创建退款记录才会登记通知。提交后独立发送，失败由逐店任务恢复，每个订单最多创建一条。

消息按实际退款构成分别描述余额及抵扣积分。投递核对老板取消状态日志、原订单和账号周期、退款记录及对应流水；抢单池额外核对本人取消回执。积分退款须匹配最终退款凭据和原订单积分流水；普通余额退款仅在本单只有一笔退款、且能唯一核对成功退款流水时发送。无法证明退款、账号退店或重入时记录跳过，不推测到账；消息创建不代表客户端已收到。关闭开关维持原取消入口通知行为。

人工核对的通知还会核对原老板申请、同单成功的客服取消审计、状态日志以及退款和流水的经办账号。积分退款按原扣核对店币、积分、等价额及原钱包，凭据缺失或金额不足时记录跳过。迁移保留已有通知，只为启用后完成的申请保存新意图。

各门店须应用 `site_messages.0056` 及依赖并运行 worker 与 beat。普通店币退款已核对首次投递失败、重试和门店及账号周期隔离。纯本金与抵扣积分混合支付的人工全退在隔离 MySQL 验证首投失败、同号客服并发和 Celery 唯一恢复。正式 60 秒调度已在独立 Beat、Redis 和 worker 实测，在线目录连续派两轮，每轮覆盖三店，只在原店创建一条通知。少退和缺凭据在 SQLite 核对。控制实例停机时，冷启动的 worker 已验错误签名索引拒绝路由，原签名索引恢复后按周期在原店补发。含赠送、赔付及门店补资的资金组合仍待联调。[普通本金验收](../../16-开发进度.md#2026-11-21-人工取消退款的老板站内通知) · [混合支付验收](../../16-开发进度.md#2026-11-21-店币与积分混合付款的人工全退) · [正式周期验收](../../16-开发进度.md#2026-11-21-退款站内信按正式周期补发) · [停机补发验收](../../16-开发进度.md#2026-11-21-控制库停机后的退款站内信补发)
