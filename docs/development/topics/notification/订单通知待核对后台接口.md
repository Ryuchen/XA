# 订单通知待核对后台接口

已发送的站内消息继续按原周期保留；待发送消息仍由各发送器核验原业务事实与账号周期，不允许重入后的账号接收旧周期消息。

后台新增本店 `GET /api/admin/notice-reviews/?kind=negotiation|gift|staff-start`，支持 `page`、`page_size`，返回三类已有 REVIEW 意图的来源编号、原账号周期、原因和时间。查询需同时有 `message:view`、`order:view`。这三类分别对应售后协商方案、赠礼付款、客服开始服务；其他通知记录尚未接入本队列。

`POST /api/admin/notice-reviews/{kind}/{id}/` 需 `message:push`、`order:view`，请求必须携带 `action`（`recheck` 或 `dismiss`）、`reason` 和查询返回的 `expected_note`。重核仅接受已记录原账号与有效原周期的意图，并要求对应恢复开关及生命周期开关已启用；提交后复用原发送器逐项重新验证真实来源、业务状态和原账号周期，不保证发送成功。缺少原周期时无法自动推测，管理员可核实后填写原因结束该提醒。结束提醒不会发送消息或改变订单、资金、历史消息。任何请求都不能提交或更改收件账号、周期和来源；处理写入本店后台审计。状态变化时返回 409，防止重复处理。

本接口复用现有意图和审计表，不新增结构迁移。`REVIEW` 产生依赖对应通知恢复开关及其未执行的结构迁移；其他缺周期的旧即时路径仍需逐项接入可靠意图，不能视为全部覆盖。未修改前端，未运行测试或迁移；启用前须在隔离门店联调权限、跨店隔离、并发重核、来源仍缺失、账号退店重入和失败恢复。

加购付款通知现可使用 `kind=addon-payment` 查询本店 REVIEW，并沿上述权限、审计和并发校验执行 `recheck` 或 `dismiss`。重核仅提交原付款通知待发送意图，发送器重新核实加购付款、原履约段、当前责任与原账号周期；责任已转移、退款结清或账号周期变化时按真实状态跳过，不代表已送达。恢复依赖 `ADDON_PAYMENT_NOTICE_RECOVERY_ENABLED` 及已部署的现有通知结构和逐店恢复任务；无新增迁移。未运行测试或迁移，待最终联调。

客服充值到账站内通知：开启 `RECHARGE_RECEIPT_NOTICE_RECOVERY_ENABLED` 后，同一门店事务保存充值意图及原付款、赠送和老板周期，逐店任务 `site_messages.tasks.recover_recharge_receipt_notices` 失败后重试。发送时核对真实钱包流水和原周期；无可信原身份的记录标记 REVIEW，不向新周期投递。若充值时赠送需审批，文案只描述充值时状态，不冒称审批已完成。部署需先应用 `site_messages/0053`（依赖 `0052` 与 `wallet/0062`）并配置逐店调度；开关默认关闭。参考 [django-jaiminho](https://github.com/loadsmart/django-jaiminho) 的同事务 outbox、提交后投递和失败重试思路，本项目使用本店数据库及账号周期核验，没有引入该依赖。未运行测试或迁移，真实双店、审批、失败恢复和客户端通知联调待完成。

充值通知待核对使用 `GET /api/admin/notice-reviews/?kind=recharge` 和 `POST /api/admin/notice-reviews/recharge/{id}/`；查询需要 `message:view` 与 `recharge:view`，处理需要 `message:push` 与 `recharge:view`。列表返回充值记录编号、原收件账号及周期、本金和当时赠送流水编号、赠送账务单位及充值时是否待审批；不返回订单号。重核仍由原发送器重新核验充值与钱包事实，原身份不可证明时只能登记原因结束，不改写来源、不冒称送达。已纳入后台审计，需 `RECHARGE_RECEIPT_NOTICE_RECOVERY_ENABLED` 与既有逐店任务；未运行测试或迁移。

充值赠送审批通知：启用 `RECHARGE_GIFT_DECISION_NOTICE_RECOVERY_ENABLED` 后，审批与赠送入账事务保存原账号周期、审批决定和真实赠送流水（零赠送无流水）；逐店任务 `site_messages.tasks.recover_recharge_gift_decision_notices` 可恢复。发送时复用充值原凭证与审批流水核验，账号周期变化则跳过，来源不明进入 REVIEW。后台用 `kind=recharge-gift-decision` 沿充值通知的权限与审计查询、重核或结束；重核不等于送达。开关默认关闭；部署需应用 `site_messages/0054`（依赖 `0053`、`wallet/0062`），逐店 beat 已登记。未运行测试或迁移，最终需联调审批通过/驳回、零赠送、失败恢复与退店重入。

提现本人提交或主动取消通知若真实申请／解冻来源待核对，可通过 `GET /api/admin/notice-reviews/?kind=withdrawal` 查询；`GET /api/admin/notice-reviews/withdrawal/{id}/` 可区分 REVIEW、MESSAGE_CREATED、CLOSED，`realtime_delivery=UNKNOWN` 不表示实时推送已收到。查询需要 `message:view` 与 `withdraw:view`；`POST` 重核或结束需要 `message:push` 与 `withdraw:view`、原因及原待核对说明并留审计。重核在提交后按原提现锁序再次核对申请、解冻和原账号周期；成功只创建一条站内消息，原来源无法核实或跨周期不得补发。复用 `WITHDRAWAL_NOTICE_RECOVERY_ENABLED`，不新增迁移；未运行测试，须最终联调并发重核、关单、送达失败及双店隔离。
