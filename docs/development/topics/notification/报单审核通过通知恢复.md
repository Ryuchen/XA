# 报单审核通过通知恢复

服务订单报单审核通过时，在原审核事务按实际报单、审核时间、陪玩账号和订单原业务周期保存站内通知意图；预览沿用原有审核结果文案，审核通过不等于收益已到账。事务提交后投递，失败时由本店已注册的 `site_messages.tasks.recover_order_assignment_notices` 扫描待发送意图；同一报单和审核时点只创建一次消息。

投递重新核对报单归属、同次通过事实及原周期。来源或原周期无法证明时记录 `REVIEW`，账号已退出或重入后不跨周期发送；审核状态变化时跳过过时意图。已有站内消息由原列表权限读取，历史消息不删除。关闭开关时保留原即时通知路径。

`REPORT_APPROVAL_NOTICE_RECOVERY_ENABLED` 默认关闭，启用还需 `PROVIDER_LIFECYCLE_INTEGRATION_ENABLED`、各店结构迁移 `site_messages/0051_reportapprovalnotice`（依赖 `0050`、`wallet/0062`）及逐店 worker/beat。驳回通知和后台核对的后续接入见下文；独立手工报单不在当前范围。未运行测试或迁移；最终须联调重复审核、消息写入失败恢复、状态变化、账号重入、双店和事务回滚。

## 订单报单驳回

实际客服驳回订单报单时，同事务保存对应审核时间、原陪玩周期及驳回原因；提交后发送失败由相同逐店任务重试。投递重新核验本人、该次驳回和原因；陪玩重提或审核状态改变后不再补发过时驳回提醒。原周期无法核实时记录 `REVIEW`，不会使用发送时的当前周期冒充来源。审核通过和驳回共用原开关与任务；启用还需 `site_messages/0052_report_rejection_notice`，依赖 `0051`。

当前公开的陪玩报单草稿创建接口要求关联真实订单，可在允许的履约状态创建草稿，提交仍须满足完成条件。独立手工报单没有首版公开创建入口，也没有可证明的原提交周期；本次没有新增或推测该业务。本次未运行测试或迁移，需最终联调重提、失败重试、账号重入和双店隔离。

## 后台核对

本店具备 `message:view` 和 `order:view` 的后台可通过 `GET /api/admin/notice-reviews/?kind=report-approval` 分页查看待核对的审核通过或驳回通知，包括原报单、审核时间、类型、接收人、已保存周期及通知内容。具备 `message:push` 和 `order:view` 的人员可向 `POST /api/admin/notice-reviews/report-approval/{id}/` 提交 `action`（`recheck` 或 `dismiss`）、2 至 255 字 `reason` 和当前 `expected_note`。

重核只允许记录了原接收人和周期的意图，恢复任务重新核验同次报单审核及原周期后发送；不能更改原始来源或向重入新周期发送。无法证明来源时可填写原因结束待办，不代表消息已送达。两种操作分别留本店审计，状态与预期原因竞争检查阻止重复处理；恢复开关未启用时不能提交重核。无需新增结构迁移，未运行测试或迁移。

报单待核对列表的 `legacy_user_id` 来自原报单的实际 `provider_id`；另返回 `current_report_account_id`、`current_report_status` 和 `current_report_audited_at` 供核对当前事实。这些字段不改变通知保存的原账号或周期；即使当前报单显示了账号，也不能据此补造缺失的历史周期。

首版开户核对：客服后台开户和陪玩注册审核均在同一事务创建陪玩业务账号、旧用户映射与陪玩档案；`users/views.py` 中旧模拟创建代码位于当前登录入口不再调用的 `_legacy_post`，不是首版公开入口。当前 `EscortProfile.user` 和 `ProviderReport.provider` 均要求旧用户。未发现可无旧用户完成陪玩档案创建的首版公开入口，因此本轮不放宽模型或新增无旧用户结算路径。该结论以现有入口为范围，最终仍需联调实际开户、报单和通知全链。
