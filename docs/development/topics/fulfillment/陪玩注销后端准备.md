# 陪玩注销后端准备

2026-11-24 在隔离双店 MySQL 验证普通已付预约转单、积分购卡及真实注销。接替陪玩注销先提交时，正在等待原周期锁的购卡与转单均拒绝，原预约占档、付款及积分保留。同号注销读回原回执，名额和注销审计只变更一次。两项业务均先取得共享锁时，购卡和转单可分别完成，转单通知按原业务周期投递。其他业务的生命周期屏障覆盖及正式开放仍待 M7 联调。[验收记录](../../16-开发进度.md#2026-11-24-陪玩注销与在途购卡及转单)

平台超级管理员核对 KOOK 授权未知事件并允许补发积分时，若来源是陪玩，现先在所属门店捕获账号并准备生命周期锁，在门店业务事务中先取共享锁，再锁原事件、账号和绑定并核对原业务周期；相同已完成请求继续按原凭证重放。平台控制库原有操作者和门店锁顺序保持不变，不能核验生命周期时返回可重试错误。此路径不在注销或重入后向新周期发旧积分；本轮未运行测试或迁移，仍须隔离联调跨库审计失败恢复、核对与注销竞争、重放及双店隔离。

提现实时状态事件在陪玩端读取真实提现申请的 `account_business_cycle`，生命周期集成开启时仅向所属原周期且仍在店的账号展示；客服仍按既有权限查看。账号已重入、原周期缺失或不匹配时不把旧提现状态推给新周期。此改动不替代提现站内消息恢复，也未覆盖尚未保存事件周期的钱包通用刷新；本轮未运行测试或迁移。

## 本轮：显式注销接口与名额

新增本店授权人员接口 `GET /api/admin/providers/{account_id}/retirement/` 预览、`POST` 同路径确认；执行体需 `reason`、`confirmation_token`、`confirm: true`、`client_request_id`。确认操作在陪玩生命周期独占锁、陪玩配额锁及账号锁内重核同一预览、结清情况和所属门店，保存注销审计后将账号标记为非在店并推进周期，License 配额因此释放；同一请求可重放。账号停用、停接或退押金本身不释放名额。已获积分、通行证和历史记录不因本操作清空。

清算增加真实单陪抢单、双陪组队、未决抢单回执及续单核实／奖励检查；已发续单奖需核对原流水。续单申请及客服核实在涉及陪玩的生命周期共享锁下重新核对席位与账号周期，防止与注销互相越过；原周期待发奖励不能借账号重入发到新周期。未能核实来源的在途业务仍需处理或核对。

`PROVIDER_RETIREMENT_ENABLED` 和 `PROVIDER_LIFECYCLE_INTEGRATION_ENABLED` 均默认关闭。接口和开关为首版受控实现，并非全链验收：仍须核对其他资金／权益写入口均使用生命周期屏障，以及正式注销与订单、提现、售后、积分、续单和抢单并发的原子性；不应仅因本次接入而在生产开启。未运行测试或迁移；最终须在隔离环境验证两店配额、请求重放、失败回滚和注销／重入竞争。

Django 原生管理站的订单管理改为只读，禁止新增、修改及删除，保留原查看权限，避免绕开订单和陪玩生命周期服务；其他管理站模型仍须独立核查。跨周期续单奖励仍缺少人工裁定补发路径。`users/pass_refund.py` 仅处理历史尚未生效通行证；首版通行证付款即生效，不能退款，因此不作为新业务注销的额外阻断或历史迁移要求。

服务入队和结单补充：单陪、双陪本人提交入队／结单截图时，生命周期集成开启后先在事务外准备名额锁行，再持本人共享锁进入原请求幂等与订单事务；订单锁内核对席位及履约段的本人业务周期，重放也核对原订单周期，异常时不写截图或履约时间。同周期停用人员已有履约不因停用单独失效；账号重入或来源缺失时待核对。正式注销仍关闭，代码未经测试；最终联调须覆盖双店、双陪分次截图、同人转回、重试、注销竞争及失败回滚。

当前只有受关闭保护的服务层准备，未开放正式注销接口。准备内容包括本店独立权限、确认快照、结清事实、审计和相同请求重试；注销时不清空积分或通行证权益。
