# 取消未来授权时的离线缓存

已激活但尚未生效的未来授权可由平台超级管理员按原接口取消。取消事务持有控制库门店锁，并先在该门店业务库将已有签名快照置为不可验证；业务库不可访问时返回授权服务不可用，控制库取消事务回滚，可使用原请求重试。已经提交的取消可重复查询／提交，不重复取消或发送新事件。未激活码的作废不需要失效已激活授权快照。

缓存发布在控制库提交及门店业务事务提交之后执行，并先持有同一控制库门店锁，重新读取控制库当前授权和档位配置，再写入本店快照。这样旧的延迟发布不能在取消后恢复已取消安排。取消提交后尽力刷新当前授权缓存；若刷新失败，已有用户核心订单、履约、售后和资金流程仍按原故障策略可用，新增账号和增值权益暂不能核验，待控制库和门店库恢复后由在线查询刷新。不验证的缓存不会作为已取消授权重新生效的依据。

两个数据库没有分布式原子提交：若门店缓存先失效、控制库事务随后回滚或进程中断，授权实际未取消而缓存可能暂时不可用；控制库可用时重新查询可恢复。操作未确认时应重查授权记录，同一作废请求可重试。控制库不可用时无法完成取消，不能据此判断平台已取消。锁顺序为控制库门店行，再到本店快照行；延迟发布同序，避免旧状态覆盖取消。外部参考 [Redis 缓存与并发重建](https://github.com/Strangedip/PREP/blob/main/01_TechGuide/28_Redis_Distributed_Caching.md) 中的失效与并发重建问题；这里的跨库锁和故障语义按本项目门店隔离及授权规则实现。

本次未运行测试或迁移，仅作 Python 语法解析。后续须在物理隔离的控制库与两门店库验证取消与快照延迟发布并发、两库任一故障、控制提交前后中断、重复取消、锁顺序、既有订单和资金；不代表真实断库验收已完成。
