# 陪玩退押金申请后端

本人 `GET /api/wallet/deposit-applications/` 查询本业务周期申请，`POST` 接受 `request_id`、`amount`（账务最小单位，10 为 1 店币）及可选 `note`，`POST /api/wallet/deposit-applications/{id}/cancel/` 可取消未处理申请。未结订单、预约、售后、收益及冻结等按既有资格函数拒绝并返回原因；结清后七天等待期内可登记意向并展示 `eligible_at`，申请本身不转账或冻结资金。

后台需 `escort:deposit_refund` 权限：`GET /api/admin/deposit-applications/` 查询，`POST /api/admin/deposit-applications/{id}/process/` 提交 `request_id` 与 `reason` 办理，`POST .../{id}/reject/` 提交 `reason` 拒绝。办理复用原退押金事务并重新核对七天及全部资金／业务条件；实际钱包入账和门店押金池配对流水与申请完成状态同事务保存。原直接退还入口遇到待处理申请须通过该申请办理；失败保留申请，重复或并发不重复入账。

申请提交时向本店拥有退押金处理权限的有效后台账号保存逐人原周期通知意图，若没有可通知人员，申请标记 `NO_STAFF` 并仍可由获授权人员从后台队列处理；拒绝时本人收到结果提示，成功时沿用真实押金退回钱包通知。通知失败保持待处理，逐店恢复 `DEPOSIT_APPLICATION_NOTICE_RECOVERY_ENABLED` 默认关闭；首次投递仍会尝试。站内记录不代表 WebSocket、短信或微信已送达。

首次部署需 wallet/0061、site_messages/0050 及前置迁移；未执行测试或迁移。须最终隔离联调双店、无授权客服、真实七天与再出现业务、申请／取消／办理竞争、失败回滚、重复请求、账号注销重入和 MySQL 锁序。客服页面对接及真实外部通知不在本轮。
本人和后台列表返回 `data.items` 与 `data.next_before_id`；支持 `status=ALL|PENDING|REFUNDED|REJECTED|CANCELLED`、`limit`（1–100，默认 50）及上一页返回的 `before_id`。后台默认仅看 PENDING，按 ID 倒序逐页继续，因此已结记录不会挤掉旧待办；本人默认 ALL 且仅限当前业务周期。

申请状态续记：本人及有权限客服列表中，`submitted_cleared_at`、`submitted_eligible_at` 保留申请时快照；待处理行的 `current_eligibility` 按查询时真实订单、售后、收益和冻结重新计算，含 `checked_at` 与申请金额是否仍足额。新业务出现会显示当前阻断，结清后的七天以实际新结清事实重新计算；此为只读提示，最终办理仍在原资金事务锁内复核。本周期仍有待处理申请时，陪玩注销清算显示数量并阻断，先由本人取消或客服处理。

有 `escort:deposit_refund` 权限的客服可 `POST /api/admin/deposit-applications/{id}/remind/` 对仍有效的待处理申请显式重新通知，操作留审计；在该操作时为新收件人保存真实周期，不复用旧周期。已创建站内消息的收件人不重复发；无可通知对象时明确返回 `NO_STAFF`，`queued` 表示意图待投递，`already_recorded` 表示已有站内记录，均不代表外部渠道送达。无需新增迁移；未执行测试或迁移，最终仍需隔离联调资格变化、注销竞争、权限和失败恢复。
