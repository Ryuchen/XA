# 积分自愿接替资金事件内核

新增 `POINTS_VOLUNTARY_HANDOVER_V1` 事件内核，复用门店加购资金事件的 JSON 和摘要字段，不新增数据表。`write_locked(run)` 供未来的最终确认事务调用：调用方必须先在同一门店事务持有订单、资金及到账锁，并保存真实资金版本与逐笔释放；写入前重算原资金事件，再核对付款、前次已确认责任、三方决定、逐段收益、客服审计与资金摘要，任一失败由调用方整体回滚。已存在事件使用原回放核验，不能改写或重复确认。

资金事件回放器已识别这一独立类型，逐次重新验证前驱及其资金事件；被明确拒绝的方案可核对三方决定、原份额和客服审计后重新发起。同一付款退款，或另一付款退款实际占用待确认方案负责人的该笔待结收益时，在退款事务中保存失效事实；重提时核验原方案、决定、真实退款及释放事件后按剩余份额重新发起。另一付款退款未占用该责任时不擅自使方案失效。接替事件只绑定真实已有付款和释放，不创建付款、退款或凭空补资。

`accepting(handover)` 临时核验上下文仅在当前门店事务内、按门店库、门店标识、订单、付款与方案编号精确匹配时，允许已三方确认的当前方案先核对真实份额，用于解除最终资金重算与事件写入之间的循环；退出时立即清除。最终确认入口在受控范围内调用它，并同事务核对和记录资金版本。

方案模型新增 `kind`，区分 `STANDARD` 和 `VOLUNTARY`；结构迁移 `orders/0262_addon_handover_kind.py` 已编写但未执行，既有方案继续使用 `STANDARD`。自愿资金事件回放只接受方案自身标记为 `VOLUNTARY`，避免把原转单负债接替误作自愿接替。已有客服创建接口可显式提交 `kind: VOLUNTARY`；未提交时保持原 `STANDARD` 行为。

创建及三方确认已接入受控积分转单路径；最终确认、整单资金版本、真实或空 RELEASE、事件摘要与到账用途记录同事务完成，失败整体回滚。自愿接替的付款及存在待确认自愿方案时的另一付款，可进入既有加购售后方案、双方确认和客服退款事务，按原支付构成退还，并复用逐人未结收益、钱包、押金承担及到账释放；报单、补资和结算回放须重新验证全部资金事件。首次实现只覆盖一次主单退款、未结算及单个待确认方案，后续扩展范围见下文。已有转单负债接替仍走原路径。本轮代码未经联调，不能认定资金链已验收或开放正式业务。

未运行测试或迁移。最终须以隔离 MySQL 联调跨店隔离、配置变化、前驱竞争、退款与确认竞争、真实及空 RELEASE、共享到账和失败回滚。

已补充已付人员退款证据结构和退款事务写入：保存退款前逐人清单、真实收益及押金流水标识，并绑定该笔真实退款与 RELEASE 资金版本；`orders/0264_points_voluntary_paid_refund_evidence.py` 尚未执行。自愿接替退款在本单清单未完结、已付流水可核验时进入既有预览、双方确认和执行；逐人承担检查禁止选择已有主单或加购结算的人员。待确认方案由实际退款改变责任时按原规则失效，其他人员的已付收益保持原值。

共享到账的真实及零 RELEASE 回读已接入独立流水核验；主单退款后的结算版本按退款与版本的实际时间回放，后续资金足额时写入前后清单版本并复核已付收益。仍沿用现有门店积分功能开关与已接入的自愿接替资金范围，不涵盖已完结订单或其他不具备真实凭证的时序。以上入口及锁顺序尚未经隔离数据库联调，尤其需核验多次退款和逐人分批结算、跨付款失效、实发及零 RELEASE、补资不足后恢复和失败回滚；未执行测试或迁移。

第二次主单退款的后续接线：自愿接替已有事件纳入原始加购历史识别；后续加购退款进入第二次主单退款的真实资金预核和 `TRANSFER_FOLLOWUP_V1` 写入，已付快照同时绑定该版本摘要。后续资金事件的到账读取复核原已付流水，结算按真实退款追加清单版本并保护已付收益；自愿接替失效按退款时已发生的主单记账事实回放，避免后续主单退款改变旧事实。此前已付清单跨第一次与第二次主单退款且中间又有加购结算版本等复杂交错，仍须逐版凭证核验，不能证明时继续拒绝；上述代码均未联调，仍需统一验证真实接口、退款、补资、零及非零 RELEASE、连续退款、并发和回滚。

补充交错结算：两次主单退款之间产生的已付清单，从第二次退款真实资金版本读取；多名已付人按本人报单、收益及押金流水逐人核对。主单结算版本和加购退款结算版本按创建时间与前后清单摘要衔接，到账回放按事件时点截断，避免用后续清单改写先前退款事实。已结算收入不重发、不修改；后续资金足额才继续结算。该交错路径尚未执行隔离数据库联调，不能将代码接线当作资金验收完成。

后续修正：此前自愿接替范围识别仍固定要求一笔主单退款，且验证时按单条主单记账查询，导致第二次主单退款后的入口实际上被阻断。现按一或两次真实主单记账读取，随后分别核验两次之间和第二次之后的加购资金事件；同单不同付款的待确认方案不再被统一限制为一条，逐笔检查并仅对退款实际改变责任的方案留存失效事实。仍需真实事务联调以验证多笔加购退款、分批结算、补资、重试与并发；不能以本次代码接线替代验收。

新增转单后首笔主单退款之后的加购：老板报价、加购申请和付款进入原订单及资金锁，付款、资金事件、实际或零 RELEASE 在原事务核验；后续自愿接替与退款沿真实付款及事件顺序读取。其他陪玩已结算时，新增付款在同事务保存原清单及实际收益、押金流水，并在补资足额后追加付款驱动的清单版本；已付人不能成为接替源或目标。结构迁移 `orders/0265_points_voluntary_paid_payment_evidence.py` 已写未执行。新付款在清单推进前已发生退款时，版本同时绑定该付款及对应真实退款、释放与已付清单；全额退款导致净清单不再含付款时须核验实际已退总额。上述混合事件代码尚未隔离联调，缺少真实凭证继续拒绝。
