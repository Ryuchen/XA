日期：2026-10-27。本文件记录源码审查和待决问题，不代表任何微信支付能力已经接入，也不代表平台已批准具体业务类目。

用户已确认下一步采用**小程序内直接支付订单**。原有余额支付和已有余额账务仍需兼容；是否支持余额与微信混合支付、以及具体售后资金规则仍须在实现前明确。当前直接支付领域代码与签名协议只供隔离测试，没有公开付款入口或真实商户调用，不能视为已可收款。

用户进一步明确：每笔订单由老板选择进入公开派单池或由客服安排；微信支付手续费由老板另行支付，按商户实际费率计算；积分和会员消费按服务成交金额计算，不含手续费。用户确认目前商户费率尚未确定，手续费计费基数与取整规则也尚未核实；系统不能假定某个行业示例费率就是本商户费率。微信支付官方说明不同商户及类目的交易费率可能不同，具体以商户实际签约和平台配置为准：[微信支付接入指引](https://pay.wechatpay.cn/static/applyment_guide/applyment_detail_app.shtml)。订单报价应冻结已核实的费率和计算规则，并与渠道账单里的实际手续费分开记录；微信优惠或退款可能造成差异，需要逐笔核对。取消时是否退还老板另付的手续费仍待用户决定，不得预设。

## 当前事实

用户确定老板另行支付手续费，按微信商户实际费率计算；积分及会员消费额按订单成交金额计算，不把这项额外费用计入积分和会员消费额。支付前应分别展示服务成交金额、另收费用和支付总额，并冻结适用费率、计费基数、舍入、金额及版本，以便复核和退款。陪玩、邀请人和俱乐部的服务分配应以服务成交金额为基础；另收费用的归属及实际支付渠道成本单独核算，不能默认为相等。实际商户费率与计费规则需通过商户协议或账单核实；微信券、费率变化或计费基数等可能使预先计算的收费与最终实扣不同。取消时的退费规则仍待用户答复。测试域已增加服务额和费用报价快照，但带费用的退款及结算尚未完成，真实支付未开放。

单位边界：现有订单金额属于内部账务单位，10 个内部单位为 1 兴安币；现有客服充值业务按 1 元兑换 10 兴安币，按该现行规则推导 1 个内部单位对应 1 人民币分。数值相等不代表字段天然是人民币分，真实直付接入前需确认该兑换适用于购买服务并固定转换及展示规则，不能仅凭整数相等跳过确认。

微信支付官方说明商户交易费率与经营类目有关，[小程序支付说明](https://pay.wechatpay.cn/doc/v3/merchant/4012791894)说明用户在微信支付页面确认收款方与总额。市场监管总局[《明码标价和禁止价格欺诈规定》](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2023/art_9a1f82a007964950a1a0f6c056f2fedf.html)要求醒目标价且不得收取未标明费用。现有公开资料不足以判断该商户合同是否允许将支付手续费单列转嫁；正式启用前应按实际商户协议及微信支付审核结果确认，不应把后台估算费用表述成微信实扣金额。

老板订单创建目前直接扣除本地钱包，写入余额支付流水，并将订单标记为已支付。人工充值由客服核实收款后操作；实收和赠币分别有流水及累计记录，但最终进入同一个余额。普通订单退款、未接单超时退款回到该余额，不是退到微信支付账户。现有积分资金批次用于积分规则，不能据此认定每一笔剩余余额都已准确区分实充本金与赠币。

例：人工充值 100 元、赠送 20 兴安币，到账 1020 兴安币；消费 1000 币后剩余 20 币。仅凭钱包当前余额，不能证明剩余 20 币究竟来自实充还是赠送。跨批次消费、部分退款和赠币回收需要单独规定并核验，不能按余额猜测。

## 两种路径

| | 微信直接支付订单 | 微信自助充值后余额下单 |
| --- | --- | --- |
| 老板体验 | 可不预充值，直接支付当前订单 | 先充值，再使用现有余额购买 |
| 当前复用程度 | 现有创建、退款及结算依赖钱包 PAY 流水，不能仅把微信交易标记为 PAID | 可复用余额订单和部分营销规则，但充值入账必须新增独立的支付渠道事实与幂等保护 |
| 退款需区分 | 微信支付原路退款、余额抵扣退款及可能的混合支付 | 订单退款回余额；充值原路退款是另一笔操作，涉及实充与赠币来源 |
| 需要确定 | 是否接受余额抵扣或混合支付；各渠道退款顺序；未履约及已结算退款规则 | 赠币使用顺序、充值退款与赠币回收、已消费或历史混合余额如何处理 |

两条路径都需要先核实微信商户主体、小程序与商户绑定、服务类目和具体充值或虚拟权益的适用准入。是否能使用该场景应由微信支付和平台实际审核确认，不能从一般接口文档推断。

## 无论选哪一条都要建立的约束

1. 一笔商户支付请求有稳定的商户单号、渠道、金额及业务归属；客户端返回不作为唯一付款事实，服务端验证渠道通知并能主动查单。重复、乱序和丢失通知不能重复扣款、入账、建单或发券。
2. 状态未知与明确失败分开；网络超时后继续使用原交易标识查询，关闭支付前核对渠道状态。支付成功、关单、订单取消和退款竞争时，订单和账务必须能解释最终结果。
3. 微信实付、钱包实付、赠币、平台/陪玩分账及退款去向分别可追踪；金额使用整数，订单金额、渠道交易及账本逐笔对账。不可用相同数额推测渠道交易或旧余额来源。
4. 外部退款需要独立的退款请求和渠道状态，不把“申请退款”当成“已到账”。渠道结果未知时先查单，不能盲目再次请求或同时给余额和原渠道退款。
5. 凭证、回调验签及解密材料保存在服务端安全配置中；真实商户、权限和回调联调以隔离测试及实际交易验收为准。本文件不要求在聊天中提供密钥。

## 验证与上线条件

直付接入须先完成隔离环境中的持久预下单、支付状态未知恢复、服务端查单、验签后通知持久化、退款执行及查询、账单核对和运营差错处理；真实发起收款前，这些资金恢复与接收能力均须具备。随后核验商户主体、类目、AppID 绑定、费率与密钥管理并进行受控联调。当前网关仅有协议封装，不等于这些流程已联通。

老板和客服的现有取消接口已对未付款直付意图加保护，避免将本地取消误称渠道关闭；相应余额路径保留。该保护不等于已经实现老板可用的查单、关单和取消恢复流程。一旦将来接入微信预下单，必须先处理渠道查单与关单：本地取消不能证明微信单已关闭，关单与付款竞争或结果未知时要保留收款事实并查询原交易，不能另开一笔或直接认定失败。取消保护在 0062 隔离 MySQL 快照的空库迁移后 33 项通过、无跳过。微信[小程序支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)描述了下单、查单和关单流程。

渠道账单与签名 API 响应的处理不同：微信说明下载账单文件的响应不带签名，商户需要使用经验证的账单申请结果中的哈希核验文件；下载地址、重定向、文件大小和敏感数据也应受控。账单中的退款记录不能代替实时退款查询。参见微信官方[账单下载](https://pay.wechatpay.cn/doc/v3/merchant/4013071254)。

在选定路径并确认退款、赠币规则后，先设计状态机和记账关系，再覆盖重复/乱序/伪造回调、金额不符、查单恢复、关单与付款竞争、退款并发和渠道对账。使用生产同类数据库做竞争测试，并由运营、财务和老板分别走查。正式前还需核实微信商户配置、服务类目、回调公网可达性、真机小额支付与退款；本地模拟和成功构建不代表平台验收。

微信支付官方[小程序开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)说明了服务端下单、支付结果确认、交易对账与退款流程；[小程序下单接口](https://pay.wechatpay.cn/doc/v3/merchant/4012791856)要求小程序 AppID 与商户号存在绑定关系。实际适用能力以商户平台配置和最新规则为准。

## 隔离端到端与真实商户联调路线

这是一份**待实施路线**，不是支付能力已经开放的声明。当前已经有测试态的订单与报价快照、假预支付会话、模拟查单、支付与退款通知收件记录、付款派单发件箱和退款领域状态机；这些切片尚未组成完整端到端支付服务。模拟观察中的 `fake_*` 状态、模拟关闭和测试数据不是微信认证事实，不得通过切换环境配置把它们变成生产凭证或真实订单状态。

### 阶段一：不使用真实商户凭证的隔离验证

可以先在独立数据库和网络受控的测试环境中，使用临时生成的密钥及显式注入的模拟传输，覆盖原始字节签名、验签、通知解密、持久化和业务状态推进。模拟环境须与真实商户的数据、证据类型、配置和身份隔离；生产默认关闭，不能把当前测试开关直接当成上线开关。

按依赖关系，这一阶段仍需实现并验证：

1. **请求与恢复。** 在现有金额、身份和报价快照之外，冻结真实下单需要的商品描述、通知地址、支付截止、请求格式与摘要；保存买家确认。短事务内登记发送尝试，提交后调用模拟网关，再在新事务中留存结果。发送超时、进程中断或租约到期不能证明渠道未收到请求；应保留原商户订单号和原请求，查验后再按明确规则处理，不自动创建第二笔。已有模拟预下单不等于这一真实请求编排已经完成。
2. **可靠回调。** 当前收件箱接收已认证、已解密的测试对象，尚无对外 HTTP 回调和生产调度。需实现原始请求字节及签名头的受控接收、验签、解密和幂等落库；只有可靠保存之后才能应答成功。验签失败不能进入可信收件箱；验签成功但解密失败、类型未知或内容超限时，需有有界、受控的隔离记录和恢复路径。处理可异步重放，不能只依赖通知。微信要求回调及时应答，并说明重复通知与查单配合：[支付成功回调](https://pay.wechatpay.cn/doc/v3/merchant/4012791902)。
3. **查单与取消恢复。** 已有的 0067 查单只接受假网关；真实查询编排及关单尚未实现。需用原商户身份和原订单号查询，保存来源可信的观察，并与付款通知共享证据冲突处理。`NOTPAY`、暂时查无订单或网络超时都不是关单成功；取消意愿须先持久化，老板能够持续查看原订单和核对状态。已交给用户的支付参数或迟发的旧预下单请求可能仍然有效，关单与付款竞争应保留两方事实并停止不安全的后续操作。模拟测试需覆盖这些情况及事务外网络边界。[小程序支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)
4. **退款执行与核对。** 已有测试域退款预留、状态机和通知收件记录，但尚无完整的渠道发送执行器、回调消费者和查询恢复。需在模拟环境验证原退款号与原参数的稳定性、异步处理、未知结果查验、重复及冲突留证，不能把退款受理当作到账，也不能同时向余额和原渠道退款。**手续费大于零的退款、部分退款、优惠出资分摊、已结算追回和权益反冲仍需规则确认后才能开放**。[微信支付退款最佳实践](https://pay.wechatpay.cn/doc/v3/merchant/4014959631)
5. **对账与运营处置。** 建设模拟交易、退款和资金账单的下载摘要验证、逐笔匹配、差错单、权限、审计及告警；账单不能取代实时查单。微信说明账单文件下载响应不带签名，应使用申请账单结果中的哈希验证下载内容：[下载账单常见问题](https://pay.wechatpay.cn/doc/v3/merchant/4013071254)。
6. **端到端和竞争验收。** 在模拟环境覆盖老板确认总额、恢复原意图、验签失败、重复和乱序通知、请求发出前后崩溃、查单/取消/付款竞争、退款未知及差异处理。用 MySQL 8 的真实行锁测试多工作进程；SQLite 跳过的并发用例不能计作通过。该阶段的成功只能证明隔离模拟链路，不能证明微信平台准入、真实回调可达或真实资金已结算。

### 阶段二：真实商户受控联调所需条件

在上述链路、费用退款规则与运营处理具备后，经营方需核实并安全配置商户主体、实际经营类目及平台审核结果、商户号与小程序 AppID 的绑定和支付权限、实际费率与结算规则，以及适用的交易类小程序发货管理要求。微信支付要求确认商户号与 AppID 的关联：[账号绑定指引](https://pay.wechatpay.cn/doc/v3/merchant/4016328613)；具体业务能否使用，应以平台审核结果和商户协议为准。

真实联调还需由授权人员在安全环境中配置 APIv3 密钥、商户证书与私钥、微信支付公钥或平台证书及轮换机制，准备可访问的 HTTPS 通知地址、网络策略、测试小程序账号和设备，并安排运营及财务验收。**不要在聊天中提供或粘贴密钥。** 真实请求、收款和小额退款联调应在上述准备完成并获得用户明确授权后进行；既有余额账务、微信支付、渠道优惠、实际手续费与陪玩结算仍须分别核对。
