# 老板微信直付：三端界面与 API 状态契约草案

日期：2026-10-27。业务选择为**在小程序内直接支付订单**，现有兴安币余额支付继续保留。本文是可供产品、设计、研发和测试共同评审的目标契约；文中新增的接口、响应字段与界面均为**建议，尚不存在于公开接口**，不能据此宣称微信付款已开放或生产验收通过。退款的细化展示与工程前置条件另见 [退款体验草案](WECHAT_DIRECT_REFUND_EXPERIENCE_DRAFT_20261027.md)。

已确认业务口径：老板额外承担微信支付费用，付款前按微信商户实际费率计算报价，最终实际扣费以微信账单为准；积分与 VIP 仅计服务成交额。是否允许向老板单独收取该费用仍需核查微信规则和商户合同；核查通过前不得上线该收费。退款时费用是否退还尚未决定，不能预设或承诺。

## 1. 当前源码与必须补齐的能力

| 项目 | 已核实的状态 | 接入前必须完成 |
| --- | --- | --- |
| 老板结算 | `apps/boss-miniapp/native/pages/checkout/` 只走余额试算、余额充足校验和 `/orders/create/`；余额不足提示联系客服。 | 接入真实可用性判断、微信支付方式、服务端支付意图、继续支付及结果确认；保留原余额流程和选择。 |
| 老板订单 | `native/core/orders.js` 已对 `UNPAID` 防御性显示“支付待确认”；已付款订单按履约状态显示。列表/详情当前使用兴安币，取消提示按退余额处理。 | 由服务端资金投影区分待支付、确认中、关闭及退款进度；按渠道与金额性质显示正确币种和去向。 |
| 直付领域 | `services/backend/orders/direct_payment.py`、`direct_refund.py` 及支付通知 inbox / 派单 outbox 为测试域；真实功能受测试开关保护。微信网关与凭证解析代码存在，并不等同于真实商户接入。 | 对外授权 API、可信回调、查单、关单、退款执行/对账、状态查询与运行保障均须完成并通过验收；真实商户、域名和类目须另行核实。 |
| 当前限制 | 直付测试域暂不支持指定陪玩、平台优惠券及体验资格；渠道优惠证据不完整或资金分配未核实会进入 `REVIEW`。 | 在限制解除前，能力接口和界面须明确不可用原因，不能创建付款后无法履约的订单，也不能静默去掉老板已选内容。 |
| 订单超时 | 余额订单有接单截止及退款规则；直付测试域确认付款后才设置 `pool_entered_at` 与接单截止。 | **支付有效期**和**付款后的接单截止**分开设计、存储与展示；不能让未付款订单进入公开池或启动接单超时。 |

上线开关必须由服务端按真实商户配置、功能支持范围和运行状态返回。未满足条件时，界面可说明“微信支付暂不可用”，保留可用的余额支付和客服入口；不展示可点击的伪支付按钮，不用测试网关或本地回执冒充真实付款。

### 金额口径及工程前置

| 名称 | 口径 | 已知时间及处理 |
| --- | --- | --- |
| 服务成交额 `service_amount_fen` | 服务定价扣除适用的订单优惠后的金额，不含老板支付费用。 | 付款前由服务端报价并冻结；是积分/VIP 的基数，退款影响另见下文。 |
| 老板支付费用报价 `customer_payment_fee_fen` | 按商户实际费率和经确认的计算规则计算的、本单老板需额外支付的金额。 | 支付前给出并随订单保存规则与报价快照；这笔报价不等于已出账的微信实际手续费。 |
| 微信订单应付 `order_total_fen` | 服务成交额 + 本单老板支付费用报价。 | 以人民币分在服务端计算和传输；提交微信的金额应与老板确认的最终报价一致。 |
| 渠道实际现金付款 `payer_total_fen` | 渠道核验后返回的用户现金付款数额。 | 可因渠道优惠与订单应付不同；未知为 `null`，不以订单应付代替。 |
| 微信实际手续费 `actual_channel_fee_fen` | 微信账单核对后的渠道实际扣费。 | 付款前未知；客服/财务按权限查看和对账，不得从报价推断微信已收金额。 |

费率适用范围、计费基数（服务成交额还是含附加费的订单总额）、最低/封顶、分位舍入、微信优惠及特殊交易的计费影响，须以实际商户规则确认并做版本化配置；不得自行编造费率或将示例数字当成实际政策。报价与微信账单不一致如何承担或处理尚待业务确定，不得事后静默向老板追加扣费。历史订单始终使用当时已确认的报价与规则快照。收费主体和名称要据实际合同准确描述，不暗示附加费一定由微信直接向老板收取，也不把它宣称为实际手续费。

现有测试域已在 `orders/direct_payment_quote.py` 中将服务内部单位、转换后的人民币服务额、费用报价及渠道总额分开快照，并用 `quote_matches_intent` 验证支付和退款意图。现有结算和积分代码仍使用 `order.amount`，直接把附加费加进它会污染陪玩分成和积分/VIP；真实渠道账单费用、退款费用政策、直付积分权益和对外接口仍须补齐和验收，测试域不等于完整资金契约或已开放直付。

积分及 VIP 以**服务成交额**计入，不包含老板支付费用；服务退款成功后按已确认的服务退款金额调整，退款中的金额不能先当成已退。规则、时间点和冲正应保留快照并幂等处理。现有余额积分使用余额资金批次，微信直付需要明确独立资金来源和对应积分计算，不能伪造余额批次；陪玩收益与现有服务分成也应仅基于服务成交额，不把老板支付费用分给陪玩或邀请人。

### 现有取消保护与迟到支付的显示缺口

目前老板和后台的旧取消接口对 `UNPAID` 且存在直付意图的订单，会在订单锁内拒绝取消，业务错误为 `DIRECT_PAYMENT_CANCELLATION_UNCONFIRMED`，提示“微信支付状态待核对，订单尚未取消，请稍后查看或联系客服”。这只是阻止误取消的保护，**不代表已经查单或关闭微信订单**。老板当前页面对未支付订单隐藏取消按钮；后台仍会展示取消按钮，提交后显示上述错误而不是“已取消”，但没有可持续查找的渠道核对任务入口。

另有不同路径：测试域构造出本地已取消订单后，如果收到满足交易绑定校验的可信迟到付款证据，`confirm_verified_payment` 会保存渠道事实并把直付意图设为 `REVIEW`，订单仍为 `CANCELLED + UNPAID`；现有测试覆盖该组合。这是测试域行为，不代表真实通知已接入。**目前老板 `OrderSerializer` 和客服 `AdminOrderSerializer` 均没有向界面暴露直付意图 `REVIEW` 或渠道已确认付款事实**，因此不能指望客户端根据 `UNPAID` 推导出真正资金状态。

| 现有界面 | 具体缺口 | 接入直付前的目标，尚未实现 |
| --- | --- | --- |
| 老板列表与详情 | `native/core/orders.js` 对上述组合显示“已取消”，并写“付款状态尚未确认”；虽未承诺退款，但不能提示已收到可信付款及需核对。金额仍使用兴安币。 | 由授权服务端投影同时提供本地履约停止和可核实的渠道付款事实；例：“订单已取消，付款已确认，平台正在核对”，可查看订单客服与核对进度。只有渠道事实足够时才写“付款已确认”，不得写“未付款”“已退款”或诱导重复下单。 |
| 老板取消 | 未支付订单隐藏入口；已付款测试直付订单若进入现有取消弹窗，会先提示“已付款金额将退回兴安币余额”，服务端随后拒绝旧余额退款路径。 | 按服务端渠道、允许动作及退款规则显示取消说明；关单结果未知时显示“订单尚未取消，支付状态待核对”，不可承诺余额退款、渠道已关闭或退款已到账。 |
| 客服后台 | `apps/admin-web/src/views/order/index.vue` 和 `AdminOrderSerializer` 基于订单字段显示“已取消／未支付”，在已核验迟到付款场景中“未支付”会误导；未提供持久待核对队列。 | 对有权限客服展示“履约已取消／渠道付款已确认、待核对”，连同核验时间、受控处理入口及审计；退款仍按独立状态显示。无权限时隐藏敏感字段与操作。 |
| 陪玩 H5 | 当前测试域正常创建订单不指定陪玩，`CANCELLED + UNPAID` 不会进入公开池；不能宣称这类单已展示给陪玩。若未来存在已关联陪玩的历史/异常订单，当前取消卡片“订单已取消/退款”会把取消与退款混在一起。 | 仅向确有归属的陪玩提供必要履约状态和本人收益影响；区分“订单已取消”和已核实退款，不展示老板支付身份或渠道交易信息，不提供接单、开始、完成操作。 |

当前接口和界面不能提供上述 `REVIEW` 投影；上线前须先设计和实现授权查询、持久核对队列、状态恢复及异常处置，不得添加依靠客户端推断的伪状态或假入口。

## 2. 统一资金状态和显示优先级

以下是建议的**面向界面的服务端投影**，并非要求把所有值写进现有 `Order.status`。同一订单的履约、支付和退款是不同维度，服务端结合已核实的事实、执行中的请求和异常状态，返回一致的投影及允许动作；客户端不得自行从一个字段猜其他状态。

| 投影 | 老板显示 | 服务端事实和允许动作 | 客服 / 陪玩 |
| --- | --- | --- | --- |
| `AWAITING_PAYMENT` 待支付 | “待支付”；显示应付 ¥、支付截止和“继续支付”。 | 仅在渠道状态支持继续、会话和订单仍有效时允许重新获取**同一支付意图**的支付参数；提供安全关闭入口。 | 客服看到未支付但不可派单；陪玩不可见。 |
| `PAYMENT_CONFIRMING` 支付确认中 | “支付结果确认中，请稍后刷新”；保留订单详情与联系订单客服入口。 | 网络异常、调用支付后未取得可信结果、查单中或关单结果不明。只能查同一商户单号；不再生成另一笔，不开放派单，不声称支付失败。 | 客服可按权限查看待核对；陪玩不可见。 |
| `CLOSING` 正在关闭 | “正在确认订单是否关闭”。 | 服务端先核对渠道付款和关单结果；存在成功竞争或结果未知时保持确认中。 | 不提供派单；不可因用户本地取消收银台就断言付款关闭。 |
| `CLOSED_UNPAID` 已关闭且未付款 | “订单已关闭，未付款”；无退款承诺。 | 只有服务端有可靠关闭及未付款依据时进入；重新购买是明确的新订单/意图。 | 陪玩不可见；客服可查看关闭原因与核验时间。 |
| `PAID` 付款已确认 | 显示服务成交额、老板支付费用、订单应付及已核验现金付款，并展示履约进度。 | 可信支付证据与订单、商户、用户、金额、币种核对一致后才标记已付款；派单可见性使用订单权威状态与原有资格规则。 | 客服待派可指派；公开单仅对符合资格及可见时间的陪玩展示。 |
| `PAYMENT_REVIEW` 付款待核对 | “付款已确认，订单状态需核对”或按服务端可核实事实显示“付款结果待核对”；不能显示未付款或退款成功。 | 包括关闭后迟到付款、账号状态变更或可信金额/优惠证据与既定规则冲突。保留渠道事实，禁止自动派单与重复付款，进入客服处理。 | 客服按权限查询处理；陪玩不可见。 |
| `REFUND_PROCESSING` 微信退款处理中 | “订单已取消，微信退款处理中”；显示申请退款金额，不写已到账。 | 退款已预留、渠道受理或处理中；无论按钮、回调或网络是否超时，沿用原退款标识查询。 | 客服看处理队列和最近核对结果；陪玩不可接单/继续服务，历史收益只显示本人应见信息。 |
| `REFUND_CONFIRMING` 退款结果确认中 | “退款结果确认中”。 | 外部请求已发出或结果未知；先查询，不换新退款号，不同时退余额。 | 客服可见待核对与下一步；陪玩不见老板渠道明细。 |
| `REFUND_SUCCESS` 微信退款成功 | “微信退款成功，实际到账以微信或银行为准”；仅已核验的退款金额可标明用户现金退款。 | 验证渠道最终成功后保存凭证及时间；微信优惠金额与现金退款分开展示。 | 客服可查凭证及记录；陪玩显示与本人份额有关的结果。 |
| `REFUND_REVIEW` 退款待核对 | “退款尚需平台核对”，不能写成功。 | 退款关闭、异常、终态冲突、渠道证据不完整或不一致。关闭与异常需保留具体内部原因；渠道关闭后是否可新退款号取决于权威状态及业务授权。 | 客服受控处理和审计；陪玩不能获得老板交易凭证。 |

显示优先级：退款成功/待核对等以最新**已核验**退款事实为准；其次是付款确认、确认中、待支付与关闭；付款确认后再展示派单/履约状态。`CANCELLED + PAID` 并不等于已退款；`UNPAID` 遇到可信迟到付款也不等于用户没有付款。若数据缺失、前后状态矛盾或服务端无法给出明确投影，显示“状态待核对”，禁止创造性的推断。

## 3. 老板端文字原型

以下用服务成交额 **¥28.00**、假设费用报价 **¥0.17**、订单应付 **¥28.17** 说明界面；费率、计费基数与舍入均为示意，不代表实际费率或确认的计算规则。

### 3.1 结算页：清楚选择付款方式

```text
确认订单
服务：双人陪玩 · 1 小时                 ¥28.00
派单：由客服指定两名陪玩

选择支付方式
(●) 微信支付       直接支付此订单
( ) 兴安币余额     可用 300 币

服务成交额                                 ¥28.00
支付费用报价                                ¥0.17
微信订单应付                               ¥28.17
[确认并使用微信支付]
支付后才会开始安排；如需退款，按订单显示的渠道处理。
```

- 微信支付是否可用由服务端能力响应决定；仅在该服务、陪玩选择、优惠和订单金额都被支持时允许提交。余额不足只影响余额选项，不能阻止可用的微信选项。若微信不可用，显示原因及可选的余额/客服路径，不能自动改扣余额。
- 所选支付渠道、服务规格、派单方式、价格及优惠须在最终确认中明确。预支付阶段不得因切换页面或修改 UI 而创建第二笔；用户决定更改内容时必须先以服务端确认旧支付意图已安全关闭。已选择的陪玩、优惠券或体验资格在本期不可用时，明确说明并允许返回调整，不能静默清除。
- 支付费用在提交前明确展示金额、费用性质和服务端报价有效期；当费率、商品、优惠、计费规则或其他影响金额的条件改变时重新报价并重新获得老板确认。报价绑定账号、支付方式、服务和规则版本；不能静默改变最终确认总额。余额支付仍按原有逻辑，不据此假定它也有这笔费用。
- 商户应付金额、优惠前金额和余额币额分别使用自己的单位。若订单最终实付为 0，微信接口不应被伪调用；是否允许零价订单、其资格与权益的结算规则须另行设计并验证，不默认按本期直付支持。

### 3.2 支付页/结果确认与页面恢复

```text
支付结果确认中
订单  XA2026…
微信订单应付   ¥28.17
正在核对支付结果，请不要重复购买。
[刷新状态]   [查看订单]
```

1. 创建意图成功后保存服务端订单编号及稳定请求标识，服务端返回可用的微信支付参数时再调用 `wx.requestPayment`。页面关闭、切后台、网络中断或微信页面返回后，均通过服务端状态接口核对；微信回调的 `success`、`fail` 或用户取消**都不能单独作为商户账务最终结果**。
2. 重入订单列表、详情、结算页或从后台恢复时，先查询账号下对应意图/未处理订单；不依赖旧页面是否还在内存中。丢失本机存储、换设备、重新登录后的恢复以服务端记录为准；本地存储只缓存非敏感恢复引用，不能是唯一防重手段。
3. 未确认状态不能显示“支付失败，可重新购买”、不能换新单号盲重试。可在适当间隔内调用服务端刷新；服务端控制对微信的查单节奏，前端轮询应退避、进入后台暂停、恢复前台后重新查，允许手动刷新。
4. 页面序号、账号及会话版本保护所有异步响应；老板 A 的支付参数、订单状态和迟到结果不能写入老板 B 的页面。应用被杀后恢复时重新向服务端读取，不重放已经由后台确认成功的付款。

### 3.3 订单列表与详情

```text
订单  XA2026…                     支付结果确认中
服务  双人陪玩 · 1 小时
微信订单应付  ¥28.17
请不要重复购买，点击查看处理进度。
```

```text
订单已取消                       微信退款处理中
申请退款  以该单退款申请为准
退款进度由微信支付确认，实际到账时间以微信或银行为准。
[刷新状态] [联系订单客服]
```

如果微信优惠使渠道用户实际现金支付或退款低于订单金额，应分别标注“微信订单应付”“用户现金付款/现金退款”，只展示已核验数值；字段为 `null` 表示未知，不显示成 ¥0.00 或假定等于订单总额。是否以及如何展示渠道优惠详情须依据可靠字段；目前遇到未完成的渠道优惠结算规则应显示待核对。微信官方退款规则也区分申请退款金额与用户实际现金退款金额，见 [微信支付退款规则](https://pay.wechatpay.cn/doc/v3/merchant/4013071001)。

退款规则未确定前，不能承诺“全额退款包含费用”或“费用不退”。规则确定后，申请前展示本次服务退款、费用退款及合计，若任一金额未确定则明确“待核定”；已申请、渠道受理、结果确认中、退款成功、异常各自显示，用户实际现金退款以核验渠道结果为准。服务退款与费用退款分开累计，避免手续费退还误冲减会员消费或陪玩收益。退款后的微信实际手续费以账单及渠道证据对账，不能假定按老板费用退款比例返还。

“待接单”列表筛选必须排除待支付/关闭/确认中订单，或新增独立“待支付/确认中”筛选；不能仅依据已有 `PENDING` 履约状态。已有余额订单的币额、取消和余额退款文案保持原口径，不因为增加直付而改写历史。

## 4. 建议接口契约与安全边界

下表为待实现契约，路径是为了讨论行为的**候选路径**，不是当前可调用接口。可根据项目 API 规范调整路径，但不得丢失下列语义。所有响应沿用项目 `{code, msg, data}` 包装；错误状态和字段须在接口文档中固定并编写契约测试。

| 操作 | 建议接口与输入 | 成功/未知结果与保护 |
| --- | --- | --- |
| 查询可用性 | `GET /api/orders/direct-payment/capabilities/`，可带服务及选项摘要 | 返回 `enabled`、支持范围和用户可读原因；服务端下单时必须再次验证。不能返回商户密钥、签名材料、敏感身份信息。 |
| 创建意图 | `POST /api/orders/direct-payment/intents/`：服务、数量、派单方式、确认服务额/费用/总额、报价及规则版本、稳定 `client_request_id` | 服务端重新报价、校验身份及支持范围并冻结订单与请求摘要；报价过期或变化须返回明确错误，重新展示并确认。同账号同编号同载荷恢复原意图，改变载荷返回冲突。超时或 5xx 保留原编号，先按原编号查找；禁止静默新建。 |
| 查询/恢复 | `GET /api/orders/direct-payment/intents/{id}/` 或按原请求号的专门恢复查询 | 仅本人可查；返回订单引用、服务端状态投影、金额性质、截止时间、服务端时间、版本及允许动作。不存在、无权限、已关闭、未知须有不同语义，不能凭本机缓存猜测。 |
| 获取支付参数 | `POST /api/orders/direct-payment/intents/{id}/parameters/` | 仅意图所属用户、当前绑定身份及允许状态可获取；复用原商户支付单，参数只用于本次拉起微信。不得把客户端回调或参数发放成功记为支付成功。 |
| 刷新支付事实 | `POST /api/orders/direct-payment/intents/{id}/refresh/` | 同一意图查渠道，服务端对并发查单合并/限频并将可证明结果原子入账；渠道未知返回确认中，不能误写失败。接口必须有身份、归属、限流和审计。 |
| 关闭未支付单 | `POST /api/orders/direct-payment/intents/{id}/close/` 带稳定操作编号 | 查询和关单结果可能未知；服务端与付款确认竞争时只承认有证据的最终状态，返回处理中或可确认的关闭。已付款/迟到付款按实际状态处理，不做客户端强制关闭。 |
| 退款状态与操作 | 老板订单详情提供授权过的退款投影；客服受权限保护地申请/查询 | 只支持已实现并验证的金额与阶段；显示 `REFUND_PROCESSING`/`CONFIRMING`/`SUCCESS`/`REVIEW`。同退款请求号与外部退款号贯穿重试、回调和查单，未知时不得换号。 |
| 微信通知 | 独立的服务端通知入口，具体 URL 由商户配置 | 验签、解密、商户/应用/订单/金额/币种与渠道编号核对；持久化接收、幂等处理与安全应答，重复/乱序/冲突进入可追踪处理。不得由小程序直接提交“支付成功”作为凭据。 |

建议的老板只读投影示例（字段和值均为拟议）：

```json
{
  "order_id": 123,
  "order_no": "示例订单号",
  "payment_channel": "WECHAT",
  "payment_view_state": "PAYMENT_CONFIRMING",
  "currency": "CNY",
  "service_amount_fen": 2800,
  "customer_payment_fee_fen": 17,
  "order_total_fen": 2817,
  "fee_quote_version": "示例规则版本",
  "payer_total_fen": null,
  "payment_deadline_at": "服务端返回的时刻或 null",
  "dispatch_deadline_at": null,
  "refund": null,
  "allowed_actions": ["REFRESH_PAYMENT", "VIEW_ORDER"],
  "state_version": "服务端变更版本",
  "server_time": "服务端返回的当前时刻"
}
```

这是数据契约示例，不是现有接口返回样例。`payer_total_fen: null` 明确表示未知，不能当作 0 或自动复制 `order_total_fen`。退款对象至少需要独立 `status`、服务与费用的申请金额和 `requested_fen` 合计、可空 `payer_refund_fen`、`currency`、渠道确认时间及允许动作；尚未核定的退款组成不能伪造为零。老板不需要商户账单费用、商户凭证或完整微信标识。`state_version` 由服务端维护，用于拒绝或忽略旧响应，不能取客户端时钟代替；服务端交易与权限仍是最终约束。

## 5. 客服后台与陪玩端

- **客服**：订单列表应能区分待支付、支付确认中、付款异常、待派、微信退款处理中和退款异常；详情分别展示服务成交额、老板支付费用报价、微信订单应付、用户已核验现金付款及其状态；按财务权限展示账单实际手续费、账单对账状态、报价差异及未知原因。退款预览分开展示服务及费用组成、预计申请总额和规则依据；未定规则不提供确定金额承诺。按权限提供刷新核对、合规的取消或退款申请；保留操作人、原因、渠道结果和审计。无法确认渠道结果时标“待核对”，不得让客服用余额调账冒充微信退款。改造位置包括 `apps/admin-web/src/views/order/index.vue` 的“实付金额”和兴安币退款弹窗及其后台序列化数据。
- **陪玩**：未确认付款、关闭单、付款待核对与退款中的订单不进入公开池，也不能接单、开始或完成。付款确认后的公开单仍需服务资格、通行证可见延迟、容量和服务器并发校验；客服待派单只向被指派的成员展示。陪玩只看履约和本人基于服务成交额计算的收益，不暴露老板支付费用、现金付款、支付身份、渠道退款编号或其他成员账务。`apps/provider-miniapp/src/pages/orders/index.tsx` 现已用“单钱已按订单平台抽成计算”区分订单抽成；预估收益不得说成已结算。
- **消息**：微信支付/退款可信状态先持久化，通知作为刷新提示；有权限人员在在线重连、进入页面及失败恢复后重新查询。网络推送丢失、Worker 重启或渠道回调重复时，可从待办列表和服务端状态恢复。用户看见支付成功与否以服务端核对结果为准。

## 6. 可执行验收矩阵

| 场景 | 必须断言 |
| --- | --- |
| 微信入口不可用/缺商户配置 | 无伪支付入口或伪成功；余额路径独立可用，不意外扣余额。 |
| 老板点击直付但网络在创建响应前中断 | 同编号恢复同一意图；更改支付方式或规格不能绕过未确认意图；无第二笔扣款或订单。 |
| `requestPayment` 返回成功、取消、失败或系统杀掉小程序 | 统一走服务端核对；已付款不会误显示失败，未确认不进入派单；重进或换设备仍能找到同一订单。 |
| 查单、回调、关闭请求并发，且回调重复/乱序 | 验签与绑定校验；至多一次入账/一次派单；关闭不覆盖可信成功，迟到成功进入明确处理状态。 |
| 当前老板/客服旧取消接口面对未支付直付意图 | 持锁拒绝并提示订单尚未取消、渠道待核对；订单、资金、意图状态不因拒绝改变；页面不得显示取消成功或暗示微信已关单。余额订单原取消和退款保持正常。 |
| 已确认付款的直付订单触发旧取消路径 | 不显示退回兴安币的确认文案，也不得调用余额退款来代替渠道退款；渠道不可用时明确说明未完成的操作。此项依赖未来按渠道的服务端投影和界面。 |
| 本地已取消后收到可信迟到付款，意图进入 `REVIEW` | 老板能同时看到履约已取消及可核实的付款事实和待核对提示；客服经授权能在待办中找到该单并查看证据和处理进度；都不能显示未付款、微信已关闭或退款成功。重复事件与刷新不得重复派单、退款或生成新订单。以上投影和待办目前尚未实现。 |
| 迟到付款 `REVIEW` 的陪玩可见性 | 正常未分配订单不在抢单池；若以后出现已有归属的历史/异常订单，只显示本人的履约和收益事实，取消不等于退款，不泄露老板支付资料，禁止继续服务。上述异常场景需构造数据验证，不能推断现有测试域会产生指定陪玩订单。 |
| 服务 2800 分，费用报价 17 分，微信订单应付 2817 分 | 三项分别展示，服务额为积分/VIP 与陪玩收益基数；17 分仅为示意，不能替代实际商户规则或账单。 |
| 费用报价已知但账单未出、账单为零或与报价不同 | 老板只看到已确认报价；有权限客服分别看到“账单待核对”、真实零值或真实账单数值和差异，不得显示报价即实际扣费；不得事后静默追加扣款。 |
| 微信用户现金付款/退款未知、为零或与订单应付/申请金额不同 | 分别展示未知、¥0.00、已核验实际金额；不混同平台优惠、微信优惠、兴安币及渠道金额。 |
| 退款费用规则尚未确定；之后发生服务与费用退款 | 未确定时不承诺费用退或不退；已确定后分别显示服务、费用及合计；处理中不计已到账，成功后仅已确认服务退款冲正积分/VIP 与服务收益。 |
| 同样服务成交额、不同支付方式；配置变动或分位舍入 | 对同等积分规则的订单核对积分/VIP 基数相同；费率及舍入改变产生新报价并由老板重新确认，老订单快照和余额订单不受影响。 |
| 渠道受理退款、处理中、成功、关闭、异常、网络超时 | 显示和操作分别正确；受理不等于成功，未知不换退款号，不同时退余额；异常可恢复并留操作记录。 |
| 老板换账号、客服权限被撤销、旧请求迟到 | 不泄露数据或覆盖新会话；服务器每次复核对象归属、员工权限和订单状态。 |
| 支付后的双陪、指定陪玩、平台优惠券、体验单 | 未实现路径必须在付款前明确拦截；解除限制时分别验证资格/名额、价格与权益、关闭/退款及并发竞争，不能仅测试单陪正向路径。 |
| 截止时间、断线恢复与通知失败 | 未支付不启动接单截止；已支付按该单冻结规则开始计时；断线重进靠服务端状态恢复，渠道与本地账目可对账。 |

技术验证需包含使用生产同类数据库的并发测试、模拟渠道的验签及故障注入、重复/迟到通知、订单和资金守恒、外部退款对账；真实小程序、商户及类目审核、线上回调与小额支付退款各自独立验收。微信支付官方[小程序开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)要求通过服务端下单、支付结果通知或查单及对账完成流程；[退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)指出受理退款不等于退款成功。
